# План реализации Tasks: CLI + NestJS + React

## 1. Цель продукта и способ распространения

**Продукт распространяется одним npm-пакетом `@gromlab/tasks-cli` и запускается
пользователем через NPX.** Пользователь работает из каталога своего проекта:

```bash
npx @gromlab/tasks-cli init
npx @gromlab/tasks-cli create "Реализовать регистрацию" --actor human
npx @gromlab/tasks-cli list
npx @gromlab/tasks-cli server --actor human --open
```

Последняя команда запускает NestJS на `http://127.0.0.1:3000`. Он предоставляет
REST API, OpenAPI, Swagger и SSE. При наличии `dist/web/index.html` сервер также отдаёт
собранное React-приложение. Общая сборка включает фронтенд; без статики API может работать самостоятельно.
Доступны `--port`, `--config`, `--actor` / `TASKS_ACTOR`; `--open` открывает браузер.
Для пользователя уже собраны JavaScript, CSS и остальные ресурсы UI.

**Готовность проверяется на установленном npm-архиве в чистом каталоге,
вне этого репозитория и без devDependencies.** Запуск через исходники или Vite
сам по себе не означает готовности пакета для NPX.

## 2. Подтверждённые требования

- Node.js 22+; один локальный проект за запуск сервера.
- React + TypeScript; полноценный канбан с созданием и редактированием задач.
- Все настроенные статусы представлены колонками, включая выполненные и отменённые.
- Колонки, их порядок и цвета берутся из `tasks.config.json`.
- Положение карточек внутри колонки задаётся перетаскиванием и сохраняется в JSON.
- CLI и NestJS используют одни операции Core, включая ревизии и блокировки.
- В `.tasks` находятся только `<id>.json` с задачами, их комментариями и отчётами.
- UI обновляется при изменениях из CLI, API и других вкладок; черновики пользователя сохраняются.
- Качество визуального дизайна, доступности и UX входит в критерии приёмки.

## 3. Архитектура

```text
apps/
  cli/src/                 Commander, команды и терминальные представления
  server/src/              NestJS: модули, контроллеры, HTTP, Swagger, статика
  web/src/                  React + Vite канбан
packages/
  core/src/                domain, application, storage, shared
  contracts/src/           независимые от Node/Nest/React типы REST и SSE
apps/cli/test/             регрессии CLI, запуск server и проверки публикации
apps/server/test/          HTTP/OpenAPI, SSE, статика и интеграция с Core
packages/core/test/        проверки ядра и границ импортов
packages/contracts/test/   проверка совместимости DTO и типов ядра
scripts/                   сборка, упаковка и публикация
```

```text
CLI ───────────────────→ Core ──→ .tasks/*.json
                            ↑
React ── REST ─────────→ NestJS
MCP ──── REST ─────────→ NestJS
      ←─ SSE ───────────────┘
```

Границы импортов:

- CLI использует `#core/*`; команда `server` лениво загружает `#server`.
- NestJS использует `#core/*` и `#contracts`.
- React использует `#contracts` и HTTP-клиент.
- Core содержит бизнес-правила и файловые операции. Представления CLI находятся в `apps/cli`.
- Contracts пригоден для браузера и содержит только переносимые типы и константы.

Корневой `package.json` управляет зависимостями и единым публикуемым пакетом.
У приложений отдельные TypeScript-конфигурации. Сборка создаёт `dist/cli`,
`dist/server`, `dist/core`, `dist/contracts` и `dist/web`. Внутренние алиасы
разрешаются внутри установленного архива, без workspace-ссылок на исходники.

## 4. Текущее состояние и следующий объём работ

Бэкенд реализован в `apps/server`: все маршруты из `docs/API.md`, OpenAPI 3.1,
Swagger и SSE. CLI и HTTP вызывают бизнес-операции Core напрямую. Общие запросы
доски и истории находятся в `packages/core/src/application/queries`.
Фронтенд реализован в `apps/web`: канбан, редактор, связи, история и синхронизация.
Сервер собирается самостоятельно через `build:server`, сервер вместе с CLI — через
`build:cli`; общая сборка продукта включает фронтенд. Визуальная проверка — agent-browser.

## 5. Как агентам работать параллельно

1. Прочитать этот план, `packages/contracts/README.md`, `docs/API.md` и ТЗ своей части.
2. Использовать общий контракт. Изменения DTO согласовывать между фронтендом и бэкендом
   и сопровождать обновлением примеров и проверок совместимости.
3. Фронтенд может разрабатывать сценарии на типизированных HTTP-моках;
   финальная проверка проводится с реальным NestJS и временным хранилищем.
4. Изменения общих build-скриптов и зависимостей синхронизировать через корневой
   `package.json` и `package-lock.json`.
5. В отчёте каждого агента указывать реализованные пункты, команды проверок,
   оставшиеся ограничения и изменения контракта.

## 6. Команды разработки

Это команды для разработчиков в репозитории. Пользовательский запуск продукта — NPX.

```bash
npm ci
npm run build
npm run dev:server
npm run dev:web
npm run dev:cli -- list --config playground/tasks.config.json
```

Nest — `127.0.0.1:3000`. Vite-сервер работает отдельно на
`127.0.0.1:5173` с проксированием `/api` в Nest, включая SSE.
Dev-сервер по умолчанию использует playground и автора `human`.
`TASKS_CONFIG`, `TASKS_ACTOR`, `TASKS_PORT` позволяют выбрать другое окружение;
при изменении порта Nest согласуйте target прокси Vite.

```bash
npm run check
npm run package:check
npm run test:cli
npm run test:server
npm run test:core
npm run test:contracts
```

Корневой каталог тестов не используется. Интеграционные тесты команд находятся
в CLI, проверки Nest — в server, проверки бизнес-правил — в Core.
Contracts проверяется компиляцией совместимости DTO с реальными типами ядра.
Фронтенд проверяется командами `lint:web`, `typecheck:web`, `build:web` и через agent-browser.
Сборка `dist/web` выполняется после очистки/сборки бэкенда в общем `build`/`prepack`.

Релиз выполняется существующим процессом публикации по тегу после приёмки.
При проверке каркаса используется локально собранный архив: опубликованная версия
пакета может ещё не содержать команду `server`.
