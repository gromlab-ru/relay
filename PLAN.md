# План реализации Tasks: CLI + NestJS + React

## 1. Цель продукта и способ распространения

**Продукт распространяется одним npm-пакетом `@gromlab/tasks-cli` и запускается
пользователем через NPX.** Пользователь работает из каталога своего проекта:

```bash
npx @gromlab/tasks-cli init
npx @gromlab/tasks-cli create "Реализовать регистрацию" --actor human
npx @gromlab/tasks-cli list
npx @gromlab/tasks-cli server --actor human --open
```

Последняя команда запускает NestJS на `http://127.0.0.1:3000`. Он отдаёт
собранное React-приложение, REST API и, после реализации этапа B, SSE.
Доступны `--port`, `--config`, `--actor` / `TASKS_ACTOR`; `--open` открывает браузер.
Для пользователя уже собраны JavaScript, CSS и остальные ресурсы UI.

**Готовность проверяется на установленном npm-архиве в чистом каталоге,
вне этого репозитория и без devDependencies.** Запуск через исходники или Vite
сам по себе не означает готовности пакета для NPX.

## 2. Подтверждённые требования

- Node.js 22+; один локальный проект за запуск сервера.
- React + TypeScript; полноценный канбан с созданием и редактированием задач.
- Все настроенные статусы представлены колонками, включая выполненные и отменённые.
- Колонки, их порядок и цвета берутся из `tasks.config.json`.
- Положение карточек внутри колонки задаётся перетаскиванием и сохраняется в JSON.
- CLI и NestJS используют одни операции Core, включая ревизии и блокировки.
- В `.tasks` находятся только `<id>.json` с задачами, их комментариями и отчётами.
- UI обновляется при изменениях из CLI, API и других вкладок; черновики пользователя сохраняются.
- Качество визуального дизайна, доступности и UX входит в критерии приёмки.

## 3. Архитектура

```text
apps/
  cli/src/                 Commander, команды и терминальные представления
  server/src/              NestJS: модули, контроллеры, HTTP, Swagger, статика
  ui/src/                  React, визуальная система, клиент API
packages/
  core/src/                domain, application, storage, shared
  contracts/src/           независимые от Node/Nest/React типы REST и SSE
apps/cli/test/             регрессии CLI, запуск server и проверки публикации
apps/server/test/          проверки Nest-каркаса; далее HTTP-интеграция
packages/core/test/        проверки ядра и границ импортов
packages/contracts/test/   проверка совместимости DTO и типов ядра
scripts/                   сборка, упаковка и публикация
```

```text
CLI ───────────────────→ Core ──→ .tasks/*.json
                            ↑
React ── REST ─────────→ NestJS
      ←─ SSE ───────────────┘
```

Границы импортов:

- CLI использует `#core/*`; команда `server` лениво загружает `#server`.
- NestJS использует `#core/*` и `#contracts`.
- React использует `#contracts` и HTTP-клиент.
- Core содержит бизнес-правила и файловые операции. Представления CLI находятся в `apps/cli`.
- Contracts пригоден для браузера и содержит только переносимые типы и константы.

Корневой `package.json` управляет зависимостями и единым публикуемым пакетом.
У приложений отдельные TypeScript-конфигурации. Сборка создаёт `dist/cli`,
`dist/server`, `dist/ui`, `dist/core`, `dist/contracts`. Внутренние алиасы
разрешаются внутри установленного архива, без workspace-ссылок на исходники.

## 4. Текущее состояние и следующий объём работ

### Этап A — каркас и интеграционная основа

- [ ] Перенести CLI и Core, сохранив поведение команд и тесты.
- [ ] Выделить типизированный REST/SSE-контракт и описать его в `docs/API.md`.
- [ ] Поднять NestJS с `/api/v1/health`, `/api/v1/context`, Swagger и раздачей React.
- [ ] Добавить React-экран проверки связи с NestJS и Vite proxy для разработки.
- [ ] Настроить сборку приложений, запуск из npm-архива и smoke-проверку сервера.
- [ ] Разместить тесты в приложениях и пакетах, с отдельными командами запуска.
- [ ] Подготовить задания агентам и явно обозначить незавершённые возможности.

Экран проверки каркаса — техническая точка входа. Продуктовый канбан разрабатывает
фронтенд-агент по `UI_SPEC.md`. Задачные HTTP-маршруты и SSE реализует бэкенд-агент
на этапе B. `/api/docs` каркаса документирует только реально доступные маршруты.

Предыдущие незавершённые прототипы сохранены в `apps/ui/reference` и
`apps/server/reference`. Они исключены из сборки, проверки типов и npm-архива.
Их можно использовать как материалы для анализа; актуальный контракт — в
`packages/contracts` и `docs/API.md`.

### Этап B — задание бэкенд-агенту

Зона работы: `apps/server/src`, `apps/server/test`; необходимые общие
операции добавляются в `packages/core`.

- [ ] Реализовать Nest-модули `tasks`, `board`, `comments`, `logs`, `events`.
- [ ] Добавить все маршруты из `docs/API.md`, включая чтение и изменение карточек.
- [ ] Использовать схемы Core через Zod validation pipe и единый exception filter.
- [ ] Возвращать типы из `#contracts`; описать запросы, ответы и ошибки в OpenAPI.
- [ ] Реализовать поиск, фильтры и курсорную пагинацию без скрытого ограничения всей доски.
- [ ] Выдавать компактные карточки; комментарии и отчёты читать отдельными страницами.
- [ ] Проверять `ifRevision` при изменении полей, перемещении и назначениях.
- [ ] Перемещать карточку атомарно: статус + позиция относительно `beforeId`.
- [ ] Проверить сохранение порядка после перезапуска, конкурирующих изменений и работы через CLI.
- [ ] Добавлять комментарии и отчёты под общей блокировкой документа.
- [ ] Реализовать SSE и наблюдение за внешними изменениями файлов и конфига.
- [ ] Освобождать наблюдателей и подписки при отключении клиентов и остановке Nest.
- [ ] Покрыть ошибки схем, блокеров, циклов, назначения, порядка и ревизий HTTP-тестами.
- [ ] Проверить изоляцию API от SPA fallback, лимит тела запроса и локальный доступ.

NestJS использует Fastify-адаптер. Раздача UI — `@nestjs/serve-static`,
документация — `@nestjs/swagger`. Middleware, ответы и тесты должны учитывать
выбранный адаптер. Операции с задачами вызываются напрямую через сервисы Core.

### Этап C — задание фронтенд-агенту

Зона работы: `apps/ui`, включая `apps/ui/test`. Подробное задание — [UI_SPEC.md](UI_SPEC.md).

- [ ] Спроектировать визуальную систему согласно подключённым UI/UX-правилам.
- [ ] Создать канбан, фильтры, создание и открытие карточек.
- [ ] Реализовать перетаскивание между колонками и внутри колонки, включая клавиатуру.
- [ ] Реализовать редактор полей, Markdown, исполнителей, тегов и связей.
- [ ] Добавить комментарии, отчёты и постраничное чтение истории.
- [ ] Обработать конкурентные изменения, сохранение черновиков и восстановление связи.
- [ ] Разработать состояния загрузки, пустых данных, ошибок, сохранения и конфликтов.
- [ ] Проверить светлую/тёмную темы, адаптивность, длинные тексты и доступность.
- [ ] Подключить реальный API и SSE; сценарии на моках использовать для независимой разработки.
- [ ] Провести браузерную проверку всего жизненного цикла задачи.

### Этап D — совместная приёмка

- [ ] Человек создаёт задачу и подзадачи через UI; CLI видит те же документы.
- [ ] Агент изменяет задачу через CLI; открытая доска обновляется автоматически.
- [ ] Перенос и порядок сохраняются после перезапуска сервера и браузера.
- [ ] Недопустимое завершение заблокированной задачи возвращает понятную ошибку.
- [ ] Устаревшее изменение возвращает 409, введённый текст остаётся доступен.
- [ ] Комментарии и отчёты переживают параллельные записи.
- [ ] Выполненные и отменённые задачи доступны на доске; родительство и зависимости различаются.
- [ ] `npm run check` и `npm run package:check` проходят.
- [ ] Из установленного архива работает `npx @gromlab/tasks-cli server --actor human`.
- [ ] UI, ресурсы, API, Swagger и прямой адрес `/tasks/<id>` доступны из произвольного рабочего каталога.
- [ ] README описывает пользовательские сценарии только через `npx @gromlab/tasks-cli`.

## 5. Как агентам работать параллельно

1. Прочитать этот план, `packages/contracts/README.md`, `docs/API.md` и ТЗ своей части.
2. Использовать общий контракт. Изменения DTO согласовывать между фронтендом и бэкендом
   и сопровождать обновлением примеров и проверок совместимости.
3. Фронтенд может разрабатывать сценарии на типизированных HTTP-моках;
   финальная проверка проводится с реальным NestJS и временным хранилищем.
4. Изменения общих build-скриптов и зависимостей синхронизировать через корневой
   `package.json` и `package-lock.json`.
5. В отчёте каждого агента указывать реализованные пункты, команды проверок,
   оставшиеся ограничения и изменения контракта.

## 6. Команды разработки

Это команды для разработчиков в репозитории. Пользовательский запуск продукта — NPX.

```bash
npm ci
npm run build
npm run dev:server
npm run dev:ui
npm run dev:cli -- list --config playground/tasks.config.json
```

`dev:server` и `dev:ui` работают в отдельных терминалах. Nest — `127.0.0.1:3000`,
Vite — `127.0.0.1:5173`; `/api` проксируется в Nest, включая будущий SSE.
Dev-сервер по умолчанию использует playground и автора `human`.
`TASKS_CONFIG`, `TASKS_ACTOR`, `TASKS_PORT` позволяют выбрать другое окружение;
при изменении порта Nest согласуйте target прокси Vite.

```bash
npm run check
npm run package:check
npm run test:cli
npm run test:server
npm run test:core
npm run test:contracts
```

Корневой каталог тестов не используется. Интеграционные тесты команд находятся
в CLI, проверки Nest — в server, проверки бизнес-правил — в Core.
Contracts проверяется компиляцией совместимости DTO с реальными типами ядра.
UI-агент добавляет тесты в `apps/ui/test` и подключает собственную команду `test:ui`.

Релиз выполняется существующим процессом публикации по тегу после приёмки.
При проверке каркаса используется локально собранный архив: опубликованная версия
пакета может ещё не содержать команду `server`.
