# План реализации Tasks: CLI + NestJS + React

## 1. Цель продукта и способ распространения

**Продукт распространяется одним npm-пакетом `@gromlab/tasks-cli` и запускается
пользователем через NPX.** Пользователь работает из каталога своего проекта:

```bash
npx @gromlab/tasks-cli init
npx @gromlab/tasks-cli create "Реализовать регистрацию" --actor human
npx @gromlab/tasks-cli list
npx @gromlab/tasks-cli server --actor human --open
```

Последняя команда запускает NestJS на `http://127.0.0.1:3000`. Он предоставляет
REST API, OpenAPI, Swagger и SSE. При наличии `dist/web/index.html` сервер также отдаёт
собранное React-приложение. Общая сборка включает фронтенд; без статики API может работать самостоятельно.
Доступны `--port`, `--config`, `--actor` / `TASKS_ACTOR`; `--open` открывает браузер.
Для пользователя уже собраны JavaScript, CSS и остальные ресурсы UI.

**Готовность проверяется на установленном npm-архиве в чистом каталоге,
вне этого репозитория и без devDependencies.** Запуск через исходники или Vite
сам по себе не означает готовности пакета для NPX.

## 2. Подтверждённые требования

- Node.js 22+; один локальный проект за запуск сервера.
- React + TypeScript; полноценный канбан с созданием и редактированием задач.
- Все настроенные статусы представлены колонками, включая выполненные и отменённые.
- Колонки, их порядок и цвета берутся из `tasks.config.json`.
- Положение карточек внутри колонки задаётся перетаскиванием и сохраняется в JSON.
- CLI и NestJS используют одни операции Core, включая ревизии и блокировки.
- В `.tasks` находятся только `<id>.json` с задачами, их комментариями и отчётами.
- UI обновляется при изменениях из CLI, API и других вкладок; черновики пользователя сохраняются.
- Качество визуального дизайна, доступности и UX входит в критерии приёмки.

## 3. Архитектура

```text
apps/
  cli/src/                 Commander, команды и терминальные представления
  cli/test/                регрессии CLI, запуск server и проверки публикации
  cli/scripts/             локальная сборка, упаковка и публикация CLI
  server/src/main.ts       самостоятельная точка входа сервера
  server/test/             source-watch, перезапуск и остановка dev-сервера
  web/src/                 React + Vite канбан
  playground/              демонстрационный проект
packages/
  core/src/                domain, application, storage, shared
  core/test/               проверки ядра и границ импортов
  contracts/src/           независимые от Node/Nest/React типы REST и SSE
  contracts/test/          проверка совместимости DTO и типов ядра
  server-runtime/src/      NestJS: модули, контроллеры, HTTP, Swagger, статика
  server-runtime/test/     HTTP/OpenAPI, SSE, статика и интеграция с Core
  typescript-config/       общие строгие настройки Node-пакетов
```

```text
CLI ───────────────────→ Core ──→ .tasks/*.json
                            ↑
React ── REST ─────────→ NestJS
MCP ──── REST ─────────→ NestJS
      ←─ SSE ───────────────┘
```

Границы импортов:

- CLI использует `@tasks/core/*`; команда `server` лениво загружает `@tasks/server-runtime`.
- Самостоятельный `@tasks/server` использует тот же `@tasks/server-runtime`, а не код CLI.
- NestJS в Server Runtime использует `@tasks/core/*` и `@tasks/contracts`.
- React использует типы `@tasks/contracts` и HTTP-клиент, без серверных зависимостей.
- Core содержит бизнес-правила и файловые операции. Представления CLI находятся в `apps/cli`.
- Contracts пригоден для браузера и содержит только переносимые типы и константы.

Корневой `package.json` приватный и управляет pnpm workspaces и Turbo. Состав пакетов
задаёт `pnpm-workspace.yaml`, общий lockfile — `pnpm-lock.yaml`. Внутренние зависимости
объявляются как `workspace:*` в манифестах потребителей, межпакетные импорты используют `exports`.
Версия публикуемого продукта принадлежит `apps/cli/package.json`.
Каждый Node-пакет собирается своим `tsc -p tsconfig.json` в локальный `dist`,
без межпакетных TypeScript project references и корневых алиасов исходников.
Порядок сборки и кеширование задаёт Turbo; web сохраняет собственный браузерный tsconfig.

Сборка CLI создаёт `apps/cli/dist/cli/main.js` и копирует `apps/web/dist` в
`apps/cli/dist/web`. Зависимость сборки CLI от web задаётся задачами Turbo, а не npm-импортом
другого приложения. Релизный stage `apps/cli/.artifacts/package` включает приватные
runtime-библиотеки в готовый JavaScript и сохраняет ленивую загрузку сервера.
Проверенные архивы находятся в `apps/cli/.artifacts/npm`; установленный пакет
не зависит от workspace-ссылок на исходники.

## 4. Текущее состояние и следующий объём работ

Бэкенд реализован в `packages/server-runtime`: все маршруты из
[API.md](../packages/contracts/docs/API.md), OpenAPI 3.1,
Swagger и SSE. CLI и HTTP вызывают бизнес-операции Core напрямую. Общие запросы
доски и истории находятся в `packages/core/src/application/queries`.
Фронтенд реализован в `apps/web`: канбан, редактор, связи, история и синхронизация.
Самостоятельный сервер собирается с runtime через `build:server`; `build:cli`
собирает CLI, runtime и web. Общая сборка продукта включает фронтенд.
Визуальная проверка — agent-browser.

## 5. Как агентам работать параллельно

1. Прочитать этот план, `packages/contracts/README.md`, `packages/contracts/docs/API.md` и ТЗ своей части.
2. Использовать общий контракт. Изменения DTO согласовывать между фронтендом и бэкендом
   и сопровождать обновлением примеров и проверок совместимости.
3. Фронтенд может разрабатывать сценарии на типизированных HTTP-моках;
   финальная проверка проводится с реальным NestJS и временным хранилищем.
4. Зависимости и локальные команды менять в манифестах владельцев; общие команды
   и порядок сборки согласовывать через корневые `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml` и `turbo.json`.
5. В отчёте каждого агента указывать реализованные пункты, команды проверок,
   оставшиеся ограничения и изменения контракта.

## 6. Команды разработки

Это команды из корня репозитория для разработчиков. Требуются Node.js 22.13+ и pnpm 11.18.0;
рекомендуется Node.js 24. Пользовательский запуск продукта — NPX на Node.js 22+.

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm run dev
```

`dev` запускает API и web вместе через Turbo. Для раздельного запуска используются
`pnpm run dev:server` и `pnpm run dev:web`. Nest — `127.0.0.1:3000`, Vite —
`127.0.0.1:5173` с проксированием `/api` в Nest, включая SSE.
Dev-сервер по умолчанию использует `apps/playground/tasks.config.json` и автора `human`.
`TASKS_CONFIG`, `TASKS_ACTOR`, `TASKS_PORT` позволяют выбрать другое окружение;
при изменении порта Nest задайте соответствующий `TASKS_API_URL` для Vite.
Для мутаций и браузерных проверок используйте временное хранилище и абсолютный `TASKS_CONFIG`.

CLI из исходников запускается отдельно, без Turbo-логов в JSON-выводе:

```bash
pnpm --silent run dev:cli list --config "$PWD/apps/playground/tasks.config.json" --format json
```

Корневой `dev:cli` сохраняет рабочий каталог вызова и выполняет
`tsx --tsconfig apps/cli/tsconfig.dev.json --conditions=tasks-source apps/cli/src/main.ts`.
Условие `tasks-source` выбирает TypeScript-экспорты библиотек без предварительной сборки.
Dev-сервер также следит за исходниками и параллельно проверяет типы.

`pnpm run build` собирает все workspaces. `pnpm start` собирает и запускает
самостоятельный сервер с UI из `apps/web/dist`; это не запуск CLI.
Собранный CLI доступен через `pnpm --silent run start:cli <args>` после `build:cli`.

```bash
pnpm run check
pnpm run package:check
pnpm run test:cli
pnpm run test:server
pnpm run test:core
pnpm run test:contracts
```

Корневой каталог тестов не используется. Интеграционные тесты команд находятся
в `apps/cli/test`, проверки Nest — в `packages/server-runtime/test`, проверки
самостоятельного dev-запуска — в `apps/server/test`, бизнес-правил — в `packages/core/test`.
Contracts проверяется компиляцией совместимости DTO с реальными типами ядра.
Фронтенд проверяется командами `lint:web`, `typecheck:web`, `build:web` и через agent-browser.
Turbo собирает web до сборки CLI; каждый workspace очищает только собственные результаты.
`pnpm run package:check` собирает продукт, подготавливает stage и проверяет установленный
архив вне репозитория. Корневой `pnpm pack` и упаковка рабочего CLI workspace не заменяют
этот процесс; `prepack` CLI запрещает прямую упаковку и указывает на `package:check`.

Релиз выполняется [процессом публикации по тегу](../apps/cli/docs/RELEASING.md) после приёмки.
Корневые `release:check` и `release:publish` делегируют pnpm workspace-скриптам
без Turbo и установки зависимостей репозитория; публикуется тот же проверенный архив.
При проверке каркаса используется локально собранный архив: опубликованная версия
пакета может ещё не содержать команду `server`.
