# Архитектура

[Документация](README.md) → Разработка → Архитектура

Основной сценарий — оркестрация потока задач между оркестратором и субагентами
на одном хосте. Оркестратор создаёт задачи и принимает результаты; человек
наблюдает через UI и при необходимости вносит дополнения.

## Слои

```text
apps/
  cli/src/                 команды, аргументы, ввод, queries и терминальное presentation
  cli/src/backend/         единый контракт операций, Core- и HTTP-адаптеры
  cli/test/                проверки CLI и пользовательского запуска сервера
  cli/scripts/release/     проверка тегов, упаковка, установка и публикация
  server/src/main.ts       самостоятельная точка входа сервера
  server/test/             source-watch, перезапуск и остановка dev-сервера
  web/                     React + Vite приложение
  playground/              демонстрационный проект
packages/
  core/src/                domain, application, storage, shared
  core/test/               проверки ядра и архитектурных границ
  contracts/src/           переносимые REST/SSE DTO
  contracts/test/          совместимость типов с Core
  rest-sdk/                generated ESM-клиент API для web и CLI
  server-runtime/src/      NestJS: bootstrap, модули, HTTP, Swagger, статика
  server-runtime/test/     HTTP/OpenAPI, SSE, статика и интеграция с Core
  typescript-config/       общие строгие настройки Node-пакетов
```

`CommandDefinition<Options>` объединяет контракт и справку команды.
`registerCommand` связывает его с Commander и общим адаптером `action`.
`run` получает контекст и типизированные опции, возвращает `Result`;
открытие проекта и вывод не дублируются. Общие наборы параметров находятся
в `apps/cli/src/options.ts`, `apps/cli/src/task-fields.ts` и `apps/cli/src/text-input.ts`.
Порядок добавления команд и пример: [EXTENDING.md](development/EXTENDING.md).

План разделения ответственности: [PLAN.md](PLAN.md). CLI и NestJS/Fastify — входные
интерфейсы к одному Core. Сервер напрямую вызывает его операции, проверяет HTTP-запросы
с помощью Zod и возвращает DTO из Contracts. Реализованы REST и SSE из
[API.md](reference/API.md).
Swagger доступен по `/api/docs`, OpenAPI 3.1 — по `/api/openapi.json`.

Локальный адаптер CLI импортирует операции через `@tasks/core/*`; CLI лениво загружает `@tasks/server-runtime`
для команды `server`. Самостоятельный `@tasks/server` использует тот же runtime;
Node-реализация не импортируется из другого приложения. Runtime зависит от Core
и `@tasks/contracts`; web и HTTP-адаптер CLI используют сгенерированный `@tasks/rest-sdk`.

## Транспорт CLI и worktree

`connectBackend` выбирает `--local`, затем URL из `--server-url`, `TASKS_SERVER_URL`
или `server.url`. `readWorkspaceConfig` читает только настройки до создания адаптера.
При HTTP локальный `openWorkspace` не вызывается; серверный контекст определяет
правила и пути проекта. `server` всегда запускает локальный runtime, `migrate`
при HTTP требует `--local`. Явный URL позволяет работать без локального конфига.

```text
CLI агента → Backend → @tasks/rest-sdk → HTTP → Server Runtime → Core → .tasks оркестратора
CLI --local → Backend → Core → .tasks выбранного --config
```

Core `ProjectQueries` строит общие read models списка, документа, связей, дерева
и групп; `TaskQueries.overview` — обзор. API не импортирует CLI. Вывод, поиск внутри
записей и байтовая пагинация остаются в CLI. HTTP read models передают краткую
выборку списка целиком; это не пагинация `/board`. Полный документ используется
для `get --full` и восстановления истории, отдельный Markdown читается без графа.

Каждая HTTP-мутация получает собственный `actor` в JSON. При отсутствии значения
используется автор сервера для совместимости с UI. Глобальное состояние автора
между запросами не изменяется. `ifRevision` у patch/claim/release необязателен,
как у CLI/Core; явное значение проверяется строго, у перемещения обязательно.
Код завершения Core передаётся в HTTP-ошибке и восстанавливается CLI.

Сервер привязан к конфигу рабочей копии оркестратора. Он сохраняет файлы в этой
копии; Git-коммиты выполняются отдельно. Десять worktree используют один URL и
собственные `TASKS_ACTOR`. Недоступность HTTP даёт ошибку, локальный fallback
требует явного `--local` и корректного пути центрального конфига.

Ключ `requestId` логов/комментариев преобразуется в детерминированный ID записи.
Под блокировкой Core сравнивает уже сохранённое нормализованное содержимое и автора:
тот же запрос возвращает исходную запись, другой — `IDEMPOTENCY_CONFLICT`.
Состояние дедупликации находится в самой задаче, поэтому запись и ключ публикуются
атомарно и переживают рестарт и Git-копирование. HTTP автоматически повторяет
только чтения и добавления с ключом (до двух повторов); CLI возвращает ключ при
неподтверждённом добавлении. Остальные мутации требуют проверки результата перед повтором.

Корневой приватный пакет управляет pnpm workspaces и Turbo. Состав пакетов задаёт
`pnpm-workspace.yaml`, зависимости фиксируются в `pnpm-lock.yaml`. Внутренние зависимости
объявлены как `workspace:*` в манифестах потребителей, импорты проходят через `exports`. Node-пакеты собираются
локальным `tsc -p tsconfig.json` в собственные `dist`, без межпакетных TypeScript
project references и корневых алиасов исходников. Порядок сборки задаёт Turbo.
Условие `tasks-source` выбирает TypeScript-экспорты для разработки через `tsx`;
production и интеграционные проверки используют скомпилированный JavaScript.

`packages/core/src/application/queries` содержит общие запросы доски и истории. Сервер открывает
актуальный конфиг для каждой операции; снимки задач и изменения выполняются под блокировкой Core.
Наблюдатель SSE отслеживает файлы, конфиг и замену каталогов, освобождая ресурсы при остановке.

API собирается и запускается самостоятельно. `pnpm run dev` запускает API и Vite,
а `pnpm start` собирает и запускает самостоятельный сервер с UI из `apps/web/dist`.
`build:server` также зависит от сборки web, поэтому standalone-запуск после сборки
сразу раздаёт статические HTML, JS, CSS и шрифты на корне.
По умолчанию используется `apps/playground/tasks.config.json`; для проверок изменений
нужно отдельное временное хранилище с абсолютным путём `TASKS_CONFIG`.

Сборка CLI содержит `apps/cli/dist/cli/main.js` и копию web в `apps/cli/dist/web`.
В установленном пакете UI подключается из `dist/web` относительно манифеста CLI;
при наличии `index.html` сервер отдаёт статику и клиентские маршруты на `/`.
`/api` зарезервирован и изолирован от SPA fallback. `pnpm run package:check` собирает
самодостаточный stage в `apps/cli/.artifacts/package`, упаковывает и проверяет архив
в `apps/cli/.artifacts/npm`; приватные библиотеки включаются в готовый JavaScript.

Корневой README является единственным источником витрины. Скрипты CLI включают его
и `docs` в архив; ссылки npm README указывают на Git-тег версии, иллюстрации — на raw-файлы.
Включённые руководства сохраняют локальную навигацию внутри архива. Проверки документации
разбирают Markdown, проверяют файлы/якоря и наличие всех команд и параметров в справочнике.

Core проверяет необязательную секцию конфига `server` и подставляет порт `3000`.
Общий runtime выбирает явный `ServerOptions.port` или `config.server.port` по одному
снимку конфига при запуске. CLI передаёт `--port` или `TASKS_PORT`, standalone —
`TASKS_PORT`. Так оба приложения используют одинаковую конфигурацию сервера.

## Вычисляемый обзор проекта

`TaskQueries.overview` использует один проверенный снимок `snapshot`. Чистая функция
в `packages/core/src/application/queries/overview.ts` строит индекс детей, определяет
область дерева, считает прогресс и влияние неудовлетворённых прямых зависимостей.
Готовность использует общие правила Core; внешние блокеры учитываются по полному графу.
Влияние считается на открытые листовые задачи, чтобы структурные родители не увеличивали рейтинг.

CLI-команда `overview [id]` подключается через `registerCommand`. Адаптер
`apps/cli/src/queries/overview.ts` подбирает объём разделов по реальному бюджету ответа,
сохраняя полные счётчики и не перечитывая хранилище. Оформление принадлежит
`apps/cli/src/presentation/overview.ts`; JSON не вызывает текстовый рендерер.
Сводка является результатом чтения, формат задачи и конфигурации остаётся прежним.

## Самодостаточный документ

Задача хранится в `.tasks/<id>.json` вместе с `comments` и `logs`.
Записи контекста адресуются случайными ID в словарях; порядок ключей при записи
детерминирован. Описание, саммари и тела записей — массивы строк Markdown.
Их порядок и пустые строки сохраняются.

Значения по умолчанию применяются только при создании. Отсутствующее обязательное поле
в сохранённой задаче считается ошибкой схемы. Документ задачи v2 использует
единственный числовой `id`; поле `number` отсутствует. ID вложенной записи должен
совпадать с ключом словаря, а её `taskId` — с ID содержащей задачи.

`revision`, `updatedAt`, `updatedBy` относятся ко всему документу. Добавление
комментария или отчёта проходит через ту же операцию изменения задачи.
Отдельных постоянных таблиц комментариев, каталогов логов и частей тел нет.

ID выделяется как максимальный сохранённый ID плюс один в той же критической
секции, что и создание. Пропуски не заполняются. Имена файлов, `parentId`,
`dependsOn` и вложенные `taskId` используют тот же ID.

## Миграция v1 → v2

Старые схемы изолированы в `packages/core/src/domain/legacy.ts` и доступны только `migrate`.
Уникальные старые номера сохраняются как ID. Остальные выдаются выше максимума;
задачи без номеров в пустой базе получают ID от 1 в порядке создания.
Все ссылки и принадлежность вложенных записей преобразуются вместе с документом.

Под общей блокировкой сначала читаются и проверяются все исходные документы,
строится таблица соответствия, проверяются новый граф и размеры JSON.
Затем весь новый каталог записывается и синхронизируется в соседнем `.tasks-runtime/migration-…`.
Готовность фиксируется атомарным журналом `migration-v2.json`.
Исходный каталог хранилища переименовывается в `original`, новый — в `.tasks`.
Журнал удаляется после синхронизации каталогов. На каждом этапе повтор команды
продолжает публикацию; обычные операции при наличии журнала возвращают
`MIGRATION_IN_PROGRESS`. До готовности журнала исходный каталог не меняется.

Резервная копия `original` и `ids.json` остаются в служебном каталоге после успеха.
Они локальны и исключены из Git. Миграция также переносит старую вложенную
структуру `tasks/` в корень, сохраняя поля и ревизии документов v2.
Повтор миграции актуального плоского хранилища — пустая операция.

## Атомарность и конкурентность

Операция записи:

1. Получает короткую блокировку общего хранилища.
2. Читает актуальные задачи, проверяет revision и условия операции.
3. Добавляет запись или изменяет поля в памяти, проверяет схемы и граф.
4. Проверяет размер будущего JSON.
5. Записывает и синхронизирует временный файл в соседнем `.tasks-runtime`.
6. Повторно проверяет владение блокировкой и атомарно публикует файл.
7. Освобождает блокировку и возвращает результат.

Общая блокировка нужна, в частности, против одновременных изменений
`A dependsOn B` и `B dependsOn A`. Чтение графа получает согласованный снимок
под короткой блокировкой. Ожидание stdin происходит до её получения.
Внутри одной записи граф читается один раз. Все ссылки разрешаются из переданного
снимка, а не отдельными обращениями к хранилищу. `claim --status` изменяет
назначение и статус в одном документе и одной критической секции.

`proper-lockfile` поддерживает контроль живости: обновление каждые 2 секунды,
устаревание через 10 секунд. Ожидание ограничено. После гибели процесса
следующая операция может восстановить устаревшую блокировку.

Временный файл создаётся на той же файловой системе. Замена использует `rename`,
а создание новой записи — эксклюзивную публикацию через hard link. Гарантии
относятся к локальным файловым системам с поддержкой этих операций.
Незавершённые временные файлы не считаются данными и исключены из Git.

Если процесс завершился после публикации файла, но до ответа, изменение уже
может существовать. Перед повтором создания проверяется актуальное состояние:
создание задачи не имеет ключа идемпотентности. Логи и комментарии можно повторить
с тем же `requestId`: Core вернёт исходную запись.

## Многострочный текст и выдача

Входной UTF-8 проверяется, CRLF/CR нормализуются в LF. Представление массивом
строк делает JSON удобным для отладки. При выводе строки соединяются в Markdown
с реальными переносами, пустыми строками и отступами. Непечатные управляющие
символы показываются как видимые escape-последовательности.

Хранение и выдача имеют разные задачи: JSON содержит всё, но обычный `get`
показывает карточку и счётчики. `--full` включает контекст, отдельные команды
читают описание, комментарий или отчёт. JSON-режим сохраняет структурированные
массивы строк; текстовый режим предназначен для непосредственного чтения.

Представление текста не входит в JSON-контракт. `Result.text` может быть ленивой
функцией от параметров терминала. JSON не запускает текстовый рендерер.
Пагинация измеряет именно тот формат, который получит вызывающий процесс,
включая ANSI-коды и курсор продолжения. Цвет и ширина передаются явно, без
глобального изменяемого состояния; переносы учитывают экранную ширину Unicode.
Неделимая слишком большая запись возвращает `RESPONSE_TOO_LARGE`.

`list` по умолчанию выбирает статусы с `terminal: false`. Его `--all` — фильтр,
включающий конечные статусы; явный `--status` переопределяет фильтр незавершённых.
Фильтры, включая `--all`, входят в область действия курсора. Параметры размера
страницы отделены от фильтров: `PageOptions.limit` необязателен, и без него
число задач определяется байтовым бюджетом. `output.defaultLimit` применяется
к спискам групп, комментариев и отчётов; их `--all` требует целый ответ в бюджете.

Пагинация сначала измеряет полный кандидат страницы. Это позволяет выдать
помещающийся список за один рендеринг, а последнюю страницу — без лишнего курсора.
При превышении бюджета обычная страница сокращается с сохранением продолжения.
`list` разделяет текущую страницу на группы только при текстовом рендеринге.
JSON сохраняет плоский список в порядке ID. Цвет статуса берётся из
`statuses.*.color` с возвратом к стандартной теме при отсутствии настройки.

## Производительность и Git

Чтение и изменение задачи обрабатывают весь её документ. Короткие отчёты
увеличивают стоимость пропорционально размеру JSON задачи; отдельного механизма
больших потоковых логов нет. Полный документ ограничен 16 МиБ и проверяется
до записи. Модель предназначена для обычных проектных объёмов.

`get` читает задачу, её родителя и прямые зависимости по числовым именам файлов.
Чтение описания, комментария или отчёта открывает один документ. Для этих команд
нет полного сканирования базы. `list`, обратные связи, дерево и изменение графа
по-прежнему читают все задачи; постоянного индекса или кэша нет.
Полную проверку целостности проекта выполняет `validate`.

Разные задачи — независимые файлы Git. Изменения одной задачи, включая
добавление комментариев в разных ветках, могут потребовать разрешения
текстового конфликта. Локальная блокировка предотвращает потерю записей
в общей папке, но не объединяет независимые Git-копии автоматически.

После слияния `validate` проверяет все вложенные данные и граф. Даже чистое
слияние разных файлов может создать цикл; это проверяется тестом с настоящим
`git merge-file`. Цикл можно устранить командой `deps remove`.
Независимые копии могут создать одинаковый числовой ID и один путь `.tasks/N.json`.
Такой Git-конфликт нужно разрешить с согласованными ID и ссылками до `validate`;
автоматического объединения разных задач под одним ID нет.

Для оперативного распределения работы используется одна общая папка данных.
Разные worktree обращаются к ней через общий HTTP-сервер; прямой доступ возможен
через общий `--config` и `--local`.
