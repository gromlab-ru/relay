# Модель продукта и инварианты

> Архив прототипа; действующая [модель](../../../product/entities/product/MODEL.md).

[Сущность «Продукт»](README.md) → Модель

## Продукт и проект

Проект Relay задаёт изолированную область данных и работы. Продукт описывает, что в этой области
создают: назначение, ожидаемое поведение, программные части и относящиеся к ним материалы.
В текущем UI у проекта один раздел продукта. Переключение проекта переключает все его данные.
Отдельный каталог продуктов и выбор нескольких продуктов внутри проекта не предусмотрены.

В моковой модели отдельного объекта с `productId` нет: корень задаётся областью проекта и паспортом.
Наличие отдельного постоянного ID продукта — [решение D-01](OPEN_QUESTIONS.md#d-01-продукт-и-существующий-паспорт).
Имя продукта не является именем регистрации проекта, а редактирование паспорта не должно
неявно переименовывать проект в реестре.

```text
Проект Relay
└── Продукт
    ├── Паспорт
    ├── Фичи
    │   └── Сценарии
    ├── Приложения
    │   └── Вклады в общие фичи
    │       └── Вклады в выбранные сценарии этих фич
    └── Документы с множественными связями

Планы → этапы → задачи ссылаются на продуктовый контекст.
```

## Словарь

| Термин                         | Смысл                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------- |
| Паспорт                        | Целостное описание назначения продукта, пользователей, границ и правил          |
| Возможность, фича              | Устойчивая часть поведения продукта, например каталог или бронирование          |
| Сценарий                       | Конкретное действие и наблюдаемый результат внутри одной фичи                   |
| Приложение                     | Логическая программная часть с собственной ответственностью: веб, API, админка  |
| Вклад, реализация в приложении | Что одно приложение обеспечивает для общего контракта фичи или сценария         |
| Документ                       | Самостоятельный Markdown-материал библиотеки: ТЗ, описание, правила или решение |
| Связанная работа               | Планы, этапы и задачи, изменяющие или проверяющие продукт                       |

В сайдбаре и заголовке каталога используется **«Возможности»**. В карточках, действиях и предметных
описаниях сохраняется слово **«фича»**. Это одна сущность, а не два каталога.

Фича продукта отличается от задачи типа `feature`. Сценарий отличается от задачи реализации.
Они сохраняют идентичность после завершения конкретного плана. Приложение отличается от
репозитория, каталога кода, окружения и процесса агента.

## Содержимое записей

Имена полей ниже соответствуют UI-мокам для сопоставления с кодом. Это минимальные предметные
данные для экранов, а не готовые DTO или окончательная схема файлов.

| Запись              | Поля содержания                                               | Условия                                                                                                               |
| ------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Паспорт             | `name`, `summary`, `description`                              | Название, краткий смысл и Markdown обязательны при сохранении; незаполненный паспорт допустим как начальное состояние |
| Фича                | `id`, `name`, `summary`, `description`, состав сценариев      | Название, краткий смысл и Markdown обязательны; новая фича может не иметь сценариев                                   |
| Сценарий            | `id`, родительская фича, `name`, `description`, `status`      | Название и Markdown обязательны; отдельного `summary` в UI нет                                                        |
| Приложение          | `id`, `name`, `summary`, `description`, `type`                | Название, краткий смысл и Markdown обязательны; состав реализации настраивается отдельно                              |
| Вклад в фичу        | Приложение, фича, `title`, `description`, `status`            | Заголовок и Markdown обязательны для включённой фичи; сценарии можно не выбирать                                      |
| Вклад в сценарий    | Приложение, фича, сценарий, `title`, `description`, `status`  | Существует в выбранной фиче; заголовок и Markdown обязательны                                                         |
| Документ библиотеки | `id`, `name`, `summary`, `body`, `kind`, области, `updatedAt` | Название и Markdown обязательны; краткое описание и связи необязательны                                               |

Доступные типы приложения в UI: «Фронтенд», «Бэкенд», «Внутренний инструмент».
Тип по умолчанию — «Фронтенд». Расширение справочника требует отдельного решения.

Типы документа: `specification` — «Техническое задание», `description` — «Описание»,
`rules` — «Правила», `decision` — «Решение». По умолчанию — `description`.

В исходниках `ProductDocument` — общий читаемый набор полей паспорта, фичи или приложения.
Самостоятельный материал библиотеки называется `ProductDocumentation`. Сходство технических
названий не означает, что все эти записи нужно объединить в одну пользовательскую сущность.

## Идентичность и принадлежность

1. Все записи и отношения принадлежат выбранному проекту; ссылка не может незаметно попасть
   в продукт другого проекта.
2. Фича имеет постоянный ID. Сценарий имеет постоянный ID и ровно одну родительскую фичу.
   Для адресации сценария достаточно пары «фича + сценарий» внутри проекта; техническая
   глобальная уникальность ID определяется постоянной схемой.
3. Названия редактируются независимо от ID. Переименование не разрушает якоря, вклады и связи.
4. Вложенность продуктового каталога ровно двухуровневая: фича → сценарии.
   Сценарий не является дочерней фичей и не имеет собственных подсценариев.
5. Фича и сценарий существуют в продукте один раз. Приложения ссылаются на них, не создавая копии.
6. Числовой ID задачи и ID продуктовой записи — разные пространства. Нельзя подставлять одно
   вместо другого даже при совпадении отображаемого названия.

Формат новых ID должен быть совместим с контрактом ядра. UUID новых моковых записей и слова
`catalog`, `web` из примеров не являются выбранным форматом постоянного хранения.

## Отношения приложений

Между приложениями и фичами действует связь многие-ко-многим с собственным содержанием.
В пределах одной пары «приложение + фича» общий вклад единственный. В пределах этого вклада
один сценарий выбирается не более одного раза.

- Выбор фичи объявляет ответственность приложения на уровне общего контракта.
- Выбор сценария включает его родительскую фичу. Выбор фичи сам по себе не выбирает сценарии.
- Снятие фичи исключает из подтверждаемого состава все её сценарии.
- Снятие последнего сценария не снимает общий вклад в фичу.
- Допустимы фича без выбранных сценариев и приложение совсем без вкладов.
- Заголовки, Markdown и готовность вкладов принадлежат приложению. Редактирование исходной
  фичи или сценария не заменяет эти тексты.
- Сохранение состава одного приложения не изменяет вклады остальных приложений.
- Список приложений у фичи и дерево фич у приложения — две проекции одних отношений.

Полный цикл выбора и атомарного сохранения описан в
[редакторе состава](pages/application-scope.md). Статус вклада и готовность общего сценария
разделены в [правилах готовности](READINESS.md).

## Документ и его области применения

Документ принадлежит библиотеке продукта даже без выбранных связей. Отсутствие связей
не означает автоматическую связь с продуктом целиком или со всеми его частями.
Один документ может одновременно относиться к любому числу областей разных видов.

| Вид области         | Что нужно идентифицировать в реальной модели                 |
| ------------------- | ------------------------------------------------------------ |
| Продукт целиком     | Продукт выбранного проекта                                   |
| Фича                | Общую фичу                                                   |
| Сценарий            | Фичу и её общий сценарий                                     |
| Приложение          | Приложение                                                   |
| Реализация фичи     | Вклад конкретного приложения в конкретную фичу               |
| Реализация сценария | Вклад конкретного приложения в конкретный сценарий этой фичи |

Это смысловая таблица целей связей, а не утверждённые имена дискриминаторов API.
Особенно важно различать «сценарий продукта» и «реализацию сценария в API».

**Сейчас** `scopeIds` содержит значения `demo-*` из независимого справочника. Они не ссылаются
на записи моковой модели, не меняются при их переименовании и не создают обратных ссылок.
Их нельзя записывать в ядро как настоящие отношения или сопоставлять по совпадению названий.

**Требование перехода:** области выбираются из существующих записей текущего продукта.
Цель связи хранится типизированно, проверяется на существование и принадлежность. Подписи
и путь берутся из текущих сущностей, один и тот же документ не дублируется для каждой связи.
Реализация доступна как область только при наличии соответствующего вклада приложения.
Выбор документа не объявляет новое участие приложения в продукте.

В отличие от выбора состава приложения, связи документа полностью независимы: выбор сценария
не включает фичу, а выбор реализации не включает приложение или исходный сценарий.
Родительский путь в UI нужен для понимания контекста, а не для каскадного выбора.

Реальные обратные выборки нужны для поиска документов по области. Размещение таких списков
в карточках фич, сценариев и приложений ещё не показано в прототипе —
[решение D-05](OPEN_QUESTIONS.md#d-05-реальные-связи-документов).

## Отношения с работой

Текущий мок содержит план → этап → задачу; работа ссылается на фичи и приложения.
Продуктовая сущность не принадлежит одному плану и не пересоздаётся для следующего цикла.
История одной фичи может включать завершённый MVP и текущий план развития.

Целевое направление — ссылки также на конкретные сценарии. Общая работа может ссылаться
на фичу целиком; техническая задача не требует искусственной фичи. В реальной реализации
нужно использовать существующие планы, этапы и задачи Relay, а не сохранять параллельную
копию `ProductWork`. Детали — [связанная работа](pages/work.md).

## Запись и согласованность

Требования к постоянной модели:

- Различать создание и изменение; исчезнувшая редактируемая запись не создаётся заново
  как побочный эффект сохранения старой формы.
- Проверять обязательные поля, допустимые статусы, уникальность и принадлежность ссылок
  в общей операции, а не только в браузере.
- Сохранять Markdown как пользовательский текст, сохраняя значимые переносы и структуру.
  Обязательность проверяется после удаления пробелов по краям.
- Хранить сведения о ревизии и авторе; конкурентная запись проверяет прочитанную версию.
- Публиковать весь состав реализации атомарно. Ошибка одного вклада не оставляет остальные
  частично сохранёнными.
- Получать счётчики и обратные представления из тех же данных, что и основные страницы.
  Поиск не меняет состав или готовность.

Окончательные единицы хранения, версии, пределы размеров и история изменений описываются
на этапе [контрактов и миграции](IMPLEMENTATION.md), а не выводятся из формы мокового снимка.
