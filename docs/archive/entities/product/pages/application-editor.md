# Создание и редактирование приложения

> Архив прототипа. Действующий [контракт Web](../../../../product/applications/web/PRODUCT.md).

[Сущность «Продукт»](../README.md) → Редактор приложения

**Создание:** `/projects/:project/product/applications/new`.
**Изменение:** `/projects/:project/product/applications/:applicationId/edit`.

## Поля

| Поле                | Смысл                                                 | Правило                                       |
| ------------------- | ----------------------------------------------------- | --------------------------------------------- |
| Название            | Имя программной части продукта                        | Обязательно                                   |
| Краткий смысл       | Назначение для быстрого чтения каталога               | Обязательно                                   |
| Тип приложения      | Класс ответственности                                 | «Фронтенд», «Бэкенд», «Внутренний инструмент» |
| Описание в Markdown | Назначение, ответственность, границы и взаимодействия | Обязательно                                   |

По умолчанию тип — «Фронтенд». В описании можно указать размещение кода и контракты взаимодействия,
но отдельных полей репозитория, окружения, запуска агента или deployment в этой форме нет.

## Поведение

- Новое приложение получает постоянный ID и пустой состав реализации.
- Форма явно объясняет следующий шаг: выбор фич и сценариев выполняется на странице приложения
  после сохранения.
- Редактирование общих сведений сохраняет весь состав, заголовки, Markdown и статусы вкладов.
- Успех открывает страницу приложения; отмена создания — каталог, отмена изменения — приложение.
- Предпросмотр, черновики, ошибки и явный конфликт работают по
  [общим правилам](../COMMON_BEHAVIOR.md).
- Отсутствующий ID не превращает редактор изменения в форму создания.

## Требования перехода

Приложение — самостоятельная продуктовая запись. Создание карточки не создаёт репозиторий,
сервер, процесс или регистрацию проекта. Операция изменения не должна перезаписывать
параллельно изменённый состав приложения, даже если технически сведения хранятся рядом.

## Критерии приёмки

1. Создание доступно в продукте без фич; карточка имеет нулевой состав и сохраняется между сессиями.
2. Смена названия/типа/описания видна в каталоге и обратных представлениях участия.
3. Существующие вклады остаются теми же после редактирования общих сведений.
4. Ошибка и конфликт не удаляют ввод; неизвестное приложение не создаётся повторно.
