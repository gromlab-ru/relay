## 1. Поручение и принятые решения

Пользователь поручил исследовать проект и UI-прототип из базового коммита, предложить
хранение, связи и агентские интерфейсы, затем сохранить план и приступить к реализации.

Ключевое уточнение пользователя после обсуждения:

> Всё хранится в JSON, включая Markdown. CLI принимает многострочный Markdown напрямую,
> без создания промежуточных MD-файлов.

Первоначальное предложение хранить `passport.md` и тексты библиотеки отдельными файлами
заменено JSON-записями. Многофайловая транзакция для Markdown и метаданных не понадобилась:
каждая операция публикует один самодостаточный JSON.

Решения первой реализации:

- В текущей области Relay находится один продукт. Его идентичность выводится из идентичности
  области; название продукта не переименовывает регистрацию Relay.
- Фронтенд, бэкенд и внутренние инструменты — `application` внутри продукта. Они отличаются
  от существующих проектов в реестре Relay.
- Паспорт, фичи, сценарии, приложения и документы имеют отдельные записи.
- Весь состав реализации одного приложения — один агрегат `scope`.
- Контракты имеют собственные постоянные ID. Снятие участия делает их неактивными,
  сохраняя разрешимость существующих ссылок документов.
- Общие фичи и сценарии не имеют ручного статуса: готовность вычисляется по реализациям.
- Ревизия записи защищает конкурентную запись; отпечаток `basis` связывает подтверждение
  реализации с содержанием актуальных требований.
- Интеграция с задачами, планами, досками и релизами отложена. Старый паспорт остаётся
  в legacy-модели, автоматического переноса или синхронизации с новым нет.

### 2.3. Core и хранение

Добавлены схемы записей и операций, продуктовый репозиторий и сервисы.
Хранилище находится в каталоге `product` рядом с конфигом области, обычно `.relay/product`.

Реализованы:

- чтение пустого продукта без подстановки примеров;
- сохранение Markdown с переносами и значимыми пробелами;
- создание и обновление как разные действия;
- общая блокировка с остальными операциями области Relay;
- атомарная публикация записи и всего состава приложения;
- ревизии, авторство, даты, события и журнал запросов;
- идемпотентные повторы по автору и `requestId`;
- проверка типов, принадлежности, уникальности и существования ссылок;
- сохранение неактивных контрактов и запрет новых связей с ними;
- автоматическая готовность и устаревание подтверждений;
- точечное изменение контракта без переподтверждения соседних контрактов;
- компактный обзор, список с поиском/пагинацией и связанный контекст,
  включая адресацию отдельного контракта.

### 2.4. REST, SDK, CLI и MCP

Добавлены `backend.product` в local/HTTP и серверный модуль с тегом OpenAPI `product`.
Расширены маршрутизация выбранной области и наблюдение SSE за продуктовыми записями.
SDK пересобран генератором `@gromlab/rest-api-codegen@5.2.4` из работающего API.

Пути относительно `/api/v1/product` или `/api/v1/projects/:project/product`:

| Метод и путь    | Результат                                                        |
| --------------- | ---------------------------------------------------------------- |
| `GET /state`    | Полный согласованный снимок без внутренних журналов              |
| `GET /overview` | Краткая карта и готовность без полных текстов                    |
| `GET /records`  | Список/поиск: `kind`, `q`, `id`, `offset`, `limit`               |
| `GET /context`  | Контекст выбранной записи и приложения с причинами включения     |
| `POST /records` | Создание, обновление, замена состава и точечная правка контракта |

CLI:

```text
product state | overview | list | get | context | validate
product save --json ... [--description ...] [--body ...]
product passport create | update
product feature create | update
product scenario create | update
product application create | update
product document create | update
product scope replace
product contract update
```

MCP: `product_overview`, `product_list`, `product_context`, `product_save`.
В workspace требуется `project`; в записи указываются автор и стабильный `requestId`.

## 5. Существенные особенности текущей версии

1. **Web читает полный снимок.** Редактор защищён версией всего продукта, поэтому внешняя
   правка другой записи тоже может вызвать конфликт. В CLI/API обычная запись может
   ограничиться собственной ревизией; состав требует также `ifVersion`.
2. **`product-demo` ещё существует.** Его провайдер и часть типов используются как адаптер
   прежнего интерфейса. Моковые сессии и служебная панель не являются рабочим источником данных.
3. **Редакция требований — отпечаток содержимого.** Числового `contractVersion` нет.
   Изменение Markdown влияет на подтверждение, переименование не переписывает контракт.
4. **`state` и `context` могут быть крупными.** Для обзора есть компактная операция,
   для постепенного чтения — `list`. MCP применяет общий бюджет ответа и не выдаёт
   незаметно обрезанный успешный результат.
5. **Существующая продуктовая документация частично историческая.** Описание старого мока
   и прежние открытые вопросы нельзя автоматически считать текущим wire-контрактом.
   Приоритет: уточнения пользователя, актуальный справочник продукта, код и тесты.
6. **Граница этапа сохранена.** Старый паспорт и жизненный цикл не мигрированы. Задачи,
   планы и релизы не определяют готовность новой продуктовой модели.

## 6. Как продолжить в новой сессии

1. Прочитать этот журнал, план и `docs/reference/PRODUCT.md`.
2. Проверить `git status --short`, текущую ветку и diff: работа пока не закоммичена,
   новые файлы могут оставаться untracked. Сохранять пользовательские правки.
3. Получить замечания пользователя. Следующий согласованный этап — приёмка и доработка
   продукта, не автоматическая перестройка планов/задач/релизов.
4. Перед изменениями Web выполнить протокол `apps/web/AGENTS.md`: прочитать применимые
   skills и профиль, установить владельцев и зафиксировать план.
5. Для ручного просмотра использовать `pnpm run dev`; для проверочных изменений данных
   поднимать отдельный стенд, а не заполнять пользовательский продукт тестовыми записями.
6. При изменении API обновлять OpenAPI и генерировать SDK. Не редактировать
   `packages/rest-sdk/src` вручную.
7. При изменении исходников скилла или отслеживаемых контрактов запускать
   `pnpm run skills:build`, затем `pnpm run skills:check`.
8. После доработки запускать подходящие проверки; результаты и оставшиеся ограничения
   добавлять новой датированной записью в этот журнал.
