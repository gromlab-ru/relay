# Раздельное хранение графа v2

## Цель и владельцы

Убрать предел 16 МиБ на весь граф и чтение/перезапись всей истории при одной операции.
Владельцы: Core storage/application graph; CLI — явная миграция и обслуживание индекса;
Server Events — лёгкое обнаружение изменения. Представления Web и формат ответов графа сохраняются.

## Решение до реализации

- `.relay/relations/current/<hash-prefix>/<id>.json`: одна текущая связь, включая
  надгробие отозванной связи для сохранения идентичности; Markdown массивом строк.
- `history/<segment>/<sequence>.json`: отдельные неизменяемые события, последовательность
  обеспечивает прежнюю пагинацию и порядок, не зависит от времени/лексикографического ID.
- `requests/<prefix>/<hash>.json`: адресная квитанция, повтор не читает весь журнал.
- `meta.json`: версия схемы 2, ревизия, число событий. Лимиты относятся к одной записи
  и одному пакету, не к суммарной базе.
- `.indexes`: сегментированный восстанавливаемый индекс кратких рёбер и входящих/исходящих
  списков в памяти; пояснения читаются только для выбранной страницы. Индекс истории
  адресует события одной связи. Авторитетны current/history/requests/meta, не индексы.
- `transactions/pending.json`: долговечное намерение с исходными хешами и итоговыми
  записями. Под общей блокировкой восстановление идёт до любой операции Core;
  несовместимая внешняя правка останавливает восстановление. Потеря производного индекса
  не мешает восстановлению канонических данных.

## Совместимость и восстановление

V1 читается совместимо без переписи. Явная локальная команда миграции переносит данные
без изменения ID, пользовательских ревизий, истории и квитанций; до миграции новые записи
в v1 отклоняются с указанием команды. Перенос возобновляется, источник сохраняется резервной
копией. Старые версии ответа-квитанции сохраняются; после миграции клиент перечитывает
версию графа перед новой записью. Старые клиенты на время переноса должны быть остановлены.

Обслуживание индекса должно быть доступно явно. Обычные записи проходят Core; ручные
изменения файлов требуют проверки/перестроения индекса. Чтение адресного файла сверяет
его хеш с индексом и не выдаёт рассогласование за актуальные данные. Это ограничение
фиксируется явно: файловое хранилище не может бесплатно обнаруживать любое внешнее
изменение миллиона файлов при каждом запросе.

## Приёмка

1. Миграция v1: Markdown, ревизии, отозванные ID, порядок событий и точные квитанции.
2. Прерывание после намерения/частичной публикации/до удаления намерения; повтор,
   конкуренция, внешняя правка, потеря/повреждение индекса, отсутствие частичного ответа.
3. Адресный контекст не читает тела всех связей/событий; запись меняет только свой пакет.
4. CLI text/JSON, REST/OpenAPI, SSE, существующие сценарии графа.
5. Нагрузочный сценарий 10 000/100 000 связей: размер, холодный/повторный контекст,
   запись, перестроение индекса, восстановление. Фиксировать реальные времена и ограничения,
   не превращать выбранные объёмы в обещание бесконечного масштабирования.

## Фактические результаты

Linux, Node.js 24.18.1, локальная файловая система NVMe. Каталог содержит 10 000 узлов
в памяти: замер изолирует хранение отношений от прежнего адаптера продуктовых файлов.
«Холодный» означает новый процесс Node.js, но кеш страниц ОС не сбрасывался. Повторный
контекст — пять запросов. Финальные замеры выполнены последовательно на готовых наборах
командой `bench:graph --measure <каталог> <размер>`. Каждый запуск CLI --local является
новым процессом; HTTP-клиент использует кеш работающего Server. Времена отдельных записей
не следует считать строгой монотонной зависимостью от размера.

| Исходных связей | Холодный контекст | Повторный контекст | Запись одной связи | Перестроение индексов | Восстановление после WAL |
| --------------- | ----------------- | ------------------ | ------------------ | --------------------- | ------------------------ |
| 10 000          | 110 мс            | 13–18 мс           | 64 мс              | 2,93 с                | 96 мс                    |
| 100 000         | 662 мс            | 15–21 мс           | 66 мс              | 16,99 с               | 639 мс                   |

В первом случае прочитаны тела двух отношений, во втором — двадцати; события и квитанции
при обычном контексте не читались. Размер JSON после измерительных записей и их истории:
23,12 / 231,08 МиБ; файлов 30 378 / 301 278, включая производные указатели истории.
Размер файловой системы с каталогами и блоками больше суммы байтов JSON.

Наполнение первого набора через обычные пакеты по 100 заняло 75,8 с. Второй набор
продолжен с 10 100 сохранённых связей после остановки раннего варианта: оставшиеся
89 900 связей записывались 813,5 с. Восстановление незавершённого пакета при продолжении
пройдено; это не измерение полного времени наполнения 100 000 с нуля.

Артефакты: `.artifacts/graph-storage-benchmark-10000.json`,
`.artifacts/graph-storage-benchmark-100000.json`, соответствующие final-логи.
Запись, cold/warm, перестроение и контрольное восстановление измерены на итоговом
варианте с групповой синхронизацией постоянных файлов; ранний вариант в таблицу не включён.
