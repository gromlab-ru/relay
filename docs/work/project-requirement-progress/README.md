# Проектные фичи и сценарии: страницы и готовность по задачам

**Статус: каскад исправлен и проверен после пользовательского уточнения.** Основание — продолжение пользователя после приёмки
[страниц реализаций приложений](../application-implementation-progress/README.md).

## Цель и критерии

Перенести принятый UI/UX на проектные фичи и сценарии. Пользователь читает полный
Markdown, видит задачи продуктовой цели, прогресс, зависимости и реализации приложений.
Фича дополнительно показывает компактный список сценариев с переходами на их страницы.
Готовность в странице, дереве и машинных ответах совпадает и обновляется через SSE.

- Каскад: задачи → активные имплементации приложений → соответствующая проектная фича/сценарий.
- Нет задач ни напрямую, ни в активных реализациях — none («Не реализовано»).
- Есть работа хотя бы в одной ветке — как минимум partial («В работе»).
- Все активные реализации готовы, а прямые задачи (если есть) завершены — done.
  Реализация без задач не готова и удерживает общий результат в partial при начатой работе.
- Cancelled не выполняет обязательство. Отсутствие прямых задач не блокирует подъём готовности.
- Ссылки feature/scenario/implementation различаются по виду и постоянному ID.
  Сценарии и реализации приложений имеют собственную готовность. Реализация поднимает
  её к своей цели; произвольные графовые зависимости не подменяют этот каскад.
  Ручные сохранённые подтверждения не задают новый статус.
- Хранение, тексты, ревизии и квитанции сохраняются без миграции. Версия для CAS
  текста не зависит от перемещения задач; версия краткого каталога учитывает статус.

## Проект UI/UX до реализации

1. Шапка с названием, ключом и статусом; описание фичи сохраняет краткий текст.
2. Полоса якорей: описание, сценарии (у фичи), задачи, реализации и зависимости.
3. Основная колонка: оформленное полное описание с Puzzle/violet или Route/teal,
   компактные сценарии (до 10 с продолжением), открытые задачи по 40 с полным прогрессом.
4. Боковая колонка: родительский контекст, продуктовая доска, зависимости и активные
   реализации приложений с отдельными статусами и прямыми переходами. На узком
   экране области идут последовательно. Якоря учитывают закреплённую шапку.
5. Реализации и зависимости читаются порциями до 5, с явным продолжением и повтором
   после ошибки версии. Нет связей и ошибка чтения — разные состояния.
6. Документы фичи сохраняются. Полные описания сценариев открываются на их страницах,
   а не дублируются длинной лентой внутри фичи. Сохраняются ключи и контекст возврата.

## Владельцы и допуск

Повторно прочитаны протокол, правила библиотеки, концепция, единый стандарт,
Web AGENTS, профиль apps/web/README.md, индекс и точка продолжения первого этапа.
Полные skills unit-architecture/react-reference уже загружены в текущем диалоге;
применяются прочитанные правила страниц, данных, Mantine, TS/JSX/CSS и генерации.
Для новой границы дополнительно прочитаны Unit Architecture: профиль, юниты и колокация.

- Core/product: обобщить первый расчёт по типизированной цели; project readiness
  агрегирует состояния активных имплементаций и прямых задач. Поля participants/completed остаются счётчиками
  активных реализаций приложений, stale=0; текстовые подтверждения остаются историей.
- Новый `compositions/widgets/product-requirement` владеет общей областью чтения
  проектной фичи/сценария, получает Markdown и родительский контекст через props.
- `implementation-dependencies` поднимается целиком в `widgets/product-dependencies`,
  поскольку нужен и реализациям приложений, и проектным требованиям. Старые пути удаляются.
- `product-contributions` читает адресный список реализаций выбранной цели через
  domains/entities и пакетные метаданные domains/product, не требует snapshot-provider.
- `product-tasks` обобщает открытый режим и тексты пустоты для продуктовой доски.
- feature-scenarios владеет компактной навигацией дочерних сценариев;
  product-feature/product-entity координируют содержимое. Данные и SSE остаются в доменах.
- Маршруты и редакторы сохраняют существующие владельцы. Межюнитные зависимости
  проходят через index.ts/lazy.ts; новых обратных зависимостей не требуется.
