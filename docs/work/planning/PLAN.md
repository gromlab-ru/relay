# UI/UX планов

## Уточнение: релиз — отдельная сущность

Основание — новое поручение пользователя 24 сентября 2026. Отменён тип «План релиза».

1. `PlanningPlan` содержит только работу: цель, этапы, задачи, состояние. Убираются
   kind, version и includedPlanIds, выбор типа, релизная вкладка и действия выпуска.
2. Самостоятельный `Release` содержит ID/ключ, название, версию, описание, плановую дату,
   статус и `planIds`. Начальный статус — «Запланирован». Незавершённые планы можно
   включать заранее. Другие состояния UI — «Выпущен» и «Отменён». Прогресс состава
   не меняет статус автоматически. Запланированный релиз не запускает планы.
3. Отдельный экран releases: каталог, просмотр и форма, в которой сразу выбирается
   состав. Форма показывает статусы планов и сохраняет скрытый поиском выбор.
   Релиз не получает собственных этапов и задач; работа подготовки остаётся обычным планом.
4. Локальные записи разделены. Новый плановый формат v2 читает прежние рабочие планы;
   старый релиз адаптируется отдельным владельцем. Его собственные этапы/задачи сохраняются
   как обычный план подготовки с детерминированным ID и включаются в его состав.
   Исходный v1 остаётся нетронутым; новые ключи записываются только явным сохранением.
   Повреждённый старый формат не подменяется примерами. Черновики работы читаются совместимо.
5. Фиксация выпуска в прототипе требует готовности включённых планов и сохраняет
   локальный снимок их содержания. Это демонстрация статуса, не публикация приложения.
   Новые TSX создаются штатным генератором; существующий release-content переносится
   из владельца планов к владельцу релизов и адаптируется без перегенерации.
6. Проверки: отсутствие релизных опций/полей в планах; создание релиза с незавершёнными
   планами и статусом, изменение состава, сохранность ввода, переходы, независимость
   статусов, совместимое чтение v1, обе темы/четыре ширины, lint/typecheck/build и документы.

Контракт будущего Core: релиз владеет линками состава; после продуктовой записи бекенд
явно устанавливает/снимает `includes`, а после создания — `part-of` на проект.
Согласованность обеспечивается восстанавливаемой операцией. Локальный UI не имитирует граф.
Используются прочитанные профиль Web, React Reference (формы, состояние, UI, TSX/CSS,
генерация) и Unit Architecture (домены, юниты, зависимости). Новый domain релизов зависит
от публичных типов/чтения планов; обратной зависимости нет. Новые каталоги не поднимают
локальные CSS в общую тему и сохраняют принятую визуальную систему.

## Цель

Полноценный интерактивный прототип вместо заглушки. Главный критерий — понятный,
аккуратный интерфейс внутри действующей графитовой темы Relay. Сначала визуальная
структура и её браузерная оценка, затем локальные взаимодействия прототипа.

## Сценарий и визуальные решения

- Каталог планов работ: статус «В работе» без отдельного блока фокуса, фильтры состояния,
  поиск и карточки с этапами и точными счётчиками; продолжение по 12.
- Отдельный адрес плана: заголовок и статус, цель, этапы с раскрываемыми задачами,
  область, основание начала, материалы и итог. Задачи не превращаются в копию канбана.
- Релизы имеют отдельную сущность и проекцию с собственным статусом и выбранными планами.
- Компактная форма плана: название, краткое описание, цель Markdown.
  Остальная детализация доступна после создания. Ошибки сохраняют ввод.
- Выбор задач: поиск, доска, состояние, выбранные элементы вне текущего фильтра,
  явное подтверждение. Включение не меняет колонку.
- Доступность: семантические ссылки, клавиатура, фокус, текст рядом с цветом,
  отсутствие горизонтальной прокрутки, полноценные мобильные состояния.
- Данные обозначены как демонстрационные. Локальное сохранение не изображает
  серверную синхронизацию или разрешение реального исполнения.

## Архитектура и контракты

Профиль `apps/web/README.md`, канон Unit Architecture (слои, юниты, зависимости),
React Reference (страницы, UI, стили, формы, состояние, TypeScript/TSX/CSS).
Новые TSX — только через `pnpm --filter @relay/web run create` из локальных шаблонов.

Композиция `planning-workspace` подключается экраном plans. Экран releases самостоятелен.
Вложенные юниты получают типы через фасет `domains/planning-demo`, координацию —
через callbacks. Домен содержит примеры, валидируемый формат и локальные операции;
UI-состояние, фильтры и формы остаются в композициях. Техническое дерево URL — в router.

Раздельные UI-модели содержат состояния, актуальные задачи, этапы и выбранные планы,
готовность и факт завершения. Процент задач не становится разрешением выпуска.
Локальные данные и формы разделены по проекту и вкладке; версия схемы проверяется.
Подключение настоящих Core/REST-операций и прогресса — следующий этап после UI.

## Проверки

1. Статические: lint Web, typecheck Web, production build, форматирование и diff.
2. Браузер: собственный agent-browser, временный проект; светлая и тёмная темы,
   1440/1024/768/390; каталог, фильтры, пустота, прямой адрес, Back/Forward,
   чтение этапа, создание, ошибки ввода, выбор задач и сохранность черновика.
3. Консоль, errors, axe; ручная оценка скриншотов обязательна.
4. Машинная граница: валидируемый локальный формат; отсутствие запросов записи
   в API проекта. Серверная конкуренция и SSE планов не объявляются проверенными.
5. Документация: продуктовый контракт Web, инженерное покрытие, README/ROUTING,
   журнал генерации, досье; `pnpm run docs:check`, Prettier, `git diff --check`.
