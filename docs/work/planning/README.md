# Раздел «Планы» и модель планирования

## Цель и основание

По поручению пользователя от 24 сентября 2026 ознакомиться с проектом и подготовить
обсуждение поведения раздела «Планы», его сценариев и необходимых реализаций.

Статус: ТЗ прогресса скорректировано для передачи в разработку по уточнению пользователя
24 сентября 2026. Выбраны отдельный контроллер и собственные расширяемые контракты по видам;
производительность отложена. ТЗ планирования остаётся черновиком. Предметная реализация
не входит в текущее поручение. Результаты прежних проверок находятся в журнале;
адресные проверки обновлённых документов прошли. Общая проверка имеет прежние пять ошибок
ссылок на отсутствующий `STORAGE-REFACTORING.md`.

## Границы и владельцы

- Изучить действующую модель продукта, задач, связей и раздела «Планы».
- Сопоставить согласованное направление с фактическими исходниками.
- Зафиксировать вопросы и предложения для обсуждения; предложение не становится требованием
  без решения пользователя.
- Реализация функционала начинается после согласования сценария и контрактов.

Затронутые владельцы: документация продукта; Core — предметные правила и хранение;
Contracts — виды сущностей и DTO; server-runtime/SDK — REST; CLI/MCP — интерфейсы агентов;
Web — экран «Планы» и взаимодействие с существующими задачами.
Точные границы будущих модулей определяются при проектировании.

## Источники и исходные ограничения

- [Направление развития](../../product/DIRECTION.md#связь-продукта-с-работой) — согласованные
  принципы цели плана, области изменения и связи с задачами.
- [Сквозные процессы](../../product/workflows/README.md) и
  [словарь](../../product/GLOSSARY.md) — роль плана и этапа.
- [Web](../../product/applications/web/README.md) и
  [архитектура](../../engineering/ARCHITECTURE.md) — действующие интерфейсы и владельцы.
- [Канбан](../../product/entities/tasks/KANBAN.md) — существующие задачи и ограничения.
- [Очистка прежней модели](../legacy-cleanup/README.md) — удаление старого жизненного цикла;
  его история не задаёт новую модель планирования.
- [Линки, связи и контекст](../../development/LINKS-AND-CONTEXT.md) — обязательное разделение
  продуктовых линков и отдельно сохраняемых связей Core.

Для будущих сценариев предстоит определить линки плана с областью изменения, этапами,
задачами и документами, кардинальность и последствия снятия/удаления. Бекенд после
продуктовой записи явно согласует соответствующие связи Core в одной восстанавливаемой
операции. Чтение контекста не подменяет хранение этих отношений. В текущем исследовании
данные Relay, контракты хранения и связи не меняются; миграция не требуется.

## План исследования и проверки

1. Прочитать правила, концепцию, связанные работы и состояние рабочей копии.
2. Сверить маршрут и экран «Планы», наличие предметных контрактов и точки интеграции
   с продуктом, задачами и графом.
3. Сохранить факты, предложения и открытые вопросы; обсудить первый пользовательский сценарий.

Проверки исследования: статическое чтение конкретных исходников, навигация документов,
`pnpm run docs:check`, форматирование изменённых документов и `git diff --check`.
Запуск пользовательских сценариев фиксируется отдельно, если фактически выполнялся.

## Результат и вопросы обсуждения

Текущее покрытие сверено по коду и сохранено у
[инженерного владельца](../../engineering/implementation/README.md#планирование-сверка-24-сентября-2026).
Согласованный пользователем сценарий «продукт → задачи → план с этапами» добавлен в
[направление развития](../../product/DIRECTION.md#связь-продукта-с-работой) и
[сквозной процесс](../../product/workflows/README.md). Планов в проекте может быть несколько.
Дополнительно пользователь определил план как обоснование начала работы: существования
задачи недостаточно для начала исполнения. Будущий релиз объединяет планы, задачи,
выполненные результаты и необходимые описания; работа по выпуску тоже требует плана.
Требования и граница предложения сохранены в
[направлении](../../product/DIRECTION.md#состав-релиза-и-работа-по-выпуску).

В последующем обсуждении пользователь предложил релизный тип плана: включённые рабочие
планы задают состав, собственные этапы/задачи — выполнение выпуска. Страница «Релизы»
представляет этот тип. Прежний вариант двух отдельных сущностей сохранён в истории журнала,
но не используется как основа нового черновика.

Подготовлены два самостоятельных документа в корне:

- [PROGRESS-SPEC.md](../../../PROGRESS-SPEC.md) — предметные ответы API по видам,
  отдельные обработчики, расширяемые контракты, актуальная готовность и раскрытие составляющих.
  Прежнее предложение обязательного универсального механизма сводок заменено по уточнению
  пользователя; оптимизация и смена хранения отложены. URL выбирается по реальному API.
- [PLANS-SPEC.md](../../../PLANS-SPEC.md) — планы работ и релизные планы, этапы,
  основание выполнения, участие задач, состав/снимок выпуска и интерфейсы.

Полные перечни открытых решений находятся в самих ТЗ. Основные вопросы: переход начала,
кардинальность участия задачи, параллельность, повторное открытие, частичный/повторный выпуск,
состав снимка, точные DTO, лимиты, хранение и миграция. Автоматическая смена колонок задач
не объявлена согласованной. Овервью остаётся будущим потребителем данных.

В обоих ТЗ определены владельцы, человеческие сценарии, машинные контракты,
границы списков и критерии приёмки. Планирование сохраняет продуктовые линки и отдельно
согласует связи Core; прогресс читает эти сведения и не устанавливает отношения при чтении.

## Точка продолжения

Последующее поручение реализации выполнено отдельно в [досье прогресса](../progress/README.md).
Ниже сохранена точка передачи этого исследования; актуальное состояние кода и проверок —
в досье реализации. Планирование остаётся открытой отдельной работой.

ТЗ прогресса подготовлено и проверено для передачи другому агенту. Следующее действие —
реализация по `PROGRESS-SPEC.md`: уточнить конкретную схему TaskProgress по требованиям,
реализовать фактическое выполнение обязательств и согласовать прежние поля/проверки;
далее добавлять отдельные прогрессы остальных существующих видов. Точные DTO и маршруты
выбирает разработчик в рамках ТЗ. Универсальный движок и новая СУБД не являются предпосылками.
Планы подключаются после появления предметной модели; её открытые вопросы остаются
в `PLANS-SPEC.md`. Последнее поручение касалось именно ТЗ прогресса; ТЗ планов не менялось.

Владельцы: документация продукта; будущий расчёт — Core с предметными правилами;
Contracts/REST/SDK — отдельные типизированные ответы; Web/CLI/MCP — потребители.
Для планов предстоят продуктовые линки и явные записи/разрывы Core; прогресс читает
согласованные данные и не создаёт отношения. Хранение, миграция и границы списков
описываются как требования будущей реализации, пользовательские базы сейчас не меняются.
