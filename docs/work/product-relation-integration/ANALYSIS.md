## Маршрут записи

Web/MCP/HTTP CLI → REST → предметные сервисы Core. Локальный CLI вызывает те же
сервисы напрямую. `EntityEngine` разрешает публичные адреса, обработчики `entities/handlers`
передают предметную запись в `ProductService` / `BoardTasksService`.

| Продуктовые данные                      | Метод и явный шаг Core                                                                          | Сохраняемые отношения                                                                               |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `scenario.featureId`                    | `ProductService.mutate` → `syncProductRelations`                                                | сценарий → `part-of` → фича                                                                         |
| Приложение и его доска                  | `ProductService.mutate` → `syncProductRelations` → `syncBoardRelations`                         | доска → `part-of` → приложение                                                                      |
| Реализация приложения                   | `ProductService.mutate` / `ProductQueries.updateImplementation` → `syncImplementationRelations` | реализация → `part-of` → приложение; реализация → `implements` → точная цель                        |
| Документ `links` / `relations`          | `ProductService.mutate` → `saveDocumentWithLinks` / `syncProductRelations`                      | документ → `documents` → цель; цель → `references` → документ                                       |
| Задача и доска                          | `BoardTasksService.mutate` → `syncTaskRelations`                                                | задача → `part-of` → доска                                                                          |
| Цели задачи                             | тот же метод                                                                                    | задача → `implements` → фича/сценарий/реализация                                                    |
| Родитель, зависимости, связанные задачи | тот же метод                                                                                    | `part-of`, `depends-on`, `related`                                                                  |
| Каскад удаления                         | `EntityDeletionService.deleteUnified`                                                           | очистка продуктовых линков, пересогласование изменённых владельцев, отзыв рёбер удалённых сущностей |

`replaceOwnedRelations` меняет только заданный slot владельца; независимые диагностические
рёбра не являются продуктовыми линками. В едином формате запись сущности и связи публикуется
одной сессией, история и квитанция входят в общий WAL. Чтение связей не создаёт их.

## Интерфейсные пути

| Интерфейс       | Путь к предметному владельцу                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------ |
| Web — продукт   | `domains/product`, `product-demo` → SDK `mutateProduct` / `updateImplementation` → ProductService / ProductQueries |
| Web — документы | `domains/documents.saveDocument` → SDK createEntity/updateEntity → EntityEngine → ProductService                   |
| Web — канбан    | `domains/board-tasks` → SDK create/update/move/linkBoardTask → BoardTasksService                                   |
| CLI             | `entities create/update/link-task/move-task`, `task`, `product` → local либо HTTP Backend → те же Core-сервисы     |
| MCP             | `entity_*`, `board_task_*`, предметные `product_*` → HTTP Backend → те же Core-сервисы                             |
| Полный контекст | Web `useEntityContext`, CLI `graph context`, MCP `entity_context` → `GraphService.context`                         |

REST-контроллеры и клиенты не содержат второго шага записи графа. Все обязательные
вызовы установлены у предметных владельцев. Материалы Web раньше использовали подборку
`product_context`; этот потребитель заменён общим графом. Совместимый endpoint остаётся
отдельной продуктовой подборкой, его DTO не выдаётся за полный граф.

## Полнота по видам и жизненному циклу

- **Проект и паспорт:** продукт принадлежит проекту, включая незаполненный паспорт.
  `syncProductRootRelations` сохраняет `product:passport → part-of → project:<ID>` в
  `product-links` после init/migrate, продуктовой записи и при reconcile.
- **Фича:** обязательный родитель — единственный продукт Workspace. После сохранения
  `syncProductRelations` записывает `feature:<ID> → part-of → product:passport` в
  `feature-links` и согласует корень продукта. Сценарии и реализации дают входящие рёбра.
  Предыдущее исключение этой принадлежности из графа было ошибкой, исправленной по замечанию.
- **Сценарий:** один неизменяемый родитель-фича; перенос между фичами отклоняется владельцем.
- **Приложение:** его доска и реализации сохраняют входящие `part-of`; slug/префикс
  после создания неизменяемы, название не влияет на ID связей.
- **Реализация:** приложение и точная цель реализации; для SI добавлена прямая FI своего
  приложения. Текст/статус/ключ сохраняют существующие ID рёбер. Снятое участие остаётся
  адресуемым, с прежними линками; у старой неактивной SI без FI новый родитель не выдумывается.
- **Доска:** приложение — реальный родитель доски приложения. Системные доски не получают
  фиктивный линк к паспорту; задачи сохраняют свою принадлежность доске.
- **Задача:** create/update/link/move/rename проходят один mutate. Замена целей,
  родителя, удаление зависимости и related с обратного конца согласуют все изменённые задачи.
  Перенос отзывает старую принадлежность и сохраняет ID задачи/алиасы.
- **Документ:** оба совместимых набора `links` и `relations` сохраняются одним владельцем;
  направление `references` обратное направлению `documents`. Пустые массивы снимают
  свои линки; независимое ребро с такими же концами остаётся независимым.
- **Удаление:** общий EntityDeletionService выполняет предметный каскад, очищает внешние
  линки, пересогласует изменённые группы и отзывает рёбра удалённых сущностей. Каскад
  не определяется произвольной достижимостью графа.
- Комментарии, критерии приёмки, статусы и Markdown не являются самостоятельными
  основными сущностями и не создают вымышленных рёбер. Готовность остаётся предметным расчётом.

## Решения реализации

- SI → `part-of` → FI своего приложения: прямая вложенность уже определяет каскад
  готовности и удаления, но отсутствовала среди сохранённых отношений. Добавляется
  в `implementation-links`; SI → `implements` → сценарий и принадлежность приложению сохраняются.
- Неактивность реализации сохраняет идентичность, целевые поля и прежние линки по
  `product/entities/product/MODEL.md`; её связи сохраняются. Удаление — отдельный каскад.
- Для уже единого хранилища добавляется явный `storage reconcile-relations`: общий
  заблокированный пакет, только группы предметных владельцев, без изменения ревизий
  сущностей и независимых рёбер. ID неизменённых связей сохраняются. Reindex остаётся
  перестроением индексов сохранённых фактов, а не импортом продуктовых полей.
- Старые базы переходят через существующий явный `storage migrate`, который вызывает
  те же функции согласования. Автоматической миграции и записи при чтении нет.
- Публичный `GraphService.mutate` в едином формате меняет только диагностические рёбра:
  предметное снятие выполняется владельцем линка. Это закрывает рассогласование через Web/CLI/REST.
- Web получает полный граф через `domains/relations`; полное содержание выбранного узла
  через `domains/entities`. Данные графа не ограничиваются прежним продуктовым подбором.
