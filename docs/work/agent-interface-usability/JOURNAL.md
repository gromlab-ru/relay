# Журнал проверки агентских интерфейсов

## 22 сентября 2026 — начало исследования

- Цель: проверить удобство восстановления контекста существующего `p2p-rental`
  штатными инструментами агента, прежде чем предлагать недостающие методы.
- Изучены обязательный протокол, правила библиотеки, концепция продукта, единый
  стандарт интерфейсов, инструкции Playground, CLI/MCP и продуктовый скилл.
- Проверены ветка, HEAD и рабочее дерево: `refactor/application-rebuild`, `f8615e9`,
  имеются чужие изменения Web/Core/contracts и документации.
- Пользователь уточнил, что MCP не работает и исправляется другим агентом.
  Живые MCP-проверки отложены; первый этап ограничен CLI и чтением контракта MCP.
- Критерий проверки: агент выбирает проект, получает обзор, находит задачу,
  читает требования и связанные записи, видит границы ответа и продолжение.
  Человеческий вывод и JSON оцениваются отдельно. Записи в память Playground не нужны.

## 22 сентября 2026 — первый маршрут CLI

Все команды запускались из `apps/playground` с префиксом
`pnpm --silent run cli`; ниже приведены аргументы после него. Использован работающий
workspace Server, без перехода на локальное хранилище. Код — исходники CLI рабочей
копии на HEAD `f8615e9` с параллельными изменениями других агентов; точная версия
серверного процесса отдельно не устанавливалась. Вывод проверялся в захвате shell,
интерактивный TTY и узкая ширина не проверялись.

### Успешные возможности

- `projects list --format json`: workspace, оба проекта доступны, `defaultProject: null`.
- `--help`: группы product, boards, task, graph, entities; русские объяснения и примеры.
- `p2p-rental task list --completion unfinished --limit 2 --format json`:
  две записи из десяти, `nextOffset: 2`, версия снимка, `meta.project`.
- `p2p-rental task get WEB-4 --format json`: полный Markdown, ревизия 10,
  выполнены 2/2 критерия, но `canComplete: false`, два ID блокеров.
- `p2p-rental task links WEB-4 --limit 10 --format json`: объясняет блокировку
  дочерними API-2 и WEB-1, раскрывает ключи, названия и состояния.
- `p2p-rental entities get WEB-4 --format json`: раскрывает имена целей WEB-FI-2,
  WEB-FI-3 и родителя PRODUCT-3 через `references`. Поэтому нельзя утверждать,
  что раскрытия ID в CLI вообще нет. Однако здесь нет вычисляемых полей
  acceptance/canComplete/blockers из `task get`.
- `p2p-rental graph context WEB-4 --depth 2 --limit 5 --format json`:
  узлы, рёбра, endpoints, пути с ключами, 24 узла/39 рёбер в выборке,
  `nextOffset: 5`, `depthLimited: true`, boundary. Неполнота обозначена явно.
- `p2p-rental entities get DOC-2 --format json` и та же команда с `--color never`:
  полные финансовые правила, открытые вопросы и ссылки на фичи доступны;
  человеческое представление отделяет содержание и метаданные.
- `p2p-rental task criterion list WEB-4 --limit 2 --format json`: два критерия
  с авторами и временем отметок. Это сохранённые утверждения, не проверка продукта.
- `p2p-rental task comment list WEB-4 --limit 2 --format json`: одно сообщение,
  `nextCursor: null`, snapshot 13.
- `p2p-rental task history list WEB-4 --limit 2 --format json`: два события,
  непрозрачный nextCursor, snapshot 13. Продолжение истории ещё не проверено.
- `p2p-rental entities list --kind document --q 'несуществующий-документ-аудит-20260922' --format json`:
  пустая выдача, `total: 0`, `nextOffset: null`; отдельно присутствуют libraryCounts.
- `p2p-rental task get AUDIT-NOT-FOUND --format json`: `ok: false`, `NOT_FOUND`,
  русское сообщение. Отсутствующая запись отличается от пустого списка.

### Подтверждённые препятствия

1. **Версия снимка перехватывается глобальным флагом версии CLI.**
   `p2p-rental boards --limit 2` выдал продолжение с `--version`.
   `p2p-rental boards --offset 2 --limit 2 --version 782482ab5eaccd849b465bea720db9738beb69cb53283ee15e5d16fdd9d0b1bf --format json`
   напечатал только `0.6.0`, без JSON и данных. Без `--version` та же команда
   вернула две оставшиеся доски. Аналогично воспроизведено для
   `p2p-rental task list --completion unfinished --limit 2 --version 56f4524a7e492a19d333b588bc1df4b4575b7d952af129dbb2e69c6f8a255cea --offset 2 --format json`.
   Это препятствие безопасной пагинации и нарушение машинного формата,
   а не отсутствие метода списка. Причина в исходниках ещё не исследовалась.
2. **Входной обзор не помещается в стандартный бюджет.**
   `p2p-rental product overview`: RESPONSE_TOO_LARGE, requiredBytes 26780,
   maxBytes 16384. С `--max-bytes 32768` успешен, но отображает 30 из 46
   записей длинной таблицей; паспорт находится после приложений, документов и фич.
   Подсказка «Все записи: product list --limit 30» не содержит offset продолжения.
   `product overview --help` не предлагает локальных фильтров/страницы; текст
   «по контрактам всех проектов» также затрудняет понимание границ выбранного проекта.
3. **Подсказки следующего вызова теряют контекст проекта.**
   Продолжение boards и task list не включает `p2p-rental`/`--project`.
   Для boards также теряется limit 2. У реестра нет defaultProject.
   Подсказка контекста после чтения DOC-2 тоже не содержит выбранного проекта.
   Попытка выполнить подсказку boards дополнительно упёрлась в дефект `--version`;
   отдельный отказ из-за отсутствия проекта этим вызовом не доказан.

### Кандидаты для проектирования, не утверждённые требования

- Компактная точка входа: паспорт, количество сущностей/задач по состояниям,
  приложения, ближайшие адресные команды в пределах стандартного бюджета.
- Согласованное чтение задачи: ключи/названия целей, причины блокировки с типом
  отношения и ссылки на критерии, обсуждения, требования. Сейчас сведения приходится
  соединять из task get, entities get, task links и graph context.
- Профиль контекста поручения: граф depth 2 включает соседние задачи через общую
  доску, а первая страница nodes не содержит корневую задачу (она есть в endpoints).
  Для агента это дополнительная нагрузка; необходимость нового метода пока не доказана.

Содержимое CLI/MCP-контрактов и единый стандарт проверены как целевое поведение;
менять требования под выявленные отклонения не нужно. В справочник CLI добавлена
ссылка на текущие ограничения. Реализация не изменялась, MCP не вызывался,
данные Playground не редактировались, собственные серверные процессы не запускались.

## 22 сентября 2026 — MCP восстановлен, реальные чтения

По сообщению пользователя выполнены прямые вызовы подключённых инструментов MCP:

- `projects_list({})`: workspace, coffee-shop и p2p-rental доступны, всего 2,
  hasMore false.
- `boards_list({project: "p2p-rental", limit: 2})`, затем offset 2 с той же
  version и limit: получены Продукт, Веб-приложение, Серверное API и Инфраструктура;
  в конце nextOffset null. Конфликта параметра version из CLI здесь нет.
- `board_task_get({project: "p2p-rental", reference: "WEB-4"})`:
  ревизия 10, колонка ready, критерии 2/2, canComplete false, два ID блокеров.
- `board_task_links` для WEB-4: родитель PRODUCT-3 и дочерние API-2/WEB-1;
  связи объясняют причину запрета завершения.
- `entity_get({project: "p2p-rental", ref: "DOC-2"})`: видимый агенту результат —
  только название, вид, ревизия и сообщение «Полные данные доступны в structuredContent».
  Полное тело документа в контекст этого вызова не поступило. По одному такому
  результату нельзя утверждать, что сервер не сформировал structuredContent;
  требуется проверка передачи между сервером, MCP-клиентом и моделью.
- `product_get` с тем же проектом и ref: полное тело DOC-2, правила, открытые вопросы,
  ссылки и метаданные доступны в JSON-ответе. Это рабочий обход для документа.

Данные и процессы не изменялись. Контракт MCP требует доступности полных данных;
наблюдение о клиентской видимости не меняет требование и пока относится только
к проверенному вызову entity_get. Точка продолжения: исследовать доставку
structuredContent, затем остальные сценарии чтения MCP.

## 22 сентября 2026 — полнота контекста фичи

Пользователь уточнил, что раздел документов дорабатывается: проверку этой области
отложили. Новая цель — выяснить, сколько знаний агент получает вместе с фичей,
особенно количество и ключи связанных задач, без множества запросов.

Проверена FEATURE-2 «Каталог и доступность техники», все MCP-вызовы с project p2p-rental:

- `entity_get({ref: "FEATURE-2"})`: агенту видны название, вид, ревизия и ссылка
  на structuredContent; содержимое не видно. Наблюдение повторилось за пределами документов,
  но причина передачи ответа не исследовалась.
- `product_get({ref: "FEATURE-2"})`: полный текст цели, правил, ошибок,
  неопределённостей, критериев и источника; ID, ключ, ревизия, авторы, даты.
  Нет списка сценариев, реализаций, задач, их количества или вычисленной готовности.
- `product_context({id: "FEATURE-2"})`: RESPONSE_TOO_LARGE, requiredBytes 82315,
  maxBytes 16384. После явного maxBytes 98304 получен полный ответ.
  В нём фича, паспорт, приложение WEB, сценарии SCENARIO-3/SCENARIO-4,
  реализации WEB-FI-2/WEB-SI-3/WEB-SI-4, связанные документы и причины включения.
  Readiness фичи partial, сценариев none. Задач, их ключей и счётчиков нет.
  В подсказке ошибки предлагаются поля и limit, хотя эти параметры инструмент
  product_context не предоставляет. Содержимое документов отдельно не оценивалось.
- `board_tasks_list({productTarget: "FEATURE-2", limit: 20})`:
  total 3, nextOffset null; WEB-1 (ready, заблокирована), WEB-5 (inbox),
  WEB-4 (ready, заблокирована). Все три имеют цель WEB-FI-2 через постоянный ID;
  прямых ссылок на FEATURE-2 у этих карточек нет. Следовательно, фильтр умеет
  включать косвенно связанные через реализацию задачи. У WEB-1 и WEB-5 заголовки пусты.

Вывод: нужная выборка задач уже есть, но чтение фичи не включает её краткий результат
или подсказку вызова. Для требований и задач нужны минимум product_get + board_tasks_list;
для сценариев/вкладов добавляется product_context с увеличенным бюджетом.
Предложение для обсуждения, не принятое требование: включить в карточку фичи
вычисленную готовность, компактные сценарии/вклады, taskSummary и ограниченную
страницу задач с ключом, названием, колонкой, причиной включения, блокировкой и
явным продолжением. Большие тексты связанных записей читать по запросу.
Код и данные не изменялись; существующие требования интерфейсов остаются верными.
