# Обсуждения и история карточки задачи

**Статус: подготовлен и проверен новый вариант обсуждений без аватаров; ожидает приёмки.**

## Цель и границы

По запросу пользователя предложить обсуждения задач с однострочным заголовком и полным
Markdown для человека, оркестратора и воркера, а также хронологию всех изменений карточки.
Сообщения Web подписываются «Оператор»; агент задаёт собственное имя.
Пользователь согласовал реализацию публикации/чтения и подробной истории через все интерфейсы.
Дополнение: три таба внутри карточки — «Задача», «Обсуждения», «История».

## Согласованная реализация

### Интерфейс и сообщения

В верхней части содержимого карточки — табы «Задача», «Обсуждения» и «История»;
начальный — «Задача». Всё существующее содержание находится в табе «Задача».
Переключение сохраняет несохранённый ввод.
Обсуждения — плоская лента сообщений: автор, роль при наличии, время, заголовок и полный
Markdown. Форма содержит обязательные заголовок и описание, кнопку «Опубликовать»;
в Web выбор имени отсутствует. Лимиты: заголовок 1024 байта, Markdown 256 КиБ.
Содержание произвольное: вопрос, решение, результат работы, ссылка или фрагмент кода.
Публикация доступна также в done/cancelled, не меняет статус и критерии задачи.

Начальный объём — публикация и чтение; редактирование и удаление сообщений требуют
отдельного решения. При их добавлении сохраняются версии и отметка удаления, история
не стирается. Черновик изолирован по проекту, задаче и вкладке, переживает закрытие окна,
ошибку сети и SSE. Используются существующие MarkdownField/MarkdownView и Mantine useForm.

Существующий строковый actor сохраняет имя. Сообщение содержит
`id`, `taskId`, `title`, `description`, `actor`, `actorRole`, `at`, `sequence`.
Роли: operator/orchestrator/worker; агент явно передаёт имя и роль, Web всегда передаёт
«Оператор»/operator через общий доменный адаптер. Это атрибуция, не система аутентификации.
Для старых событий роль остаётся неизвестной; имена не переписываются.

### История

История автоматически формируется Core при успешной записи. Событие содержит постоянный ID,
ID задачи, серверное время UTC, последовательный номер в ленте задачи, автора, действие,
идентификатор общей операции и типизированные изменения до/после. Для Markdown сохраняются
полные прежний и новый тексты; UI раскрывает сравнение по запросу. Снимки подписей связанных
сущностей позволяют понимать запись после их переименования; постоянные ID сохраняют ссылки.

Охват: создание, заголовок, описание, цели реализации, статус, отмена/повторное открытие,
доска и ключ, положение на доске, критерии и их выполнение/сброс, родитель/подзадачи,
зависимости и связанные задачи, публикация сообщения. Для составной операции связанные
события имеют общий operationId. Изменения родительства видны у ребёнка, прежнего и нового
родителя; изменение зависимостей — у обеих сторон. Причины изменения вычисляемых блокеров
должны быть доступны в хронологии затронутой задачи. Общие связи графа с участием задачи
включаются через события владельца графа, без повторного создания самих отношений.
Техническая перенумерация rank обозначается как следствие переноса, а не действие оператора
над каждой соседней карточкой. Открытие окна, локальный ввод и несохранённые действия
не являются изменениями карточки; ошибки записи не создают успешных событий.

Операции CLI local, REST, MCP и движка сущностей проходят тот же Core-механизм. SSE только
уведомляет о необходимости перечитать REST и не является хранилищем истории. Ручная правка
JSON вне Core не гарантирует автора и подробную историю; её нельзя выдавать за отслеженное действие.

### Хранение, конкуренция и API

Используется раздельное хранение сообщений и подробных событий по постоянному taskId в
`.relay/task-activity`: содержимое не переносится при смене доски.
Причина: текущий файл задачи ограничен 16 МиБ, а список
задач сейчас читает записи целиком; длинные обсуждения не должны замедлять канбан.
Markdown на диске — массив строк, во внешнем контракте — строка.

Состояние, событие, сообщение и квитанция публикуются под общей блокировкой и через
расширенное долговечное намерение с восстановлением после сбоя. Квитанции обсуждений
хранятся отдельно от основного файла задачи, но сохраняют существующую область повтора
«автор + проект» и проверку полного хеша запроса. Индексы ленты производные и восстановимые.
Публикация сообщения не требует ifRevision карточки и не изменяет её содержательную ревизию:
одновременные сообщения не конфликтуют с редактированием описания. Лента имеет свою sequence.
Повтор requestId возвращает исходный результат, без второго сообщения и события.

Операции относительно `/board-tasks/:reference`:

- `POST /comments`: title, description, actor, actorRole, requestId.
- `GET /comments`: компактные записи с заголовками и метаданными.
- `GET /comments/:commentId`: полный Markdown.
- `GET /history`: компактные события с фильтрами типа/автора.
- `GET /history/:eventId`: полное изменение до/после.

Точные действующие DTO и пути описаны в [справочнике](../../reference/TASK-ACTIVITY.md).
Списки: по 20, максимум 100, cursor/nextCursor и граница снимка по sequence. Новые записи
не сдвигают следующие страницы; новые события читаются после известной sequence.
Web показывает новые записи сверху и подгружает ранние снизу, сохраняя позицию чтения.
Это уточнение UX: после публикации сообщение сразу видно, подгрузка не сдвигает прочитанное.
Полные тексты читаются адресно. Название задачи расположено над табами, форма сообщения
раскрывается по действию; технические номера и идентификаторы операций не загромождают ленту.
CLI получает предметные команды с Markdown и `--format json`; MCP — отдельные инструменты
публикации, чтения сообщений и истории с открытыми параметрами автора и содержания.

Реализованы новая версия дисковой схемы и возобновляемый переход версий 1–4 и старых pending.
Старые события сохраняются с доступными action/actor/at/revision и пометкой отсутствия
подробностей. На границе перехода фиксируется исходный снимок; прошлые значения не выдумываются.
ID, ключи, содержимое, ревизии и исходные квитанции сохраняются. Старый исполняемый код
не должен записывать новую схему; чтение и миграция проверяются отдельно.

### Границы Web

Данные, адаптеры SDK, SWR и инвалидация принадлежат существующему `domains/board-tasks`.
TaskModal координирует название и три таба: TaskEditor содержит прежний интерфейс задачи,
TaskActivity — ленту выбранного вида и внутренние форму/записи/сравнения без фасетов.
Вложенные юниты не импортируют друг друга или родителя. Общий транспорт остаётся
в `infra/tasks-api`, Markdown — в `ui`.
Новые TSX создаются штатным генератором. Отдельный глобальный домен комментариев пока не нужен.

### Приёмка реализации

- Web публикует от «Оператор»; два агента сохраняют разные заданные имена и роли.
- Markdown без потерь проходит API/хранение/UI, включая код, таблицы и пустые строки.
- Каждая перечисленная операция даёт понятные кто/когда/что/до/после; составная запись атомарна.
- Параллельные публикации, повтор после таймаута, смена доски и падение между этапами WAL
  не теряют записи и не создают дубликатов; пагинация остаётся стабильной.
- Длинные ленты читаются адресно, без загрузки Markdown в списки канбана.
- Миграция сохраняет старые квитанции и честно обозначает ограниченную детализацию прошлого.
- Core/HTTP/CLI/MCP проверяются отдельно; Web — собственным headless agent-browser на временной
  базе, обе темы, 1440/1024/768/390, клавиатура, ошибки, SSE и черновики; без фронтенд-автотестов.
