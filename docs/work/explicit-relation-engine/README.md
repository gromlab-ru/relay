# Единственный механизм явно сохраняемых связей

## Цель и границы

22 сентября 2026 пользователь поручил привести движок к
[стандарту линков, связей и контекста](../../development/LINKS-AND-CONTEXT.md): убрать
автоматическое вычисление отношений и оставить явную запись/изменение/отзыв Core.
Интеграцию всех продуктовых сценариев пользователь выделил в следующую задачу.

Статус: движок реализован и проверен; документация, скилл и точка передачи актуальны.
Предшествующая работа —
[согласование и исправление стандарта](../links-and-context-standard/README.md).

Владельцы: Core/graph, переносимые контракты, CLI/MCP как потребители, REST/SDK.
Каталог предоставляет существующие сущности и алиасы, но не отношения.
Хранилище графа — единственный источник рёбер. Контекст обходит его без скрытого
отсечения документов/приложений; глубина, направление, тип и пагинация остаются явными.
Отдельные продуктовые подборки (например product_context), поля продукта и расчёты
готовности не переделываются в этой работе. Изменения экранов Web и новые кнопки — отдельно.

## Совместимость и переход

- Существующие сохранённые рёбра, ID, история и квитанции v1/v2 сохраняются; физическая
  схема не меняется, механизм явной миграции v1 остаётся.
- Domain-рёбра не были сохранёнными записями. Удаляется их вычисление, не продуктовые
  поля. Контекст с одними продуктовыми линками станет пустым до их явной интеграции.
- Автоматический импорт продуктовых линков не добавляется. План сопоставления старых
  данных и записи нужных связей относится к последующей предметной работе.
- Поле ответа source остаётся совместимым по форме, но допускает только graph.
- Параметр profile=context принимается как совместимое имя полного обхода all;
  отдельная скрытая политика удаляется. Новые клиенты используют all по умолчанию.
- После обновления клиенты перечитывают снимок перед новой записью/продолжением.

## План и проверки

1. Удалить отношения из каталога и объединение источников в GraphService; оставить
   одну запись и один обход. Сохранить блокировку, CAS, повтор, историю и восстановление.
2. Согласовать схемы, CLI/MCP и SDK; отметить диагностическое назначение прямой записи.
3. Проверить отсутствие рёбер от продуктовых полей, полный обход через разные виды,
   жизненный цикл явной связи, рестарт, повтор и совместимость хранения.
4. Выполнить подходящие Core/REST/CLI/MCP тесты и typecheck, собрать скилл,
   проверить документы, форматирование и diff. Сохранить точку продолжения интеграции.

## Точка продолжения

Проверки: все 86 Core-тестов, 9 MCP-тестов; полные REST/CLI прогоны с исправлением
прежних ожиданий и успешным адресным повтором; сборка CLI/MCP с зависимостями;
typecheck контрактов, Core, runtime, SDK, клиентов и Web; docs:check, skills:check,
адресный Prettier и git diff --check. Детали и неуспешные первые попытки — в журнале.

Ветка `refactor/application-rebuild`; на старте есть параллельные изменения библиотеки
документов, клиентов, Core, SDK и предыдущей документационной работы. В каталоге графа
сохранённое поведение документов учитывается как продуктовые данные, но проекции
целенаправленно удаляются согласно новому поручению. Остальные чужие правки сохраняются.
Удалены вычисление рёбер и скрытая политика обхода; контракты, CLI/MCP, SDK и скилл
согласованы. Существующие продуктовые функции не подключались к записи движка в этой задаче.
Временный сервер генерации SDK закрыт, база удалена. Скрипт воспроизведения находится
в игнорируемом `.artifacts/explicit-graph-sdk.mts`. По запросу пользователя подготовлен
отдельный коммит только изменений агента; проверен изолированный состав без параллельной
библиотеки документов. Подробности разделения и проверок — в журнале.

### Передача следующей задаче

1. Для каждого продуктового сценария составить карту линков и соответствующих связей:
   документы, сценарий → фича, реализации → цели/приложения, задачи → цели/доска/родитель/
   зависимости. Не восстанавливать старый универсальный проектор полей.
2. Подключить вызовы `GraphService.mutate` после продуктовой записи; определить стабильное
   сопоставление ID связей и ключей повтора. Для замены — remove/add одним пакетом,
   для разрыва — remove конкретных связей сценария, а не всех рёбер между концами.
3. Обеспечить общий контракт восстановления двух шагов. Версия графа учитывает каталог:
   читать её после продуктового изменения под согласованной блокировкой. Существующий
   WAL пакета графа сам по себе не является транзакцией всех продуктовых репозиториев.
4. Спланировать явный перенос ранее сохранённых продуктовых линков с проверкой дублей
   и существующих graph-рёбер. Сейчас импорт намеренно отсутствует, данные не удалены.
5. Проверить создание/замену/разрыв и удаление сущности через все предметные интерфейсы.
   До интеграции пустой граф при существующем продуктовом линке — честное состояние.
6. Отдельно согласовать старый `product_context` и UI: диагностический редактор, подписи
   источника и будущие кнопки/диаграммы контекста. Web-код в этой работе не менялся;
   его совместимость с SDK проверена typecheck, визуальная приёмка не проводилась.
