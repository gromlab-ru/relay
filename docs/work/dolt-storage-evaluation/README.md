# Оценка Dolt для хранилища Relay

## Цель и статус

Исследование по вопросу пользователя от 22 сентября 2026: может ли
[Dolt](https://github.com/dolthub/dolt) заменить собственный механизм хранения Relay
и какие сложности возникнут. Сопоставление требований и первичных источников выполнено;
проверки документов пройдены. Исследование завершено. Выбор СУБД и изменение требований
пока не приняты.

**Вывод: Dolt — обоснованный кандидат на замену физического хранилища.** Его преимущества
совпадают с дорогими механизмами текущего рефакторинга: индексы, транзакционная публикация,
восстановление, снимки и слияния. Основные сложности — интеграция с Git/worktree,
семантика конкурентных записей и предметная корректность после merge. Рекомендация —
проверить небольшой сквозной прототип до дальнейшего вложения в собственную СУБД.

## Границы и владельцы

- Core: предметные репозитории, транзакции, история, идентичность и граф контекста.
- Project Runtime, CLI и Server Runtime: локальный доступ, процессы, рабочие копии и события.
- Основания: [ТЗ хранения](../../../STORAGE-REFACTORING.md),
  [состояние нового слоя](../../engineering/entity-storage.md),
  [текущее досье рефакторинга](../entity-storage/README.md),
  [правила Git](../../guides/GIT.md).
- Проверки исследования: статическое чтение кода и официальной документации;
  достоверность ссылок, форматирование и `git diff --check`.
- Производительность Dolt, реальная миграция и запуск SQL-сценариев требуют отдельного прототипа.

## Контракты для оценки

Нужно сохранить ID, ключи и алиасы, ревизии, точный Markdown, события, квитанции повторов,
отозванные связи и полный согласованный контекст. Ветки с одинаковыми публичными ключами
должны сохранять обе сущности и возможность разрешить коллизию по ID.

Применяется [стандарт линков и связей](../../development/LINKS-AND-CONTEXT.md):
продуктовый сервис сохраняет линк и явно вызывает Core для отдельной записи связи.
SQL-транзакция потенциально объединяет оба шага, историю и квитанцию, но не заменяет
предметную интеграцию или алгоритм контекста. Исследование не выполняет продуктовых записей.

## Что подтверждено о Dolt

Через GitHub MCP прочитаны README и последний опубликованный релиз:
[v2.3.5 от 16 сентября 2026](https://github.com/dolthub/dolt/releases/tag/v2.3.5).
Документация проверена 22 сентября 2026, отдельные утверждения сверены с исходниками.

- MySQL-совместимая SQL-СУБД с первичными/вторичными индексами, JSON, ограничениями,
  атомарными SQL-транзакциями и отдельным версионированием данных/схемы.
- Ветки, diff, merge, история и чтение старых состояний доступны через CLI и SQL.
- Лицензия Apache-2.0; локальное использование и собственное размещение поддерживаются.
- `dolt sql` работает без сервера. Для обычного Node.js SQL-клиента используется
  MySQL-совместимый `dolt sql-server`; поставляется отдельный исполняемый файл.
- GitHub/GitLab могут служить Git remote для Dolt. По умолчанию данные хранятся под
  `refs/dolt/data`; это подтверждено и в исходнике тега v2.3.5. DoltHub не обязателен.
- Автоматический сбор мусора существует с 1.75. История использует разделение неизменённых
  блоков между версиями, а не полную физическую копию на каждый коммит.

## Что заменяется и что остаётся у Relay

### Механизмы, которые можно передать СУБД

- Физические индексы адресов и смежности вместо собственных JSON-сегментов.
- Публикацию изменений нескольких таблиц, восстановление и согласованный снимок чтения.
- Физическое хранение истории версий, сравнение состояний и механическое слияние веток.
- Обслуживание файлов/блоков вместо отдельных файлов сущностей, рёбер и операций.

Это потенциальная замена `hash-index.ts`, файловой части `transaction.ts` и значительной
части низкоуровневого `store.ts`, а не обещание удалить все эти файлы без адаптации.

### Ответственность Relay

- Схемы видов, ID, ключи/алиасы/надгробия и политика выдачи человеческих адресов.
- Готовность, критерии приёмки, зависимости, каскады и остальные предметные правила.
- Явные вызовы движка связей, владение `owner/slot`, стабильные ID и отзыв нужных рёбер.
- Семантическая история операций, авторство, `requestId`, хеш запроса и исходный результат повтора.
- Алгоритм полного контекста, ограниченные кеши, версии ответов, бюджеты и SSE.

История Dolt отвечает на вопрос об изменениях таблиц между коммитами. Она сама не знает,
какой HTTP/MCP-запрос уже выполнен и какую квитанцию вернуть после потери ответа.

## Основные сложности

### 1. Git кода и Dolt данных остаются разными историями

Существующее ТЗ требует читаемых JSON-файлов в обычных Git-коммитах. В Dolt текущие
данные хранятся в собственном формате. SQL-экспорт может сохранить переносимость,
но экспорт не равнозначен прежнему файловому источнику истины.

Git remote решает размещение базы в том же GitHub, но не привязывает автоматически
`git checkout`, PR и `git merge` к нужной ветке/ревизии Dolt. Понадобятся явное соответствие
Git-коммита ревизии данных, порядок публикации и восстановление после частичного push.
Человеку нужно показывать предметный diff, а не бинарные изменения внутренних блоков.

Команды `dolt worktree` нет по таблице совместимости. Вместо неё один Dolt server умеет
одновременно обслуживать несколько веток; клиент выбирает `database/branch`.
Для Relay нужно решить, какие данные общие для оркестрации, а какие ветвятся вместе с кодом.
Автоматическая отдельная ветка для каждого агента может скрыть от оркестратора его текущую работу.

### 2. Конкурентность отличается от привычного MySQL

`SELECT ... FOR UPDATE` не устанавливает блокировку строки; код планировщика явно
содержит no-op. Конкурирующие транзакции объединяются через сравнение изменений;
конфликт может обнаружиться при финальном commit.

Одинаковое изменение ячейки и изменения разных ячеек способны слиться успешно.
Поэтому обычного числового `revision = revision + 1` недостаточно считать доказательством
эксклюзивности: два писателя из ревизии 7 могут оба подготовить 8. Нужна проверенная
стратегия конфликтов — например, уникальный токен записи агрегата или сериализация
предметных мутаций — с обработкой отказа и перечитыванием исходных условий.
Это варианты для прототипа, не принятый контракт.

Особенно важны выдача ключа, назначение исполнителя, замена набора связей и одновременное
выполнение одного `requestId`. Ограничения строк не защищают автоматически инварианты,
зависящие от нескольких записей, например отсутствие цикла зависимостей.

В официальной документации есть расхождение: страница Transactions называет Read Committed,
а Using Branches — `REPEATABLE_READ`. Код v2.3.5 фиксирует исходные корни транзакции.
Гарантии согласованного чтения следует подтвердить на закреплённой версии отдельным сценарием,
а не выводить из общего заявления о совместимости с MySQL.

### 3. Успешный merge не означает корректное состояние продукта

Пример: в одной ветке добавлена зависимость A → B, в другой B → A. Разные строки могут
объединиться без конфликта СУБД, хотя предметное правило Relay нарушено.

Другие случаи: удаление цели и новое прикрепление, разные цели одного `slot`, соединение
продуктового линка из одной ветки со связью из другой. Внешние ключи и ограничения полезны,
но соответствие двух механизмов и кардинальность требуют предметной проверки результата.
Публикация merge в рабочую ветку должна проходить проверяемый процесс согласования.

Отдельно действует контракт `WEB-17`: независимые ветки могут выдать его разным ID,
и обе сущности должны остаться доступны по ID. Механическое `UNIQUE(key)` превращает
этот сценарий в нарушение SQL-ограничения. Схема адресов и процедура ремонта должны
сохранять текущую семантику неоднозначности либо она требует отдельного решения пользователя.

### 4. Нужна осмысленная SQL-модель

Перенос всех файлов в одну таблицу с непрозрачным JSON не гарантирует хороших запросов.
Адреса, концы рёбер, владельцы/назначения, активность, история и квитанции требуют
явно индексируемого представления. Расширяемые данные видов могут оставаться JSON.

Dolt умеет структурно объединять изменения разных ключей JSON-объекта: утверждение,
что JSON всегда сливается только целиком, неверно. Но это не предметное слияние списков.
Нужно проверить массивы целей, критериев и Markdown. Если весь Markdown положить в `TEXT`,
правки разных абзацев одной ячейки могут конфликтовать, хотя построчный Git их объединил бы.
Потребуются SQL-миграции и обработка слияний разных версий схемы.

### 5. SQL COMMIT и Dolt commit имеют разные назначения

SQL `COMMIT` сохраняет транзакцию в рабочем состоянии ветки. Исторический Dolt commit
создаётся отдельно либо автоматически через `@@dolt_transaction_commit = 1`.
Push в remote переносит Dolt-коммиты; `dolt backup` способен сохранять и незакоммиченное
в Dolt рабочее состояние.

Нужно определить границу исторического коммита, авторство и связь с операцией Relay.
Слишком редкие коммиты дают грубую историю; слишком частые требуют измерить рост базы
и цену записи. GC удаляет недостижимые блоки, но не отменяет стоимость сохраняемой истории.
Один SQL-запрос не равен одному предметному действию: автокоммит каждого UPDATE
не обеспечит атомарность задачи, её линков, рёбер и квитанции.

### 6. Локальный запуск, конфигурация и события потребуют адаптации

Сегодня локальный CLI вызывает Core внутри Node.js и читает файловую базу напрямую.
С Dolt появляется исполняемый файл и выбор: управляемый локальный SQL server либо
процессный адаптер `dolt sql`. Потребуются установка, закрепление версии, запуск/остановка,
готовность процесса, адрес подключения и стратегия одновременного доступа CLI/Server.

В workspace и пуле соединений выбор базы/ветки должен быть явным для каждой операции.
Оставшаяся от прошлого запроса сессионная ветка не должна перенаправить запись другого проекта.
Одна транзакция не может зафиксировать изменения сразу двух веток по текущему контракту Dolt.

Файловые наблюдатели Relay нужно заменить или адаптировать: SSE и кеш должны замечать
SQL-мутации, merge и pull. Один HEAD недостаточен, если рабочие SQL-записи ещё не стали
Dolt-коммитом; у Dolt есть отдельный hash рабочего состояния.

### 7. Полный контекст и миграция остаются отдельной работой

Dolt не является готовым движком графового контекста Relay. SQL-индексы могут удешевить
чтение связей, но сбор всей компоненты, циклы, параллельные рёбра, кеш и сериализация остаются.
Нельзя превращать каждый переход графа в отдельный сетевой SQL-запрос.

В опубликованном benchmark v2.3.5 есть запросы быстрее и медленнее MySQL; TPC-C показывает
52,38 против 96,87 транзакции/с в условиях авторов. Это не предел Dolt вообще и не прогноз
для Relay. Нужен одинаковый корпус 10 000/100 000 сущностей и связей, измерение полного
вызова Core/CLI, процессов Node.js + Dolt и накопления истории.

При переходе нужно сохранить все перечисленные выше контракты, включая старые `scope`,
отозванные связи и квитанции. Пересоздание демонстрационной базы не подтверждает миграцию
сохраняемых пользовательских данных. Готовый низкоуровневый слой сейчас ещё не подключён
к предметным приложениям; этот рубеж удобен для сравнительного прототипа.

## Предлагаемый прототип

Это рекомендация следующей работы, не выполненная реализация.

1. Минимально представить сущности, адреса, предметные прикрепления, связи `owner/slot`,
   операции и квитанции. Избежать привязки внешних ID и DTO к физической SQL-схеме.
2. Провести один существующий сценарий через общий Core: изменение документа → запись
   продуктового линка → явный вызов движка связей → история/квитанция в одной SQL-транзакции
   на одном соединении и одной ветке. Ошибка между шагами не даёт частичного успеха.
3. Проверить двух писателей: разные сущности, одна сущность/разные поля, одно поле,
   одинаковый числовой прирост ревизии, один ключ, один `requestId`, потерянный ответ.
4. Проверить две ветки: коллизия публичного ключа, цикл зависимостей, удаление/изменение,
   линки/связи, Markdown, версии схемы и последующая предметная валидация.
5. Проверить полный контекст с тем же контрактом, холодный/повторный вызов, память обоих
   процессов, размер истории, восстановление и отражение изменения в SSE.
6. Проверить local/workspace, два Git worktree, пул соединений, публикацию в Git remote
   и восстановление выбранной пары ревизий кода/данных; отдельно человеческий CLI и JSON.

Успех определяется сокращением обслуживаемого низкоуровневого кода при сохранении
предметных гарантий и приемлемых измеренных задержках. Установка Dolt сама по себе
и успешный `SELECT` этот результат не подтверждают.
