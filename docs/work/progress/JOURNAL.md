Прочитаны протокол, библиотека, концепция, стандарт линков, интерфейсные правила и инструкции
владельцев. Рабочая копия сверена: исходные незакоммиченные изменения только в документации.
Выбран отдельный прикладной владелец прогресса; правила выполнения задач остаются у задач,
продуктовый каскад переиспользуется. Текущий каскад и блокеры опираются только на колонки,
поэтому сначала требуется устранить это расхождение. Расчёт чтения не записывает отношения.

## 24 сентября 2026 — первый вертикальный срез

Добавлены общие правила фактического выполнения, отдельные строгие схемы шести видов,
согласованное чтение, REST-контроллер, сгенерированный SDK и доставка CLI/MCP.
Типизация Server Runtime, CLI и MCP прошла. Первичный Core test: 147/148; обнаружена
регрессия ремонта старых смешанных циклов. Выбрано консервативное невыполнение для прежних
карточек/каталогов и явная ошибка для нового прогресса; это сохраняет путь ремонта базы.
Новая функциональность ещё не прошла итоговую приёмку; продолжаются тесты и Web-интеграция.

## 24 сентября 2026 — допуск и план Web

Прочитаны skills Unit Architecture и React Reference, профиль `apps/web/README.md`,
правила доменов/зависимостей, data-fetching/REST/SWR и строгий TypeScript/JSX styleguide.
Исследованы `infra/tasks-api`, домен `board-tasks` и потребители `ProductTasks`,
`ApplicationProgress`, `TaskEditor`. Сохраняются существующие владельцы и фасеты:
адаптеры прогресса задач принадлежат `board-tasks`, используют прежний клиент SDK;
композиции получают предметную модель через фасет домена. Новых юнитов и TSX не требуется.

План: заменить клиентские подсчёты по колонкам вызовами отдельных прогрессов; показать
фактическую готовность и причины, сохранив раскрытие по существующим адресам; SWR и SSE
обновляют только данные, не черновик. Проверить typecheck/lint/build и собственным
headless agent-browser на временной базе обе темы, адаптивность и повторное открытие зависимости.

## 24 сентября 2026 — интеграционные проверки и исправления

Предметные вычисления выделены в шесть обработчиков `handlers.ts`; `snapshot.ts` отвечает
за согласованное чтение, адреса, полные счётчики и страницы. Прежний каскад использует
общую проверку выполнения. Адресное чтение снятой реализации явно возвращает INACTIVE.
Проверены legacy и relay-entities: пустая обязательная реализация блокирует готовность
при счётчике 1/1; снятие участия меняет готовность; чтение не меняет `.indexes/state.json`.

Первые сквозные прогоны нашли и помогли исправить:

- Лишние поля строки списка в `reason.source` нарушали strict-схему: источник теперь
  строится адресом сущности, отдельно от строки с вычисленным состоянием.
- Проектный rewrite маршрутов имел явный перечень разделов: добавлен progress.
  `PROGRESS_CHANGED` внесён в карту HTTP 409; продолжение без версии — HTTP 400.
- CLI `--version` перехватывается глобальной справкой версии, поэтому введён предметный
  `--snapshot-version`, как в диагностике графа. Команды продолжения не разрывают токен версии.
- Дополнены проверки покрытия команд/инструментов в документации и примеров OpenAPI;
  тестовый helper MCP учитывает человеческий текст вместе со структурированным результатом.
- Сборщик скилла отклонил непереносимые ссылки из нового справочника на исходники/досье;
  справочник связан с включёнными контрактами, инженерная навигация остаётся в библиотеке.

Последний полный REST-прогон: 35/35; MCP: 11/11. В полном CLI-прогоне 35/37, затем обе
найденные ошибки исправлены; адресный повтор `progress.test.ts` + `documentation.test.ts` —
6/6. Core ранее 151/151; дополненная адресная группа прогресса — 4/4.
Typecheck Core/Server Runtime/CLI/MCP, lint Web и сборка CLI/MCP/Web прошли.
Штатный `docs:check` повторил только пять прежних ссылок на `STORAGE-REFACTORING.md`.
