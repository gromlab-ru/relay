# Критерии приёмки задачи

**Статус: реализовано и проверено; ограничения общих проверок перечислены ниже.**

## Цель и основание

По поручению пользователя добавить в карточку задачи самостоятельный раздел
«Критерии приёмки» рядом с существующими продуктовыми целями и подзадачами.
Человек и оркестратор задают критерии: заголовок, краткое описание и полное описание
Markdown. Список позволяет раскрыть описание и отметить выполнение.

## Решения и границы

- Критерий принадлежит задаче, имеет постоянный ID и сохраняемый порядок.
- Название обязательно и однострочно; summary — обычный многострочный текст;
  description — Markdown. Новые критерии не выполнены.
- Выполнение сохраняет автора и время. Изменение текста сбрасывает отметку.
- Невыполненные критерии препятствуют done, но не влияют на blocked/ready.
  Автоматического завершения нет; для изменения критериев done-задачи её сначала открывают.
- Максимум 100 критериев, список по 20 с продолжением; подробности читаются адресно.
- Все записи используют ревизию задачи, requestId и общую блокировку Core.
- Хранение v4; v1–v3 читаются с пустым массивом без записи. Следующая мутация
  обновляет формат атомарно, сохраняя ID, историю, квитанции и точный Markdown.

## Владельцы и план

1. Contracts/Core: схемы, вложенный массив, чтение и адресные операции, условия done.
   Проверить старые записи, повторы, конфликт, пагинацию и восстановление pending.
2. Server/Project Runtime/CLI/MCP: общий контракт, предметные интерфейсы;
   SDK обновить закреплённым генератором из OpenAPI.
3. Web: domains/board-tasks владеет данными, адаптацией и SWR/SSE;
   вложенный task-acceptance у task-editor — самостоятельная область списка/формы.
   Дети не импортируют родителя; сеть доступна через фасет домена.
   Mantine Checkbox/Collapse/useForm, существующие MarkdownField/MarkdownView.
   Собственные изменения обновляют ревизию редактора без потери черновика.
4. Проверки Core/HTTP/CLI/MCP, Web lint/typecheck/build и agent-browser на временных
   данных: обе темы, 1440/1024/768/390, клавиатура, ошибки, конфликт и SSE.
5. Обновить канонические документы и исходники скилла; docs:check, skills:check,
   форматирование и git diff --check.

Основания: протокол, стандарт интерфейсов, профиль apps/web/README.md;
