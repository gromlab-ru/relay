# План реализации единого хранилища

Основание — [целевое ТЗ](../../../STORAGE-REFACTORING.md). Владелец дисковых механизмов —
Core (`storage`), переносимых схем — Contracts. Профиль Unit Architecture применяется к Web;
серверный код сохраняет действующее разделение `domain/application/storage`.

## Этапы

1. **Общая основа:** оболочка записи, реестр кодеков, постоянные ID-пути, пространства ключей,
   неизменяемые сегменты производных индексов, WAL и проверяемое восстановление.
2. **Предметные адаптеры:** продукт, реализации, прежние scope, доски, задачи, настройки,
   удаления и история; устранение старых путей и встроенных растущих квитанций.
3. **Связи:** наборы владельца и `slot`, явные вызовы после предметной записи, отзыв,
   сопоставление ID и объединённый журнал операции.
4. **Полный контекст:** обе стороны, циклы и параллельные рёбра, согласованный снимок,
   общий индекс карточек и смежности, ограниченный кеш.
5. **Доставка и обслуживание:** явная миграция, reindex/validate, лёгкое обнаружение изменений,
   local/HTTP, REST/OpenAPI/SDK, CLI/MCP и документы владельцев.
6. **Приёмка:** реальные файловые базы, 10 000/100 000 записей, подсчёт чтений прогретого
   контекста, Git-слияния, сбои, повтор миграции, человеческий и машинный интерфейсы.

Переход по этапам фиксируется по факту, наличие нового модуля не означает перевод старых
предметных операций. Playground остаётся базой последующей проверки пользователем.

## Инварианты общей основы

- `storage.json` отличает новый формат от прежнего. Открытие старой базы новым читателем
  требует миграции; инициализация не маскирует прежние данные пустой базой.
- ID и коллекция определяют путь. Технические записи получают отдельное определение владельца.
- Кодек вида валидирует данные и сохраняет Markdown через `split("\n")` / `join("\n")`.
- Операция выполняется под блокировкой реального пути базы. До публикации сохраняется WAL
  с контрольными суммами до/после; recovery сначала проверяет весь пакет на внешние конфликты.
- Индексы — JSON-деревья по хешу точного ключа. Лист ограничен количеством и байтами;
  переполнение делит сегмент. Неизменяемые сегменты переиспользуются снимками.
- Потерянный ожидаемый сегмент — повреждение, не пустой результат. Явное перестроение
  восстанавливает индекс из постоянных записей.
- Ключи, алиасы и ID индексируются с несколькими кандидатами. Коллизия не запрещает
  адресное чтение и исправление по квалифицированному ID.
- Удаление оставляет надгробие на прежнем ID-пути. Адреса остаются зарезервированными.
- Продуктовые линки и отношения движка сохраняются отдельно внутри общего пакета.
  Читатель не создаёт связи; нессылочные изменения не порождают событий отношений.

## Проверки

Изолированные временные каталоги: ID-пути, точный Markdown, регистрация нового вида,
коллизии адресов, сохранность алиасов, контроль версий, повтор с другим содержимым,
прерывание каждого шага WAL, отказ при внешней правке, повреждение индекса и его перестроение,
конкуренция экземпляров, realpath и изоляция worktree. Для графа — петли, циклы, параллельные
рёбра, обратные цепочки, изолированный корень, полнота и счётчики чтений.

Проверки существующих Core-сценариев обязательны после подключения адаптеров. Публичные
интерфейсы проверяются после их перевода; тест низкоуровневого модуля не подтверждает CLI/MCP.

## Проверка Web после подключения

Прочитаны react-reference (Quality, Data Fetching, Realtime), Unit Architecture
(проверка и зависимости), профиль `apps/web/README.md` и инструкции приложения.
Транспорт остаётся в `infra/tasks-api` / `infra/workspace-events`, предметные адаптеры —
в `domains`, визуальные сценарии — у существующих композиций. Новых UI-границ и TSX не требуется.
План: lint/typecheck/build; отдельный Server с временной единой базой; именованная
headless-сессия agent-browser; проверить запись и чтение карточки, документы, SSE,
обе темы и размеры. Свою сессию и сервер завершить после проверки.
