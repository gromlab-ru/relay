# План и архитектурный допуск

## Контракт

1. Каталог девяти видов и адресное описание: назначение, JSON-схемы полей/операций,
   фильтры, связи, политика ключей и поддерживаемые действия.
2. Единый каталог записей, адресное и пакетное чтение. Краткая карточка содержит kind,
   ID, key, название, краткое описание, ревизию и состояние; полный ответ — типизированные данные.
3. Резолвер работает в контексте проекта по назначенным адресам, а не угадывает вид по
   префиксу. При коллизии выдаёт явную ошибку; вид можно уточнить. Внутренние ссылки — ID.
4. Общий конвейер записи вызывает зарегистрированный предметный обработчик после
   нормализации ссылок под той же блокировкой. Сущность и обязательные связи сохраняются
   одной предметной транзакцией. Идемпотентность проверяется до конфликта версии.
5. Основной контракт общ для local, REST, CLI, MCP и Web. Предметные аргументы MCP
   доступны по именам; CLI имеет отдельные читаемые представления.

## Идентичность и совместимость

- kind — стабильное имя определения; ID — постоянная идентичность записи; key — текущий
  читаемый адрес; алиасы сохраняют прежние адреса и не назначаются другой записи.
- Существующие ID, Markdown, задачи и реализации сохраняются. Кодеки совместимо читают
  прежние записи. Изменение дискового формата получает версию и проверяемый переход.
- Метаданные контрактов и дисковая сериализация разделены. Markdown остаётся строкой API
  и массивом строк на диске. Вычисляемые поля и проекции отношений не создают второго факта.
- Списки ограничены 100 записями, сообщают total/nextOffset/version. Изменение версии
  требует перечитать выборку. Неизвестные фильтры и неподдерживаемые действия отклоняются.

## Последовательность

1. Перенести совместно используемые схемы основных сущностей в переносимый пакет контрактов;
   прежние импорты Core оставить совместимыми фасадами. Устранить циклическую зависимость пакетов.
2. Реализовать определения, резолвер, каталог и обработчики движка, включая адресацию ключами,
   алиасы, проверку версии и фильтров. Проверить реальные предметные записи.
3. Подключить граф к общему каталогу и разрешению внешних ссылок. Добавить REST и backend.
4. Получить SDK закреплённым генератором из фактического OpenAPI. Подключить CLI/MCP и
   существующий выбор сущностей Web к новому API.
5. Проверить сквозные сценарии и обновить продуктовую, техническую и справочную документацию.

## Web и SDK

Прочитаны `react-reference`, `unit-architecture`, профиль SPA, зависимости, формы,
получение данных и качество; SDK — `rest-api-codegen-ru`. Ответственность нового
`domains/entities` — адаптация API, карточки, поиск и SWR. Существующий
`project-relations/ui/entity-picker` остаётся компонентом своей композиции, импортирует
публичный фасет домена. Направление: composition → domain → infra/tasks-api → SDK.
Графовый обход остаётся Core. Новые TSX при необходимости создаются только генератором.

## Проверки

- Core: все девять видов, схемы и семантика текста, пары key/ID, вложенные ссылки,
  коллизии, смена формата ключа, алиасы, конкурентная запись, повтор, изоляция, страницы.
- REST: те же операции в local/project-scoped, ошибки, OpenAPI и SSE.
- CLI: text/JSON, справка и реальное продолжение; MCP: discovery, аргументы и ответы.
- Web: выбор по ключу/названию, контекст, сохранение связей, ошибки и сохранность ввода;
  headless agent-browser, lint/typecheck/build.
- Документы и скилл: форматирование, docs:check, сборка/проверка скилла, diff --check.
