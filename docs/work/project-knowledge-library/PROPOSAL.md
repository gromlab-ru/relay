# Библиотека знаний проекта: предложение

После пересборки движка 22 сентября правила интеграции уточнены в
[разборе контекста](CONTEXT-ALIGNMENT.md). Его требования к продуктовым линкам,
отдельным связям Core, полному обходу и восстановлению имеют приоритет над прежними
техническими формулировками этого предложения. Общая концепция UI и черновиков сохраняется.

Статус: **проект для согласования**, 22 сентября 2026. Код не изменён.
[Цель и продолжение](README.md) · [Источники и проверки](JOURNAL.md).

## 1. Основная идея

Библиотека хранит дополнительные знания, которые помогают человеку и агенту понять
проект и восстановить контекст. Документ существует один раз и доступен как из
библиотеки, так и из связанных сущностей. Он не заменяет обязательные поля требований
и не получает силу утверждённого требования только из-за ссылки на фичу.

Три независимых измерения:

| Измерение | Вопрос            | Пример                                 |
| --------- | ----------------- | -------------------------------------- |
| Раздел    | Где искать?       | Инфраструктура                         |
| Тип       | Что за материал?  | Инструкция                             |
| Связи     | К чему относится? | Серверное API, задача настройки деплоя |

Пример: «Выкладка API в staging» находится в «Инфраструктуре», имеет тип «Инструкция»
и связан с приложением API и задачей настройки pipeline. После завершения задачи
документ остаётся полезным и доступным из приложения.

## 2. Организация библиотеки

Название страницы и пункта навигации — «Библиотека знаний», адрес `/documents`
сохраняется. Внутри сущностей блок продолжает называться «Документы».

Начальный набор разделов:

| Раздел         | Что хранит                                                           |
| -------------- | -------------------------------------------------------------------- |
| Продукт        | Бизнес-правила, исследования, объяснения возможностей и сценариев    |
| Архитектура    | Устройство системы, интеграции, технические решения и ограничения    |
| Разработка     | Локальный запуск, соглашения, тестирование, практики работы          |
| Инфраструктура | CI/CD, окружения, размещение, деплой, наблюдаемость и восстановление |
| Процессы       | Совместная работа, жизненный цикл изменений, выпуск и приёмка        |

Это редактируемые записи проекта, а не закрытый enum. Разделы можно создавать,
переименовывать и упорядочивать. У документа один основной раздел либо «Без раздела».
Удаление раздела предлагает перенести материалы или оставить без раздела, но не удаляет их.
Название не является идентификатором. Сортировка не требует drag-and-drop: доступно меню.

Общие представления: «Все документы», «Закреплённые», «Без раздела», «Архив».
Закрепление общее для проекта и влияет на видимость, а не на авторитет документа.
Нет обязательного заполнения раздела или связей перед первым сохранением.

Типы первой версии: описание, требования/ТЗ, правила, инструкция, проект решения,
решение, исследование. «Проект решения» подходит для проектирования будущей реализации:
вариантов устройства, открытых вопросов и ещё не принятых предложений.
При миграции существующие типы сохраняются либо явно отображаются на согласованные
эквиваленты без потери исходного значения. Пользовательские типы и теги можно добавить
после проверки реального использования; для гибкости первого среза достаточно своих разделов.

Состояние документа: «Черновик», «Действующий», «Архив». Это состояние публикации,
не автоматическое подтверждение истинности. Новый документ по умолчанию — черновик;
переход в действующий явный. Локальный несохранённый ввод редактора обозначается отдельно.
Сохранённые черновики видны в библиотеке, архив скрыт по умолчанию и сохраняет прямые ссылки.

### Проектирование в черновике

Черновик — полноценный серверный документ с постоянным адресом, содержанием и связями,
доступный человеку и агенту. Например, «Новая схема подтверждения бронирования»:
раздел «Архитектура», тип «Проект решения», состояние «Черновик», связи с фичей,
сценарием и существующей реализацией API. Если реализации ещё нет, достаточно связать
с приложением или требованием; создание документа не создаёт фиктивную реализацию.

В локальной навигации добавляется представление «Черновики» со счётчиком. Оно собирает
сохранённые черновики всех разделов; это фильтр, а не папка. Черновики также остаются
видимыми во «Всех документах» и своих разделах.

Визуальное различение обязательно во всех точках входа:

- Каталог, поиск, picker и обратный список сущности показывают текстовый бейдж
  «Черновик» с небольшой иконкой карандаша и мягким янтарным оформлением.
  Название остаётся обычной контрастности; пунктирные рамки и бледный текст не нужны.
- Рядом с состоянием показан тип: «Проект решения · Черновик». Проектирование
  будущей реализации не путается с описанием уже существующей.
- Страница чтения показывает под заголовком компактную полосу
  «Черновик · Проектируется, ещё не принято» и действие продолжить редактирование.
  Для черновика другого типа подпись — «Черновик · Материал ещё готовится».
- Состояние доступно агенту в структурированном ответе вместе с типом документа;
  черновик в контексте не выдаётся за действующее правило.

Жизненный цикл: сохранить проект решения → обсуждать и редактировать → явно принять
решение. При принятии пользователь может одной операцией сменить тип на «Решение»
и состояние на «Действующий», сохраняя ID и связи. Отвергнутый вариант можно архивировать
с объяснением в содержимом. Сохранение очередных правок не означает принятия.

В редакторе различаются три понятия: «Состояние: Черновик» — серверный документ;
«Есть несохранённые изменения» — текущий ввод; «Локальная копия сохранена в этой вкладке» —
восстановление ввода после reload. Сохранённый документ может одновременно быть черновиком
и иметь новые несохранённые правки. Индикация должна это показывать без двусмысленности.

## 3. Каталог

Основной вид — компактный список в одной спокойной поверхности. Большие карточки
слишком быстро расходуют высоту и затрудняют сравнение десятков материалов.
Не вводим переключение списка/плитки до подтверждённой потребности.

```text
Библиотека знаний                                  [+ Документ]
Контекст, решения и инструкции проекта

Все документы       │ Поиск по названию и содержанию…
Закреплённые         │ [Тип ▾] [Связано с…] [Ещё фильтры]   Обновлены ▾
Черновики            │
                    │
РАЗДЕЛЫ         +   │ Закреплённые · до трёх строк
Продукт             │   Обзор продукта                  Описание
Архитектура         │   Как запустить проект            Инструкция
Разработка          │
Инфраструктура      │ Все документы                          24
Процессы            │
                    │ Выкладка API в staging                   ⋯
Без раздела         │ Порядок релиза, проверки и откат
Архив               │ Инфраструктура · Инструкция · API · +2
                    │ Обновлён сегодня
                    │ ──────────────────────────────────────────
                    │ Правила отмены бронирования               ⋯
                    │ Условия возврата и исключения
                    │ Продукт · Правила · Бронирование · +1
                    │
                    │ Показано 40 из 124       [Показать ещё]
```

Левая локальная навигация около 208–224 px, основная область гибкая. Она находится
внутри раздела, не заменяет общую навигацию проекта. Одна строка — ориентировочно
96–120 px с учётом описания, без фиксированной высоты и обрезания названия.
Основное действие — название документа. Справа — дата и меню, при узком экране дата
переходит вниз. Описание до двух строк в каталоге; полный текст доступен в документе.

Не более двух связей на строке; «+N» открывает компактный список остальных.
У каждой связи есть иконка, название и тип; цвет помогает, но не заменяет текст.
Не повторять «MD», «Читать», большую иконку файла и разделительную полосу в каждой карточке.
Закреплённые представлены компактно, блок сворачивается; в поиске отдельный блок исчезает.

Поиск — название, краткое описание и тело; поиск сущности — отдельный фильтр
«Связано с…». Результат поиска по телу показывает фрагмент совпадения.
При выбранном разделе поиск ограничен им, доступно явное действие «Во всей библиотеке».
Фильтры, сортировка и раздел живут в URL; возврат восстанавливает положение списка.

Списки серверные: 40 записей, общее число, продолжение и версия выборки; сортировка
по обновлению с ID как стабильным вторичным ключом. Новая версия между страницами
предлагает обновить выдачу. Счётчики считаются по полному набору, не по загруженным строкам.
Счётчики разделов отражают активные документы без текущего поискового запроса;
число результатов отдельно отражает все фильтры. Полный Markdown загружается по открытию.

## 4. Чтение документа

```text
Библиотека знаний / Инфраструктура

Выкладка API в staging                   [Редактировать] [⋯]
Инструкция · Действующий · Обновлён 22 сентября

Читаемая колонка 680–760 px       │ Контекст
                                │ Инфраструктура
## Назначение                   │
…                               │ Связанные сущности       [+]
                                │ Приложения
## Подготовка                   │   API
…                               │ Задачи
                                │   Настроить pipeline
## Порядок выкладки              │
…                               │ Содержание
                                │   Назначение
                                │   Подготовка
                                │   Порядок выкладки
```

Ширина контекстной колонки около 280 px. Группы связей раскрываются независимо,
показывают ключ, название, пояснение и переход. Для реализаций обязательно название
приложения; для задач — доска. Длинный контекст имеет продолжение и не вытесняет оглавление.
Связи можно менять прямо при чтении без открытия текстового редактора.

В меню: копирование ссылки/ключа, закрепление, перемещение в раздел, архивирование,
удаление по существующему контракту предпросмотра последствий. Архивирование предпочтительно
для устаревших знаний; оно не разрушает объяснение истории задачи.

Оглавление строится по заголовкам Markdown, появляется только при наличии структуры.
Не обещать историю версий текста: сейчас история графа не равна истории документа.
Вкладку истории документа добавлять только вместе с реальным источником редакций.

## 5. Связи: основной пользовательский механизм

### Из документа

Нажатие «Добавить связи» открывает широкое модальное окно. Оно сохраняет страницу
и её положение, не требует переходить в общий исследователь графа.

```text
Связать документ                                         ×
Поиск по названию или ключу…
[Все] [Задачи] [Фичи] [Сценарии] [Приложения] [Реализации]

□ FEATURE-12   Бронирование
  Фича · Продукт
☑ API-SI-3     Подтверждение бронирования
  Реализация сценария · API → Бронирование
☑ API-42       Повторная отправка подтверждения
  Задача · Доска API

Выбрано 2                                      [Показать выбранные]
API-SI-3   [Контекст ▾]   [Добавить пояснение]                 ×
API-42     [Контекст ▾]   [Добавить пояснение]                 ×

[Отмена]                                      [Добавить 2 связи]
```

1. По умолчанию ищем по всем доступным видам в текущем проекте. Проект, продукт,
   доски и другие документы доступны в списке видов; расширение каталога не требует
   добавлять ещё один обязательный горизонтальный таб.
2. Поиск серверный, по 40 результатов, с продолжением. Выбранные записи сохраняются
   при поиске, смене вида и страницы. Уже связанные обозначены явно и не дублируются.
3. Разные реализации одного сценария различимы по приложению; совпавшие названия
   задач — по доске и ключу. Выбор родителя не выбирает детей.
4. По умолчанию отношение «Контекст»; дополнительных обязательных полей нет.
5. Для выбранной записи можно раскрыть смысл связи и Markdown-пояснение
   «Когда и зачем читать». Смысл можно применить ко всем выбранным одной командой.
6. «Отмена», крестик и Escape отменяют изменения именно этого окна. «Применить»
   в редакторе меняет его черновик; «Добавить N связей» на сохранённой странице
   выполняет запись. Подписи и текст явно объясняют разницу.
7. После успеха обновляются документ, обратный список сущности и общий граф.
   При ошибке выбор остаётся; при конфликте пользователь перечитывает связи
   и проверяет сохранённый набор изменений. Повтор использует тот же requestId.

Семантика первой версии:

| Подпись UI | Направление хранения               | Назначение                               |
| ---------- | ---------------------------------- | ---------------------------------------- |
| Контекст   | сущность → `references` → документ | Полезный материал для работы             |
| Описывает  | документ → `documents` → сущность  | Документ подробно описывает эту сущность |

Тип документа «Требования/ТЗ» отдельно показывает характер текста; выбор отношения
не объявляет требования принятыми и не меняет статус фичи или задачи.
При чтении обратные подписи адаптируются к точке входа. Это одно ребро, не две записи.
Старые `documents` сохраняют прежний смысл. Неизвестные типы общего графа остаются
видимыми через «Все связи»; упрощённый редактор их не удаляет.

Удаление связи называется «Убрать связь» и сохраняет сам документ. Историю изменения
отношений использует существующий граф. Различные смыслы пары могут сосуществовать,
точный дубль одного отношения не создаётся.

### Из сущности

На страницах задачи, фичи, сценария, приложения и реализации единый блок:

```text
Документы · 3                         [Прикрепить] [+ Создать]
Правила отмены · Правила
Описывает фичу · Условия возврата и исключения

Повторная отправка · Решение
Контекст · Читать при изменении повторов
```

«Прикрепить» ищет существующие документы с выбором нескольких. «Создать» открывает
редактор с заранее выбранной исходной сущностью. Название, раздел и тип не угадываются
молча; выбранный раздел библиотеки можно перенести из точки входа. Возврат ведёт к
исходной задаче или странице с восстановлением контекста.

Прямые документы показаны первыми. Косвенные материалы через фичу или приложение —
отдельное действие «Контекст через связи» с объясняющим путём. Нет автоматического
наследования сотен документов проекта и нет скрытого связывания с родителями.

## 6. Создание и редактирование

Полноценная страница редактора: крупное название, необязательное многострочное краткое
описание «Когда читать», Markdown с предпросмотром. Справа раздел, тип, состояние и связи.
Для создания обязательны только название и содержание; остальные параметры имеют
понятные значения по умолчанию. Название однострочное, summary — обычный многострочный
текст, тело и пояснения — Markdown. Поле summary требует textarea вместо текущего TextInput.

Создание из сущности готовит связь в черновике и показывает её до сохранения.
Никакой пустой постоянной записи только от открытия редактора. Внизу ясный индикатор
«Локальная копия сохранена в этой вкладке» и кнопка «Сохранить документ». Это не серверное
автосохранение; после успеха показана подтверждённая запись.

Текст, свойства и начальные связи должны сохраняться одной предметной операцией.
Если нужная транзакция ещё не реализована, нельзя выдавать отдельные запросы за общий
успех. Это условие сквозной реализации, а не гарантия существующего API.
Черновик сохраняет содержимое и выбор при reload, сетевой ошибке и конфликте.

## 7. Визуальный язык и адаптивность

- Сохранить Mantine, текущую типографику, Lucide и CSS-токены `--tasks-*`.
  Нейтральный фон, тонкая граница поверхностей, умеренный радиус; одна основная
  акцентная кнопка. Цвета сущностей совпадают с исследователем связей.
- Уменьшить пустой промежуток между заголовком и поиском. Иерархию дают название,
  краткое описание и вторичные метаданные, а не одинаково заметные рамки вокруг всего.
- При 1440 px каталог имеет две локальные колонки, читатель — текст и контекст.
  При 1024 px ширины пересчитываются по реальному свободному месту общего каркаса.
- При 768 px разделы открываются кнопкой над выдачей; контекст документа располагается
  перед текстом в компактной раскрываемой области. Оглавление доступно отдельной кнопкой.
- При 390 px одна колонка, фильтры в drawer, выбор связей — полноэкранный диалог.
  Основное действие остаётся видимым; горизонтальная прокрутка страницы не появляется.
- Все действия доступны с клавиатуры и имеют текстовые доступные названия.
  Диалог удерживает фокус и возвращает его инициатору; цвет и hover не единственный
  способ обнаружить действие. Размеры интерактивных зон проверяются на мобильном.

Пустая библиотека предлагает первый документ и объясняет возможность связать его позже.
Пустой раздел предлагает создание в нём. Пустой поиск предлагает сбросить фильтры.
Загрузка имеет скелетоны, ошибка — повтор с сохранением предыдущей выдачи, если она есть.
Удалённая выбранная сущность помечается и требует убрать/заменить связь до записи.

## 8. Модель и границы реализации

### Что уже есть

- Постоянные документы и Markdown, версии записей, черновики, SSE.
- Маршруты `/documents`, `/documents/new`, `/documents/:id` и `/edit`.
- Общий каталог сущностей и граф с пояснениями, пакетной записью и историей отношений.
- Контекстный обход для агента; отдельное чтение полного документа.

### Что нужно изменить

Сейчас библиотека зависит от полного продуктового снимка и `scopeIds`, получаемых
из `record.fields.links`. Это не универсальная модель связи с задачами. Нужны
проектные операции каталога и разделов, а также единое чтение и изменение отношений
документа через общий граф. Не хранить новые связи одновременно в `scopeIds` и графе.

Предварительные владельцы:

- Core/Contracts — документ, раздел, состояние, фильтры, общая предметная операция
  сохранения и совместимость прежних ссылок; граф остаётся владельцем отношений.
- `domains/documents` — предметный API Web, адаптеры и кеш документов/разделов.
  Это обоснованное выделение из продуктового адаптера: библиотека обслуживает весь проект.
- `domains/entities`, `domains/relations` — существующие каталог и отношения.
  Они не импортируют новый домен документов обратно.
- `compositions/screens` — каталог, чтение и редактор. Локальные части колоцированы
  у экрана. `app/router` только подключает их публичные фасеты.
- Общий виджет связанных документов обслуживает страницы перечисленных сущностей.
  Общий выбор сущностей выделяется из текущего владельца только при подключении
  реальных новых потребителей; глубокие импорты из `project-relations/ui` недопустимы.
- `ui/markdown-*`, тема и примитивы Mantine переиспользуются. Предметный picker
  не становится универсальным `ui` только из-за одинакового внешнего вида.

Контракты списка возвращают компактные карточки, ID/ключ, свойства, сводку связей,
total и продолжение. Чтение тела отдельное. Точный REST/CLI/MCP синтаксис проектируется
после утверждения UX, вместе с русскими описаниями всех публичных параметров.

### Совместимость и миграция

1. Сохранить постоянные ID, ключи, URL и все тела/summary документов.
2. Существующие документы первоначально оставить «Без раздела»: связь с продуктом
   не доказывает тематический раздел. Предложить явное групповое перемещение.
3. Состояние прежних документов переносить как «Действующий» в смысле прежней
   доступности, без заявления об утверждении; это решение должно быть согласовано.
4. Спроектировать идемпотентный перенос domain-проекций `documents` в общий граф
   с сохранением направления, происхождения и соответствия старых адресов.
   Совместимые старые операции делегируют единому владельцу, не пишут второй набор ссылок.
5. Пока миграция не завершена, старые связи явно читаются как проекции и изменяются
   только у их владельца. Нельзя незаметно складывать дубли из двух источников.
6. Формат Markdown на диске — массив строк. При изменении хранения нужны версия
   схемы, проверка прерывания переноса, CAS и сохранение квитанций повторов.

Физическое перемещение документов из `.relay/product` не является условием визуального
прототипа. Решение о дисковой схеме принимается вместе с транзакцией, а не отдельным
переименованием каталога во время UI-работы.

## 9. Использование агентом

После обсуждения агент создаёт документ с названием, summary «Когда читать»,
типом, разделом и явными связями. Если вывод ещё не согласован, сохраняет черновик.
Получатель контекста видит карточку, состояние, тип отношения и поясняющий путь;
полный Markdown дочитывает адресно. Документ не загружается целиком в каждый контекст.

Закреплённые материалы доступны отдельным запросом проектного контекста. Закрепление
само по себе не запускает агента и не гарантирует прочтение: клиент/продуктовый skill
должен явно запросить эти материалы. Предметная MCP-запись документа и связей требует
расширения: текущий MCP-контекст графа не означает наличие произвольной записи рёбер.

## 10. Этапы и приёмка

1. **Визуальный прототип:** каталог, чтение, модальное окно выбора и создание из
   сущности. Репрезентативные данные: длинные заголовки, документы без связей,
   реализации одного сценария в двух приложениях, десятки документов. Сначала
   оценить композицию, плотность и понятность выбора в обеих темах и на четырёх ширинах.
2. **Предметный контракт:** разделы, метаданные, списки, единые связи, совместимость,
   атомарное сохранение, REST/CLI/MCP и источники продуктового skill. Уточнить
   дизайн хранения и миграцию до изменения существующих данных.
3. **Сквозная интеграция:** каталог, читатель и редактор; затем одинаковый блок
   документов на страницах сущностей, обратные переходы и SSE.
4. **Приёмка:** человек создаёт инфраструктурную инструкцию и связывает её
   с приложением и задачей; агент находит тот же документ из задачи и читает тело.

Дополнительные критерии:

- Раздел меняется независимо от связей и типа; несколько привязок не создают копии.
- Снятие связи не удаляет документ; выбор фичи не выбирает все сценарии.
- Отмена диалога не меняет черновик, применение в редакторе не делает преждевременную запись.
- Прямой и обратный списки отражают один факт; контекстные пути не превращаются в прямые ссылки.
- Поиск и продолжение работают на полном наборе; карточки не требуют загрузить весь Markdown.
- Ошибка, повтор и конфликт не теряют текст или выбранные сущности.
- Сохранённый черновик проекта решения различим в каталоге, поиске, выборе,
  чтении и обратном списке; агент получает его состояние. Принятие явно и не меняет ID.
- Сохранены старые адреса и документы; миграция повторяема и восстанавливается после прерывания.
- Web проверяется вручную через собственный headless agent-browser; машинные контракты,
  атомарность и миграция — отдельными подходящими тестами Core/REST/CLI/MCP.

Глубокие папки, теги, личное избранное, произвольные типы документов, визуальный граф,
вложения и история редакций текста не входят в первый срез. Их можно развивать
после приёмки основной библиотеки и единого механизма связей.
