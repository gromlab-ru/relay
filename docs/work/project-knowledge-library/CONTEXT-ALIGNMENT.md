# Переработка библиотеки под действующий механизм контекста

Статус: историческая сверка перед интеграцией. Серверная часть впоследствии реализована.
Предложение добавить UI просмотра контекста отклонено пользователем как расширение
задачи: библиотека только линкует документы к сущностям, бекенд записывает связи.
Актуальные границы и результат — в [README](README.md) и [журнале](JOURNAL.md).
Сверка рабочей копии 22 сентября 2026 после сообщения пользователя о пересборке движка.

Старое предложение «всё хранить только в графе» и переходная модель domain-проекций
не задают текущую архитектуру. Исправляется и предыдущий вывод этой работы, что двух
записей быть не должно: продуктовый линк и связь движка намеренно сохраняются отдельно.

## Что подтверждено кодом

- `application/graph/catalog.ts` возвращает только узлы и алиасы. Поля документа не
  превращаются в рёбра. `GraphService.read` обходит только хранилище движка.
- `GraphService.mutate` сохраняет отдельные отношения, историю и квитанции. Версия графа
  включает каталог сущностей. Продуктовый сервис должен читать её после продуктового изменения.
- Прежняя `application/graph/context.ts` удалена; по виду сущности обход больше не
  останавливается. `context` совместим с полным `all`, с явными границами запроса.
- Наш `ProductService.mutate` сохраняет `fields.relations` как продуктовые данные,
  но не вызывает запись движка. Успешное прикрепление пока не создаёт связи для контекста.
- `DocumentRelations` читает массив продуктовых прикреплений и названия через каталог.
  Это UI линков, а не чтение всех отношений графа. `EntityDocuments` с `target` —
  обратная продуктовая выборка, также не транзитивный контекст.
- Тест библиотеки после пересборки движка честно ожидает ноль рёбер от одной продуктовой
  записи. Он подтверждает отсутствие проекций, а не готовность интеграции библиотеки.

## Исправленный контракт сценариев

| Сценарий                                     | Продуктовый результат              | Действие движка                                |
| -------------------------------------------- | ---------------------------------- | ---------------------------------------------- |
| Создание без прикреплений                    | Документ и его свойства            | Нет новых рёбер                                |
| Документ описывает сущность                  | Линк у документа                   | Документ → documents → сущность                |
| Материал прикреплён для чтения               | Линк у документа                   | Сущность → references → документ               |
| Изменение пояснения                          | Изменённое назначение линка        | update соответствующего ребра                  |
| Замена цели или смысла                       | Замена конкретного линка           | remove старого и add нового одним пакетом      |
| Открепление                                  | Удалён конкретный линк             | remove обслуживающей его связи                 |
| Удаление документа/цели                      | Предметный каскад и очистка линков | Очистка соответствующих сохранённых связей     |
| Название, текст, тип, состояние, закрепление | Изменены свойства документа        | Топология не меняется                          |
| Выбор раздела библиотеки                     | Классификация документа            | Не создаётся отношение с одноимённой сущностью |

Раздел «Продукт» не является линком на паспорт, «Инфраструктура» — не вымышленным
инфраструктурным узлом. Если разделам потребуется собственный контекст как сущностям,
это отдельное расширение каталога и предметного контракта.

## Переработка записи

1. Сохранить продуктовые линки у владельца документа, явно назвать их прикреплениями
   в доменной модели и справке. Само наличие массива допустимо; недопустима подмена им движка.
   Схемы legacy `links` и нового `relations` требуют совместимого единого продуктового контракта.
2. Общий бекенд создания/изменения/прикрепления после продуктовой части вызывает
   `GraphService.mutate`. Web, local CLI и MCP вызывают одно предметное действие.
3. Задать стабильное соответствие продуктового линка конкретным ID рёбер движка.
   `source=graph` не отличает обслуживающую линк связь от независимой диагностической.
   При снятии нельзя удалять все отношения с совпавшими концами.
4. Вычислять разницу наборов, сохранять незатронутые линки и рёбра. Изменение только
   содержания не пересоздаёт отношения и их историю. Ключи/ID нормализуются в бекенде.
5. Спроектировать долговечное восстановление составной операции. Продуктовая квитанция
   сама по себе ещё не подтверждает её завершение; повтор должен закончить запись графа,
   если продукт уже записан. Сохранить исходные ключи повтора и параметры графового пакета.
6. Общая блокировка и существующий WAL графа сами по себе не решают сбой между двумя
   владельцами. Финальный успех — только после согласования обоих состояний. Не запускать
   второй запрос из клиента, не чинить данные побочным эффектом чтения.

## Переработка чтения и UI

- Блок «Прикреплено к» на документе управляет продуктовыми линками. Он показывает
  название, вид, смысл и пояснение, но не объявляет этот массив полным контекстом.
- Блок «Связи и контекст» читает общий граф от ID документа: входящие и исходящие
  отношения, пути, `nextOffset`, `boundary`, `depthLimited`. У других сущностей тот же
  механизм с другим корнем, без отдельного дерева библиотеки.
- На задаче различимы прямо прикреплённые документы и материалы, достижимые через
  граф. Документ, найденный по пути, не становится новым прямым линком автоматически.
- Сохранённый путь через документ к другому приложению должен быть виден при достаточной
  глубине. Он не означает наследование чужих требований. Не возвращать скрытое отсечение видов.
- «Для чтения»/«Материал для работы» точнее для смысла references, чем название «Контекст»,
  совпадающее с публичным механизмом обхода. Точные подписи согласуются при доработке UI.
- Технические add/remove и ввод произвольного типа ребра не являются основным сценарием
  прикрепления. Диагностический граф не подменяет продуктовую форму.
- «100 операций в пакете» — не общий лимит числа связей сущности. Собственный предел
  линков документа нужно обосновать отдельно; большой граф всегда имеет продолжение.
- Черновик остаётся обычной адресуемой сущностью. Его состояние визуально заметно, но
  не исключает документ из обхода и не прерывает путь.

## Совместимость и зависимости

Существующие `fields.links`/`fields.relations` могут быть сохранены без рёбер. Нужна явная
возобновляемая операция согласования, а не восстановление прежнего проектора. Она сопоставляет
сохранённые связи, проверяет неоднозначности и не удаляет независимые рёбра, ID или историю.

Полная цепочка задача → реализация → сценарий → фича требует интеграции соответствующих
продуктовых сценариев и наличия каждого сохранённого ребра. Только запись связи документа
не восстановит недостающие участки. Эта зависимость должна быть явно отмечена в приёмке
библиотеки; подключение всех сценариев проекта не объявляется выполненным данной задачей.

## Проверки после исправления

- Линк и отдельное ребро существуют после одной предметной операции до первого чтения UI/графа.
- Сбой после продуктовой записи, до/после записи графа, рестарт и потеря ответа не дают
  ложного успеха и дублей. Повтор возвращает согласованную исходную квитанцию.
- Замена, изменение пояснения и открепление затрагивают только обслуживающие линки связи.
- Снятый прямой линк может оставить документ в контексте по другому пути; UI объясняет путь.
- Полный обход проходит через документ и приложение, обрабатывает циклы и честно показывает границы.
- Product filters/готовность не меняются от независимого диагностического ребра.
- Одинаковый результат Web/REST/local CLI/MCP, ревизии, переименование, изоляция и каскад удаления.
- Старая проверка видимости проекций не считается подтверждением этих требований.
