# Правила библиотеки знаний

## Владельцы информации

| Раздел        | Что хранит                                                                       |
| ------------- | -------------------------------------------------------------------------------- |
| `product`     | Назначение Relay, ожидаемые возможности, модель, сценарии и поведение приложений |
| `engineering` | Текущее техническое устройство, покрытие реализации и причины решений            |
| `reference`   | Точные действующие контракты: команды, API, схемы, конфигурация и ошибки         |
| `guides`      | Практические инструкции использования и эксплуатации                             |
| `development` | Обязательные правила и процессы изменения самого Relay                           |
| `work`        | Цели, ход конкретных работ, проверки и точки восстановления контекста            |
| `archive`     | Прежние спецификации и исходные материалы с объяснением их статуса               |

Справочники сохраняют стабильные адреса в `reference`: их используют CLI-поставка,
скилл и внешние ссылки. Навигатор инженерного раздела связывает их с реализацией.
Корневые страницы `docs` могут оставаться короткими совместимыми точками входа.

## Один владелец факта

Общее правило сущности описывается у сущности. Приложение описывает свою реализацию
пользовательского взаимодействия и ссылается на правило. Справочник определяет точный
синтаксис; руководство показывает применение. Журнал объясняет изменение и ссылается
на действующее описание, а не становится вторым справочником.

README приложения возле кода — локальная инструкция запуска и разработки, а
`product/applications/<имя>` — продуктовый контракт приложения. Они связываются через
библиотеку. Бизнес-правила в README возле кода постепенно заменяются ссылками при их изменении.

## Статус и достоверность

- Действующая спецификация задаёт ожидаемое поведение. Предложение помечается отдельно
  и не становится требованием без решения пользователя или другого явного основания.
- Состояние реализации содержит дату сверки, область, ссылки на код и проверки.
  Статическое чтение кода не равно успешному запуску сценария.
- Историческая проверка относится к указанной версии и окружению. При переносе её дата
  не меняется; непроверенное сегодня остаётся непроверенным сегодня.
- Архивный документ получает явную отметку и ссылку на замену. Его прежние формулировки
  сохраняются как источник, а не действуют параллельно с новой спецификацией.
- При конфликте требований и кода фиксируется расхождение. Код не отменяет требования
  автоматически; хронологически последняя заметка также не доказывает решение.

## Структура документов

Начинай с назначения, статуса при необходимости и точки входа. Используй содержательные
заголовки, Markdown и относительные ссылки. Путь именуется по предмету, а не по сессии агента.
Не создавай пустую иерархию ради одинакового количества файлов.

Спецификация включает пользователя, предусловия, нормальный сценарий, исключения,
ограничения и наблюдаемые критерии. Для списка фиксируются границы и продолжение.
Подробности выносятся в отдельный файл, когда у них есть самостоятельный сценарий чтения.

## Досье работы

Путь: `docs/work/<устойчивое-имя-цели>/`. Обязательны `README.md` и `JOURNAL.md`.
`PLAN.md` нужен для многоэтапной работы; маленький план можно поместить в README.

README: цель и основание, статус, границы, владельцы, документы, выполненное, оставшееся,
блокеры, следующий шаг и состояние рабочей копии. Журнал: датированные существенные
события, причины решений, изменённые области, проверки и ограничения.

Исправление истории оформляется новой записью. Сводка README обновляется на месте.
Не храни секреты, полные дампы окружения или большие stdout; необходимые артефакты
связывай с записью и обозначай, если они локальные и не попадут к следующему агенту.

## Проверка

`pnpm run docs:check` проверяет локальные ссылки и якоря. Проверка форматирования и
`git diff --check` дополняют её. Человекочитаемая проверка проходит маршруты:
назначение → возможность → приложение → реализация → история → продолжение работы.
Автоматическая проверка не доказывает истинность описания или полноту требований.
