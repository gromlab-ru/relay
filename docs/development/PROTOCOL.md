# Обязательный агентский протокол Relay

Протокол действует на любые действия агента в рамках работы над Relay: разработку,
доработку, исправление, рефакторинг, исследование, диагностику, проверки, настройку,
зависимости, миграции, поставку и ведение документации. Размер изменения не отменяет
документирование. Он определяет объём записи: для небольшой работы достаточно короткого досье.

## Перед началом

1. Прочитай корневой `AGENTS.md`, инструкции владельца, [правила библиотеки](DOCUMENTATION.md)
   и [общую концепцию](../product/README.md). **Перед любой задачей обязательно прочитай
   [«Линки, связи и контекст»](LINKS-AND-CONTEXT.md)** — фундаментальный механизм Relay,
   независимо от вида работы и упоминания связей в поручении. Для интерфейсов обязателен
   [единый стандарт](INTERFACE-STANDARD.md).
2. Найди затронутые возможности, приложения, технические контракты и актуальное состояние.
   Прочитай связанную работу в [индексе](../work/README.md), её точку продолжения и нужные записи.
3. Сверь рабочее дерево, ветку, код и окружение с сохранёнными сведениями. Не принимай старый
   отчёт за свежую проверку. Сохрани чужие изменения.
4. До действий, меняющих проект или окружение, создай либо актуализируй досье работы:
   цель, основание, границы, владельцы, затронутые документы, контракты, проверки и следующий шаг.
   Первичное чтение для ориентации допустимо до создания досье; существенные выводы запиши туда.
5. Для нового поведения зафиксируй требования и критерии приёмки. Для хранения определи
   совместимость и миграцию; для списков — границы и продолжение. Неизвестное запиши вопросом.
   Для каждого продуктового сценария определи продуктовые данные/линки и отдельно
   необходимые связи движка. Укажи, где после продуктовой записи бекенд вызывает Core
   для установки, изменения или разрыва связей, как согласуются оба шага и как читается
   контекст. Если связи не нужны, обоснуй это; не пропускай вопрос при проектировании.

## Во время любых работ

- После смыслового изменения обновляй соответствующий действующий документ, не откладывай
  всю документацию на финальный ответ. Принятое изменение требований и фактический результат
  реализации описывай раздельно.
- Веди `JOURNAL.md` после значимых действий: результат исследования, изменение, техническое
  решение, существенная неудачная попытка, проверка, блокер или изменение поручения.
- Пиши, что сделано **и почему**: исходная проблема, выбранное решение и существенные основания.
  Записывай наблюдаемые факты и выводы, а не поток внутренних рассуждений или копию всей консоли.
- Найденное постоянное знание переноси в документ владельца. Причину долгосрочного
  технического решения сохраняй в `engineering/decisions`; журнал содержит ссылку.
- Для проверки указывай команду или ручной сценарий, результат, область, версию/состояние кода
  и ограничения. «Проверка запланирована» и «проверка пройдена» — разные состояния.
- При изменении плана сохраняй причину. Новая сессия продолжает прежнее досье той же цели.
  Отдельная цель получает отдельное досье со связью с предыдущей работой.

Не требуется запись на каждое чтение файла или вызов инструмента. Все существенные действия
должны быть восстановимы: исследования и работы без изменения кода тоже оставляют результат.

## Какие документы обновлять

| Действие                                     | Обязательная актуализация                                                                                  |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Новая возможность или изменение поведения    | Спецификация в `product`, затронутые приложения, состояние реализации, журнал                              |
| Исправление ошибки                           | Ожидаемое/фактическое поведение и причина в журнале, состояние реализации; спецификация, если была неверна |
| Рефакторинг                                  | Технические владельцы, зависимости и устройство, если изменились; журнал и проверки сохранения поведения   |
| API, CLI или MCP                             | Справочник контракта, продуктовые сценарии приложения, примеры, источники скилла при необходимости         |
| Конфигурация, зависимости, CI, сборка, релиз | Инструкция соответствующего процесса, техническое состояние и журнал фактических действий                  |
| Исследование, диагностика, проверка          | Источники, факты, выводы, ограничения и следующий шаг в журнале; подтверждённые знания у владельца         |
| Переработка документации                     | Канонические документы, навигация, ссылки, журнал переноса и причины решений                               |

Если документ остаётся верным, в журнале перечисли проверенные материалы и объясни, почему
обновлять их содержание не требуется. Это не освобождает от записи результата работы.

## Перед паузой или передачей

Обнови `README.md` досье: что сделано, что осталось, блокеры, ближайшее конкретное действие,
место незакоммиченных изменений, состояние своих процессов и ссылки на результаты.
Сохраняй контрольную точку также после завершения крупного этапа: внезапное прерывание сессии
не должно уничтожать весь контекст. Не обещай, что процесс или окружение останутся доступны.

## Перед завершением

1. Сопоставь результат с целью и критериями, проверь затронутую документацию по коду.
   Проверь оба результата: продуктовые данные сохранены, нужные связи отдельно записаны
   явным вызовом Core после продуктового действия. Снятие линка вызывает разрыв связи;
   проверены отказ между шагами, повтор и чтение контекста. Видимость вычисляемой проекции
   сама по себе не подтверждает интеграцию. Клиенты не синхронизируют граф вручную. Если механизм
   не затронут, укажи основание в досье без формальных изменений кода.
2. Обнови состояние реализации: реализовано, частично, не реализовано или не проверено.
   Укажи основания и оставшиеся расхождения; неизвестное не превращай в готовность.
3. Выполни применимые проверки. Для изменения интерфейса отдельно проверь человеческий
   результат и машинный контракт. Для документов — ссылки и читаемость навигации.
4. Выполни `pnpm run docs:check`, проверку форматирования изменённых документов и
   `git diff --check`. Если менялись источники скилла, выполни его сборку и `skills:check`.
5. Заверши запись журнала и обнови индекс работ. Незавершённую или заблокированную работу
   оставь в соответствующем состоянии с точкой продолжения.
6. В ответе пользователю сообщи результат, проверки, ограничения и ссылку на досье.

**Без актуальных документов затронутой области и журнала работа не завершена.**
Протокол не даёт разрешения на коммиты, публикацию или расширение поручения.
