# Спецификация @gromlab/tasks-cli: формат задач v2

Материал проектирования формата v2. Актуальные инструкции и контракты собраны
в [документации](README.md), схема JSON — в [справочнике формата](reference/FORMAT.md).

## 1. Назначение и основные решения

Локальная JSON-база задач для оркестратора и субагентов на одном хосте.
Оркестратор ставит и распределяет работу; человек наблюдает через UI и может вносить дополнения.
Движок — Node.js 22+, реализация — TypeScript, npm-пакет содержит готовый JavaScript.
Взаимодействие с трекером выполняется через CLI `npx @gromlab/tasks-cli`, REST API
или отдельный MCP-сервер `npx @gromlab/tasks-mcp`.

**Одна задача — один самодостаточный JSON-файл.** В нём находятся поля карточки,
описание, зависимости, саммари, все комментарии и отчёты агентов.

Логи — короткие отчёты о работе и принятых решениях. Модель рассчитана на обычные
проектные объёмы. Для отладки достаточно открыть JSON нужной задачи.

Описание, саммари, комментарии и отчёты поддерживают многострочный Markdown:
абзацы, пустые строки, списки и блоки кода. В JSON текст хранится массивом строк,
в текстовом выводе CLI строки соединяются настоящими переносами.
Названия задач, групп, теги, авторы и заголовки отчётов однострочны.

## 2. Архитектура

Разделить предметную модель, файловое хранилище, прикладные операции,
представление текста и адаптеры CLI. Команды не содержат прямых операций
с JSON или правил обхода графа. Модули небольшие, с одной ответственностью.
Комментарии в исходном коде и документация — на русском языке.

Команда описывается единым определением: синтаксис, смысл аргументов, подробное
поведение, примеры, опции и обработчик. Общий адаптер открывает проект и печатает
ответ; обработчики получают типизированные опции. Справка доступна без конфига.

Параллельная работа процессов CLI выполняется с одним общим хранилищем.
Разные worktree обращаются к серверу оркестратора через HTTP; прямой доступ выбирается
через `--local` и общий `--config`. Независимые копии данных
объединяются через Git; глобальное назначение между несинхронизированными
копиями не координируется.

## 3. Конфигурация

Файл `tasks.config.json` находится в корне проекта. CLI ищет ближайший конфиг
вверх от рабочей директории. `--config <path>` задаёт его явно.
Путь `storageDir` разрешается относительно конфига.

Для нескольких проектов CLI и MCP поддерживают `tasks.orchestrator.json` с именами,
путями и URL REST API. В одном каталоге реестр имеет приоритет над проектным конфигом.
Оба вида выбираются через `--config`; тип проверяется по содержимому. Именованный CLI
ищет реестр. MCP читает реестр на каждом запросе и передаёт задачи через REST SDK.
Актуальные схемы и правила: [конфигурация](reference/CONFIGURATION.md), [MCP](reference/MCP.md).

```json
{
  "version": 1,
  "storageDir": ".tasks",
  "defaultStatus": "todo",
  "readyStatuses": ["todo"],
  "statuses": {
    "todo": { "terminal": false, "color": "cyan" },
    "in_progress": { "terminal": false, "color": "yellow" },
    "review": { "terminal": false, "color": "blue" },
    "done": { "terminal": true, "satisfiesDependencies": true, "color": "green" },
    "cancelled": { "terminal": true, "satisfiesDependencies": false, "color": "gray" }
  },
  "output": { "format": "text", "defaultLimit": 20, "maxBytes": 16384 }
}
```

Названия статусов произвольны. Правила используют свойства статуса, а не строки
`done` или `cancelled`. `satisfiesDependencies` по умолчанию false и может быть
true только для конечного статуса. Начальный и доступные для захвата статусы
должны существовать и быть неконечными.
`color` необязателен: `black`, `red`, `green`, `yellow`, `blue`, `magenta`,
`cyan`, `white`, `gray`, `none`. Цвет применяется во всех представлениях статуса.

## 4. Задачи и связи

Карточка: `version`, `id`, `title`, `description`, `status`, `group`, `tags`,
`parentId`, `dependsOn`, `assignee`, `summary`, `createdAt`, `updatedAt`,
`createdBy`, `updatedBy`, `revision`, `comments`, `logs`.

- Единственный числовой ID от 1, назначаемый под общей блокировкой как `max(id) + 1`.
  Пропуски не заполняются; ID и ссылки в JSON — числа, имя файла — `<id>.json`.
- Старые UUID-документы переносятся явно через `migrate`, со всеми ссылками и контекстом.
  Исходные файлы сохраняются; прерывание миграции допускает продолжение.
- Создание, получение, изменение, назначение, снятие назначения, смена статуса.
- Одна основная группа и набор тегов; фильтры по статусу, группе, исполнителю,
  родителю, тегу и тексту.
- Один родитель и произвольная вложенность. Родительство описывает декомпозицию
  и само по себе не создаёт блокирующую зависимость.
- `A dependsOn B` означает, что B блокирует A. Обратные связи вычисляются.
- Запрещены отсутствующие ссылки, самоссылки и циклы в обоих графах.
- `blockedBy` вычисляется по текущим статусам прямых зависимостей.
- Отмена зависимости не удовлетворяет связь. Переоткрытие пересчитывает блокеры.
- Успешное завершение задачи с текущими блокерами отклоняется. Ранее закрытые
  зависимые задачи автоматически не переоткрываются.
- `list --ready`: задачи в `readyStatuses`, без исполнителя и с выполненными
  зависимостями.
- `claim` атомарно назначает текущего автора свободной доступной задаче. Статус
  сохраняется либо меняется в той же операции через `--status`.
  Из нескольких конкурирующих захватов успешен один.
- `release` доступен исполнителю; `--force` позволяет оркестратору снять чужое
  назначение. `assign` — явное назначение оркестратором.
- `--if-revision` проверяет ранее прочитанную версию документа.

## 5. Комментарии и отчёты

`comments` и `logs` — словари по уникальным ID внутри JSON задачи. У записи есть
собственный ID, ID задачи, автор, время и многострочный `body`.
Отчёт также имеет `kind`, однострочный `title`, многострочное короткое `summary`
и необязательный `sessionId`.

Типы отчётов: `progress`, `decision`, `execution`, `error`, `summary`.
Записи добавляются целиком. Добавление комментария или отчёта обновляет
`revision`, `updatedAt` и `updatedBy` того же документа задачи.

Хранение объединено, выдача остаётся выборочной:

- `get` — карточка и количество записей; `get --full` — весь контекст.
- `description` / `summary` — только нужный многострочный текст.
- `comment list` / `log list` — страницы с кратким контекстом.
- `comment get` / `log get` — полная запись.
- `log search` — отчёты с искомой подстрокой, номером первой подходящей строки
  и числом подходящих строк. Полный текст читается через `log get`.

## 6. Многострочный ввод и вывод

Обычный ввод — аргумент либо stdin через `--stdin`. Файловые параметры остаются
необязательным источником текста. CLI не требует сохранения отчёта во внешний файл.
У файлового параметра значение `-` также означает stdin.
Два источника одного поля и повторное использование stdin в одной команде запрещены.

CRLF/CR нормализуются в LF. Пустые строки, завершающие переносы и отступы
сохраняются. Хранимые Markdown-массивы не сортируются. Текстовый режим выводит
Markdown с реальными переносами, сохраняя списки и кодовые блоки.
Непечатные управляющие символы отображаются видимыми escape-последовательностями.

По умолчанию используется текстовый режим. `--format json` возвращает один
структурированный ответ; многострочные поля в нём остаются массивами строк.
Текстовый режим использует таблицы, рамки, деревья, Markdown и цветовые статусы.
Список задач разделяется на группы с отдельными таблицами или карточками;
задачи без группы имеют отдельную секцию. Пустые группы скрыты.
Внутри группы задачи идут по ID. JSON остаётся плоским списком.
`--color auto|always|never` управляет цветом; JSON всегда свободен от ANSI.
Ширина терминала учитывает Unicode. Блокировка показывается отдельно от статуса.

## 7. Контракт CLI

Основные команды:

```text
init
config get
group list
migrate [--actor ...]
create [title] [--title ...] [--stdin] [--group ...] [--parent ...] [--depends-on ...]
list [--all] [--ready] [--status ...] [--group ...] [--assignee ...]
get <id> [--full] [--fields id,title,status,summary]
description <id>
summary <id>
update <id> ... [--if-revision N]
status <id> <status>
assign <id> <actor>
claim <id> [--status ...]
release <id> [--force]
deps add/remove <id> <dependency-id>
links <id>
tree <id> [--depth N]
comment add/list/get ...
log add/list/get/search ...
validate
```

Для записи автор задаётся `--actor` или `TASKS_ACTOR`.
JSON-успех: `{ "ok": true, "data": ..., "meta": ... }`.
JSON-ошибка: `{ "ok": false, "error": { "code", "message", "details" } }`.
Коды завершения: 0 — успех, 2 — ввод/конфиг, 3 — не найдено,
4 — конфликт/блокировка, 5 — повреждение данных/ввод-вывод/выполнение.

Списки используют `--limit` и `--cursor`, привязанный к фильтрам. Задачи идут
по возрастанию ID; комментарии и отчёты — от новых к старым.
Это страницы актуальных данных, а не изолированный снимок на время всего обхода.

`list` по умолчанию выбирает все незавершённые задачи (`terminal: false`), включая
заблокированные. `--all` включает конечные статусы, явный `--status` выбирает только
заданный статус и переопределяет фильтр незавершённых. Все остальные фильтры
объединяются условием И. Блокировка отображается отдельной отметкой с ID зависимостей.

Для `list` нет ограничения количества по умолчанию: размер страницы определяется
байтовым бюджетом или явным `--limit`. `--all` совместим с `--limit` / `--cursor`.
Большой список показывает «показано N из M» и продолжение. Если открытых задач нет,
выводится подсказка истории `list --all`; пустая выборка по фильтрам имеет отдельное сообщение.
Списки групп, комментариев и отчётов используют `output.defaultLimit`; их `--all`
выдаёт весь ответ в бюджете, несовместим с `--limit` / `--cursor` и при превышении
возвращает ошибку.

`--max-bytes` ограничивает фактически сериализованный UTF-8 ответ. Списки
уменьшают страницу, сохраняя продолжение. Слишком большая неделимая запись
даёт `RESPONSE_TOO_LARGE`; JSON не обрезается как строка.

Ограничения: название 1024 байта, описание 256 КиБ, саммари 4096 байт,
комментарий 64 КиБ, отчёт 256 КиБ UTF-8. JSON задачи целиком — до 16 МиБ;
проверка выполняется до записи, поэтому успешная операция не создаёт
нечитаемый для CLI документ.

## 8. Хранение и конкурентность

```text
tasks.config.json
.tasks/
  <task-id>.json             # задача, comments и logs вместе
.tasks-runtime/              # блокировки, временные записи, резервные копии миграции
```

Каждая постоянная запись имеет версию схемы. Словари по ID сериализуются
детерминированно. Содержимое `.tasks-runtime` исключено из Git.

Общая короткая блокировка охватывает чтение актуальных задач, проверку revision,
изменение, проверку графа и атомарную публикацию одного файла. Это защищает
и от гонки при добавлении двух зависимостей, которые вместе образовали бы цикл.
Ожидание stdin выполняется до блокировки.
Граф читается один раз за изменение; ссылки разрешаются из этого снимка.
Карточка читается по имени файла, вместе только с родителем и прямыми зависимостями.

Запись публикуется через подготовленный и синхронизированный временный файл
на той же локальной файловой системе. После прерывания процесса видна старая
либо полная новая версия. Блокировка имеет контроль живости и восстановление
после устаревания.

Git объединяет независимые задачи. Параллельное изменение одной задачи,
включая её комментарии и отчёты, может потребовать разрешения конфликта.
После слияния `validate` проверяет весь документ, все записи и граф связей.
Для создания задач из нескольких worktree используется общее хранилище:
независимые копии могут создать одинаковый ID, что приводит к Git-конфликту одного файла.

## 9. Приёмка

1. Оркестратор создаёт frontend/backend, подзадачи и зависимости.
2. Backend блокирует frontend до успешного завершения.
3. Описание, комментарии и отчёты реально находятся в одном JSON задачи.
4. Ввод через stdin сохраняет абзацы, пустые строки, отступы и Unicode.
5. CLI выводит многострочный текст, а названия с переносами отклоняет.
6. Два агента не могут одновременно захватить одну свободную задачу.
7. Параллельное добавление контекста сохраняет все записи и обновляет revision.
8. Циклы и устаревшие изменения отклоняются без изменения данных.
9. Прерывание записи не повреждает JSON; устаревшая блокировка восстанавливается.
10. Семантически некорректное Git-слияние обнаруживается проверкой.
11. Пакет собирается и проходит проверку установки из npm-архива.
12. ID от 1 уникальны при конкурентном создании, растут от максимума и используются во всех ссылках.
13. Цветные и бесцветные ответы сохраняют содержание; JSON не получает ANSI-коды.
14. Пагинация учитывает ANSI-байты, а оформление — ширину терминала и Unicode.
15. Рабочий список скрывает конечные статусы, сохраняет группы и продолжается по бюджету без пропусков; `--all` и явный `--status` позволяют читать историю.
16. Цвета статусов задаются конфигом, сохраняя семантику и чистый JSON.
17. Каждая команда имеет доступную без проекта справку с примерами и аргументами.
18. Миграция сохраняет исходники и контекст и возобновляется после остановки на границах публикации.
