# Архитектура Relay

[Техническая библиотека](README.md) → Архитектура

## Режимы и границы

- **local:** один проект с `.relay/config.json` и базой `.relay/tasks`.
- **workspace:** `relay.workspace.json` объединяет независимые проектные базы.

Режим задаёт область работы, транспорт — способ доступа. CLI в local вызывает Core
напрямую либо REST API. Рабочие операции CLI в workspace проходят через сервер.
MCP и Web всегда используют API. Workspace с одной записью остаётся workspace.

```text
CLI local ──────────────────────────────── Core → проект/.relay/tasks
CLI HTTP ─┐
MCP ──────┼── REST SDK → Relay Server ──── Core → A/.relay/tasks
Web ──────┘                         └──── Core → B/.relay/tasks
```

У сервера один HTTP-listener. Реестр перечитывается перед операциями; каждый запрос
имеет собственный неизменяемый выбор проекта. Глобального активного проекта нет.

## Владельцы

| Область                    | Ответственность                                                     |
| -------------------------- | ------------------------------------------------------------------- |
| `apps/cli`                 | Команды, аргументы, файловый ввод, представления терминала          |
| `apps/server`              | Пользовательский запуск сервера, окружение, остановка, поставка Web |
| `apps/mcp`                 | MCP-протокол, инструменты, бюджет и форма ответов                   |
| `apps/web`                 | React SPA, маршруты, выбор проектов, доска и редактор               |
| `apps/playground`          | Демонстрационные local и workspace                                  |
| `packages/core`            | Правила задач, JSON-хранилище, ревизии и блокировки одной базы      |
| `packages/project-runtime` | Конфигурации, реестр, разрешение путей и адаптеры CLI/MCP           |
| `packages/server-runtime`  | NestJS/Fastify, каталог проектов, REST, OpenAPI, SSE и статика      |
| `packages/contracts`       | Переносимые DTO без Node.js/Nest/React                              |
| `packages/rest-sdk`        | Сгенерированный клиент общего API                                   |

Межпакетные импорты проходят через публичные `exports`. Приложения не импортируют
исходники друг друга. Сервер вызывает Core напрямую, MCP использует SDK.
Приватные workspace-библиотеки бандлятся в публичные npm-дистрибутивы.

## Конфигурация

CLI и сервер используют общий локатор: `--config`, затем `RELAY_CONFIG`, затем
поиск вверх от cwd. В ближайшем каталоге `relay.workspace.json` имеет приоритет
над `.relay/config.json`. Факт существования одной папки `.relay` режим не определяет.
Относительные пути разрешаются от файла конфигурации.

Подробности: [CONFIGURATION.md](../reference/CONFIGURATION.md).

## Серверные контексты

`ProjectCatalog` в `packages/server-runtime/src/modules/workspace` владеет выбором
зарегистрированной базы и операциями реестра. `ProjectContext` фиксирует путь и
идентичность проекта. Request-scoped `WorkspaceService` передаёт выбранный контекст
существующим контроллерам задач, комментариев, логов и общих запросов.

`GET /api/v1/server` и `GET /api/v1/projects` возвращают режим, список проектов и
`defaultProject` для local. Проектные запросы используют
`/api/v1/projects/:project/...`. Сервер принимает ключ реестра или `projectId`.
Маршрутизация сохраняет поток HTTP/SSE и переиспользует единый набор контроллеров.
В local те же операции доступны непосредственно под `/api/v1`; workspace требует
явного проекта. OpenAPI описывает оба варианта с уникальными `operationId`.

Задачи адресуются парой проект + ID: у нового канбана ID из 8 символов, у прежнего — число.
При `init` проект получает ID из 8 символов; старые UUID остаются допустимыми.
Каталог не объединяет базы и не проксирует URL из проектных конфигов.
Недоступный проект отмечается отдельно; остальные регистрации доступны.

## SSE и изменение реестра

`EventsService` управляет отдельным наблюдателем для каждого проектного конфига.
События мутаций и изменения файлов доставляются только его подписчикам. После
удаления или перенаправления регистрации ресурсы предыдущего проекта освобождаются.
Остановка сервера завершает наблюдатели, таймеры и потоки.

Конфигурация и хранилище перечитываются. `fs.watch` дополняется периодической сверкой,
SSE поддерживается heartbeat. После восстановления соединения клиенты перечитывают REST.

## Web: Unit Architecture

Веб-приложение имеет общий каркас `compositions/layouts/project` и независимые экраны
обзора, паспорта, планов, доски, знаний, работы и проверок, релизов, истории.
`app/router` задаёт вложенные маршруты; каркас выводит `Outlet`. `domains/lifecycle`
владеет проектной моделью, адаптерами REST, SWR и синхронизацией. Общие сценарии чтения
документа, редактирования, списка связанных задач и контекста задачи находятся в
`compositions/widgets`. Доска является одним экраном приложения.

Профиль React SPA действует в `apps/web/src`, фасеты — `index.ts` и `lazy.ts`.

- `compositions/screens/relay` получает workspace, связывает URL и выбор проекта,
  подключает `ProjectScope`, синхронизацию и доску.
- `domains/workspace` адаптирует серверный контекст и предоставляет SWR-хук реестра.
- `domains/project` владеет настройками проекта и областью `ProjectScope`.
- `domains/tasks` получает ID проекта в каждой операции; GET-ключи, мутации и черновики
  разделены по проектам.
- `infra/tasks-api` создаёт неизменяемые проектные HTTP-клиенты над SDK.
- `infra/workspace-events` разделяет соединения только между подписчиками одного проекта.
- `app/router` подключает готовую композицию. URL имеет вид `/projects/:project/tasks/:id`.

Поздний ответ предыдущего проекта остаётся в его кеше. Переключение перемонтирует
проектную область и освобождает её подписки. Markdown-ссылки и прямые адреса учитывают
проект. Новые TSX создаются локальным генератором; команды записаны в `apps/web/GENERATION.md`.

## Хранение и операции

Универсальные отношения принадлежат `packages/core/src/application/graph`; схемы —
`domain/entity-graph.ts`, хранение — `storage/graph.ts`. Адаптер каталога соединяет
существующие сущности, новые отношения сохраняются в `relations` рядом с конфигом:
отдельные текущие записи, события и квитанции; WAL восстанавливает составную запись,
производные индексы ускоряют адресный обход. V1 переносится явно через graph migrate.
Предметные политики отделены от механизма. Прежние ссылки пока являются
проекциями своих владельцев. [Покрытие](implementation/relations.md),
[контракт графа](../reference/GRAPH.md).

`packages/core/domain/project` описывает типизированные документы жизненного цикла.
`application/project` владеет ссылками, приёмкой, снимками, прогрессом и поручениями.
`storage/project` сохраняет отдельные JSON в `project` рядом с проектным конфигом,
под общей блокировкой с задачами. Файл содержит поля, ревизию, авторство и события;
контрольная точка дополнительно содержит снимок ревизий. Чтение согласует задачи
и проектные записи в одной критической секции. API описывает эти же схемы, SDK
генерируется из OpenAPI. Поле `kind` задаёт конкретный вид документа.

SSE наблюдает оба каталога. Версия доски учитывает проектные документы: изменение
этапа или контекста задачи инвалидирует фильтры и счётчики. Workspace не имеет
собственных планов, паспорта или других продуктовых данных.

Новая продуктовая модель принадлежит `packages/core/src/application/product` и хранится
отдельно в `.relay/product`. Она содержит паспорт, фичи, сценарии, приложения, составы
и документы. Markdown кодируется массивами строк на диске; DTO передаёт строки.
Подробности: [состояние продукта](implementation/product.md) и [контракт](../reference/PRODUCT.md).

Доски принадлежат `packages/core/src/application/boards`, схемы — `domain/board.ts`,
хранение — `storage/boards.ts`. Контейнер `boards/<slug>/` расположен рядом с конфигом,
содержит `board.json` и `tasks/`. Init создаёт системные доски; создание приложения
публикует его запись и доску через долговечное намерение с восстановлением под общей
блокировкой. [Контракт хранения и REST](../reference/BOARDS.md).
Web читает доски через `domains/boards`, показывает их в каркасе проекта и на экране
`project-board`. Прежнее хранилище задач продолжает обслуживать прежний канбан;
новая модель принадлежит `application/board-tasks` и `storage/board-tasks.ts`.
Перенос файлов и порядка публикуется через долговечное `kanban-pending.json` с восстановлением.
Точный контракт — [канбан](../reference/KANBAN.md).

`domains/board-tasks` владеет адаптацией SDK, кешем, согласованной подгрузкой и SSE.
Общий pathless-маршрут `boards/:boardSlug`/`tasks/:id` сохраняет фон доски при открытии
модального окна. Пустая задача создаётся до перехода; первоначальный ответ заполняет
кеш редактора без обязательного GET. Генерируемые ID содержат букву и различимы
с числовыми задачами прежнего канбана. Технические helpers коллизий и клавиатуры
обоих канбанов принадлежат `ui/kanban-dnd`; предметные операции остаются у доменов.

<a id="атомарность-и-конкурентность"></a>

Один JSON в `.relay/tasks` содержит задачу, комментарии и отчёты. Многострочные тексты
сохраняются массивами строк. Core проверяет схемы, граф, автора и ревизии. Изменения
выполняются под блокировкой выбранного хранилища с атомарной публикацией файла.

`.relay/runtime` содержит временные данные и исключается из Git. Workspace использует
собственную блокировку реестра. Реальные пути обеспечивают общую блокировку при доступе
к одной базе через разные пути. Разные worktree могут обращаться к общему серверу,
сохраняя независимые копии кода.

## Проверка и поставка

`pnpm run check` проверяет форматирование, ссылки, типы и тесты. Web дополнительно
проверяется в собственном headless-браузере через agent-browser. Сборка проходит по
графу Turbo. SDK обновляется только генератором из OpenAPI.

`pnpm run package:check` создаёт отдельные архивы CLI, Server и MCP, устанавливает их
независимо и выполняет сквозные сценарии local/workspace. Web принадлежит серверному
дистрибутиву. [Публикация локально и через CI](../development/RELEASING.md).
