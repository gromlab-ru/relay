## Что хранить в Git

Обычно в репозиторий добавляются:

- `.relay/config.json` — процесс и настройки проекта.
- `.relay/tasks/*.json` — задачи, комментарии и отчёты.
- `.relay/project/` и `.relay/product/` — жизненный цикл и продуктовая память.

Если настроен другой `storageDir`, используйте его путь.
Внутренний `.gitignore` служебного `.relay/runtime` исключает его содержимое:
блокировки, временные файлы и резервные копии миграций остаются локальными.

Выполняйте команды Git в той рабочей копии, в которой хранятся изменения:

```bash
npx @gromlab/relay-cli --local validate
git diff -- .relay
git add .relay/config.json .relay/tasks
git commit -m "Обновить задачи и результаты работы"
```

Relay сохраняет файлы; решение о коммите и его составе принимает участник проекта.
Если ведутся проектные документы и продукт, включайте соответствующие каталоги
в согласованный состав коммита. Для Playground самого Relay действует отдельное
правило: все его `.relay` игнорируются, уже отслеживаемые файлы остаются в индексе.

## Несколько worktree

Каждый Git worktree содержит собственную рабочую копию файлов. Копия `.relay`
в ветке агента не становится общей автоматически.

Для оперативной оркестрации используйте **один сервер с конфигом оркестратора**.
Агенты обращаются к нему по HTTP; все записи появляются в его рабочей копии.
Подробный сценарий: [оркестрация](ORCHESTRATION.md).

Альтернативный прямой доступ на одном хосте:

```bash
npx @gromlab/relay-cli --local --config /work/orchestrator/.relay/config.json list
```

Такие обращения используют одну базу и одну блокировку, независимо от рабочего
каталога кода. В режиме HTTP `config get` показывает серверные пути; с `--local` —
пути выбранного локального конфига.

## Независимые копии и слияние

Разные задачи обычно меняют разные JSON-файлы. Изменения одной задачи, включая
параллельно добавленные комментарии, могут привести к текстовому Git-конфликту.
Локальная блокировка координирует процессы одной базы, а объединение независимых
Git-копий выполняется отдельно.

Особенно важны два случая:

1. Разные копии создали новую задачу с одним числовым ID — конфликтуют один путь
   и ссылки. Нужно согласовать ID задач, имена файлов, `parentId`, `dependsOn`
   и вложенные `taskId` перед проверкой.
2. Изменения разных файлов слились чисто, но образовали цикл зависимостей.

После слияния выполните:

```bash
npx @gromlab/relay-cli --local validate
```

Проверка охватывает документы, записи и весь граф. Чистое текстовое слияние само
по себе не подтверждает корректность задач. Для осмысленного удаления одной
зависимости предусмотрена `deps remove`; оставшиеся связи сохраняются.

## Резервная копия

Для согласованного снимка остановите сервер и процессы, изменяющие выбранную базу.
Сохраните конфиг, весь каталог `storageDir`, проектные и продуктовые документы,
затем проверьте восстановленную копию
через `--local --config <путь> validate`. При другом расположении конфига проверьте
относительный `storageDir`.

Core рассчитан на локальную файловую систему с атомарным `rename` и hard link.
Документ ограничен 16 МиБ; логи подходят для кратких отчётов о работе.
Подробности гарантий: [архитектура](../ARCHITECTURE.md#атомарность-и-конкурентность).

Далее: [формат JSON](../reference/FORMAT.md), [миграция](MIGRATION.md),
[ошибки целостности](../reference/ERRORS.md).
