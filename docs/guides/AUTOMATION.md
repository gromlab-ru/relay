## Машинный вывод

```bash
npx @gromlab/tasks-cli list --ready --format json
npx @gromlab/tasks-cli get 1 --fields id,status,assignee,summary,revision --format json
npx @gromlab/tasks-cli overview --format json
```

Успех содержит `ok: true` и `data`; ошибка — `ok: false` и `error` с кодом и сообщением.
CLI возвращает ненулевой код завершения при ошибке. Проверяйте оба признака, сохраняйте
диагностику и используйте `error.code` для выбора действия. Справка и версия текстовые.

Выбор `--fields` и отдельное чтение `summary`, `description`, `log get` помогают
получить нужный контекст в ограниченном ответе. Markdown в JSON — массив строк.

Полная спецификация: [вывод и пагинация](../reference/OUTPUT.md).

## Чтение всех страниц

`list --all` включает конечные статусы, но не отменяет лимит ответа.
Продолжение определяется `meta.hasMore` и `meta.nextCursor`.
Пример для Bash с установленным [jq](https://jqlang.org/):

```bash
args=(list --all --limit 20 --format json)
while true; do
  if response=$(npx --yes @gromlab/tasks-cli "${args[@]}"); then
    printf '%s\n' "$response" | jq -e '.ok == true' >/dev/null || exit 1
  else
    code=$?
    printf '%s\n' "$response" >&2
    exit "$code"
  fi
  printf '%s\n' "$response" | jq -c '.data.items[]'
  if [ "$(printf '%s\n' "$response" | jq -r '.meta.hasMore')" != true ]; then
    break
  fi
  cursor=$(printf '%s\n' "$response" | jq -r '.meta.nextCursor')
  args=(list --all --limit 20 --format json --cursor "$cursor")
done
```

При продолжении повторяйте все фильтры, включая `--all`. Курсор непрозрачный.
Для списков групп, комментариев и отчётов `--all` имеет другой смысл: весь результат
одним ответом в пределах байтового бюджета, без `--limit` и `--cursor`.

CLI читает актуальные данные; постраничный обход не является транзакционным снимком
на весь цикл. У REST-доски отдельный контракт: при смене снимка возвращается
`BOARD_CHANGED`. Оба варианта описаны в своих справочниках.

## Назначения и повторные запросы

Потоком работы управляет оркестратор:

1. Прочитать `overview` и `list --ready`, выбрать подходящую задачу.
2. Назначить исполнителя и статус через `update --assignee --status` с автором оркестратора.
3. Передать конкретный ID субагенту; подключение CLI уже определяется конфигом.
4. Субагент читает контекст и пишет отчёты, а оркестратор контролирует статус и результат.

Субагент не вызывает `claim` и не выбирает работу из очереди самостоятельно.

Для замены полей используйте `--if-revision` из актуального `get`.
Логи и комментарии получают стабильный `--request-id` на одну логическую запись.
После потерянного ответа повторяйте прежние автора, ключ и содержимое.
Создание задачи не имеет ключа идемпотентности: перед повтором проверьте базу.

Готовый сценарий общего сервера — [оркестрация](ORCHESTRATION.md).

## REST и SDK

Сервер предоставляет тот же Core через HTTP. Swagger доступен на `/api/docs`,
OpenAPI 3.1 — на `/api/openapi.json`. Например, при работающем локальном сервере:

```bash
curl --fail-with-body http://127.0.0.1:3000/api/v1/context
curl --fail-with-body 'http://127.0.0.1:3000/api/v1/board?ready=true&limit=20'
```

[Контракт API](../reference/API.md) описывает мутации, `actor`, `ifRevision`,
`requestId`, пагинацию и ошибки. SSE — уведомления об изменениях; после события
или переподключения клиент сверяет данные через REST.

В монорепозитории CLI и web используют приватный `@tasks/rest-sdk`, сгенерированный
из OpenAPI. Он включён в продуктовую сборку, но не является отдельным публичным
npm-пакетом. Внешний клиент может работать по OpenAPI или вызывать установленный CLI.
Порядок изменения внутреннего клиента — [SDK workspace](../../packages/rest-sdk/README.md).
