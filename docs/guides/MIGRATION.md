# Обновление пакета и миграция базы

[Документация](../README.md) → Практические руководства → Обновление

## Версия пакета и версия данных

`npx @gromlab/relay-cli --version` показывает версию CLI.
Текущий формат задачи — `version: 2`, конфига — `version: 1`.
Это независимые версии: новый выпуск пакета не обязательно меняет формат базы.

Пакеты CLI, Server и MCP выпускаются согласованным комплектом с одинаковой версией.
Формат нового продукта имеет собственную дисковую версию и отдельную миграцию.
История несовместимых изменений — [CHANGELOG](../../apps/cli/CHANGELOG.md).

## Обновление

Для явного выбора выпуска укажите версию:

```bash
npx @gromlab/relay-cli@0.6.0 --version
```

Для последней опубликованной версии используйте `npx @gromlab/relay-cli@latest`.
Длительный серверный процесс продолжает использовать загруженную версию до остановки.
Обновляя HTTP-клиенты, остановите прежний сервер и запустите новую версию с тем же
конфигом. Обновляйте используемые CLI, Server и MCP вместе. Совместимость проекта
обозначает серверная возможность `relay-projects-v1`.

## Старые UUID и вложенное хранилище

При `MIGRATION_REQUIRED` выполняется явный перенос выбранной локальной базы:

```bash
npx @gromlab/relay-cli --local --config /work/project/.relay/config.json migrate --actor orchestrator
npx @gromlab/relay-cli --local --config /work/project/.relay/config.json validate
```

Подставьте путь к своему конфигу. Миграция переносит UUID-документы v1 в v2 и прежний
вложенное хранилище в плоский каталог JSON выбранного `storageDir`.
Для действительно старой базы передавайте существующий конфиг, не подменяя путь
новым примером; совместимость настроек сначала сверяйте со справочником.

- Уникальные старые `number` становятся новыми ID.
- При совпадении номер сохраняет более ранняя задача; остальные ID выдаются выше максимума.
- Переносятся родительство, зависимости, вложенные `taskId` и весь контекст.
- Исходники и `ids.json` сохраняются в служебной резервной копии миграции.
- Ответ содержит пути резервной копии и таблицы соответствия.
- Перенос уже существующих документов v2 в плоскую структуру сохраняет поля и ревизии.

Пока существует журнал незавершённой миграции, обычные операции возвращают
`MIGRATION_IN_PROGRESS`. Повторите ту же команду `migrate`: она продолжит публикацию.
На актуальном плоском хранилище повтор миграции возвращает `migrated: 0`.

После переноса проверьте данные и изменения в Git. Внешние ссылки на старые ID
обновляются по таблице соответствия. Для независимой резервной копии см.
[сохранность базы](GIT.md#резервная-копия).

Связанные материалы: [формат хранения](../reference/FORMAT.md),
[команда migrate](../reference/CLI.md#migrate), [диагностика](../TROUBLESHOOTING.md).

## Миграция продукта

`product migrate` переносит старую продуктовую схему отдельно от задач. До запуска
сохраните резервную копию и остановите несовместимые старые клиенты. Гарантии,
команда и ограничения отката: [продуктовое хранение](../reference/PRODUCT.md#json-хранилище).
