# Паспорт продукта

[Сущность «Продукт»](../README.md) → Паспорт

**Адрес:** `/projects/:project/product/passport`.

## Назначение

Дать человеку и агенту первое целостное понимание: что создаётся, для кого, зачем и из каких
возможностей и приложений состоит продукт. Это постоянное описание, не отчёт отдельного плана.

## Состав страницы

- Название продукта и краткий смысл из паспорта; действие «Редактировать».
- Основная область чтения полного Markdown.
- Боковая «Карта продукта»: число реализованных, частично готовых и неготовых фич;
  переход ко всем фичам и к приложениям с общими количествами.
- «Текущий цикл», если есть текущий план: его название, краткий смысл и ссылка «Открыть план».
- Пояснение, что готовность фичи определяется сценариями, а текущая работа учитывается отдельно.

Markdown должен позволять описать назначение, ценность, пользователей и роли, основной путь,
границы, ограничения и термины. Эти разделы рекомендуются автору, но не являются набором
обязательных структурированных полей новой формы.

## Действия и данные

| Действие      | Результат                                       |
| ------------- | ----------------------------------------------- |
| Редактировать | Открыть [редактор паспорта](passport-editor.md) |
| Реализовано   | Каталог `features?status=done`                  |
| Частично      | Каталог `features?status=partial`               |
| Впереди       | Каталог `features?status=none`                  |
| Все фичи      | Полный каталог возможностей                     |
| Приложения    | Каталог приложений                              |
| Открыть план  | Связанная работа текущего цикла                 |

Все три счётчика вычисляются из полной карты фич по [единому правилу](../READINESS.md).
Они не редактируются в паспорте и не копируются из его Markdown. Число приложений включает
приложения без выбранного состава.

## Состояния

Без заполненного паспорта показаны заголовок «Паспорт продукта», пояснение и действие
«Заполнить паспорт». В моках признак этого состояния — пустое `name`; в постоянной модели
нужно корректно обрабатывать также отсутствие записи. Это не ошибка чтения продукта.

Если текущего плана нет, блок цикла отсутствует. Отсутствие плана не делает продукт
незаполненным и не запрещает создавать фичи, приложения или документы.

## Требования перехода

В моках текущий план — первый `kind: plan` со статусом `active`. Для реальной модели
использовать согласованный фокус проекта, учитывая существующий `focusPlanId`; не выбирать
случайную запись при нескольких планах. Это часть D-01/D-06.

Новый паспорт должен иметь один источник данных со старой записью. Поля стадии, режима,
ответственного и следующего действия не должны теряться только потому, что новый экран
показывает цельный Markdown.

## Критерии приёмки

1. Пустой проект предлагает заполнение; успешное сохранение открывает новый паспорт.
2. Счётчики совпадают с каталогом и ведут к нужным фильтрам.
3. Изменение сценария обновляет карту без ручного изменения текста паспорта.
4. Отсутствие плана скрывает только текущий цикл; переход к плану сохраняет продуктовый контекст.
