## Согласованные принципы следующего этапа

### Множественные доски

В каждом проекте раздел «Доски и задачи» содержит сначала «Продукт», затем доски
приложений, последней — «Инфраструктура». Две системные доски создаются при init;
создание приложения создаёт его доску. Продуктовая доска предназначена для общепродуктовой
работы, доски приложений — работы над приложениями, инфраструктурная — CI/CD и окружений.

У каждой доски есть slug в URL и собственный каталог `.relay/boards/<slug>/`:
`board.json` описывает доску, `tasks/` содержит её задачи. Миграция существующих данных
не требуется по решению пользователя: Relay ещё разрабатывается. Сначала реализуются
доски, затем полностью пересматривается модель задач. Отдельный тип эпика отклонён
пользователем: крупная работа выражается обычными задачами и родительскими связями.
Этап досок описан в [досье](../work/multiple-boards/README.md).
Следующий этап реализует [канбан задач](entities/tasks/KANBAN.md): короткие постоянные
ID, ключи с префиксом доски, пустое создание, Markdown и междосочные зависимости.
UI/UX перерабатывается по пользовательской обратной связи; ход и проверки —
в [досье канбана](../work/board-kanban/README.md).

### Связь продукта с работой

- Продукт — постоянная основа понимания. Планы меняют его, задачи исполняют работу,
  релизы фиксируют выпущенные результаты. Фича не принадлежит единственному плану.
- Самостоятельная цель изменения оформляется планом, в том числе с одной задачей.
  Количество задач не определяет необходимость плана. Работа в рамках уже существующей
  цели дополняет её план; маленький план не должен требовать лишних формальностей.
- Область изменения может быть продуктом целиком, приложением, фичей, сценарием
  или конкретным контрактом реализации. Искусственная фича для технической работы не нужна.
- Общепроектная область указывается явно. Связь с приложением сама по себе
  не означает изменение или неготовность всех его фич.
- Не каждый завершённый план требует релиза приложения: настройка проверок PR может
  начать действовать после применения конфигурации. Выпуск фиксируется по смыслу результата.

Явные связи новых канбан-задач с фичами, сценариями и контрактами приложений реализованы.
Связи планов и релизов, наследование области и удобное создание небольшого плана ещё
не реализованы. Нынешнюю связь прежней задачи с планом через этап нужно учесть при переходе.

## Сценарии, которые должна поддержать связанная модель

| Ситуация                          | Ожидаемый процесс                                                                                                           |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Разработка с нуля                 | Описать назначение и ближайшие сценарии → выбрать объём первого плана → реализовать и принять → выпустить                   |
| Доработка через полгода           | Прочитать продукт и выпущенное состояние → определить изменение существующей фичи или новый сценарий → выполнить новый план |
| Баг общей вёрстки                 | План исправления с областью приложения → одна или несколько задач → проверка → включение в выпуск                           |
| CI/CD всего проекта               | План с общепроектной областью → задачи настройки → приёмка процесса и актуальная инструкция                                 |
| Подключение существующего проекта | Восстановить поведение по коду и источникам, обозначить неизвестное → описать исходное состояние → планировать изменения    |

Каталог продукта может быть шире ближайшего плана. Исторические проверки при подключении
проекта не становятся новыми подтверждениями. Автоматический импорт всего проекта не заявлен.

## Обсуждается: инфраструктура

Потребность — постоянный технический контекст: стек, репозитории, окружения, запуск,
CI/CD, выпуск, откат и эксплуатация. Предложение — подраздел «Инфраструктура» внутри
«Продукта», с материалами для продукта целиком и отдельных приложений.

Возможный первый шаг — представление существующих документов с классификацией
и связями. Отдельные структурированные окружения, сервисы и pipeline пока не согласованы.
Общая инструкция «как выпускаем» должна отличаться от записи конкретного релиза.
Раздел ещё не создан; его точный состав и модель требуют решения.

## Открытые решения перед реализацией связей

Варианты универсального графа связей поверх JSON и восстановления контекста агентами
собраны в [предложении](../work/entity-relations/PROPOSAL.md). По поручению пользователя
реализован первый сквозной срез: [правила](RELATIONS.md),
[покрытие и ограничения](../engineering/implementation/relations.md).
Расширенные возможности предложения не означают завершённую реализацию.

1. **Изменение требований:** где хранить предложение, пока оно не принято? Нужно различать
   целевое поведение, подтверждённую реализацию и выпущенную версию. Текущий `basis`
   обнаруживает изменение текста, но не восстанавливает прежнюю редакцию требований.
2. **Приёмка поведения:** как связать проверки и коммит с контрактом приложения
   и сквозным сценарием? Сейчас общая готовность основана на отметках вкладов.
3. **План и выпуск:** как фиксировать объём плана и состав релиза по продуктовым целям,
   сохраняя возможность нескольких выпусков одного плана и общего выпуска разных работ?
4. **Совместимость:** как объединить старые паспорт, требования и знания с новым продуктом,
   сохранить действующие задачи, ссылки и контрольные точки?
5. **Жизненный цикл записей:** нужны ли архивирование, удаление и перенос сценариев?
   Сейчас эти операции отсутствуют; снятие участия приложения уже сохраняет контракт.

Следующая предметная работа — согласовать модель изменения и её связи, затем обновлять
операции, интерфейсы и контекст агентов совместно. Этот документ не задаёт очередь
автоматической реализации всех перечисленных предложений.
