## Состояние реализации

Все перечисленные ниже REST-маршруты и SSE реализованы в `packages/server-runtime`.
Swagger доступен по `/api/docs`, OpenAPI 3.1 — по `/api/openapi.json`.
Операции имеют стабильные уникальные `operationId`; схемы запросов и ответов формируются
из Zod/Core и проверяются HTTP-тестами. Сервер вызывает Core напрямую.
Подробности запуска и интеграции: [apps/server/README.md](../../apps/server/README.md).

## Запуск и транспорт

```bash
npx @gromlab/relay-server --actor human --open
```

Один локальный адрес обслуживает UI и API. Префикс — `/api/v1`.
Серверный дистрибутив включает `dist/web` и отдаёт UI на `/`.
Встраиваемый runtime может работать без статики; в таком случае корень возвращает 404.
Все тела запросов — UTF-8 JSON с `Content-Type: application/json`, лимит 1 МиБ.
Автор мутации задаётся необязательным `actor` в JSON-запросе. Это позволяет CLI
передать своего `--actor` / `RELAY_ACTOR`, в том числе Unicode. Без поля используется
автор серверного `--actor` / `RELAY_ACTOR`, доступный в контексте. `assignee` — отдельное поле.

Успех:

```json
{ "ok": true, "data": {} }
```

Ошибка сопровождается HTTP-статусом и стабильным кодом:

```json
{
  "ok": false,
  "error": {
    "code": "REVISION_CONFLICT",
    "message": "Карточка изменилась после чтения",
    "details": { "expected": 3, "actual": 4 }
  }
}
```

Основные статусы: 400 — аргументы/валидация, 403 — источник запроса, 404 — объект
или маршрут, 409 — конфликт ревизии/порядка/назначения/зависимостей,
413 — размер тела, 415 — Content-Type, 500 — повреждение хранилища или ошибка IO.
Исключения Nest также нормализуются в `ApiFailure`.
Ошибки Core дополнительно содержат `error.exitCode`, чтобы HTTP-клиент CLI сохранял
код завершения локальной операции. `context.capabilities` содержит `cli-http-v1`
и `record-request-v1`; эти возможности появились в пакете 0.3.0.

## Маршруты

### Жизненный цикл

Эти маршруты доступны в local и с префиксом `/api/v1/projects/:project` в workspace.
Все схемы документов и ответов представлены в OpenAPI и сгенерированном REST SDK.

| Метод | Путь относительно `/api/v1`              | Результат                                                                 |
| ----- | ---------------------------------------- | ------------------------------------------------------------------------- |
| GET   | `/project/state`                         | Полный согласованный снимок документов, задач, прогресса и внимания       |
| GET   | `/project/context`                       | Компактная сводка оркестратора со ссылками на детали и полными счётчиками |
| GET   | `/project/tasks/:id/briefing`            | Markdown-поручение работнику                                              |
| GET   | `/project/checkpoints/:recordId/changes` | Изменения после контрольной точки                                         |
| POST  | `/project/records`                       | Создание или ревизионное обновление документа                             |

Запись: `{ fields, actor?, id?, ifRevision?, requestId? }`. `fields.kind` определяет
вид документа. При обновлении `fields` заменяются целиком, `ifRevision` обязателен.
Создание обычных записей поддерживает стабильный `requestId`. Паспорт имеет ID
`passport`, контекст задачи — `task_<id>`. Контрольные точки неизменяемы.

Ошибки ссылок возвращают 404, ревизии и приёмки — 409. Доска и `task-list`
поддерживают фильтры `planId`, `stageId`, `type`. Источник состояния исполнителя
фиксируется явно; отсутствие свежих наблюдений требует проверки.

Рабочий процесс: [жизненный цикл](../guides/LIFECYCLE.md).

### Настройки проекта

`GET /api/v1/context/settings` возвращает `{ name, slug, revision }` в обычном конверте.
`PUT /api/v1/context/settings` принимает `{ name, slug, ifRevision }` и возвращает
подтверждённый снимок. Оба маршрута доступны также под `/api/v1/projects/:project`.
Имя — непустая строка до 120 символов без переносов; пробелы по краям удаляются.
Slug — 2–64 строчные латинские буквы/цифры и одиночные дефисы между частями.
Адрес `local` зарезервирован; занятость проверяется среди подключённых проектов,
включая их ID и ключи реестра. Отказ — 409 `PROJECT_SLUG_TAKEN`.
Конфликт исходной ревизии — 409 `REVISION_CONFLICT`, неверные поля — 400 `VALIDATION_ERROR`.
Повтор пары значений, уже совпадающей с текущей, успешен без новой ревизии.

В `.relay/config.json` добавлен необязательный документ `projectSettings` версии 1
с полями `name`, `slug`, `revision`. Внешняя версия конфигурации остаётся 1.
При init создаются имя каталога и случайный `project-xxxx`. Старые конфигурации
читаются без записи: имя каталога, стабильный производный slug и ревизия 0;
первая изменяющая запись добавляет документ, не меняя ID и остальные настройки.
Сохранение атомарно и защищено общей блокировкой проекта; изменения slug внутри
workspace сериализуются блокировкой реестра. Настройки не переименовывают каталоги,
ключи регистрации или паспорт продукта.
Реестр сервера возвращает актуальное `name` и необязательный `slug`. Если slug
неоднозначен после ручного подключения баз, используйте ID и задайте свободный адрес.

### Режим и проекты сервера

`GET /api/v1/server` и `GET /api/v1/projects` возвращают `{ mode, configPath,
projects, defaultProject }`. Каждая запись содержит `key`, `id`, `name`, `configPath`,
`available` и при недоступности `error`. В local проект по умолчанию выбирается автоматически;
в workspace он равен `null`, проектные операции требуют явного выбора.

`PUT /api/v1/projects/:project` регистрирует инициализированную локальную базу:
тело `{ path?, config?, replace? }`. `DELETE /api/v1/projects/:project` удаляет регистрацию.
Обе операции доступны в workspace и возвращают актуальный серверный контекст.

Все проектные маршруты таблицы ниже также имеют адрес
`/api/v1/projects/:project/...`: например, `/api/v1/projects/a/tasks/1`.
Принимается slug, ключ реестра или ID проекта (новый из 8 символов либо прежний UUID).
Каждый запрос имеет собственный контекст;
SSE обслуживает только выбранную базу. Непроектные `server`, `projects`, `health`
остаются на корне API. OpenAPI описывает оба варианта с уникальными operationId.

В local маршруты таблицы доступны и без проектного префикса. Workspace на такой
запрос возвращает `PROJECT_REQUIRED`. Неизвестный проект — `PROJECT_NOT_FOUND`, HTTP 404.

## Задачи

ID — положительное безопасное целое число. Группа, исполнитель и родитель
могут быть `null`; теги и зависимости — массивы. Markdown (`description`,
`summary`, возвращаемый `body`) представлен массивами строк.

Создание:

```json
{
  "title": "API регистрации",
  "description": ["## Требования", "", "- Добавить POST /users."],
  "group": "backend",
  "tags": ["registration"],
  "parentId": 1,
  "dependsOn": [],
  "assignee": null
}
```

Обязателен только `title`; остальные поля получают значения Core/конфигурации.
`rank`, ID, авторы, даты и ревизии назначаются сервером.

Изменение полей:

```json
{
  "patch": { "summary": ["Контракт готов. Следующий шаг — форма."], "status": "review" },
  "ifRevision": 3
}
```

Отправляются изменённые поля. Пустые массивы очищают многострочный текст,
теги и зависимости; `null` снимает группу, родителя или исполнителя.
Пустой patch — ошибка. `PATCH` возвращает компактную сохранённую `TaskCard`.
`GET /tasks/:id` возвращает обёртку с `task` и актуальными связями, блокерами, `ready`.
Комментарии и логи загружаются через отдельные маршруты, а их счётчики входят в карточку.

`ifRevision` у PATCH, claim, release и изменения зависимости необязателен:
без него операция применяется к актуальному документу под блокировкой Core.
При переданном значении несовпадение всегда возвращает 409 `REVISION_CONFLICT`.
Перемещение через `/move` требует ревизию. UI передаёт её при сохранении редактора.

## Порядок и назначения

Перемещение:

```json
{ "status": "review", "beforeId": 9, "ifRevision": 4 }
```

Поставить карточку перед задачей 9 в колонке review. `beforeId: null` означает
конец полной колонки. Сервер проверяет целевую карточку, ревизию и ограничения
и атомарно сохраняет статус и порядок. Порядок выдаётся сервером; клиент не
сравнивает и не вычисляет рациональные значения `rank` самостоятельно.

Захват:

```json
{ "ifRevision": 4, "status": "in_progress" }
```

`status` необязателен. Задача должна быть свободной, находиться в `readyStatuses`
и иметь удовлетворённые зависимости. Исполнителем становится автор запроса.
Release принимает `{ "ifRevision": 5 }`; снятие чужого назначения требует явного
`force: true`. Release сохраняет статус.

Успех зависимости определяется `satisfiesDependencies`. Отмена не равна успеху.
Изменение статуса сохраняет исполнителя; завершение детей автоматически не
закрывает родителя. Авторитетные проверки выполняются в Core под блокировкой.

## Списки и пагинация

API доски по умолчанию включает все статусы. Фильтры `status`, `group`,
`assignee`, `tag`, `search`, `ready`, `blocked`, `unassigned`, `ungrouped` объединяются через И.
Boolean-параметры передаются как `true`/`false`. Поиск задач включает ID, название,
описание и summary без учёта регистра. Группы и исполнители сравниваются точно.

`BoardResponse` содержит `context`, `items`, `total`, счётчики колонок,
списки групп/исполнителей/тегов и `version` снимка. Порядок: колонки по конфигу,
внутри колонки — сохранённый rank с детерминированным разрешением совпадений.
`total` и `counts` относятся ко всем отфильтрованным задачам до пагинации; `counts`
содержит также пустые колонки. Варианты групп, исполнителей и тегов берутся из полного снимка.
`groupCounts: Array<{ group: string | null; count: number }>` содержит полные размеры
групп проекта независимо от любых фильтров и пагинации. Сумма равна числу всех задач
проекта; конечные задачи тоже учитываются. `ungrouped=true` выбирает `group: null`,
`ungrouped=false` — задачи с назначенной группой.
Лимит страницы доски: по умолчанию 200, диапазон 1–500.

**Одинаковая пагинация у доски, комментариев и отчётов:**

```json
{
  "ok": true,
  "data": { "items": [] },
  "meta": { "hasMore": false, "nextCursor": null }
}
```

Вместе с `cursor` повторяются фильтры. Курсор непрозрачный; клиент не разбирает
его формат. При изменении снимка доски между страницами возвращается
409 `BOARD_CHANGED`, клиент начинает чтение заново с ограниченным числом повторов.

История идёт от новых записей к старым, поддерживает `author`, `kind` и буквальный
`search` по телу с учётом регистра; `kind` применим к отчётам.
Лимит страницы истории: по умолчанию 20, диапазон 1–100. Большие записи учитываются
при ограничении ответа; клиенту доступны продолжение и отдельное чтение записи.
Бюджет JSON-страницы истории — 512 КиБ. Сокращённая страница имеет `meta.truncated: true`.
Если одна запись не помещается, ответ 400 `RESPONSE_TOO_LARGE` содержит `details.recordId`
для отдельного чтения и `details.nextCursor` для продолжения после неё (`null`, если история закончилась).
Курсор истории основан на `(createdAt, id)` и сохраняет позицию при добавлении новых записей.

## Записи контекста

Комментарий:

```json
{ "text": "## Проверка\n\nДобавьте сценарий повторного email." }
```

Отчёт:

```json
{
  "kind": "summary",
  "title": "API готов",
  "summary": "Проверены ответы 201 и 409.",
  "text": "## Результат\n\nРеализован POST /users.",
  "sessionId": "api-session-1"
}
```

`text` обязателен и содержит непустой текст. Типы: progress, decision, execution,
error, summary. Добавление увеличивает ревизию задачи и атомарно объединяется
с существующими записями. Оно не заменяет остальные поля документа.

Оба POST принимают `requestId` (1–128 ASCII-символов: буквы, цифры, `.`, `_`, `:`, `-`,
первый символ — буква или цифра). Область ключа — задача и тип записи. Пример:

```json
{ "actor": "agent-1", "requestId": "wave-1-step-2", "text": "Обработчик готов" }
```

Повтор с тем же автором и нормализованным содержимым возвращает исходную запись
с прежним `createdAt` и ID, без изменения revision задачи. Повтор с другим содержимым
или автором даёт 409 `IDEMPOTENCY_CONFLICT`. Ключ детерминирует ID вложенной записи,
поэтому дедупликация атомарна, переживает рестарт и работает также при локальном вызове Core.

## Read models для CLI

`/task-list` возвращает всю отфильтрованную краткую выборку, без описаний и истории,
с порядком `id` или `board` и отдельными `readyIds`. Фильтры: `status`, `group`,
`assignee`, `parent`, `tag`, `search`, `ready`, `all`, `sort`. По умолчанию выбраны
неконечные статусы; поиск совпадает с CLI и не включает ID. CLI применяет свой
байтовый бюджет и курсор к результату. Пагинация `/board` является отдельным контрактом.

`/document` возвращает полный документ с комментариями/логами и краткие прямые связи.
`/markdown?field=summary` или `description` читает только выбранный текст без графа.
`/links`, `/tree`, `/groups` и `/overview` вычисляются в Core. Обзор принимает `rootId`,
`limit` (1–100, по умолчанию 5), повторяемый `reviewStatuses` и использует один снимок.
Дерево содержит плоские `items` с глубиной, `truncated` и `blockedCounts`.

Изменение зависимости выполняется атомарно:

```json
{ "dependencyId": 2, "action": "add", "actor": "agent-1", "ifRevision": 3 }
```

`action` — `add` или `remove`; остальные зависимости сохраняются под той же блокировкой.
`/validation` проверяет все документы и граф проекта.

Лимиты UTF-8: название 1024 байта, описание и тело отчёта 256 КиБ,
summary 4096 байт, комментарий 64 КиБ, JSON одной задачи 16 МиБ.

## SSE

`GET /api/v1/events` возвращает `text/event-stream`; типы событий заданы в Contracts:

- `connected`: `{ projectId }` — соединение установлено, клиент сверяет состояние.
- `heartbeat`: `{ timestamp }` — каждые 15 секунд; сохраняет поток активным при простое.
  Не означает изменения данных и не требует повторных REST-запросов.
- `changed`: `{ source: "api" | "storage", taskIds?, version? }` — данные изменились.
- `workspace-error`: `{ code, message }` — хранилище временно недоступно/некорректно.

Пример:

```text
event: changed
data: {"source":"storage","taskIds":[12]}

```

События — уведомления, а не единственный источник состояния. После разрыва
соединения клиент заново читает REST API. Сервер отслеживает атомарную замену
файлов, изменения из CLI и обновление конфига. На отключение и shutdown
освобождаются подписки и наблюдатели.
Уведомления могут объединяться и дублироваться; гарантии воспроизведения по `Last-Event-ID` нет.
Наблюдатель использует `fs.watch` с объединением событий за 40 мс и восстановительную
проверку раз в 3 секунды. Изменение `storageDir` переключает наблюдение на новый каталог.

## Локальный доступ

Сервер слушает `127.0.0.1`. HTTP Host должен быть локальным; Origin браузера должен
совпадать с origin сервера. Вызовы локальных CLI/MCP-клиентов без Origin разрешены.
Dev-запуск дополнительно разрешает Vite на `http://127.0.0.1:5173` и `http://localhost:5173`.
Лимиты запросов и единый формат ошибок действуют также при наличии SPA fallback.

## Независимый продуктовый API

Семейство `/api/v1/product` и `/api/v1/projects/:project/product` описано в
[справочнике продукта](PRODUCT.md): JSON-хранение с массивами строк Markdown, строковый ввод API, типизированные связи,
автоматическая готовность, ревизии и идемпотентность. Публичные операции также доступны
в OpenAPI с тегом `product`.
