# Обсуждения и история задач

[Канбан](KANBAN.md) · [CLI](CLI.md#task-comment-publish) · [MCP](MCP.md#обсуждения-и-история)

## REST

Корень — `/api/v1/projects/:project/board-tasks/:reference`; local также допускает
`/api/v1/board-tasks/:reference`. Reference — постоянный ID, текущий или прежний ключ.
Ответ — обычный `{ok:true,data:...}`.

| Метод | Путь                 | Результат                                       |
| ----- | -------------------- | ----------------------------------------------- |
| POST  | `/comments`          | Публикация сообщения, первоначальная квитанция  |
| GET   | `/comments`          | Компактная страница сообщений                   |
| GET   | `/comments/:entryId` | Сообщение с полным Markdown                     |
| GET   | `/history`           | Компактная страница событий, включая публикации |
| GET   | `/history/:entryId`  | Полные изменения до/после либо сообщение        |

POST принимает обязательные `title`, `description`, `actor`, `actorRole`, `requestId`.
Title — однострочный непустой текст до 1024 байт; description — непустой Markdown до
256 КиБ UTF-8. Роли: `operator`, `orchestrator`, `worker`. Web передаёт «Оператор»/operator,
агент задаёт собственное имя. Атрибуция не является аутентификацией.

Квитанция: `{id,commentId,action:"comment-publish",revision,requestId}`. Revision — номер
в ленте, а не ревизия содержания задачи. `ifRevision` не нужен; запись не меняет статус,
критерии, updatedAt и ревизию карточки. Публикация допустима в done/cancelled.
Повтор с тем же автором/requestId и содержимым возвращает исходную квитанцию, включая
после переноса задачи. Область повторов общая с операциями канбана: автор + проект.
Правка и удаление сообщений в первой версии отсутствуют.

## Страницы и полные записи

Общие параметры списка: `limit` (20 по умолчанию, 1–100), `cursor`, `after` (номер,
после которого нужны записи), `actor` (точное имя), `action` (тип действия).
Ответ `{items,nextCursor,snapshot}` упорядочен от новых к старым.
Курсор привязан к проекту, задаче, виду ленты, фильтрам и верхней границе снимка;
новые записи не сдвигают страницы. Для новых записей передайте `after: snapshot` без курсора.
Один запрос просматривает максимум 1000 компактных записей: пустая страница с nextCursor
означает продолжение редкого фильтра, а не конец ленты.

Список содержит `id`, `taskId`, `sequence`, `at`, `actor`, `actorRole?`, `action`, `title`,
`operationId`, `revision`, `legacy`, `fields`. ID записи — строковый положительный номер
в ленте конкретной задачи, не короткий ID сущности. At — время UTC, sequence задаёт
однозначный порядок при одинаковом времени. Revision в событии — ревизия карточки.
Полная запись добавляет `changes: [{field,label,format,before,after}]` и `description?`
для сообщения. Format — text/markdown, null означает отсутствие поля, пустая строка —
пустое значение. Изменения критериев адресуются их постоянными ID. OperationId связывает
события составной операции разных задач; это не отдельный публичный ресурс.

История охватывает содержание, статус, доску/ключ/порядок, критерии, цели реализации,
прямые и обратные предметные связи, блокеры и новые операции графа с участием задачи.
Старые графовые события остаются в истории владельца графа и задним числом не копируются.
Неизвестные значения старых событий задач не восстанавливаются: `legacy=true`, changes пуст.
При первой записи старой задачи добавляется `snapshot` исходного состояния.
Открытие окна, локальные черновики и неуспешные записи не создают события успешного действия.

Ошибки: `VALIDATION_ERROR` — неверные поля/курсор; `NOT_FOUND` — задача/запись не найдена
или запрошенное сообщение является другим событием; `IDEMPOTENCY_CONFLICT` — ключ использован
с другим содержимым; `INVALID_DATA` — повреждённое хранилище; `RESPONSE_TOO_LARGE` — лимит записи.

## Хранение и восстановление

В едином формате события и квитанции включены в `operations/{operationId}.json`, а индексы
содержат указатели на них. Отдельных постоянных файлов summaries и receipts нет. Сохраняются
публичные ID/последовательности событий, Markdown, авторство и курсоры. Общий WAL публикует
изменение карточки, связи и историю вместе. [Точный формат](STORAGE.md).
Далее описано совместимое прежнее хранение, которое переносится через `storage migrate`.

Каталог `.relay/task-activity/` расположен рядом с конфигом:

- `<taskId>/events/<sequence>.json` — неизменяемые полные записи;
- `<taskId>/summaries/<sequence>.json` — компактные проекции; при отсутствии читается событие;
- `<taskId>/meta.json` — версия 1 и последний sequence;
- `receipts/<sha256>.json` — отдельные квитанции публикаций;
- `signal.json` — малый сигнал изменения для SSE.

Markdown сообщения и Markdown-значения changes сохраняются массивами строк без потерь.
Служебные файлы не перемещаются между досками. Повреждение/потеря meta новой задачи не
считается пустой историей. Каталог канбана не читает полные записи ленты.

Новая версия файла задачи — 5. Версии 1–4 читаются совместимо, без записи при обычном GET.
При первой предметной записи канбана/публикации происходит атомарное обновление до v5,
с переносом старых событий в ленту и исходным снимком. ID, ключи, ревизии и квитанции
не меняются вследствие технического перехода. Краткие events в файле задачи сохраняются
для совместимого `entity_history`; подробности принадлежат отдельной ленте.

WAL канбана версии 2 содержит задачи, удаления старых путей и файлы ленты. WAL графа
версии 2 содержит также события задач. Старые намерения версии 1 восстанавливаются.
Запись защищена общей блокировкой, файл события ограничен 16 МиБ, WAL канбана — 32 МиБ,
графа — 128 МиБ; лимиты проверяются до публикации. Восстановление завершается до чтения.
Старый исполняемый код не поддерживает запись новой схемы; откат требует совместимой версии.
Ручное редактирование JSON вне Core не обеспечивает достоверное авторство и историю.

SSE наблюдает signal ленты и периодически сверяет его, поэтому сообщения локального CLI
видны Web без изменения ревизии карточки. После подключения Web перечитывает REST.
