# Задачи, контекст и совместная работа

[Документация](../README.md) → Модель задач

В основном процессе задачи выбирает и назначает оркестратор. Он же управляет
связями, статусами и приёмкой. Субагент получает конкретный ID, читает контекст
и сохраняет действия и результаты. Техническая возможность `claim` описана ниже
как часть CLI, но самостоятельный захват не входит в процесс субагента.

## Локальная JSON-база

По умолчанию задача `12` находится в `.tasks/12.json`. В этом файле находятся поля
карточки, описание, связи, комментарии и отчёты. Формат документа — v2; ID задачи —
положительное безопасное целое число. Новый ID равен максимальному существующему плюс один.

Путь базы задаёт `storageDir` относительно `tasks.config.json`. Служебный каталог
`.tasks-runtime` рядом с базой содержит блокировки, временные файлы и резервные копии
миграций. Постоянные документы остаются самостоятельными JSON-файлами.

Точная схема — [формат хранения](../reference/FORMAT.md).

## Статусы

Ключи `statuses` в конфиге задают доступные статусы и порядок колонок доски.
Поведение определяется свойствами статуса:

| Свойство                | Смысл                                                                    |
| ----------------------- | ------------------------------------------------------------------------ |
| `terminal`              | Работа в этом статусе считается конечной и скрывается из обычного `list` |
| `satisfiesDependencies` | Задача успешно выполнена и удовлетворяет зависимости других задач        |
| `color`                 | Оформление статуса                                                       |

В начальном процессе `done` — успешный конечный статус; `cancelled` — конечный без
успеха. Поэтому отмена не разблокирует зависимые задачи. `defaultStatus` задаёт статус
новой задачи; `readyStatuses` — статусы, из которых разрешён захват через `claim`.

## Связи и готовность

- **`parentId` — декомпозиция:** задача является частью другой задачи.
- **`dependsOn` — блокировка:** задача ждёт успешного завершения перечисленных задач.

Родительство само по себе не блокирует работу. Завершение всех детей не закрывает
родителя автоматически. Переоткрытие зависимости пересчитывает блокеры, сохраняя
статусы остальных карточек. В обоих графах запрещены циклы и отсутствующие ссылки.

Задача доступна для `claim`, когда одновременно:

1. Нет исполнителя: `assignee: null`.
2. Статус входит в `readyStatuses`.
3. Все прямые зависимости имеют `satisfiesDependencies: true`.

Именно такую выборку возвращает `list --ready` для отбора работы оркестратором.
Уже назначенная задача имеет `ready: false`, даже если блокеров нет.
Обычный `list` включает также
заблокированные и уже назначенные незавершённые задачи. `links <id>` показывает
текущие блокеры, а [overview](../reference/OVERVIEW.md) помогает выбрать следующий шаг.

## Автор и исполнитель

**Автор** (`--actor` / `TASKS_ACTOR`) отвечает на вопрос «кто записал изменение».
**Исполнитель** (`assignee`) — «кому назначена задача». Например, оркестратор может
назначить задачу `backend-agent`, оставшись автором назначения.

`claim` атомарно назначает задачу текущему автору. `assign` явно устанавливает
исполнителя, в том числе заменяет прежнего. `release` снимает назначение, сохраняя
статус; снятие чужого назначения требует `--force`. Автор — метаданные операции,
а не учётная запись или механизм разграничения доступа.

## Где сохранять контекст

| Поле или запись  | Что хранить                                                     |
| ---------------- | --------------------------------------------------------------- |
| `description`    | Требования, ограничения и критерии готовности                   |
| `summary` задачи | Актуальное состояние и следующий шаг; заменяется через `update` |
| `comment`        | Вопросы, замечания и обсуждение                                 |
| `log`            | Ход работы, решения, проверки, ошибки и итог сессии             |
| `summary` отчёта | Краткое содержание конкретного отчёта для чтения списка         |

Markdown хранится массивами строк, включая пустые строки и отступы.
`get` показывает карточку и счётчики записей; `get --full` включает весь контекст.
Большую историю можно читать выборочно: `comment list/get`, `log list/search/get`.

## Ревизии и параллельные изменения

`revision` относится ко всему документу. Добавление комментария или отчёта также
увеличивает ревизию. Переданный `--if-revision` защищает изменение от записи поверх
нового состояния. При конфликте сначала перечитайте карточку и согласуйте изменения.

Операции Core проверяют актуальные данные под общей блокировкой базы и атомарно
публикуют JSON. Из конкурирующих захватов свободной задачи успешен один.
Логи и комментарии допускают повтор с тем же `requestId`, автором и содержимым.

Эти гарантии действуют для одного хранилища. Для нескольких worktree используется
[общий сервер](../guides/ORCHESTRATION.md); правила объединения независимых копий
описаны в [руководстве по Git](../guides/GIT.md).
