# ТЗ: интеграция планов и релизов с бекендом

**Цель:** подключить готовые разделы Web к постоянным данным Relay вместо локальных
примеров. Сохранить текущий UI и сценарии, без нового редизайна.

Предметные правила: [планы работ](PLANS-SPEC.md), [самостоятельные релизы](RELEASES-SPEC.md),
[прогресс](PROGRESS-SPEC.md). Это задание следующего этапа, а не описание готового бекенда.

## 1. Модель и хранение

- Добавить в Contracts/Core отдельные сущности плана работ, этапа и релиза с ID,
  ключами, проектом, ревизиями и историей. Использовать действующее единое хранилище.
- Этап содержит ссылки на существующие задачи; релиз — ссылки на планы целиком.
  Релиз не является типом плана и не имеет собственных этапов/задач.
- Сохранить поля готового UI. Заголовки — одна строка, краткие описания — обычный текст,
  полные описания и итоги — Markdown; в JSON Markdown хранится массивом строк.
- Существующие проекты и задачи должны продолжить работать. Изменение формата требует
  явной возобновляемой миграции. Демоданные браузера не импортировать автоматически.

## 2. Предметные операции

- **Планы:** список, чтение, создание, редактирование, управление этапами и их порядком,
  включение/исключение задач, начало, завершение с итогом, отмена.
  Статусы: «Черновик», «В работе», «Завершён», «Отменён».
- **Релизы:** список, чтение, создание с выбором планов, изменение состава и реквизитов,
  планирование, отмена и явная фиксация выпуска. Статусы: «Запланирован», «Выпущен», «Отменён».
  Незавершённые планы можно включить в запланированный релиз; выпуск требует готовности
  всего состава и сохраняет неизменяемый снимок результатов, автора и фактическую дату.
- Готовность рассчитывать в Core через предметные обработчики прогресса, а не по загруженным
  карточкам или одному полю `done`. Переходы повторно проверять под блокировкой.
  Действия плана и релиза не должны автоматически менять колонки задач.

До включения обязательного основания начала работы уточнить переход старых задач,
правила переноса между планами и повторного открытия; не вводить их молча из UI-проверок.

## 3. Связи и надёжность

Продуктовые сервисы сохраняют линки, затем **явно вызывают Core для записи/снятия связей**:
план → проект, этап → план, задача → этап (`part-of`), план → область (`affects`),
релиз → проект (`part-of`), релиз → выбранный план (`includes`). Материалы подключать
через существующие операции документов. Контекст читает сохранённый граф.

Одна предметная операция согласует данные, связи, историю и снимок; клиент не синхронизирует
рёбра отдельным запросом. Нужны проверка ревизии, безопасный повтор по requestId и
восстановление после отказа между шагами. Удаление/снятие состава не оставляет висячих связей.

## 4. API и подключение Web

- Добавить предметные REST-операции в server-runtime, обновить OpenAPI и сгенерированный SDK.
  Бизнес-правила общие в Core; CLI/MCP используют те же операции. Точные DTO и URL
  выбрать по действующим соглашениям проекта.
- Заменить источники `planning-demo` и `releases-demo` серверными доменами. Планы,
  задачи выбора, релизы и прогресс читать с сервера; sessionStorage оставить для черновиков.
- Подключить SSE-обновления, состояния загрузки/ошибки, конфликты ревизий и повтор сохранения.
  Фоновое обновление не затирает ввод; выбор не теряется при поиске и смене страницы.
- Каталоги и вложенные списки имеют пагинацию, полное количество и продолжение.
  Полный прогресс не зависит от числа загруженных строк. Изоляция по проекту обязательна.

## 5. Приёмка

План из реальных задач создаётся, изменяется и сохраняется после перезапуска сервера.
Релиз планируется из этих планов; после готовности явно выпускается, а дальнейшие правки
планов не меняют его снимок. Проверены независимость статусов, граф и обратные связи,
конфликты, повтор запросов, отказ/восстановление, пагинация и два изолированных проекта.
Web, REST, CLI и MCP работают с одними данными. Готовый UI, черновики и адаптивность сохранены.
