# Субагент: выполнение назначенной задачи

[К основному алгоритму](../SKILL.md)

## Получить контекст

Оркестратор передаёт конкретный ID, имя автора и рабочий каталог кода.
В каталоге уже доступен конфиг проекта. CLI сам выбирает серверный API по `server.url`
или локальную базу при отсутствии URL. Субагент не устанавливает переменные подключения,
не запускает сервер и не создаёт отдельное хранилище.

Для задачи `12` (замени на полученный ID):

```bash
npx @gromlab/tasks-cli get 12 --format json
npx @gromlab/tasks-cli links 12 --format json
npx @gromlab/tasks-cli log list 12 --limit 5 --format json
```

Прочитай требования, критерии, актуальное summary, исполнителя, статус, блокеры
и замечания. Полные тела нужных записей читай через `log get`/`comment get` по их ID.

## Проверить поручение

- `assignee` совпадает с твоим автором — работай по поручению и текущему контексту.
- `assignee: null` или другой исполнитель — сообщи оркестратору; он корректирует назначение.
- Есть блокеры, задача завершена или поручение расходится с данными — сообщи оркестратору.

У назначенной задачи `ready: false`: это признак доступности **для захвата свободной
работы**, а не запрет исполнения своего назначения. Проверяй реальные блокеры отдельно.

Не вызывай `claim`, `assign`, `release`, `status` и команды изменения зависимостей.
Не переходи к самостоятельному выбору из `list --ready`: следующую задачу выдаёт оркестратор.

## Выполнить работу и записать прогресс

```bash
npx @gromlab/tasks-cli log add 12 --actor backend-agent --kind decision \
  --title "Контракт ошибок" --session-id wave-1 --request-id backend-wave-1-decision-1 \
  --text "При повторном email используем code EMAIL_TAKEN" --format json
npx @gromlab/tasks-cli update 12 --actor backend-agent \
  --summary "Контракт согласован, реализую обработчик; затем проверки 201 и 409" --format json
```

Автор подписывает запись и не задаёт адрес базы. Записывай значимые решения и действия,
а не весь вывод терминала. Добавление лога меняет ревизию задачи; перед защищённым
обновлением summary бери актуальный `revision` через `get`.
Новый шаг получает новый `request-id`, повтор — прежние поля и ключ.

## Передать результат

После фактической проверки запиши итоговый `log --kind summary`:

- Реализованный результат и выполненные критерии.
- Команды проверок и наблюдаемые результаты.
- Ограничения и то, что не проверено.
- Следующий шаг для оркестратора.

Обнови summary задачи и верни оркестратору ID и краткий результат.
Перевод на проверку, завершение и возврат на доработку выполняет оркестратор.
Сам факт добавления итогового лога не меняет статус.

При паузе сохрани частичный результат и блокер. При сетевой ошибке сохрани диагностику
и ключ неподтверждённого отчёта; восстановление сервера организует оркестратор.

См. [формы контекста](WORK_CONTEXT.md) и [обработку ошибок](RECOVERY.md).
