# Ошибки и восстановление

[К основному алгоритму](../SKILL.md)

## Назначение и ревизии

| Ошибка              | Что проверить                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| `TASK_ASSIGNED`     | У назначенного субагента нет шага `claim`; перечитай назначение и сообщи о расхождении оркестратору |
| `TASK_BLOCKED`      | Прочитай `links` и `blockedBy`; назначение не удовлетворяет зависимости                             |
| `TASK_NOT_READY`    | Статус должен входить в `readyStatuses` для свободного захвата                                      |
| `ASSIGNEE_MISMATCH` | Снимается чужое назначение; решение принимает оркестратор, при необходимости используя `--force`    |
| `REVISION_CONFLICT` | Прочитай новое состояние и согласуй patch вместо повтора со старой ревизией                         |

Комментарий и отчёт меняют ревизию всей задачи. После их добавления прежняя
`--if-revision` уже не подходит. Обновляй только относящиеся к поручению поля.
При отсутствии назначения или чужом исполнителе субагент не выбирает другую задачу.

## Потерян ответ на запись

Запрос мог сохраниться до разрыва соединения. Для `comment add` и `log add`
используется `--request-id`: 1–128 ASCII-символов, первый — буква/цифра,
дальше допускаются также `.`, `_`, `:`, `-`.

- Один ключ соответствует одной записи в рамках задачи и типа записи.
- Повтор с тем же автором и нормализованным содержимым возвращает исходный ID,
  `createdAt` и не увеличивает ревизию.
- Для нового шага нужен новый ключ. `session-id` объединяет несколько шагов,
  но не заменяет `request-id`.
- При `IDEMPOTENCY_CONFLICT` сравни поля исходного запроса: автора, тело, тип,
  заголовок, summary и session-id. Не меняй ключ только ради обхода непонятного конфликта.

Пример одного запроса, который разрешено повторить с теми же значениями:

```bash
npx @gromlab/tasks-cli log add 12 --actor backend-agent --kind progress \
  --session-id wave-1 --request-id backend-wave-1-step-1 \
  --text "Контракт готов, реализую обработчик" --format json
```

Без явного ключа CLI создаёт его сам; при неподтверждённом сетевом добавлении
он возвращается в `error.details.requestId`. Сохрани исходные параметры и ключ.
Если ключ неизвестен, сначала проверь историю; новый ключ может создать дубликат.

Чтения и добавления с ключом допускают до двух автоматических повторов при сетевых
ошибках/HTTP 5xx; тайм-аут попытки — 15 секунд. Создание задачи, изменение полей,
назначения и зависимостей автоматически не повторяются. При неопределённом результате
сначала перечитай состояние; у создания задачи нет ключа идемпотентности.

## Сервер недоступен

Субагент сохраняет диагностику и ключ неподтверждённой записи и сообщает оркестратору.
Оркестратор сверяет `server.url` и проект в конфиге, проверяет запуск сервера на этом
хосте и порту. При `SERVER_INCOMPATIBLE` он обновляет и перезапускает сервер.

Для явного восстановления на том же хосте оркестратор может выбрать прямой доступ
к **той же базе**. Повтор предыдущего примера:

```bash
npx @gromlab/tasks-cli --local --config /work/orchestrator/tasks.config.json \
  log add 12 --actor backend-agent --kind progress --session-id wave-1 \
  --request-id backend-wave-1-step-1 --text "Контракт готов, реализую обработчик" --format json
```

Подставь точный конфиг центрального хранилища. Ключ переживает рестарт, поскольку
хранится в ID записи самого JSON-документа. `--local` не выбирает ветку автоматически
и работает также при запущенном сервере. Core использует общую блокировку.

Не убирай HTTP-настройки ради автоматической записи в worktree субагента.
Если путь центральной базы неизвестен, запроси его у оркестратора.

## Другие отказы

| Ошибка                                                 | Действие                                                                     |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `CONFIG_NOT_FOUND`, `LOCAL_ONLY`                       | Уточни URL/конфиг; новый проект и миграция — локальные операции оркестратора |
| `ACTOR_REQUIRED`                                       | Передай автора каждому процессу CLI                                          |
| `TASK_NOT_FOUND`, `LOG_NOT_FOUND`, `COMMENT_NOT_FOUND` | Проверь проект и ID; запись должна принадлежать указанной задаче             |
| `RESPONSE_TOO_LARGE`                                   | Поля, страницы, отдельная запись или больший `--max-bytes`                   |
| `INVALID_CURSOR`                                       | Повтори исходные фильтры либо начни чтение заново                            |
| `STORAGE_BUSY`, `LOCK_LOST`                            | Дождись освобождения базы и перечитай состояние перед новой записью          |
| `DEPENDENCY_CYCLE`, `PARENT_CYCLE`                     | Пересмотри соответствующие связи с оркестратором                             |
| `INVALID_DATA`, `VALIDATION_FAILED`                    | Сохрани диагностику `validate`; согласуй исправление базы                    |
| `MIGRATION_REQUIRED`, `MIGRATION_IN_PROGRESS`          | Оркестратор выполняет или продолжает `--local migrate` с тем же конфигом     |

Независимые Git-копии могут создать одинаковый ID или цикл после слияния.
Для оперативного распределения работы используй один сервер; после Git-слияния
проверь `validate`. Не удаляй JSON или служебные файлы блокировки для обхода ошибки.

См. [конфигурацию](CONFIGURATION.md) и [контекст](WORK_CONTEXT.md).
