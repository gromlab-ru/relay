# Tasks CLI

## Назначение

Tasks — локальная JSON-база для организации потока задач между **оркестратором
и субагентами на одном хосте**. Оркестратор создаёт план, ставит и назначает задачи,
управляет зависимостями и статусами, контролирует и принимает результаты.
Субагент получает конкретную задачу как источник контекста и записывает в неё ход работы.
Человек наблюдает через веб-доску и при необходимости добавляет уточнения.

Пакет `@gromlab/tasks-cli` включает CLI, локальный сервер, REST API и готовую доску.
Отдельный `@gromlab/tasks-mcp` предоставляет общий HTTP MCP-сервер и использует REST SDK.
Сам запуск субагентов выполняет используемый инструмент оркестрации.
Одна задача — один `.tasks/<id>.json`: требования, связи, назначение, комментарии и отчёты.
База сохраняет контекст между сессиями и делает результаты всех субагентов видимыми оркестратору.

## Разделение ролей

| Оркестратор                                                    | Субагент                                                          |
| -------------------------------------------------------------- | ----------------------------------------------------------------- |
| Настраивает проект и запускает сервер, если в конфиге есть URL | Работает из подготовленного каталога с конфигом проекта           |
| Создаёт, выбирает и назначает задачи                           | Получает конкретный ID и своего автора                            |
| Управляет статусами, связями и передачей назначения            | Читает требования, связи, summary и историю                       |
| Проверяет и принимает результат                                | Выполняет поручение, пишет логи, комментарии и актуальное summary |

**Субагент не выбирает себе задачи, не вызывает `claim`, `assign`, `release`
и не меняет статусы или зависимости.** Если задача отсутствует, назначена другому
или заблокирована, сообщи оркестратору. Новую работу назначает он.

## Сначала выбери режим и проект

- Проектный `tasks.config.json`: CLI и MCP работают без имени проекта.
- Реестр `tasks.orchestrator.json`: CLI получает префикс `<проект>` либо `--project`,
  MCP — поле `project`. Имя обязательно даже при единственной записи в реестре.
- Оба приложения принимают `--config` или `TASKS_CONFIG`; при поиске вверх реестр
  имеет приоритет над проектным конфигом в одном каталоге.
- В MCP сначала вызови `projects_list`: он показывает режим и актуальные имена.
  В CLI используй `projects list`. Не угадывай проект по одному числовому ID.
- Оркестратор поддерживает реестр через CLI `projects init/add/remove` или MCP
  `project_register`/`project_unregister`. Субагент использует выданный проект.
- MCP перечитывает реестр без перезапуска. При отсутствии URL он автоматически
  запускает локальный REST API; при явном URL использует готовый API.
- Все агенты подключаются к одному MCP URL, обычно `http://127.0.0.1:3010/mcp`.
  Поручение содержит проект, ID, автора и каталог кода; MCP не требует конфига в worktree агента.

```text
task_get({ project: "backend", id: 12 })
log_add({ project: "backend", id: 12, actor: "backend-agent", requestId: "step-1", text: "Контракт проверен" })
```

При прямом проектном конфиге опусти `project`. Для записи MCP передавай `actor`,
для `comment_add`/`log_add` также обязательный `requestId`. [Контракт MCP](reference/MCP.md).
Дальнейшие CLI-примеры показывают прямой проектный конфиг; при реестре добавляй имя перед командой.

## Подключение CLI

Основной источник подключения — `tasks.config.json`. Пример секции существующего конфига:

```json
{ "server": { "port": 3000, "url": "http://127.0.0.1:3000" } }
```

- Есть `server.url` — CLI сам обращается к API этого сервера.
- Нет `server.url` — CLI выполняет локальные операции через Core.
- Один `server.port` задаёт порт запуска, но не включает HTTP-режим CLI.
- При заданном URL и недоступном сервере возвращается ошибка; запись не уходит в другую базу.

Оркестратор видит URL в конфиге и обеспечивает запуск сервера до выдачи задач.
Он же обеспечивает наличие этого конфига в worktree субагентов на том же хосте.
**Субагенту не нужно задавать URL, переменные подключения или выбирать local/HTTP.**
Он вызывает обычные команды CLI из подготовленного каталога.

Выбор транспорта CLI принадлежит адаптеру, локальные операции и их бизнес-правила — Core.
Флаги и переменные окружения остаются дополнительными переопределениями для специальных
случаев; см. [конфигурацию](reference/CONFIGURATION.md).

## Рабочий цикл оркестратора

1. Определи режим и проект из поручения. Для MCP используй `projects_list` и `project_config`.
   Для CLI проверь версию и прочитай `tasks.config.json`
   или `--local config get --format json`. `init` нужен только для новой базы.
2. Если задан `server.url`, проверь доступность сервера нужного проекта и при необходимости
   запусти `server` с этим конфигом. Команда `server` всегда запускает локальный процесс.
3. Прочитай настроенные статусы и существующие задачи через `overview`/`list`.
   Декомпозируй работу, запиши результат, границы и критерии в `description`.
4. Выбери готовую работу сам. Назначь конкретного субагента и установи рабочий статус
   до делегирования. Для атомарного назначения и статуса можно использовать `update`.
5. Передай ID, имя автора, рабочий каталог кода и критерии результата. Подключение
   уже должно определяться конфигом; агенту не поручается настраивать сервер.
6. Читай отчёты, summary и комментарии. Сам переводи задачу на проверку, возвращай
   на доработку или завершай после фактической приёмки. Родителя заверши отдельно.

В новом проекте пример задачи получит ID `1`; в существующем бери ID из ответа:

```bash
npx @gromlab/tasks-cli create "API пользователей" --group backend --actor orchestrator --format json
npx @gromlab/tasks-cli update 1 --assignee backend-agent --status in_progress --actor orchestrator --format json
```

В примерах используется начальный процесс `todo → in_progress → review → done`.
Для другого процесса используй ключи из конфига.
Подробный порядок: [оркестратор](reference/ORCHESTRATOR.md).

## Рабочий цикл субагента

1. Получи конкретный ID и имя автора от оркестратора. Прочитай `get <id> --format json`.
   При необходимости открой `links`, последние комментарии и отчёты.
2. Проверь соответствие поручению: исполнитель, требования, статус и блокеры.
   У уже назначенной задачи `ready: false` нормально — это поле относится к захвату
   свободной работы, а не к исполнению своего назначения.
3. Выполни поручение. Значимые действия, решения и результаты записывай в `log`;
   актуальное состояние и следующий шаг — в `summary` задачи.
4. Проверь результат и запиши фактически выполненные проверки, ограничения и следующий шаг.
   Передай результат оркестратору; статус и дальнейшее назначение меняет он.

Пример для назначенной задачи `12`; подставь ID и автора из поручения:

```bash
npx @gromlab/tasks-cli get 12 --format json
npx @gromlab/tasks-cli log add 12 --actor backend-agent --kind progress --session-id wave-1 \
  --request-id backend-wave-1-step-1 --text "Контракт готов, реализую обработчик" --format json
npx @gromlab/tasks-cli update 12 --actor backend-agent \
  --summary "Обработчик готов, осталось проверить ошибки" --format json
```

Автор — метаданные записи, а не настройка подключения. Для чтения он не нужен.
Последний пример не подтверждает завершение проверок: итоговый отчёт формируется
после их фактического выполнения. См. [субагента](reference/SUBAGENT.md).

## Модель и контекст

- `parentId` — декомпозиция, `dependsOn` — ожидание успешного завершения.
  Завершение детей не закрывает родителя автоматически.
- `satisfiesDependencies` означает успех, `terminal` — конечность.
  Начальный `cancelled` не удовлетворяет зависимости.
- Автор (`--actor`) подписывает изменение, `assignee` определяет исполнителя.
- `description` — требования; `summary` задачи — текущее состояние;
  `comment` — обсуждение; `log` — история. `--session-id` объединяет записи сессии.
- Пиши через CLI/MCP/API: Core проверяет схемы, граф и ревизии под общей блокировкой.
  Комментарии и отчёты тоже меняют `revision`. Для защищённого обновления summary
  используй свежую `--if-revision` после последней записи.
- Перед паузой сохрани прогресс и следующий шаг; после новой сессии перечитай задачу.
  Передачу другому исполнителю и переоткрытие организует оркестратор.
- Используй `--format json`, проверяй код завершения и `ok`. Большой контекст читай
  выборочно через `--fields`, `log list/get`, `comment list/get`; не загружай всё без необходимости.

Формы отчётов: [контекст](reference/WORK_CONTEXT.md).

## Ошибки и повторы

| Ситуация                                      | Действие                                                  |
| --------------------------------------------- | --------------------------------------------------------- |
| Нет порученного ID, чужое назначение, блокеры | Сообщи оркестратору; не выбирай другую задачу сам         |
| `REVISION_CONFLICT`                           | Перечитай задачу и согласуй обновление своего контекста   |
| `SERVER_UNAVAILABLE`                          | Сообщи оркестратору; не настраивай другую базу в worktree |
| Потерян ответ на добавление                   | Повтори прежний ключ, автора и содержимое в той же базе   |
| `IDEMPOTENCY_CONFLICT`                        | Сравни исходный запрос; новый шаг требует нового ключа    |
| `RESPONSE_TOO_LARGE`                          | Выбери поля/страницу или увеличь `--max-bytes`            |

`--request-id` относится к одной записи в рамках задачи и типа. Без флага CLI создаёт
ключ сам; при неподтверждённом сетевом добавлении он доступен в `error.details.requestId`.
Повтор сохраняет автора и все поля записи. Создание задач, изменение полей и назначений
автоматически не повторяются — сначала проверяется фактическое состояние.

Аварийный `--local --config <центральный-конфиг>` организует оркестратор, сохраняя
ту же базу, автора и ключ повторяемого отчёта. Подробнее: [восстановление](reference/RECOVERY.md).
