# Relay — рабочая память проекта

Relay хранит требования, работу и основания результата. Человек через Web и агент через
CLI/MCP используют одни данные. Действующие области: **Продукт**, **Доски и задачи**, **Связи**.
Обзор, планы, релизы и общая история Web находятся в разработке. У карточки задачи есть
собственные обсуждения и подробная история; прежние операции числовой доски удалены.

## Подключение

Сначала вызови `projects_list` или `relay-cli projects list --format json` и установи
нужный проект. Workspace — реестр независимых баз; в каждом вызове указывай project.
В local проект выбирается автоматически. MCP работает через Server, CLI — через HTTP
или напрямую с Core. Не переключайся на локальную копию после отказа HTTP.
[Запуск и режимы](references/STARTUP.md), [конфигурация](references/CONFIGURATION.md).

## Контекст и модель

`entity_types` / `entities types` объясняет девять видов: project, product, feature,
scenario, application, implementation, board, task, document. `entity_type_get` /
`entities type <kind>` возвращает контракт вида. Ищи через `entities_list`, читай
полное содержание через `entity_get`. Ключи удобны для работы; ID постоянны, прежние
ключи сохраняются как алиасы. Не определяй вид только по префиксу.

`entity_context({ref})` или `graph context <ref>` возвращает отношения и пути включения.
Контекст читает только явно сохранённые связи Core. Продуктовые поля больше не создают
рёбра автоматически; пустой контекст при наличии продуктового линка означает отсутствие
установленной связи, а не исчезновение продуктовых данных. Интеграция всех предметных
операций с записью связей — отдельный этап. Не исправляй это массовой ручной записью без поручения.
Обход по умолчанию полный (`all`); прежнее `context` — совместимое имя без скрытых
ограничений для документов/приложений. Направление, тип и глубина задаются явно.
Проверяй nextOffset/version, boundary и depthLimited; полные тексты читай адресно.
История действующих сущностей (`entity_history`) и связей сохраняется.
[Модель](references/DATA-MODEL.md), [контракты сущностей](references/ENTITIES.md),
[граф](references/GRAPH.md).

## Запись

- Заголовок — одна строка; summary — многострочный обычный текст; описание и инструкция —
  структурированный Markdown. Передавай его напрямую, хранилище само кодирует массивы строк.
- Предпочитай предметные `entity_<kind>_create/update` и `product_*_save`.
  Параметры доступны на верхнем уровне. Прочитай исходную запись перед изменением.
- Каждая запись подписана actor и имеет стабильный requestId. Изменение требует
  прочитанной ifRevision; состав продукта и граф также проверяют версию снимка.
- После потери ответа повтори тот же запрос с тем же ключом. При конфликте перечитай
  запись и согласуй поля, не подставляй новую ревизию к устаревшему содержимому.
- Перед серией записей объясни цель; после перечитай содержимое и связи.
  `product_lint` проверяет структуру, но не доказывает полноту требований.

## Работа на досках

`boards_list`, `board_tasks_list`, `board_task_get/create/update/move/link/links`;
CLI: `boards`, `task list|get|create|update|move|link|links`. Задача получает постоянный
ID и ключ вроде PRODUCT-1; перенос меняет ключ, сохраняя ID и связи.
Колонки: inbox, ready, in-progress, review, done, cancelled. Только done выполняет зависимость.
Родительство задаёт декомпозицию, зависимости — порядок. `readiness=ready` выбирает
работу без блокеров; `completion=unfinished` исключает готовые/отменённые до пагинации.
На продуктовой доске цели — фичи и сценарии продукта; на доске приложения — только
его объявленные реализации; на инфраструктурной доске целей реализации нет.
Несовместимые цели перед переносом снимаются явно. Фича, сценарий и реализация приложения
получают готовность каскадно: задача → активная реализация → её проектная цель.
Если работа есть хотя бы в одной ветке, цель как минимум partial; все активные
реализации и существующие прямые задачи должны быть готовы для done. Без задач — none.
FI приложения включает выбранные SI той же фичи и приложения; проектная фича также
требует готовности всех своих сценариев. Не считай FI выполненной только по её прямым задачам.
Проверку фактического результата выполняет участник до завершения задачи. [Канбан](references/KANBAN.md).

При постановке задачи задавай проверяемые acceptanceCriteria (title, summary,
description) через `board_task_create` или `entity_task_create`. Для существующей
задачи используй `task_criteria_list`, `task_criterion_get/add/update/complete/remove`;
CLI — `task criterion list|get|add|update|complete|reopen|remove`.
Полный Markdown читается адресно. Отмечай completed=true только после фактической
проверки: сохраняются автор и время. Изменение текста снимает отметку. Критерии
не мешают начать работу, но все должны быть выполнены перед done; задача закрывается явно.

## Роли и достоверность

Обсуждение задачи: `task_comment_publish` принимает reference, обязательные title и
description (Markdown), собственное имя actor, actorRole (orchestrator/worker) и requestId.
CLI: `--actor <имя> task comment publish <задача> --role worker --title <тема> --description <Markdown>`.
Публикация не требует ifRevision, не завершает задачу и не подтверждает критерии автоматически.
Сообщения человека из Web подписаны «Оператор».

Читайте `task_comments_list` / `task_comment_get`, хронологию — `task_history_list` /
`task_history_get`; CLI — `task comment list|get`, `task history list|get`.
Списки по 20, nextCursor означает продолжение даже у пустой страницы. Snapshot используйте
как after для новых записей. Полное содержание читайте адресно и проверяйте после публикации.
Старые события без подробностей не позволяют выдумывать прежние значения.

Оркестратор уточняет цель, организует задачи, выдаёт поручения и проверяет общий результат.
Работник выполняет конкретное поручение и сохраняет фактические проверки, ограничения
и следующий шаг в Markdown задачи или связанного документа. Запуск процессов, Git,
тесты и поставка выполняются внешней средой в рамках поручения; Relay их не запускает.
Не выдумывай результаты и не объявляй прежнюю проверку свежей.
