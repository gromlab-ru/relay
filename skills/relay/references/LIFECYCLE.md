# Жизненный цикл проекта

Relay объединяет паспорт, планы, задачи, требования, знания, работу агентов, проверки,
релизы и передачу контекста. Все сведения принадлежат одному проекту. Workspace
содержит только регистрации проектов и позволяет переключаться между ними.

## Разделы приложения

- **Обзор** — текущая цель, прогресс, внимание и следующий шаг; контекст можно скопировать для агента.
- **Паспорт** — назначение, пользователи, границы, ограничения, ответственный, стадия и режим продукта.
- **Планы** — цели, этапы, критерии и приёмка. План можно выбрать текущим фокусом.
- **Доска задач** — общая база задач с фильтрами по плану, этапу и виду работы.
- **Требования и знания** — правила продукта, решения, архитектура и инструкции.
- **Работа и проверки** — попытки исполнения, проверки, приёмка и вопросы.
- **Релизы** — состав версии, коммит, ограничения, откат и установки в окружения.
- **История и передача** — изменения проектных документов и неизменяемые точки продолжения.

Основные маршруты: `/projects/<projectId>/`, `passport`, `plans`, `board`, `knowledge`,
`activity`, `releases`, `history`. Карточка адресуется `/projects/<projectId>/tasks/<id>`.

## Планы и задачи

Создайте план, затем этап с ожидаемым результатом и критериями. На странице этапа
можно связать существующие задачи или открыть создание на доске. Контекст задачи
находится во вкладке **«Проект и результат»**.

У задачи один основной этап. Подзадачи наследуют этап ближайшего родителя, пока
не получили собственный контекст. Явное пустое значение снимает связь. Связи с планом
не заменяют `parentId` и `dependsOn`. Прогресс учитывает листовые задачи; отменённые
показываются отдельно. Принятие этапа требует заключения, завершения его работ и
приёмки зависимых этапов. План завершается после приёмки всех этапов.

Требования и знания выбираются в контексте задачи. Для бага доступны ожидаемое и
фактическое поведение, воспроизведение, версия, окружение, серьёзность и обходное решение.

## Исполнители и подтверждения

Оркестратор читает контекст проекта, назначает задачи и выдаёт готовое поручение.
Работник получает только выбранную задачу, цель плана, этап, ограничения и связанные
документы. Его отчёт содержит результат, коммиты, проверки и ограничения.

Исполнение — отдельная попытка. Состояния: `running`, `succeeded`, `failed`, `cancelled`,
`unknown`. `source` различает ручную запись, сообщение агента и наблюдение runtime.
Среда выполнения может записывать наблюдения через API, CLI или MCP, передавая
`source: "runtime"`, сессию и время `observedAt`. Relay хранит и показывает наблюдения;
запуск процессов принадлежит агентской среде. Через две минуты без наблюдений
работающая попытка помечается как требующая сверки, без автоматического объявления ошибки.

Завершённая попытка не меняет статус задачи. Для повторного исполнения создаётся
новая запись. Флаг `integrated` фиксирует включение результата в общую версию.

Проверка связывается с задачей, этапом, требованием или релизом. Она содержит коммит,
окружение, команду, источник и подтверждение. Приёмка задачи хранит заключение и
ссылки на пройденные проверки; их коммит должен соответствовать коммиту приёмки.

## Хранение и конкурентность

```text
.relay/
├── config.json
├── tasks/
│   └── 1.json
├── project/
│   ├── passport.json
│   ├── task_1.json
│   ├── plan_<id>.json
│   ├── stage_<id>.json
│   └── …
└── runtime/
```

Проектные документы находятся в `project` рядом с проектным конфигом. Каждый документ
содержит версию схемы, ID, ревизию, авторство, типизированные поля и события изменений.
Контекст задачи хранится отдельно от её карточки; существующие базы открываются без миграции.
Чтение отсутствующего каталога `project` возвращает пустое состояние.

Задачи и проектные документы используют общую блокировку. Один документ вместе с
историей сохраняется атомарно. При обновлении передавайте `ifRevision` прочитанной
записи. Несовпадение возвращает конфликт и сохраняет ввод в UI.

Для повторяемого создания обычного документа передавайте `requestId`: тот же автор,
вид и ключ возвращают исходный документ; другое содержание даёт конфликт. Обновления,
паспорт и контекст задачи после неподтверждённого ответа сначала перечитываются.
Поля при сохранении передаются целиком; пропущенные необязательные поля получают
значения по умолчанию. Для изменения прочитайте запись и измените её `fields`.

Контрольная точка сохраняет ревизии задач и документов. Сравнение показывает изменённые,
новые и удалённые записи. Саму точку изменить нельзя: следующая передача создаёт новую.

## CLI

```bash
relay-cli project context --format json
relay-cli project records --kind plan
relay-cli project get passport
relay-cli project briefing 1
relay-cli project changes checkpoint_<id>
relay-cli list --plan-id plan_<id> --stage-id stage_<id>
relay-cli list --type bug
relay-cli project save --actor orchestrator --json '{"fields":{"kind":"plan","title":"Первый выпуск","goal":"Работающий основной сценарий","status":"active"},"requestId":"first-release"}'
```

`project save --file -` читает JSON из stdin. В workspace укажите проект префиксом,
например `relay-cli backend project context`. В local поддерживаются Core и HTTP.

## MCP

Начните с `projects_list`, затем `project_context`. Для чтения документов используйте
`project_records` и `project_record_get`; для изменения — `project_record_save`.
`task_briefing` выдаёт поручение, `checkpoint_changes` — изменения после передачи.
Схемы операций доступны через tools/list. Подробнее: [MCP](MCP.md).
