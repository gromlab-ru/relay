# Модель данных и условия переходов

[Основное руководство](../SKILL.md) · [Все поля из схем Core](RECORDS.md)

## Два вида объектов

**Карточка задачи** имеет числовой ID, `description`, `summary`, статус, исполнителя, связи, комментарии и логи. Она создаётся через `task_create` / `create`; частичная правка — `task_update.patch` / `update`.

**Проектный документ** имеет строковый ID и оболочку с `fields`, `revision`, авторством и историей. Он создаётся и обновляется через `project_record_save` / `project save`. В `fields.kind` находится его тип. Поля при обновлении заменяются целиком.

Паспорт имеет ID `passport`; контекст карточки `12` — `task_12`. Остальные ID выдаются системой, например `plan_` с 32 шестнадцатеричными символами. Получай их из ответов, а не составляй вручную. Ревизии карточки и её контекста независимы.

## Карточка и текстовые записи

| Поле / запись | Назначение                                          |
| ------------- | --------------------------------------------------- |
| `description` | Постановка, ожидаемый результат, требования         |
| `summary`     | Актуальное состояние работы и следующий шаг         |
| `assignee`    | Исполнитель; `actor` подписывает отдельную операцию |
| `parentId`    | Декомпозиция; ссылки только на другие карточки      |
| `dependsOn`   | Зависимости карточек внутри этого проекта           |
| `comment`     | Обсуждение, дополнение, замечание                   |
| `log`         | Прогресс, решение, исполнение, ошибка или итог      |

Комментарии и логи добавляются новыми записями и меняют ревизию карточки. Текстовый `log.kind: "execution"` не создаёт структурированную попытку `run`. `description` и `summary` карточки имеют собственные пределы: 256 КиБ и 4096 байт UTF-8 соответственно.

Статусы карточек задаёт конфиг. `terminal: true` означает конечность, `satisfiesDependencies: true` — успешное завершение, удовлетворяющее зависимости. Отмена может быть конечной, но не успешной. `ready` означает свободную задачу в разрешённом для захвата статусе и с выполненными зависимостями.

## Паспорт, план, этап

### passport

Долгоживущий смысл проекта: `purpose`, `audience`, `scope`, `constraints`, `owner`. `productStage` описывает стадию продукта, `mode` — режим работы. `summary` и `nextStep` объясняют текущее состояние; `focusPlanId` выбирает план ближайшей работы.

Проектный документ паспорта создаётся явно. Defaults, возвращённые обзором пустой базы, не являются подтверждённым описанием существующего продукта.

### plan

Изменение с целью `goal`, объёмом `scope`, ответственным и собственными summary/nextStep. Возможны планы создания, развития, исправления и технического улучшения.

`completed` требует хотя бы одного этапа и приёмки всех этапов плана. `cancelled` сохраняет историю отменённого намерения. Выбор фокуса выполняется через паспорт.

### stage

Часть плана с `outcome`, `criteria`, `order` и зависимостями `dependsOn`. Все зависимые этапы должны относиться к тому же плану; циклы запрещены.

Для `accepted` Core требует:

1. Непустого основания `acceptance`.
2. Приёмки зависимых этапов.
3. Конечных статусов листовых задач этого этапа.

Проверка конечности допускает отменённые карточки. Оркестратор отдельно оценивает выполнение результата и объясняет исключённую работу. Счётчики прогресса различают выполненные, отменённые и открытые задачи.

## Контекст задачи и знания

### task — контекст карточки

`taskId` указывает на уже существующую карточку. `stageId` связывает её с этапом; `requirementIds` и `knowledgeIds` выбирают документы для briefing. `boundaries` и `acceptanceCriteria` задают локальный контракт работника.

Подзадача наследует этап ближайшего предка, пока у неё нет собственного контекста. При создании контекста без `stageId` применяется default `null`: это явное снятие связи. Поэтому при добавлении требований существующей подзадаче передавай нужный этап явно.

`type` различает задачу, функцию, баг, исследование и техдолг. Для бага используй `expectedBehavior`, `actualBehavior`, `reproduction`, `affectedVersion`, `environment`, `severity` и `workaround`. Эти поля хранятся в контексте, а не в `task_update.patch` карточки.

### requirement

Описание ожидаемого поведения и способа проверки. Требование живёт дольше задачи, которая его реализовала. `retired` означает прекращение действия; обновляй связанные поручения при изменении правил.

### knowledge

`category` — решение, архитектура, инструкция или ограничение. `body` хранит содержание, `rationale` — причины, `url` — ссылку на источник. `supersededById` указывает замену, `status: "superseded"` помечает прежнюю запись.

Briefing включает явно выбранные документы. Сверяй актуальность: наличие старой ссылки не делает заменённое решение действующим.

## Исполнение, проверка, приёмка

### run

Одна попытка для конкретной задачи: исполнитель, Session ID, родительская попытка, время, рабочая копия, ветка, базовый и результирующий коммиты, результат и ограничения.

`running`/`unknown` описывают незавершённое или требующее сверки состояние. `succeeded`, `failed`, `cancelled` завершают попытку; вернуть такую запись в другое состояние нельзя. Перенос исполнения в другую задачу запрещён.

`source` различает сообщение агента, ручную запись и данные runtime. `observedAt` — время наблюдения. Более двух минут без свежего наблюдения у `running` вызывает сигнал внимания. `integrated` фиксирует реальное включение результата в общую версию; запуск/завершение попытки не изменяет статус карточки.

### check

Проверка должна относиться хотя бы к задаче, этапу, релизу или требованию. Один `runId` без такого предмета недостаточен. Если указаны и попытка, и задача, они должны соответствовать друг другу.

Сохраняй `command`, `commit`, `environment`, `details`, `evidence` и источник. Значение `pending` означает, что подтверждённого результата ещё нет. Запись `passed` должна опираться на реально выполненную проверку; API само её не запускает.

### review

Заключение оркестратора: `accepted` или `changes_requested`. `conclusion` обязателен по смыслу и проверяется Core. Выбранные `checkIds` должны принадлежать этой задаче; для принятия все они должны быть `passed`.

Если задан `review.commit`, коммиты выбранных проверок должны совпадать с ним. Пустой коммит или список проверок технически допустимы; не представляй такой документ как подтверждение тестов конкретной версии. Объясни фактическое основание ручной приёмки.

### question

Вопрос связан с задачей и/или планом, имеет адресата, контекст и ответ. `answered` требует непустого `answer`. После сохранения ответа сообщи ожидающему участнику о решении доступным каналом.

## Выпуск и продолжение

### release

Версия, состав задач, коммит, примечания, ограничения и инструкция отката. Для `ready`/`released` нужен непустой коммит и успешное завершение всех включённых карточек, а не просто конечный статус. Реальный выпуск выполняется средствами проекта.

### deployment

Факт установки релиза в окружение. Содержит `releaseId`, окружение, время, состояние и подтверждение. `verified` требует непустого `evidence`. Информация о фактической установке должна поступать после её выполнения, включая откаты.

### checkpoint

Неизменяемая точка продолжения с summary, оставшейся работой, следующим шагом, ссылками на задачи и подтверждения, местом кода и окружением. Relay добавляет снимок ревизий задач и документов.

`checkpoint_changes` сравнивает эти ревизии с текущими. Он не делает Git-снимок, не сохраняет процессы и не восстанавливает файлы кода. Ссылки на реальные результаты и их местонахождение сохраняй в полях точки. Следующая передача создаёт новую запись.

## Полное обновление и повтор запроса

Схема безопасной правки документа:

```text
current = project_record_get(project, recordId)
nextFields = копия всех current.fields + необходимые изменения
project_record_save(project, actor, id=current.id, ifRevision=current.revision, fields=nextFields)
```

У карточки другая семантика: `task_update.patch` изменяет только переданные поля. Никогда не передавай `revision`, `events`, `snapshot` или `createdBy` внутрь `fields`.

`requestId` обеспечивает повторяемое создание обычного проектного документа для того же автора, вида и содержимого. Это не общий ключ идемпотентности всех операций. Паспорт, контекст задачи и обновления после неопределённого ответа сначала перечитываются. Подробности — [восстановление](RECOVERY.md).
