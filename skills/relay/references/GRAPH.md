# Граф сущностей

Статус: действующий контракт с раздельным хранилищем v2 и единственным источником рёбер —
явными записями Core. Автоматические domain-проекции удалены. Продуктовые линки остаются
в своих данных; подключение всех продуктовых сценариев к записи связей — следующий этап.

## Адреса и отношения

Постоянный адрес — `{kind,id}`. Во внешнем API и CLI допускаются читаемый ключ, ID или
уточнённый `kind:id`; их разрешает общий [движок сущностей](ENTITIES.md). Каталог содержит `project`, `product`, `feature`,
`scenario`, `application`, `implementation`, `document`, `board`, `task`.
Движок получает каталог через адаптер и не ограничивает пары видов.
Тип отношения расширяемый; допускает циклы, несколько родителей и несколько отношений
между одной парой. Произвольный тип не меняет готовность задач автоматически.

Тип — значение отношения, а не вид сущности. Используемые имена:

| Тип                    | Смысл                                                                           |
| ---------------------- | ------------------------------------------------------------------------------- |
| `contains` / `part-of` | Содержит / является частью; не нужно дублировать один факт в обоих направлениях |
| `implements`           | Намерение реализовать поведение или контракт; не подтверждение готовности       |
| `depends-on`           | Требуется результат другой работы; последствия определяет приложение            |
| `references`           | Материал для контекста без переноса его области и обязательности требований     |
| `affects`              | Работа затрагивает выбранную область                                            |
| `verifies`             | Работа проверяет выбранный объект                                               |
| `related`              | Общая связь без более точного утверждения                                       |

`description` поясняет назначение конкретной связи. Приложение может ограничивать и
интерпретировать типы; в универсальном ядре это расширяемый идентификатор. Для предметных
сценариев также допустимы `documents`, `belongs-to`, `on-board`, `board-of`.

`source` сохранён для совместимости формы ответа и имеет единственное значение `graph`.
Все отношения отдельно сохранены в движке. Каталог предоставляет узлы и алиасы, но не
создаёт рёбра из полей документа, задачи или другой сущности. Продуктовая запись сама
не создаёт, не изменяет и не разрывает связь без явного вызова Core из бекенда сценария.

## Чтение

`GET /api/v1/graph` (также проектный префикс) принимает `root?` (ключ/ID), `type?`, `direction`
(`both/outgoing/incoming`), `depth` (0–100, по умолчанию 3), `profile` (`all/context`),
`q?`, `offset`, `limit` (1–100, по умолчанию 40), `version?`.

Без root выбирается весь граф, включая изолированные узлы. Поиск q оставляет узлы
по адресу/ключу/названию и отношения между найденными узлами. Ответ: `nodes`, `edges`,
`endpoints` для рендера концов текущих рёбер, `paths` (один кратчайший путь на узел),
`totalNodes`, `totalEdges`, `nextOffset`, `version`, `boundary`, `depthLimited`.
Пути также содержат keys — актуальные читаемые ключи промежуточных узлов для страницы.
Смещение одновременно применяется к узлам и рёбрам; страницы одной выборки используют
одну версию. Изменение требует перечитать с начала (`GRAPH_CHANGED`).

`profile=all` — полный обход сохранённых отношений в заданных границах; это значение
по умолчанию также в CLI context и MCP entity_context. `profile=context` принимается
как совместимое имя того же обхода: скрытого отсечения документов, приложений, досок,
фич и других видов больше нет. Вид сущности не запрещает продолжать цепочку.
Циклы обрабатываются итеративно с посещёнными адресами.
`depthLimited` не означает конец графа; продолжайте от boundary. `nextOffset` означает
непрочитанную страницу выбранной области. Карточки не содержат полного Markdown сущностей.

## Запись и хранение

`POST /api/v1/graph`: `operations` (1–100), `ifVersion`, `requestId`, `actor?`.
Операции: `add` с type/from/to/description?, `update` с id/description,
`remove` с id. Автор, версия снимка и цели проверяются под общей блокировкой.
from/to принимают ключ, ID или объект `{kind,id}`. В сохранённом ребре остаются только ID.
Повтор проверяется перед версией и возвращает исходную квитанцию.
Квитанция: `ids`, `revision`, `version`, `requestId`.

### Вызов движка из бекенда

`GraphService.read`, `mutate`, `history` — единый Core API чтения, записи и истории.
`mutate` принимает add/update/remove и сохраняет результат до успешного ответа.
Update меняет пояснение; для замены концов/типа используется атомарный пакет remove/add.
Прямая запись CLI/REST — диагностический/ремонтный доступ к тому же механизму, а не
альтернативный источник связей. Продуктовые поля и статусы она не изменяет.

Бекенд продуктового сценария сохраняет свой линк, затем явно вызывает `mutate` с
постоянными адресами и версией графа, учитывающей уже выполненную продуктовую запись.
Он сохраняет ID нужных связей/квитанцию для последующего разрыва и обеспечивает общий
контракт повтора и восстановления. Нельзя взять версию до изменения сущности и
предположить, что она останется актуальной. Блокировка и WAL графа гарантируют атомарность
самого пакета рёбер, но не превращают произвольные две операции разных владельцев
в готовую общую транзакцию. Такая интеграция продуктовых сценариев — отдельный этап.

### Физическая схема v2

```text
.relay/relations/
  meta.json
  current/<hash-prefix>/<id>.json
  history/<segment>/<sequence>.json
  requests/<hash-prefix>/<request-hash>.json
  transactions/pending.json
  transactions/migration.json
  .indexes/edges.json
  .indexes/edges/<hash-prefix>.json
  .indexes/history/<hash-prefix>/<id>/<segment>.json
```

`current` содержит одну связь и признак active. Отзыв оставляет надгробие: ID не
переиспользуется, число событий связи сохраняется. Markdown-пояснение — массив строк.
История — отдельные неизменяемые события с последовательным номером; сегмент охватывает
1000 номеров. Квитанция читается по хешу автора/requestId, без чтения остальных запросов.
Метаданные содержат `schemaVersion: 2`, ревизию, число событий и отпечаток индекса.

Суммарного ограничения 16 МиБ больше нет. Лимиты: 1 МиБ на постоянную запись,
32 МиБ на сегмент индекса, 128 МиБ на долговечное намерение пакета. Ограничения внешнего
ввода прежние: до 100 операций, до 64 КиБ Markdown на пояснение, HTTP body до 1 МиБ.
История и квитанции не удаляются автоматически. Предел сегмента индекса требует дальнейшего
разбиения при его достижении; не является обещанием бесконечного масштабирования.

Журнал `pending.json` сохраняет исходные хеши и итоговые записи. Под общей блокировкой
Core восстанавливает его до любой операции. WAL удаляется после fsync постоянных файлов
и каталогов; несовместимая внешняя правка вызывает `GRAPH_RECOVERY_CONFLICT`.
Производные индексы можно потерять: их контрольные суммы и счётчики запускают перестроение.
Восстанавливаемые кеши не требуют отдельного fsync каждого файла.

Индекс не содержит пояснений: холодное чтение загружает компактные сегменты, повторное
использует ограниченный кеш и список смежности. Тела читаются только для рёбер страницы.
Полный граф и поиск всё ещё могут обходить весь краткий индекс. Каталог сущностей
собирается своим адаптером; его стоимость не исчезает от индекса связей.

### Удаление вычисляемых проекций

Ранее ответы включали рёбра `source=domain`, вычисленные из продуктовых полей.
Теперь их нет. Это не удаление постоянных связей или продуктовых данных: проекции
не имели записей в relations. Старые сохранённые graph-рёбра v1/v2, события, ID,
Markdown и квитанции сохраняются; новой версии физической схемы не требуется.

Автоматического импорта продуктовых линков при чтении, миграции v1 или reindex нет.
Сущность с продуктовыми линками без установленных связей возвращает контекст из одного
узла и нуля рёбер. Это ожидаемая граница до отдельного подключения продуктовых сценариев
и явного переноса старых отношений. После обновления перечитайте снимок: прежние версии
страниц/записи могут не совпасть. Повтор старой записи сохраняет исходную квитанцию.

### Переход с v1 и обслуживание

Существующий `.relay/relations.json` v1 совместимо читается без изменения файлов.
Новая запись в v1 требует явной локальной миграции:

```bash
relay-cli --local --config .relay/config.json graph migrate
relay-cli --local --config .relay/config.json graph reindex
```

Перед миграцией остановите старые клиенты. Перенос сохраняет ID, пользовательские ревизии,
порядок событий, точные тексты и квитанции. Прерванный перенос возобновляется перед операциями
Core; исходник остаётся `relations/v1-backup.json`. После переноса перечитайте версию графа
перед новой записью; повтор прежнего запроса возвращает прежнюю квитанцию.
Старые форматы продукта и задач эта операция не переносит.

Все обычные записи проходят Core. После намеренной внешней правки файлов выполните
`graph reindex`: он перечитывает текущие записи и историю, восстанавливает индексы и принимает
новый отпечаток. Это не создаёт вымышленное пользовательское событие для внешней правки.
Адресное чтение обнаруживает несовпадение файла и индекса как `GRAPH_INDEX_STALE`.
Автоматическое обнаружение любой ручной правки всех файлов при каждом запросе не обещается;
внешний редактор не защищён блокировкой Core.

`GET /graph/history`: id?, offset, limit, revision?; события содержат действие, автора,
время и состояние отношения. Отозванные связи остаются в истории.

### Значение счётчиков

В отчёте migrate/reindex «Связей» — число активных явных отношений v2, «Событий» —
число сохранённых операций add/update/remove, «Ревизия» — номер сохранённого пакета
изменений графа. Один пакет из восьми добавлений создаёт восемь событий и одну ревизию.
Последующее добавление и удаление временной связи дают восемь активных связей,
десять событий и ревизию 3. Миграция и переиндексация сами не создают событий и не повышают ревизию.
Продуктовые линки без вызова записи Core не входят ни в граф, ни в его журнал.

Для записи используется `--if-version` со значением поля version из list/context:
отпечаток учитывает также каталог сущностей. Числовая ревизия хранилища не заменяет его.

## CLI

```bash
relay-cli graph list --limit 20
relay-cli graph list --limit 20 --offset 20 --snapshot-version VERSION
relay-cli graph context SCENARIO-1 --depth 5 --format json
relay-cli --actor agent graph link --from WEB-24 --to DOC-1 \
  --type references --description 'Пример для реализации' --if-version VERSION --request-id link-1
relay-cli --actor agent graph update RELATION_ID --description 'Новое пояснение' --if-version VERSION
relay-cli --actor agent graph unlink RELATION_ID --if-version VERSION
relay-cli graph history --id RELATION_ID
```

`graph apply --json '<массив операций>' --if-version VERSION` публикует пакет.
В CLI версия продолжения задаётся `--snapshot-version`, чтобы не конфликтовать с глобальным
`--version` программы. В REST параметр остаётся `version`.
Текстовый вывод показывает названия, направления, Markdown-пояснения, причины включения
и точную команду продолжения. JSON использует обычный конверт CLI.
