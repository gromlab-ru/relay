# ТЗ: React-интерфейс Tasks

## Назначение

Разработать качественный канбан для человека, который управляет задачами
параллельно с AI-агентами. Интерфейс входит в единый npm-пакет:

```bash
npx @gromlab/tasks-cli server --actor human --open
```

NestJS отдаёт собранный UI, REST API и SSE с одного локального адреса.
Архитектура, порядок реализации и обязанности бэкенда описаны в
[docs/PLAN.md](../../docs/PLAN.md). Запуск и команды CLI описаны в
[руководстве CLI](../cli/README.md).

## Исходные условия

- Основная зона реализации: `apps/web/src`.
- Стек: React, TypeScript, Vite, Mantine, SWR, dnd-kit,
  react-markdown, remark-gfm, lucide-react. Направление дизайна — сдержанный рабочий интерфейс.
- Переносимые HTTP- и SSE-типы предоставляет публичный пакет `@tasks/contracts`;
  приложение импортирует из него только типы. Описание API: [API.md](../../packages/contracts/docs/API.md).
- Сервер предоставляет продуктовые маршруты и SSE; интерфейс использует реальный API.
- REST-клиент находится в `apps/web/src/infra/tasks-api`.
- Автотесты фронтенда не добавляются по решению пользователя. Браузерные сценарии
  проверяются через agent-browser в собственной headless-сессии.
- Визуальную систему, композицию и компоненты проектирует UI-агент по подключённым
  правилам UI/UX. Критерии качества ниже являются частью приёмки.

## 1. Визуальная система и качество

Перед реализацией основной доски определить и последовательно использовать:

- типографическую шкалу, читаемые размеры и межстрочные интервалы;
- сетку, плотность карточек и согласованную шкалу отступов;
- дизайн-токены цветов, границ, скруглений, теней и состояний;
- компоненты кнопок, полей, тегов, меню, уведомлений, вкладок и диалогов;
- светлую и тёмную темы;
- иерархию основных и второстепенных действий.

Макет должен быть удобен для длительной работы с реальными данными: длинными
названиями, множеством задач, произвольными статусами и русским текстом.
Каждый отображаемый элемент управления имеет работающий сценарий.
Анимации объясняют изменения состояния и учитывают `prefers-reduced-motion`.

## 2. Канбан

- Показывать все статусы из `context.config.statuses`, в порядке ключей конфигурации.
- Использовать настроенные цвета; неизвестные имена статусов отображать как есть.
- Включать выполненные и отменённые задачи. Фильтры явно ограничивают выборку.
- Заголовок колонки содержит статус, количество задач и действие создания.
- Уметь работать с количеством колонок, превышающим ширину экрана.
- При большой выборке использовать подгрузку/виртуализацию с понятными счётчиками.
- Различать полное отсутствие задач, пустую колонку и отсутствие результатов фильтра.

Карточка на доске содержит ID, название, исполнителя, группу и теги, блокеры,
счётчики комментариев/отчётов и прогресс непосредственных подзадач.
Второстепенные данные не должны затруднять чтение названия.

Фильтры: поиск по ID/тексту, группа, исполнитель, теги, заблокированные задачи.
Нужен сброс фильтров. Предпочтения сохраняются отдельно для каждого `projectId`.
Поиск описания и summary использует серверный поиск, а не только название карточки.

## 3. Перетаскивание и порядок

- Перенос между колонками меняет статус и положение одной атомарной операцией.
- Порядок внутри колонки сохраняется между сеансами и доступен другим участникам.
- Клиент передаёт `status`, `beforeId`, `ifRevision`; `rank` вычисляет сервер.
- `rank` — непрозрачный строковый ключ. Клиент использует порядок API и не преобразует его в Number.
- `beforeId: null` означает конец полной колонки, в том числе при активных фильтрах.
- Обработать пустую колонку, длинную колонку, прокрутку и перенос с клавиатуры.
- Во время сохранения ограничить повторные конфликтующие действия.
- При отказе сервера восстановить подтверждённое состояние и показать причину.
- Должно быть доступно изменение статуса обычным элементом управления.

## 4. Карточка и навигация

Открытие карточки сохраняет контекст доски: боковая панель на большом экране,
полноэкранный режим на небольшом. Адрес `/tasks/<id>` открывается напрямую;
работают обновление страницы и история браузера.

Доступно редактирование:

- названия;
- Markdown-описания и критериев готовности;
- текущего состояния `summary`;
- статуса, исполнителя, группы, тегов;
- родителя и блокирующих зависимостей.

Карточка показывает автора, даты, ревизию, подзадачи, блокируемые задачи и причины
блокировки. Связанные карточки открываются по нажатию.

Действия: создать подзадачу, взять себе, назначить, освободить, завершить, отменить,
переоткрыть, скопировать ссылку. Отмена и завершение используют семантику конфига.
Удаление документов и редактирование колонок не входят в согласованный объём этой версии.

Создание из колонки подставляет статус, из подзадач — родителя, из выбранной группы — группу.
Пользователь видит и может изменить подставленные значения.

## 5. Редактор и контекст

- Явное сохранение полей, заметное состояние несохранённых изменений.
- Markdown-редактор с предпросмотром, поддержкой абзацев, списков, кода и ссылок.
- `description` хранит требования, `summary` — актуальный результат и следующий шаг.
- История обсуждения и отчёты доступны отдельными разделами карточки.
- Комментарии и отчёты добавляются новыми записями; история сохраняется.
- Отчёты поддерживают типы progress, decision, execution, error, summary,
  заголовок, текст, краткий результат и необязательную сессию.
- Историю загружать страницами, с фильтрами по автору и типу отчёта.
- При ошибке отправки оставлять введённый текст доступным.

В API многострочные поля задач и возвращаемые тела записей — массивы строк.
Редактор работает со строкой. При добавлении комментария/отчёта отправляется
строковое поле `text`; точные DTO находятся в Contracts.

## 6. Конкурентность и SSE

- Сохранять карточку с ревизией, на основе которой начато редактирование.
- Ответ 409 не должен приводить к потере ввода или незаметной перезаписи чужих правок.
- При конфликте показать актуальное состояние и дать осознанно применить изменения.
- Добавление комментариев/отчётов тоже увеличивает ревизию документа.
- Внешнее обновление чистой карточки подхватывается автоматически.
- Во время редактирования внешний ответ сохраняет локальный черновик.
- SSE сообщает об изменениях; актуальное состояние читается через REST.
- После переподключения выполнять сверку данных: поток не является журналом доставки.
- Связанные карточки и счётчики также обновляются после изменения зависимости.
- Сохранять черновики отдельно по проекту и ID; предусмотреть их восстановление и удаление после сохранения/отмены.

## 7. Состояния и доступность

Разработать и проверить:

- первоначальную загрузку и фоновое обновление;
- пустой проект и пустую выборку;
- загрузку карточки и истории;
- сохранение, успешное действие и серверную ошибку;
- отсутствие соединения, переподключение и конфликт ревизии;
- неизвестный ID, неверные данные и повреждённое хранилище.

Нужны видимый focus, осмысленные accessible names, управление диалогами с клавиатуры,
возврат фокуса после закрытия, доступный перенос карточек и текстовые обозначения
состояний наряду с цветом. Учитывать сенсорное управление и прокрутку.

Проверить ширины 1440, 1024, 768 и 390 CSS-пикселей, масштаб 200%, обе темы,
длинные названия и большое количество тегов/колонок.

## 8. Интеграция и проверка

Команды выполняются из корня репозитория. Разработка: `pnpm run dev` либо
`pnpm run dev:server` и `pnpm --filter @tasks/web run dev` в отдельных терминалах.
Vite проксирует `/api` в Nest. Фронтенд можно разрабатывать на типизированных
HTTP-моках по Contracts; финальная приёмка требует реального сервера.

Обязательные проверки приложения: `pnpm run lint:web`, `pnpm run typecheck:web`,
`pnpm run build:web`. Корневые команды через Turbo собирают необходимые зависимости.
Локальная сборка находится в `apps/web/dist` и включается в дистрибутив CLI.
Визуальная приёмка использует `pnpm --filter @tasks/web run browser ...`; правила изоляции
и headless-режима закреплены в [AGENTS.md](AGENTS.md).

Браузерные сценарии приёмки:

1. Создать общую задачу, API и форму с зависимостью от API.
2. Редактировать Markdown, теги, исполнителя и связи; перечитать сохранённые данные.
3. Переместить карточку между колонками и внутри колонки; перезапустить и проверить порядок.
4. Получить отказ при завершении заблокированной задачи и сохранить корректное состояние доски.
5. Пройти review → доработка → review → done с комментариями и отчётом.
6. Завершить зависимость через CLI и увидеть разблокировку формы в браузере.
7. Изменить открытую карточку из второго клиента; сохранить черновик и разрешить конфликт.
8. Отключить и восстановить сервер; проверить уведомление и восстановление данных.
9. Открыть прямую ссылку, использовать Back/Forward, закрыть карточку с черновиком.
10. Прочитать более одной страницы задач и истории без пропусков.
11. Пройти основные действия с клавиатуры и на узком экране.
12. Открыть UI из установленного npm-архива через NPX.

Финальный отчёт: реализованные сценарии, команды проверок, браузерные скриншоты
доски и карточки в двух темах, мобильный вид, оставшиеся ограничения.
