# Relay Web

[Продуктовый контракт Web](../../docs/product/applications/web/README.md) ·
[Состояние реализации](../../docs/engineering/implementation/applications.md) ·
[Протокол разработки](../../docs/development/PROTOCOL.md).

Приложение сопровождения проекта на React, TypeScript и Vite. Канбан — один из разделов.
Отдельные экраны: обзор, паспорт, планы, требования и знания, работа и проверки,
релизы, история и передача контекста. [Сценарии](../../docs/guides/LIFECYCLE.md).
Компоненты — Mantine,
серверный кеш — SWR, перенос — dnd-kit. Приватный pnpm workspace `@relay/web`
собирается в `apps/web/dist`; его содержимое входит в серверный дистрибутив
`@gromlab/relay-server`. Сам workspace отдельно не публикуется.

Основное назначение UI — наблюдение за потоком задач оркестратора и субагентов
на одном хосте, с возможностью добавить уточнения и отредактировать задачи.

Документация: [обзор продукта](../../README.md), [руководство по доске](../../docs/guides/WEB.md),
[справочник CLI](../../docs/reference/CLI.md),
[история изменений CLI](../cli/CHANGELOG.md), [план](../../docs/PLAN.md),
[HTTP API](../../docs/reference/API.md), [ТЗ интерфейса](UI_SPEC.md).

## Разработка

Команды выполняются из корня репозитория. Для разработки и agent-browser используется Node.js 24+;
пользовательский npm-пакет по-прежнему запускается на Node.js 22+.

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm run dev
```

Эта команда запускает API и Vite вместе. Их также можно запускать раздельно
в двух терминалах:

```bash
pnpm run dev:server
pnpm --filter @relay/web run dev
```

Vite: `http://127.0.0.1:5173`. `/api`, включая SSE, проксируется на
`http://127.0.0.1:4700`. Для другого адреса сервера задайте `RELAY_API_URL`,
для другого порта Vite задайте `RELAY_WEB_PORT` (по умолчанию 5173).
`pnpm run dev:app` остаётся псевдонимом `dev`, а `pnpm run dev:ui` — `dev:web`.
При отдельном запуске web сервер API должен уже работать: иначе прокси
сообщит `ECONNREFUSED`. Vite автоматически определяет корень pnpm workspaces
и разрешает общие зависимости без ручного списка `server.fs.allow`.
Скрипт `dev` перед запуском Vite собирает workspace `@relay/rest-sdk`.
Его публичные импорты ведут в compiled `dist`, как и при production-сборке.

## Навигация продукта

Раздел «Связи проекта» (`/projects/<project>/relations`) читает общий граф Core и позволяет
добавлять произвольные направленные отношения с Markdown-пояснением. Выбор корня,
профиль контекста и глубина восстанавливают цепочки с причинами включения. Предметные
проекции прежних связей помечены отдельно. [Контракт и ограничения](../../docs/reference/GRAPH.md).

Шестерёнка в шапке открывает настройки проекта `/projects/<slug>/settings`.
Имя и slug сохраняются через Core/REST; UI показывает адрес, сохранение/отмену,
конфликт ревизий и изолированный черновик. Постоянный ID остаётся ключом данных;
useProjectBasePath предоставляет путь Web. Ссылки по ID канонизируются на актуальный slug.
Общая шапка больше не содержит создания задачи. Контракт — в
[настройках Web](../../docs/product/applications/web/README.md#настройки-проекта).

В сайдбаре проекта раздел «Продукт» раскрывает пункты «Паспорт», «Возможности», «Приложения»
и «Документы». Их адреса: `/projects/<projectId>/product/{passport,features,applications,documents}`.
На узком экране сайдбар открывается кнопкой навигации в шапке и закрывается после выбора.

В подразделах используется интерфейс продуктового прототипа с постоянными данными:
паспорт, фичи и сценарии, приложения, редакторы описаний и связей. Данные хранятся
в JSON через Core/REST; примеры «Напроката» не подмешиваются. Черновики остаются
локальными вкладке. Прежний экран паспорта относится к legacy-модели по старому адресу.
Действующие контракты описаны в [справочнике продукта](../../docs/reference/PRODUCT.md).

Каталог фич представлен двухуровневым деревом: блок фичи раскрывает сценарии, её
заголовок открывает страницу. Сценарий имеет собственные описание, редактор и постоянную
ссылку `features/FEATURE-N/scenarios/SCENARIO-N` в контексте фичи. Раскрытие дерева
хранится в браузере по ID проекта и не запускает навигацию; фильтры остаются в URL.
Готовность родителя вычисляется по всем сценариям,
включая скрытые поиском, и учитывает общие контракты приложений. Поведение страниц
описано в [контракте Web](../../docs/product/applications/web/PRODUCT.md), предметные
правила — в [спецификации сущности «Продукт»](../../docs/product/entities/product/README.md).

Приложение объявляет свой состав на `/projects/<projectId>/product/applications/<id>/scope`:
выбирает общие фичи и сценарии и описывает вклад в каждый выбранный элемент. В редакторе
дерево и текущий текст разделены на две области; на узком экране между ними переключаются.
Состояния реализаций определяют готовность общих сценариев и фич. Снятые контракты
сохраняют идентичность и ссылки документов. После изменения требований нужно переподтверждение.

«Документы» — библиотека самостоятельных Markdown-материалов: требования,
описания, правила и решения. Каталог поддерживает поиск по тексту и реальным областям,
фильтры и сортировку. У документа есть просмотр и редактор с предпросмотром и черновиком.
Множественный выбор областей создаёт настоящие типизированные связи:
продукт / фича / сценарий и приложение / реализация фичи / реализация сценария.
Обратные списки документов доступны в карточках продукта, фич и приложений.

## Сценарии

Фичи, сценарии, приложения и реализации имеют читаемые ключи. ID остаются основой
хранения, связей, кеша и черновиков. ProductKey показывает ключ без визуальной конкуренции
с названием; копирование доступно в заголовках. Страницы сценария и реализации используют
адресный API, а TaskContext и ProductLinks для задач/планов — компактный каталог с пагинацией.
Полные требования и расширенный контекст загружаются по запросу. Вклад редактируется
по собственной ревизии. ProductLinks обслуживает также планы и этапы.

- Новый пункт «Доски и задачи» показывает продуктовую доску, доски приложений и инфраструктуру.
  Адрес — `/projects/<projectId>/boards/<slug>`. У приложения появился обязательный неизменяемый slug.
  [Контракт досок](../../docs/product/entities/boards/README.md) и [канбан](../../docs/product/entities/tasks/KANBAN.md)
  описывают отдельную модель: префикс, короткий ID, Markdown и междосочные связи.
  Кнопка создания сразу сохраняет пустую задачу и открывает редактор по `/boards/<slug>/<id>`.
  Старый `/tasks/<id>` перенаправляется для новых задач. Рабочее окно разворачивается
  вручную; единый обзор показывает описание, постоянные продуктовые связи и задачи.
  Статус и доска выбираются компактными меню и сохраняются сразу. Типа эпика нет.
  Связь добавляется кнопками типа и двумя селекторами. Dropdown задач выбранной доски
  сужается вводом ключа/названия, completion=unfinished исключает done/cancelled
  до пагинации. Описание кандидата раскрывается отдельно, большие карточки выбора убраны.
  Форма связи не открывает dropdown автоматически. Поля и селекторы имеют одну рамку:
  фокус меняет её цвет вместо внешнего outline. CodeMirror использует тот же принцип.
  После DnD domains/board-tasks адресно обновляет кеш полной задачи, в том числе закрытой;
  обычное открытие проверяет актуальность, первоначальное создание обходится без второго GET.
  Контекст читается product/context, связи productLinks сохраняются в Core.
  MarkdownField использует лениво загружаемый CodeMirror 6; просмотр находится у
  владельца формы, внутри ввода нет второго предпросмотра. Подсветка учитывает тему,
  Ctrl/Cmd+Enter сохраняет ближайшую форму до обработки сочетания самим CodeMirror.
  Доска занимает доступную ширину и высоту окна; колонки прокручиваются независимо.
  Просмотр — центральное модальное окно. Локальная проекция `task-kanban` удерживает
  порядок во время жеста и записи; overlay имеет размеры исходной карточки. На границе
  страницы читается одна дополнительная запись-якорь, пользователь видит порции по 40.
  Shared DnD helpers — `ui/kanban-dnd`; подгрузка сохраняет предыдущие данные и count.
- «Прежняя доска» сохраняет существующий `/board` и его возможности для сравнения.

### Прежняя числовая модель

- Все колонки и их семантика берутся из конфигурации проекта.
- Каждая колонка загружает 40 карточек; продолжение доступно через «Показать ещё».
- Во время подгрузки SWR сохраняет предыдущую проекцию. Скелетоны показываются
  только при первой загрузке, а кнопка продолжения исключена из scroll anchoring:
  добавление следующих карточек не уводит страницу к новому концу списка.
- Вертикальная прокрутка общая для страницы: колесо над карточками перемещает всю доску.
  На узком экране доска дополнительно прокручивается горизонтально.
- Навигация показывает все группы и полное число задач в каждой, включая конечные.
  «Без группы» появляется для задач с `group: null`. Счётчики независимы от поиска,
  дополнительных фильтров и загруженной страницы; рядом с поиском — размер текущей выборки.
  Переходы между группами поддерживают Back/Forward; группа сохраняется после обновления страницы.
- Поиск включает ID, название, описание и summary. Фильтры находятся в URL
  и сохраняются отдельно для проекта.
- `/projects/<projectId>/tasks/<id>` открывает панель задачи; на узком экране она занимает всю ширину.
- Поля сохраняются явно. Черновики задачи, создания, комментариев и отчётов
  хранятся локально; черновики разных вкладок разделены.
- Markdown поддерживает предпросмотр, списки, код, ссылки и таблицы.
- Ссылки на задачи и доску в Markdown используют React Router, сохраняют фильтры
  и исходную точку возврата. Описание, история и предпросмотр используют один
  настроенный компонент ссылки; переход не перезапускает приложение и SSE.
- Подзадачи и зависимости представлены раздельно. Связи выбираются поиском.
- Статус меняется перетаскиванием или обычным контролом. Ручка переноса доступна
  с клавиатуры: пробел, стрелки, пробел; Escape отменяет перенос.
- Внешние изменения приходят через SSE. Данные перечитываются через REST;
  изменённая форма сохраняет свою исходную ревизию и введённый текст.
- Heartbeat раз в 15 секунд поддерживает SSE при простое, не вызывая REST-запросов.
  Короткое переподключение видно в индикаторе шапки; предупреждение о потере связи
  появляется через 10 секунд недоступности и исчезает после восстановления.
- В dev-режиме открытие SSE отложено до завершения текущего цикла эффектов,
  а окончательное освобождение — на 100 мс. StrictMode и быстрый remount при
  Fast Refresh используют одно соединение вместо отмены ещё загружающегося запроса.
- Если dev-прокси вернул 502/503 и браузер окончательно закрыл EventSource,
  транспорт создаёт новый поток с задержками 1, 2, 4, 8 и далее до 10 секунд.
  После восстановления API данные сверяются автоматически; повторы не сбрасывают
  таймер предупреждения о длительной недоступности.
- При конфликте пользователь выбирает значения пересекающихся полей, затем
  явно сохраняет объединённую версию.

Сочетания: `N` — новая задача, `/` — поиск, `?` — справка,
`Ctrl/⌘ + Enter` — сохранить редактор, `Escape` — закрыть панель.

## Архитектура

Область профиля React SPA — `apps/web/src`. Применяется Unit Architecture из
React Reference, указанного в `AGENTS.md`: фасеты `index.ts` и `lazy.ts`,
алиасы слоёв без префикса `@`, вложенные юниты доступны своему родителю.
Единственный список алиасов слоёв находится в `tsconfig.json`; Vite 8 читает
его через `resolve.tsconfigPaths`. Межпакетный импорт `@relay/contracts`
использует публичный `exports` пакета, а не алиас его исходников.

Браузерные tsconfig остаются самостоятельными: `module: ESNext`,
`moduleResolution: Bundler` и DOM не наследуют общий NodeNext-профиль серверных пакетов.

| Владелец                          | Ответственность                                            |
| --------------------------------- | ---------------------------------------------------------- |
| `app`                             | Запуск, маршруты, подключение провайдеров                  |
| `compositions/screens/relay`      | Выбор проекта, URL и область жизни проектной доски         |
| `compositions/layouts/project`    | Общая навигация и место для вложенных экранов              |
| `domains/lifecycle`               | Проектные документы, проверка ответов, операции и кеш      |
| `compositions/widgets`            | Редактор, чтение документов, связанные задачи и поручения  |
| `domains/workspace`               | Режим и актуальный реестр сервера                          |
| `compositions/screens/board`      | Доска, URL, фильтры, открытие задачи и создание            |
| Вложенные юниты доски             | Колонки, панель, редактор, история и сравнение версий      |
| `board/ui/group-navigation`       | Выбор группы и отображение полных счётчиков                |
| `domains/project`                 | Контекст, автор и семантика статусов                       |
| `domains/tasks`                   | Задачи, адаптеры, кеш, операции, черновики и синхронизация |
| `infra/tasks-api`                 | Браузерный экземпляр клиента из `@relay/rest-sdk`          |
| `infra/workspace-events`          | Жизненный цикл EventSource                                 |
| `infra/browser-storage`           | Доступ к браузерному хранению                              |
| `ui/themes`                       | Типографика, токены и три цветовые схемы                   |
| `ui/markdown-*`, `ui/state-panel` | Универсальные визуальные возможности                       |

Сгенерированный клиент принадлежит [SDK-пакету](../../packages/rest-sdk/README.md).
Его обновление из работающего актуального сервера:

```bash
pnpm --filter @relay/rest-sdk run generate
pnpm --filter @relay/rest-sdk run build
```

`packages/rest-sdk/src` полностью принадлежит `@gromlab/rest-api-codegen@5.2.4`.
SDK собирает ESM и декларации через NodeNext. Настройки браузерного экземпляра
находятся в `infra/tasks-api/tasks-api.ts`; доменные адаптеры получают wire-типы
через этот инфраструктурный фасет и проверяют ответы во время выполнения.
Команда `generate:api` приложения остаётся псевдонимом генерации SDK.

Новые TSX создаются локальным генератором; журнал фактических команд — [GENERATION.md](GENERATION.md).

## Проверка и сборка

Автотесты фронтенда не добавляются по согласованному решению. Проверки:

```bash
pnpm run lint:web
pnpm run typecheck:web
pnpm run build:web
pnpm run package:check
```

Корневые команды через Turbo сначала собирают зависимости, включая SDK.
`pnpm --filter @relay/web run lint`, `pnpm --filter @relay/web run typecheck` и
`pnpm --filter @relay/web run build` запускают только локальные инструменты, без Turbo;
для двух последних команд `@relay/rest-sdk` должен быть уже собран.

`package:check` проверяет установленный npm-архив в отдельном каталоге.
Общая сборка включает локальный `apps/web/dist` в серверный дистрибутив вместе с Node-частью.
Turbo сохраняет `dist/**` каждого workspace отдельно: JavaScript и декларации SDK
принадлежат пакету, а сборка браузера — приложению. `pnpm --filter @relay/web run clean`
удаляет локальные `dist` и оставшийся от предыдущей структуры `.cache`.

Для визуальной проверки устанавливается отдельный Chrome для agent-browser:

```bash
pnpm --filter @relay/web run browser:install
pnpm --filter @relay/web run browser --session tasks-web-review open http://127.0.0.1:5173
pnpm --filter @relay/web run browser --session tasks-web-review snapshot -i
pnpm --filter @relay/web run browser --session tasks-web-review close
```

Версия agent-browser закреплена в корневом `package.json`; команды workspace
используют этот бинарный файл и локальный `agent-browser.json`.
Используйте уникальную сессию каждого запуска. `agent-browser.json` задаёт headless
и отключает автоматическое подключение к пользовательскому браузеру. Для проверки
применяются снимки, реальные действия, `a11y`, `errors` и `console`.
Ожидайте конкретный результат, а не `networkidle`: соединение SSE остаётся открытым.
Браузерные проверки выполняются на временном проекте; скриншоты сохраняются в
корневом `.artifacts/web` (из workspace это `../../.artifacts/web`).
