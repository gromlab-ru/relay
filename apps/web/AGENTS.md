# Блокирующий протокол разработки

Для задач по `apps/web`, включая связанные изменения вне приложения,
РЕАЛИЗАЦИЯ ЗАПРЕЩЕНА до выполнения всех четырёх пунктов ниже.
До допуска разрешены только чтение, исследование, уточнения и планирование.
Запрет включает изменение файлов, генерацию кода и делегирование реализации.

1. **Прочитай skills.**
   Загрузи `unit-architecture` и `react-reference`, полностью прочитай
   их `SKILL.md`. Используй актуальные документы, а не память прошлых задач.

2. **Определи архитектуру изменения.**
   Прочитай применимый архитектурный профиль и необходимые по задаче
   разделы Unit Architecture.
   Исследуй затронутый код и потребителей. Определи ответственность,
   ближайшего владельца, слой, необходимость отдельного юнита,
   публичный контракт и допустимые зависимости.
   Проверь соответствие правилам фасетов, вложенности и отсутствия циклов.
   Выбирай владельца по ответственности, не по типу файла или библиотеке.
   Существующий код сам по себе не доказывает архитектурную корректность.

3. **Выбери инструкции реализации.**
   По карте `react-reference` найди и прочитай нужные прикладные разделы,
   затем необходимые инструкции библиотек, правила кода и профильные skills.
   Читай только относящуюся к задаче документацию, не весь reference.
   Выбор подхода должен опираться на прочитанные правила.

4. **Зафиксируй план.**
   До первой правки составь краткий план: что изменить, у какого владельца,
   по каким прочитанным документам и как проверить результат.
   План должен соответствовать архитектуре и инструкциям React Reference.

**Допуск получен только после фактического выполнения всех четырёх пунктов.**
Если необходимые источники недоступны или остаётся влияющая на решение
неопределённость, реализация заблокирована: уточни вопрос, не угадывай.

После допуска строго следуй плану, Unit Architecture и React Reference.
Для нового и изменяемого кода обязателен строгий режим правил кода reference.
Самовольные исключения и замена правил привычными подходами запрещены.
При появлении новой области задачи сначала дополни чтение и план.
Перед завершением проверь соответствие обоим skills и выполни проверки проекта.

## Проверка интерфейса

- Автотесты фронтенда не добавлять: это согласованное решение пользователя.
  Для проверки сценариев и визуальной приёмки использовать **agent-browser**.
  Версия закрепляется в devDependencies корневого проекта. Команды и их возможности
  сверять через `agent-browser --help` и https://agent-browser.dev/commands.
- Браузер запускается в **headless**-режиме по умолчанию. `--headed` применять только
  по явному запросу пользователя. Проверки не требуют открывать окно на его рабочем столе.
- Каждый проверочный запуск использует собственную именованную сессию
  `--session tasks-web-<уникальный-суффикс>` с отдельным экземпляром браузера.
  Не подключаться к пользовательскому браузеру через `--cdp` или `--auto-connect`,
  не использовать его профили. Дополнительная вкладка общей сессии не является изоляцией.
- Рабочий цикл: `open` → `snapshot -i` → действие по актуальному ref или доступному
  имени → ожидание наблюдаемого результата → новый snapshot / screenshot.
  После изменения страницы получать свежие refs. Для SSE-приложения ждать конкретный
  элемент, текст или условие; `networkidle` не использовать как признак готовности.
- Проверять обе темы, ширины 1440 / 1024 / 768 / 390, клавиатуру, сохранность черновиков,
  ошибки сети и конкурентные изменения. Использовать `a11y`, `console`, `errors`
  и снимки экрана; автоматически успешный аудит не заменяет визуальную приёмку.
- Браузерные проверки проводить на временном хранилище задач. После проверки закрывать
  только свою сессию командой `--session <имя> close` и свой сервер. Не применять `close --all`.
- Если собственный headless-браузер недоступен, сообщить блокер и использовать
  пользовательские скриншоты для визуальной оценки; непроверенные сценарии не отмечать пройденными.
- Независимо от браузерной проверки выполнять lint, typecheck и сборку приложения.
