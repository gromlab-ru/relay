# Команды CLI

В примерах `tasks-cli` — исполняемая команда установленного `@gromlab/tasks-cli`.
Её можно заменить на `npx @gromlab/tasks-cli`; из корня собранного репозитория:
`node apps/cli/dist/cli/main.js`.
`<task-id>` — числовой ID задачи от 1. `<comment-id>` и `<log-id>` — полные ID
из ответов `comment add/list` и `log add/list/search`.

Пошаговый жизненный цикл задач с примерами запуска через `npx` находится в [README](../README.md).
`tasks-cli <команда> --help` объясняет условия и аргументы конкретной команды.
У вложенных команд справка вызывается так: `tasks-cli log add --help`.
Без аргументов CLI и группы `log`, `comment`, `deps`, `config`, `group` показывают справку.

## Общие параметры

| Параметр                      | Назначение                                                |
| ----------------------------- | --------------------------------------------------------- |
| `--config <path>`             | Явный конфиг вместо поиска ближайшего `tasks.config.json` |
| `--actor <id>`                | Автор записи; имеет приоритет над `TASKS_ACTOR`           |
| `--format text\|json`         | Настоящий многострочный текст или структурированный JSON  |
| `--color auto\|always\|never` | Автоматическая, принудительная или отключённая подсветка  |
| `--max-bytes <N>`             | Объём UTF-8 ответа, от 1024 байт до 16 МиБ                |
| `--help`                      | Справка по команде                                        |
| `--version`                   | Версия из `package.json`                                  |

Начальный конфиг задаёт текстовый режим и лимит 16 КиБ. `list` не имеет ограничения
числа задач по умолчанию; `output.defaultLimit` (20) задаёт страницы списков групп,
комментариев и отчётов.
Для машинной обработки передайте `--format json`. Справка и версия всегда текстовые.
Для чтения автор не нужен, для записи обязателен.

Текстовый режим оформляет статусы, таблицы, карточки, связи и Markdown.
Цвет автоматически включается в TTY; `NO_COLOR` отключает автоматическую подсветку.
Явные `--color always` и `--color never` имеют приоритет над окружением.
`--format json` всегда отключает ANSI-коды. Подробности: [терминал](TERMINAL.md).

## Настройка проекта

```bash
tasks-cli init --storage .tasks
tasks-cli config get
tasks-cli group list
```

`storageDir` разрешается относительно конфига. Это позволяет нескольким worktree
обращаться к одной базе через общий `--config`.
Группы показывают `total`, успешные `completed` и все конечные `terminal` задачи.

Настройки редактируются в `tasks.config.json`; `config get` показывает точный путь.
Пример полного конфига с пользовательским цветом `review`:

```json
{
  "version": 1,
  "storageDir": ".tasks",
  "defaultStatus": "todo",
  "readyStatuses": ["todo"],
  "statuses": {
    "todo": { "color": "cyan" },
    "in_progress": { "color": "yellow" },
    "review": { "color": "blue" },
    "done": { "terminal": true, "satisfiesDependencies": true, "color": "green" },
    "cancelled": { "terminal": true, "color": "gray" }
  },
  "server": { "port": 3000 },
  "output": { "format": "text", "defaultLimit": 20, "maxBytes": 16384 }
}
```

`color`: `black`, `red`, `green`, `yellow`, `blue`, `magenta`, `cyan`, `white`,
`gray`, `none`. Без поля используется стандартная тема. Цвет не влияет на
`terminal` и `satisfiesDependencies`; их значения по умолчанию — `false`.

`server.port`: целое число от `0` до `65535`, по умолчанию `3000`.
`0` выбирает свободный порт. Секция `server` необязательна для существующих конфигов.
Порт читается при запуске; после его изменения перезапустите сервер.

## Создание и изменение

```bash
export TASKS_ACTOR=orchestrator

tasks-cli create --title "API пользователей" --group backend --tags api,registration --stdin <<'MD'
## Требования

- Добавить POST /users.
- Возвращать ошибки в формате {code, message}.
MD

tasks-cli create --title "Форма регистрации" --group frontend --parent <parent-id> --depends-on <backend-id>
tasks-cli update <task-id> --summary 'Контракт готов' --if-revision 3
```

Поля `create`/`update`: `--title`, `--description`, `--description-file`, `--stdin`,
`--summary`, `--summary-file`, `--status`, `--group`, `--parent`, `--tags`,
`--depends-on`, `--assignee`.

Название при создании можно передать позиционно: `create "API пользователей"`.
Это альтернатива `create --title "API пользователей"`; одновременная передача
обоих вариантов считается ошибкой. Отсутствующее название не создаёт задачу.

`--stdin` читает описание. `--description-file -` и `--summary-file -` также
читают stdin. Один поток нельзя использовать для нескольких полей одновременно.
`--file` и аналогичные параметры — необязательные источники ввода;
работа через CLI не требует создания внешних файлов с отчётами.

`--clear-group` и `--clear-parent` снимают соответствующие значения.
Пустые `--description ""`, `--summary ""`, `--tags ""`, `--depends-on ""` очищают
поле. Отсутствующее поле сохраняется. Теги и зависимости передаются через запятую;
`--depends-on` заменяет весь набор, а `deps add/remove` меняет одну связь.

Задачи получают единственный числовой ID от 1: `get 3`, `status 3 done`,
`--parent 1`, `--depends-on 2,3`. Новый ID равен максимальному существующему
плюс один; пропуски не заполняются. Все JSON-ссылки содержат эти же числа,
файл задачи 3 — `.tasks/3.json`. В ответе записи: `{id: 3, revision: 1}`.
Поле `number` и UUID задач в текущем формате отсутствуют.

### Миграция старых задач

Для хранилища с UUID-документами v1 или прежней структурой `.tasks/tasks/`:

```bash
tasks-cli migrate --actor orchestrator
tasks-cli validate
```

Уникальный старый `number` становится новым `id`. При совпадении номер сохраняет
более ранняя задача; остальным и задачам без номера выдаются ID выше максимума.
Если номеров не было вообще, ID назначаются от 1 в порядке создания.
Уже существующие документы v2 сохраняют свои ID. Переносятся `parentId`,
`dependsOn` и вложенные `taskId`, содержимое записей сохраняется. У изменённых
задач увеличивается revision и указывается автор миграции.

Ответ содержит `migrated`, `total`, а при переносе — `backupPath` и `mappingPath`.
В резервной копии находятся исходные файлы, в `ids.json` — соответствие UUID → ID.
Они остаются локально в соседнем `.tasks-runtime/migration-…` и исключены из Git.
Старый каталог целиком сохраняется в резервной копии, включая его служебные данные.
Документы публикуются непосредственно в `.tasks/<id>.json`. Перенос структуры v2
сохраняет ID, поля и revision. `flattened` в ответе отмечает перенос вложенного каталога.
Новый каталог готовится до публикации. Прерванный перенос блокирует рабочие
операции с понятной ошибкой; повторный `migrate` завершает его.
На уже обновлённых данных команда не делает записей и возвращает `migrated: 0`.

## Чтение задачи и контекста

```bash
tasks-cli list --ready --group frontend
tasks-cli list --all
tasks-cli list --status review --assignee frontend-agent
tasks-cli list --parent <parent-id> --tag registration
tasks-cli list --search "формат ошибок"
tasks-cli get <task-id>
tasks-cli get <task-id> --full
tasks-cli get <task-id> --fields id,status,summary --format json
tasks-cli description <task-id>
tasks-cli summary <task-id>
tasks-cli links <task-id>
tasks-cli tree <parent-id> --depth 2
```

`get` показывает карточку и число записей, `--full` добавляет все комментарии
и отчёты. Хранение общего контекста в одном файле не увеличивает автоматически
объём каждой выдачи агенту.

Обычный `list` показывает все незавершённые задачи, включая заблокированные:
статусы с `terminal: false`. В начальном конфиге это `todo`, `in_progress` и `review`.
`done`, `cancelled` и другие конечные статусы скрыты. `--all` включает их,
а явный `--status` выбирает только указанный статус, в том числе конечный.
`--ready`, группа, исполнитель и остальные фильтры дополнительно сужают выборку.

```bash
tasks-cli list                  # Текущая работа и очередь
tasks-cli list --ready          # Что можно взять сейчас
tasks-cli list --status review  # Что ожидает проверки
tasks-cli list --status done    # Выполненные задачи
tasks-cli list --all            # Включая выполненные и отменённые
```

Текстовый `list` разделён на секции групп с отдельными таблицами. Группы идут
по имени, «Без группы» — последней; внутри секции задачи расположены по ID.
На узком экране сохраняются секции, а строки становятся карточками.
Пустые группы не показываются. Возле статуса отображаются до трёх ID блокеров
и количество остальных; полный набор доступен через `links` и поле `blockedBy` в JSON.
Если открытых задач нет, выводится подсказка истории `tasks-cli list --all`.
Пустая выборка по явным фильтрам имеет отдельное сообщение.
JSON остаётся плоским списком по ID.

`list --sort board` использует порядок статусов из конфига и сохранённый порядок
карточек; без этого параметра остаётся порядок по ID.

`description` и `summary` возвращают непосредственно многострочный Markdown
в текстовом режиме. Абзацы, пустые строки и отступы кодовых блоков сохраняются.
В JSON-режиме многострочные поля представлены массивами строк.

`links` показывает родителя, детей, зависимости, блокируемые задачи и актуальные
блокеры с номерами, названиями и цветными статусами. `tree` в текстовом режиме
рисует иерархию, в JSON возвращает список с `depth`; корень имеет глубину 0.
При ограничении глубины устанавливается `meta.truncated`.

## Обзор проекта

```bash
tasks-cli overview
tasks-cli overview 1 --limit 20
tasks-cli overview 9 --format json
tasks-cli overview --review-status qa,acceptance
```

`overview [id]` — вычисляемая сводка существующих задач. Читает один согласованный
снимок через Core, проверяет граф и не изменяет документы. Автор для чтения не нужен.
Без ID область — весь проект; с ID — сама задача и все её потомки по `parentId`.
Неизвестный ID возвращает `TASK_NOT_FOUND`, некорректный — `INVALID_ID`.

### Разделы и подсчёты

1. **Прогресс крупных задач.** Все задачи области, у которых есть непосредственные
   подзадачи. Для каждой приведены состояние родителя и отдельные счётчики детей.
   Вложенные родители тоже показаны; порядок — по ID. Понятие эпика не требует
   отдельного типа задачи или обязательного тега.
2. **Готовы к работе.** Те же правила, что у `list --ready`: исполнитель отсутствует,
   статус входит в `readyStatuses`, все зависимости удовлетворены. В выборку могут
   входить обычные родительские задачи, если они соответствуют этим правилам.
   Порядок — по ID.
3. **На проверке.** Задачи области в выбранных статусах. По умолчанию — `review`,
   если он существует и неконечный. Иначе раздел пуст с подсказкой параметра.
   `--review-status` принимает одно или несколько имён через запятую; неизвестный
   статус даёт `UNKNOWN_STATUS`, конечный — `INVALID_REVIEW_STATUS`.
4. **Основные блокеры.** Неудовлетворённые прямые зависимости открытых задач области,
   **у которых нет подзадач**. Родительские агрегаты не увеличивают влияние блокера
   только за счёт структурной связи с детьми. Сам блокер может быть родительской
   задачей, если от неё зависит такая работа.

Влияние выражено тремя показателями:

| Поле                        | Значение                                                                  |
| --------------------------- | ------------------------------------------------------------------------- |
| `blockedCount`              | Число непосредственно зависимых открытых задач без подзадач в области     |
| `unblocksCount`             | Для скольких из них это единственная неудовлетворённая зависимость        |
| `readyAfterCompletionCount` | Сколько разблокируемых задач также свободны и находятся в `readyStatuses` |

Разблокировка не равна готовности к `claim`: задача может уже иметь исполнителя
или находиться в другом статусе. Транзитивные потомки не прибавляются к прямому влиянию.
Очередь проверки и блокеры сортируются по убыванию `readyAfterCompletionCount`,
затем `unblocksCount`, затем `blockedCount`; равенство разрешается по возрастанию ID.

Числа описывают результат **гипотетического успешного завершения одного блокера**.
Если сам блокер ожидает зависимости, его `blockedByCount` это показывает; `links`
раскрывает препятствия. Отменённая зависимость остаётся блокером до изменения
связи или успешного выполнения по правилам проекта.

Связи проверяются по полному графу, даже при обзоре одного дерева. Блокер за пределами
области имеет `outsideScope: true` и пометку `[вне области]` в тексте. Его влияние
считается только на выбранную работу; посторонние потребители не увеличивают рейтинг.

### Общие счётчики

- `counts` — все карточки области, включая родительские и конечные.
- `leafCounts` — только карточки без подзадач, включая отменённые.
- `progress.items[].children` — только непосредственные дети этого родителя.

Во всех трёх случаях: `total`, `open`, `completed`, `terminal`, `byStatus`.
`completed` определяется `satisfiesDependencies`, `terminal` — свойством `terminal`.
Конечных без успеха — `terminal - completed`; произвольные названия статусов не
подменяют эту семантику. `byStatus` содержит все настроенные статусы, включая нулевые.

Общие и дочерние счётчики имеют разные области, их не следует складывать.
Например, проект и его эпики входят в `counts`, но не в `leafCounts`.

### Ограничение вывода и JSON

`--limit N` задаёт максимум строк **каждого** раздела: 1–100, по умолчанию 5.
Он не использует `output.defaultLimit`, поскольку обзор должен оставаться компактным.
Каждый раздел имеет `{ total, items }`, где `total` относится к полной выборке.

`--max-bytes` учитывает фактический формат, UTF-8 и ANSI. При нехватке места
снижается общий лимит строк разделов с сохранением хотя бы одной строки в каждом
непустом разделе. Счётчики не сокращаются. Если минимальный обзор не помещается,
возвращается `RESPONSE_TOO_LARGE` с требуемым размером; увеличьте бюджет.

JSON использует стандартную оболочку `{ ok, data, meta }`:

| Поле `data`            | Содержимое                                                |
| ---------------------- | --------------------------------------------------------- |
| `root`                 | Компактная выбранная задача либо `null` для всего проекта |
| `version`              | Версия согласованного снимка полного проекта              |
| `limit`                | Запрошенный максимум строк на раздел                      |
| `counts`, `leafCounts` | Полные счётчики области                                   |
| `reviewStatuses`       | Фактически используемые статусы проверки                  |
| `progress`             | Родительские задачи и счётчики их детей                   |
| `ready`                | Задачи, которые можно захватить сейчас                    |
| `review`               | Задачи проверки с показателями влияния                    |
| `blockers`             | Блокеры с показателями влияния и `outsideScope`           |

Компактная задача содержит `id`, `title`, `status`, `group`, `assignee`, `parentId`,
`revision` и `blockedByCount`. Описания, summary и история читаются отдельно.

`meta.truncated` означает, что в одном из разделов показаны не все строки;
`meta.limitedByBytes` — что строки дополнительно сокращены байтовым бюджетом.
Обзор не имеет курсора: повторите его с большим лимитом/бюджетом или откройте
нужную область и подробности через `list`, `get`, `links`, `tree`.

## Назначение и зависимости

```bash
tasks-cli assign <task-id> backend-agent
tasks-cli claim <task-id> --actor backend-agent
tasks-cli claim <task-id> --status in_progress --actor backend-agent
tasks-cli status <task-id> in_progress --actor backend-agent
tasks-cli status <task-id> done --actor backend-agent
tasks-cli release <task-id> --actor backend-agent
tasks-cli release <task-id> --force --actor orchestrator
tasks-cli deps add <task-id> <dependency-id>
tasks-cli deps remove <task-id> <dependency-id>
```

`claim` атомарно занимает свободную доступную задачу. Доступность определяется
`readyStatuses`, отсутствием исполнителя и выполненными зависимостями.
Без `--status` статус сохраняется. С `--status` назначение и смена статуса
выполняются атомарно; недопустимый статус отменяет всю операцию.
`assign` — явное назначение оркестратором, допускающее замену исполнителя.
`release` снимает исполнителя, сохраняя статус.

Удовлетворённость зависимости определяется `satisfiesDependencies`, а не
названием статуса. Отмена не считается успешным выполнением. Переоткрытие
зависимости обновляет блокеры, но не меняет автоматически статус других задач.

Команды изменения полей карточки поддерживают `--if-revision`.
Добавление комментария или отчёта также увеличивает `revision`: это изменение
того же самодостаточного документа.

## Комментарии

```bash
tasks-cli comment add <task-id> --stdin <<'MD'
## Проверка

Основной сценарий работает.

Осталось проверить повторный запрос.
MD

tasks-cli comment list <task-id> --author backend-agent --limit 10
tasks-cli comment get <task-id> <comment-id>
```

Источник выбирается один: `--text`, `--stdin` или `--file`.
Список показывает автора, время и короткий многострочный фрагмент.
`comment get` выводит полную запись. Комментарии добавляются новыми записями;
исправление можно описать следующим комментарием.

## Отчёты агентов

````bash
tasks-cli log add <task-id> --kind summary --title "Результат работы" --stdin <<'MD'
## Сделано

- Реализован API.
- Добавлены интеграционные проверки.

## Проверка

```text
pnpm test
```

Все тесты прошли.
MD

tasks-cli log list <task-id> --kind summary --limit 5
tasks-cli log get <task-id> <log-id>
tasks-cli log search <task-id> --query "интеграционные" --kind summary
````

Типы: `progress`, `decision`, `execution`, `error`, `summary`.
Дополнительно доступны `--summary` с многострочным кратким результатом
и `--session-id`. Заголовок `--title` остаётся однострочным.

`log get` возвращает отчёт целиком. `log list` показывает краткие саммари;
`log search` возвращает подходящие отчёты, номер первой подходящей строки,
число подходящих строк и фрагмент. Поиск буквальный, с учётом регистра.

Фильтры списка и поиска: `--author`, `--kind`, `--session-id`, `--since`, `--until`.
Дата задаётся как `YYYY-MM-DD` или ISO 8601 с часовым поясом.

## Ограничения и пагинация

- Название задачи и заголовок отчёта: до 1024 байт UTF-8.
- Описание и тело отчёта: до 256 КиБ.
- Саммари: до 4096 байт.
- Комментарий: до 64 КиБ.
- Один JSON задачи: до 16 МиБ. Превышение проверяется до сохранения.

Списки задач, групп, комментариев и отчётов, а также поиск поддерживают
`--limit` от 1 до 100, `--cursor` и `--all`. В JSON ответе используются `data.items`,
`meta.hasMore`, `meta.nextCursor`, `meta.truncated`. В текстовом режиме курсор
показывается строкой `Продолжение: --cursor ...`.

**У `list`** без `--limit` нет ограничения числа задач. CLI старается выдать всю
выборку в пределах байтового бюджета; иначе возвращает страницу с курсором
и текстом «показано N из M». Явный `--limit N` дополнительно ограничивает количество.
`--all` отвечает только за включение конечных статусов и совместим с `--limit`
и `--cursor`. На следующей странице нужно повторить `--all`, если он был указан.

**У списков групп, комментариев и отчётов, включая поиск отчётов,** размер страницы
по умолчанию берётся из `output.defaultLimit`. Их `--all` возвращает все записи одним
ответом и несовместим с `--limit` / `--cursor`. Если такой полный ответ не помещается,
возвращается `RESPONSE_TOO_LARGE` с `requiredBytes`.

Курсор привязан к команде и фильтрам; при продолжении можно менять размер страницы
и байтовый бюджет. Задачи идут по возрастанию ID, комментарии и отчёты — от новых к старым,
группы — по имени. Это постраничное чтение актуальных данных.

CLI измеряет реальный объём UTF-8 ответа, включая ANSI-коды. Списки уменьшают страницу без пропуска
продолжения. Для слишком большой неделимой карточки или записи возвращается
`RESPONSE_TOO_LARGE`: увеличьте `--max-bytes` или выберите нужные поля.

## Локальный сервер

```bash
npx @gromlab/tasks-cli server --actor human --open
npx @gromlab/tasks-cli server --actor human --port 3001 --config ./tasks.config.json
TASKS_PORT=3002 npx @gromlab/tasks-cli server --actor human
```

NestJS на `127.0.0.1` предоставляет API, OpenAPI и Swagger; статическая сборка React
подключается из `dist/web` относительно манифеста CLI и открывается на `/`.
HTML, JS, CSS, шрифты и API обслуживаются одним сервером на одном порту.
Полный npm-дистрибутив всегда включает UI; исходный CLI может работать без него.
`--open` открывает корневой адрес в браузере,
`--port 0` выбирает свободный порт, `Ctrl+C` корректно останавливает приложение.
С `--format json` первое сообщение содержит `data.url`, `data.actor`, `data.pid`.
Порт выбирается в порядке `--port` → `TASKS_PORT` → `server.port` в выбранном
`tasks.config.json` → `3000`. Параметры `--actor`, `--config` имеют приоритет над
`TASKS_ACTOR`, `TASKS_CONFIG`. Без фронтенда `/` возвращает 404, а `/api/docs` предоставляет Swagger UI.
Реализованы задачные маршруты, история, доска и SSE. Контракт описан в
[API.md](https://github.com/gromlab-ru/tasks-cli/blob/main/packages/contracts/docs/API.md).

## Ошибки и проверка данных

```bash
tasks-cli validate
```

Проверка читает каждый самодостаточный документ, включая комментарии и отчёты,
проверяет схемы, принадлежность записей, статусы, ссылки и циклы.

| Код завершения | Значение                                            |
| -------------- | --------------------------------------------------- |
| 0              | Успех                                               |
| 2              | Неверные параметры или конфигурация                 |
| 3              | Объект или файл не найден                           |
| 4              | Конфликт revision, назначения, графа или блокировки |
| 5              | Повреждение данных или ошибка ввода-вывода          |

В JSON-режиме ответ имеет форму `{ "ok": true, "data": ..., "meta": ... }`
либо `{ "ok": false, "error": { "code", "message", "details" } }`.
Слишком большие детали ошибки заменяются `details.omitted: true`.
Синтаксические ошибки содержат `details.hint` со справкой именно той команды,
в которой возникла ошибка. Неизвестная подкоманда перечисляет допустимые варианты.
