# Unit Architecture

Выбирай владельцев и границы ответственности, а не генерируй одинаковые деревья каталогов. Этот skill задаёт порядок действий; точные правила находятся в `reference/docs` рядом с установленным `SKILL.md`.

## Источники решений

- Канон в references определяет инварианты. Читай относящиеся к задаче главы до выбора решения, а не после него.
- Применимый профиль проекта определяет frontend root, пути слоёв, маркеры фасетов, внутреннюю структуру и смысл групп. Он конкретизирует канон, но не отменяет его правила.
- Фактические файлы, импорты и потребители показывают состояние проекта, но не доказывают его архитектурную корректность.
- Имена `index.ts`, `client.ts`, `lazy.ts`, группы `pages/layouts/screens/widgets` и сегменты из примеров не являются значениями по умолчанию. Используй только соглашения применимого профиля.

## Рабочий алгоритм

1. Определи намерение: объяснение, проектирование, реализация, миграция или ревью. Объяснение и ревью сами по себе не разрешают менять код.
2. Найди профиль в инструкциях и документации проекта. Установи его область действия и соглашения. Если изменяется архитектурная граница, проверь полноту профиля по reference о профилях.
3. Исследуй затронутые файлы, маркеры, импорты, экспорты и реальных потребителей. Установи ближайшего владельца либо подтверждённое исключение для framework-файла `app` или допустимого ресурса `shared`.
4. Сформулируй результат ответственности без названий библиотек и типов файлов. Прочитай тематические references по таблице ниже; выбери слой и действие: оставить внутри владельца, выделить юнит, поднять его или изменить контракт.
5. Определи минимальный API для фактических потребителей, фасеты и среды. Для состояния и ресурсов раздели владельца механизма жизненного цикла и место подключения экземпляра.
6. Проверь затронутый свёрнутый граф: каждый файл относится к ближайшему юниту, вложенные юниты являются отдельными узлами. Учти обычные и динамические импорты, `import type` и реэкспорты. Исследуй и обратные пути, необходимые для обнаружения циклов, а не только изменённые строки.
7. Внеси минимальное согласованное изменение, если задача требует реализации. Не создавай пустые слои, сегменты, фасеты и API для предполагаемых потребителей.
8. Проверь результат по checklist ниже. В ответе сообщи существенные изменения, проверки и ограничения, а не весь внутренний процесс рассуждения.

## Выбор владельца и действия

| Ситуация | Действие |
|---|---|
| Framework entry, инициализация, конфигурация маршрута | Оставь техническую интеграцию в `app`. Подключи проекцию маршрута через фасет композиции; не собирай продуктовый интерфейс в framework-файле |
| Новый Provider или context | Найди владельца по смыслу ответственности. Храни реализацию у него, а не в `app`. Глобальное подключение возможно в `app`, узкое — в композиции или соответствующем юните |
| Страница, layout, screen, widget | Реализуй вёрстку, локальное состояние интерфейса и координацию в `compositions`. Свяжи визуал с доменными данными и операциями через публичные API |
| Самостоятельная область композиции | Предпочти вложенный юнит с собственным контрактом. Колоцируй его у родителя; каждый ребёнок может выделять следующие области |
| Обёртка, divider, технический DOM-блок | Оставь разметкой или внутренним компонентом без фасета, если самостоятельной ответственности нет |
| Предметные модели, операции, состояние и исходы | Размести в `domains`. Адаптируй технические источники к предметному контракту здесь, не в композиции |
| UI напрямую использует типы, операции или состояние своего домена | Оставь внутренним компонентом домена без собственного маркера. При необходимости публикуй через фасет домена |
| Самостоятельная доменная UI-проекция без импортов родителя | Рассмотри вложенный юнит с независимым входным контрактом; не создавай такой контракт искусственно ради симметрии с композициями |
| Техническая интеграция без предметного смысла | Размести в `infra`; JSX или Provider не меняют техническую ответственность |
| Универсальное визуальное поведение без продуктового смысла | Размести в `ui`. Повторное использование или props-based API не делают ProductCard универсальной |
| Чистый детерминированный фундамент | Рассмотри `shared`; сеть, storage, browser runtime и framework lifecycle не относятся к этому слою |
| Прямой API ребёнка нужен вне родителя | Подними юнит в подходящую общую область вместе с реализацией и детьми; обнови потребителей и удали старые пути |
| Возможность ребёнка является частью общего контракта родителя | Допустима публикация через фасет родителя. Не используй цепочку реэкспортов вместо подъёма для самостоятельных прямых потребителей |

Готовая возможность не обязательно является готовым UI. Композиция может строить собственный интерфейс из `ui`, данных и операций домена. Не выноси каждую локальную деталь в другой слой и не переноси предметные правила в композицию ради удобства вызова.

Подключение Provider не меняет владельца. Например, `app` может вызвать публичную фабрику, передать конфигурацию и собрать JSX-дерево Providers. Но ThemeProvider, context и useTheme остаются в `ui/theme`; потребители импортируют фасет владельца, а не место подключения.

## Границы и зависимости

- Наличие маркера фасета объявляет папку юнитом независимо от размера и имени. Если нет самостоятельной ответственности, реального контракта или непустого фасета, диагностируй некорректный юнит, а не локальный barrel. Зарезервированные маркеры нельзя использовать для внутренних реэкспортов.
- Группы содержат юниты и группы, но не собственную реализацию. Сегменты и внутренние папки не имеют фасетов и не образуют отдельных узлов графа.
- У юнита один логический API. Межюнитный импорт проходит только через разрешённый фасет и подчиняется матрице слоёв; совпадение слоя не разрешает циклы или глубокие импорты.
- Фасет вложенного юнита доступен непосредственному родителю. Ребёнок не импортирует родителя, предков или соседних детей, включая их типы. Родитель координирует детей через их контракты.
- Props и callbacks нужны для связи с родителем и соседями, но не являются единственным источником возможностей: ребёнок может использовать разрешённые внешние фасеты.
- Два отображения одним владельцем не требуют подъёма. Если Header нужен MainLayout и CabinetLayout напрямую, подними Header вместе с Navigation и Search; дети останутся доступны только Header, пока им самим не нужны внешние прямые потребители. Общую группу выбирай по профилю.
- Проверяй смысл импорта отдельно от его направления: разрешённая связь `compositions → infra` не разрешает композиции превращать transport DTO в предметную модель.

## Фасеты, состояние и среды

Перед изменением API составь карту «потребитель → возможность → способ потребления → среда». Не добавляй фасет без подтверждённой потребности и не экспортируй внутренние stores, contexts или helpers только ради тестов.

При разделении сред универсальный фасет не должен достигать несовместимого runtime-кода. Проверяй весь транзитивный исполняемый граф: имя файла, `typeof window`, tree shaking или `use client` не доказывают безопасность. Исполняемую возможность размещай в минимально подходящем фасете без дублирования между средами. Type-only связь может не создавать runtime-зависимость, но остаётся архитектурной зависимостью.

Владелец определяет механизм создания, хранения и очистки ресурсов, точка подключения — область действия в пределах его контракта. Не переноси реализацию к месту инициализации. Не маскируй programming defects под ожидаемые предметные исходы.

## Ограничения и остановка

Не представляй архитектуру идеальным решением и не диагностируй известный компромисс как нарушение. Отсутствие фасета у UI, напрямую использующего родительский домен, само по себе корректно. Если отдельная граница важна для задачи, открой разбор ограничений и объясни конфликт: внутренний компонент не получает отдельного узла графа и межюнитной защиты от остальной реализации домена.

Не обещай устранить эту цену без изменения связей. Предложи применимые варианты с последствиями: внутренний компонент, независимый входной контракт или пересмотр владельца. Не создавай искусственные props и не поднимай UI только ради обхода запрета. Не разрешай обратные импорты как исключение из канона самостоятельно.

Задай адресный вопрос, если после исследования остаётся неопределённость, влияющая на решение:

- Нет применимого профиля или он не определяет маркеры, структуру либо смысл используемых групп при создании или изменении границы. Приостанови изменение границы; исследование и локальная работа внутри установленного владельца без новой границы допустимы.
- Нельзя установить ответственность, ожидаемые предметные исходы, владельца или фактических потребителей.
- Неясны среда, область экземпляра, инициализация или очистка ресурса.
- Требование пользователя или профиль конфликтует с каноном. Покажи конкретный конфликт; не подменяй его молчаливым исключением.

Не задавай вопросы о соглашениях, которые уже однозначно установлены профилем и кодом. В остальных случаях продолжай до результата и проверки.

## Проверка и отчёт

После изменения проверь:

- У каждого затронутого файла установлен владелец; слой соответствует ответственности, а не типу файла.
- Новые маркеры объявляют корректные юниты; публичный API минимален, фасеты непусты, структура соответствует профилю.
- Потребители используют фасеты, включая type-only и динамические импорты; матрица, вложенность и отсутствие циклов соблюдены.
- После переноса не осталось старых глубоких путей или второго владельца той же ответственности; вложенные дети не раскрыты автоматически.
- Среды и жизненный цикл проверены в необходимом объёме. Запусти доступные проверки проекта; не выдавай ручную проверку за автоматическую валидацию графа.

Для реализации кратко сообщи результат, существенные изменения владельцев или API, выполненные проверки и оставшиеся риски. Не перечисляй все прочитанные references и рёбра графа без необходимости. Для проектирования объясни выбранную границу и значимые компромиссы; не меняй код вместо обсуждения.

В ревью сначала показывай замечания по убыванию риска. Для каждого приведи `path:line`, наблюдаемый факт, нарушенное правило с точным reference и необходимое изменение владельца, фасета или зависимости. Укажи рёбра графа, если вывод зависит от них. Отделяй нарушение инварианта от рекомендации или известного ограничения. Один `fetch`, Provider, hook, store, большой файл или внутренний доменный компонент без фасета не доказывает нарушение.
