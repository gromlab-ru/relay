# Доменные юниты

Доменный юнит — юнит слоя `domains`, который владеет одной предметной ответственностью.

## Предметный контракт

Публичный API домена выражается языком предметной области:

```ts
export type Product = {
  id: ProductId
  name: string
  availability: ProductAvailability
}

export { getProducts } from './libs/get-products'
export { ProductCard } from './ui/product-card/product-card'
```

Контракт не открывает transport response, ORM entity, generated SDK internals или framework store, если они не являются продуктовой моделью.

## Адаптация источников

Домен может зависеть от `infra` и адаптировать технический источник к предметному смыслу.

```text
domains/products → infra/backend-api
```

HTTP client сообщает status, payload и transport error. Products интерпретирует их как Product, недоступность каталога или другой предметный исход.

Композиция не должна выполнять эту адаптацию только потому, что инициирует загрузку из UI.

Source boundary является смысловой границей, а не обязательным названием сегмента. В примерах относящиеся к ней файлы могут находиться в `libs`, но команда приложения вправе выбрать другую внутреннюю структуру.

## Исходы и defects

Домен различает ожидаемые предметные исходы и programming defects. Предметный исход является частью контракта сценария: например, каталог недоступен или Product больше не существует. Нарушенный внутренний инвариант остаётся defect и не маскируется под ожидаемый результат.

Публичный API открывает runtime-механизм идентификации исхода только при наличии реального потребителя. Внутренние transport errors и структуры внешнего SDK не становятся частью доменного контракта автоматически.

## Продуктовое состояние

Состояние принадлежит домену, если его смысл и жизненный цикл определяются предметной ответственностью. Способ реализации состояния архитектура не задаёт.

```text
products/
├── index.ts
├── types/
│   └── product.type.ts
├── libs/
└── stores/
```

`types`, `libs` и `stores` здесь являются сегментами, выбранными для примеров, а не обязательной формой домена.

## Жизненный цикл

Домен владеет механизмом жизненного цикла предметного состояния и ресурсов, созданных для его сценария. Его контракт определяет допустимые области экземпляра и правила инициализации и очистки. Framework Provider, store или hook остаются внутренними механизмами этой ответственности без собственных маркеров фасетов, пока не появляются отдельная ответственность и независимый контракт.

Готовый Provider может инициализироваться и подключаться в `app` для глобальной области или в `compositions` для области страницы либо другой проекции. Точка подключения выбирает область действия в пределах доменного контракта; код Provider, контекста, состояния и операций остаётся в домене. Потребители обращаются к фасету домена, а не к месту подключения.

## Доменный UI

UI остаётся в домене, если он выражает конкретную предметную ответственность и меняется вместе с ней.

Обычная форма такого UI — внутренний компонент без собственного маркера фасета, если ему нужны типы, операции, состояние или другая реализация домена. Он может импортировать внутренние файлы своего владельца напрямую; внешним потребителям его при необходимости открывает фасет домена. Например, SignInForm использует операции Authentication, а композиция страницы определяет её размещение, не реализуя правила авторизации.

```text
products/
├── index.ts
└── ui/
    └── product-card/
        ├── product-card.tsx
        ├── styles/
        │   └── product-card.module.css
        └── types/
            └── product-card.type.ts
```

В этом дереве ProductCard является компонентом Products, а не отдельным юнитом. Фасет Products публикует его из файла `./ui/product-card/product-card`.

### Независимый вложенный UI-юнит

ProductCard может стать вложенным юнитом Products, если владеет самостоятельной проекцией, имеет собственный входной контракт и не импортирует Products, его предков или соседних детей. Тогда папка получает маркер фасета, Products импортирует этот фасет и может реэкспортировать возможность через свой API. Внешний потребитель не импортирует `products/ui/product-card` напрямую.

Предметный UI или hook, использующий контракт либо реализацию Products, остаётся внутренней папкой без маркера фасета. Его публикует корневой фасет Products. Добавление маркера такой папке объявит вложенный юнит и сделает обратный импорт Products недопустимым; если Products импортирует или реэкспортирует ребёнка, возникнет цикл.

Не следует выделять UI-юнит только ради симметрии с композициями или создавать искусственный входной контракт, чтобы скрыть естественную связь компонента с доменом. Предпочтение вложенных юнитов при вёрстке композиций не является требованием к доменному UI.

У этого решения есть цена: внутренний компонент не получает отдельного узла графа и защиты своих файлов от остальной реализации домена по правилам межюнитных импортов. Допустимая форма компонента не всегда удовлетворяет потребность в самостоятельной границе. Этот недостаток и открытый вопрос о его решении описаны в [разборе ограничений доменного UI](./trade-offs.md#доменный-ui-и-границы-юнитов).

Если визуальный элемент не имеет предметного смысла, он принадлежит `ui`. Доменный ProductCard может зависеть от универсальных Button и Badge.

## Связи доменов

Допустима направленная связь:

```text
domains/checkout → domains/products
```

Она означает, что Checkout использует публичный предметный контракт Products. Обратная зависимость запрещена, если создаёт цикл. При взаимном знании необходимо:

- уточнить владельца сценария;
- передать данные через контракт вызывающего юнита;
- поднять координацию в `compositions`;
- выделить третью предметную ответственность, только если она реально существует.

## Ошибочные границы

Не следует:

- создавать домен для каждого backend endpoint;
- переносить transport DTO в публичный предметный контракт;
- размещать весь продуктовый UI в `compositions` только из-за JSX;
- размещать ProductCard в `ui` из-за повторного использования;
- давать вложенному UI-юниту обратный импорт Products;
- добавлять маркер фасета внутреннему hook или UI, который зависит от Products;
- создавать универсальный `common`-домен без одной ответственности.
