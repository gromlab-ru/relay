# Архитектурный профиль проекта

Unit Architecture определяет владельцев, границы и направления зависимостей, но не выбирает за команду физические соглашения приложения. Эти решения фиксируются в архитектурном профиле проекта.

Профиль читается до проектирования, создания или изменения архитектурной границы. Он не заменяет архитектурный канон и не переопределяет смысл юнита, фасета, группы или сегмента. Профиль конкретизирует только те варианты, которые канон намеренно оставляет проекту.

Unit Architecture не задаёт имя, формат или расположение файла профиля. Команда выбирает их сама и делает профиль обнаружимым из основной документации приложения или инструкций для разработки.

## Область действия

Профиль определяет область, в которой его соглашения однозначны:

- frontend root;
- приложение или пакет, если репозиторий содержит несколько независимых областей;
- поддерживаемые среды выполнения;
- локальное сопоставление путей со слоями.

Если в репозитории действуют несколько профилей, для каждого пути должна однозначно определяться область применимого профиля.

## Обязательные решения

До изменения архитектурных границ команда фиксирует следующие решения.

### Публичные фасеты

Для каждого маркера фасета указываются:

- физическое имя файла или пути;
- назначение и способ потребления;
- допустимая среда выполнения;
- ограничения на экспорт и транзитивные зависимости.

Если специализированные фасеты не нужны, профиль явно устанавливает единственный маркер. Имена `index.ts`, `client.ts`, `browser.ts` и `server.ts` не являются обязательными.

### Структура юнита

Профиль определяет локальные соглашения внутренней формы:

- используется ли свободная структура или ограниченный словарь сегментов;
- что означает каждый закреплённый сегмент;
- какие соглашения действуют для имён и колокации файлов;
- есть ли дополнительные правила для отдельных слоёв или сред.

Профиль может прямо оставить внутреннюю структуру свободной. Он не обязан вводить сегменты или одинаковый шаблон каталогов. Пустые папки и файлы ради соответствия форме не создаются.

### Группы compositions

Если слой `compositions` использует группы, профиль перечисляет их и для каждой формулирует:

- ответственность классифицируемых юнитов;
- отличие от соседних групп;
- существенные ограничения потребителей или среды, если они есть.

Профиль может отказаться от групп полностью. Группы не образуют дополнительную архитектурную иерархию, не владеют реализацией и не меняют матрицу зависимостей.

## Дополнительные решения

При необходимости профиль также фиксирует:

- сопоставление framework-файлов с `app` и отображаемых проекций с `compositions` для выбранного router или framework;
- правила динамической загрузки;
- aliases и допустимые формы межюнитных импортов;
- словарь профильных сегментов отдельных слоёв;
- проектные проверки и ограничения tooling.

Эти решения обязательны только внутри области конкретного профиля и не становятся требованиями Unit Architecture для других проектов.

Профиль не может разрешить хранение продуктовой реализации или кода Providers в `app`. Он уточняет framework-точки подключения готовых API и места сборки продуктового интерфейса в `compositions`, не меняя владельцев ответственностей.

## Отсутствие решения

Если применимый профиль не найден или не позволяет однозначно определить маркеры фасетов, структуру юнита либо смысл групп, изменение архитектурной границы приостанавливается до уточнения соглашения командой.

Это не запрещает исследование, локальный прототип или реализацию внутри существующего владельца без новой границы. Требование действует в момент, когда работа объявляет новый юнит, меняет его публичный API или переклассифицирует архитектурные сущности.

## Минимальная форма

```text
Область действия:
Frontend root:
Среды выполнения:
Слои и пути:

Маркеры фасетов:
- Маркер:
  Назначение:
  Потребление:
  Среда:

Структура юнита:
Сегменты:

Группы compositions:

Дополнительные правила:
Проверки:
```

Конкретный заполненный вариант приведён в [примере профиля React SPA](../examples/react-spa-project-profile.md).
