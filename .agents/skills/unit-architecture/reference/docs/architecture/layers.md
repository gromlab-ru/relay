# Слои

Слой описывает роль ответственности и ограничивает допустимые направления зависимостей. Он не задаёт внутреннюю структуру юнита и не заменяет владельца.

## Выбор слоя

Слой выбирается по ответу на вопрос:

> Какую ответственность обеспечивает юнит для приложения?

Тип файлов не является критерием. JSX может находиться в `app`, `compositions`, `domains`, `infra` и `ui`; Provider может принадлежать предметной, инфраструктурной или проекционной ответственности.

## app

`app` содержит только технический код интеграции с framework runtime. Он запускает приложение и подключает готовые публичные API, но не собирает продуктовый интерфейс.

Обычно слой владеет:

- точками входа;
- конфигурацией маршрутов и адаптацией публичных API к контрактам router;
- инициализацией и подключением глобального дерева готовых Providers;
- подключением глобальных Error Boundaries;
- application bootstrap;
- техническими механизмами запуска, необходимыми framework.

`app` не хранит реализацию продуктового UI, предметных сценариев, инфраструктурных клиентов, Providers, контекстов или связанного с ними состояния и поведения. Код этих возможностей находится у владельцев соответствующих ответственностей. Это относится и к UI, используемому только одним маршрутом, а не только к повторно используемым проекциям.

Framework-файл маршрута подключает отображаемую проекцию из `compositions` через её фасет. Layout, page или screen собирает продуктовый интерфейс вне `app`. Конкретные группы композиций определяет профиль проекта; обязательной цепочки между ними нет.

Техническая сборка дерева готовых Providers в `app` допустима, в том числе через JSX. `app` может вызвать публичную фабрику, передать конфигурацию и подключить Provider. Это не переносит код Provider и владение его ответственностью в `app`.

Технические entry-файлы framework могут находиться непосредственно в слое и не обязаны становиться юнитами, если framework определяет их форму и они не образуют самостоятельную ответственность.

### Место подключения Provider

Provider, контекст и доступ к нему принадлежат юниту соответствующей ответственности. Владелец определяет механизм создания, хранения и очистки состояния и ресурсов. Точка подключения задаёт область действия экземпляра в пределах этого контракта, но не меняет владельца.

Глобальный Provider может подключаться в `app`, а более узкий — в `compositions` или внутри соответствующего юнита. Потребители импортируют API владельца, а не места подключения, с соблюдением матрицы зависимостей и правил вложенности. Например, ThemeProvider и useTheme принадлежат `ui/theme`, даже если Provider подключён в корне приложения.

## compositions

`compositions` — слой реализации, вёрстки и сборки продуктового интерфейса. Его юниты создают целостные области продукта, связывая визуальное представление и действия пользователя с публичными API доменов, инфраструктуры, универсального UI и других композиций.

Сборка отображаемого продукта, включая проекцию конкретного маршрута, выполняется здесь. `app` только подключает готовую композицию к framework runtime.

Примеры ответственностей:

- layouts;
- pages;
- screens;
- widgets;
- другие продуктовые проекции, определённые проектом.

Композиция владеет устройством своей проекции: разметкой, оформлением, размещением областей, локальным состоянием интерфейса и координацией взаимодействий. Она получает предметные данные через доменные API, связывает действия пользователя с готовыми операциями и определяет отображение загрузки, ожидаемых исходов и результатов. Например, выбранный режим списка или открытость панели принадлежат проекции, а предметное состояние корзины и правила добавления товара — домену.

Готовая возможность не обязательно является готовым компонентом: домен может предоставлять данные и операции, а композиция строит для них интерфейс из `ui` и собственной реализации. Она не присваивает себе предметные правила, адаптацию transport DTO или техническую интеграцию. Доменный UI остаётся у домена, если выражает его ответственность; сборка продукта не означает перенос всего UI в `compositions`.

### Декомпозиция и колокация

При декомпозиции композиции предпочтение отдаётся вложенным юнитам самостоятельных областей интерфейса. Родитель определяет их размещение и координацию, а ребёнок владеет внутренним устройством своей области. Например, layout собирает Header, Content и Footer, а Header — Navigation и Search. Каждый уровень может выделять следующие вложенные ответственности.

Входные данные и возможности, необходимые для связи с родителем или соседями, передаются через контракт ребёнка, например props и callbacks. Ребёнок также может самостоятельно использовать разрешённые внешние фасеты. Требование не означает передачу всех зависимостей только через props и не отменяет запрет импорта родителя, предков и соседних детей.

Вёрстка колоцируется у ближайшего владельца. Если Header нужен только MainLayout, он остаётся вложенным юнитом. Когда его прямой API требуется также CabinetLayout, Header поднимается в общую область, например `compositions/widgets`, вместе со своей реализацией и детьми. Два отображения внутри одного владельца сами по себе не требуют подъёма.

Предпочтение юнитов не обязывает выделять каждый DOM-блок: технические обёртки, разделители и контейнеры без самостоятельной ответственности остаются внутренними компонентами или разметкой владельца.

Названия и назначение групп внутри слоя определяет архитектурный профиль проекта. В примерах используются `layouts`, `pages`, `screens` и `widgets`: каркасы, маршрутные страницы, экранные проекции и самостоятельные крупные области интерфейса. Это демонстрационная таксономия, а не обязательная структура или дополнительная иерархия зависимостей Unit Architecture.

## domains

`domains` владеет предметными возможностями приложения.

Доменный юнит определяет:

- предметный контракт;
- модели, правила и исходы;
- продуктовые данные и состояние;
- адаптацию внешних источников к предметному смыслу;
- доменный UI;
- жизненный цикл предметных ресурсов.

Один домен может использовать публичный API другого домена, если связь направлена и не создаёт цикл.

## infra

`infra` владеет техническими возможностями без предметного смысла.

Примеры:

- HTTP transport;
- storage;
- telemetry transport;
- Query Client;
- feature flag transport;
- browser API adapters;
- SDK внешней платформы до адаптации к предметной модели.

Инфраструктура сообщает технические результаты и ошибки, но не называет их продуктовыми исходами.

## ui

`ui` владеет универсальными визуальными ответственностями, не зависящими от предметной модели приложения.

Примеры:

- Button;
- Select;
- Modal;
- typography;
- theme;
- универсальные interaction primitives.

Универсальность означает отсутствие продуктового смысла, а не максимальную настраиваемость. ProductCard не становится `ui` из-за props-based API.

## shared

`shared` содержит детерминированный фундамент без продуктовой, проекционной, технической интеграционной или визуальной ответственности.

Примеры:

- чистые преобразования;
- базовые типы;
- compile-time helpers;
- небольшие неизменяемые значения;
- общие детерминированные алгоритмы.

Код `shared` не взаимодействует с сетью, browser runtime, storage, framework lifecycle или продуктовым состоянием.

Небольшие leaf-файлы могут находиться непосредственно в `shared`, когда у них нет самостоятельной ответственности и публичной границы. Связный набор с собственным контрактом оформляется юнитом.

## Матрица выбора

| Вопрос | Слой |
|---|---|
| Подключает готовые API к framework runtime, запускает приложение или объявляет маршруты? | `app` |
| Реализует вёрстку и сборку продуктового интерфейса, связывая визуал с публичными возможностями? | `compositions` |
| Определяет предметный смысл и исходы? | `domains` |
| Даёт техническую возможность без предметного смысла? | `infra` |
| Даёт универсальную визуальную возможность? | `ui` |
| Является чистым детерминированным фундаментом? | `shared` |

Если для ответственности подходят несколько строк, формулировка слишком описывает механизм и должна быть уточнена через результат для потребителя.
