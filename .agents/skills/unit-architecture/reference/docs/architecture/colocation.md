# Колокация и рост

Колокация размещает код рядом с ближайшим владельцем, ради которого этот код существует.

## Код рождается локально

Новая функция, тип, стиль или framework-файл сначала создаются в самой узкой области фактического использования. Предполагаемое будущее переиспользование не является основанием для преждевременного подъёма.

```text
header/
├── index.ts
├── header.tsx
└── format-header-title.ts
```

Если formatter нужен только реализации Header, он остаётся внутри юнита Header независимо от выбранной проектом папки.

Это правило распространяется и на вёрстку. Layout колоцирует свои Header, Content и Footer, а Header — Navigation и Search. Для самостоятельных областей с собственным контрактом в `compositions` предпочтительны вложенные юниты; техническая разметка без отдельной ответственности остаётся реализацией ближайшего владельца.

## Расширение потребителей

Когда код нужен нескольким частям одного юнита, он поднимается к их ближайшей общей внутренней области. Это изменение колокации, но не графа юнитов.

```text
До:
ui/header/format-title.ts

После появления второго внутреннего потребителя:
lib/format-title.ts
```

Названия `ui` и `lib` приведены только как пример проектной структуры.

## Появление ответственности

Когда локальная область начинает обеспечивать отдельный результат и нуждается в контракте, проект может объявить её вложенным юнитом, добавив маркер фасета.

```text
До:
main-layout/header.tsx

После появления самостоятельной проекции Header:
main-layout/ui/header/
├── index.ts
└── ...
```

Добавление маркера фасета объявляет новую архитектурную границу и отдельный узел графа. Если самостоятельной ответственности и связного контракта нет, результатом будет некорректно выделенный юнит, а не внутренняя папка с локальным `index.ts`.

Локальные component, hook, Provider и предметный UI, использующие контракт или реализацию родительского юнита, остаются внутренними папками без маркеров фасетов. Их возможности при необходимости публикует фасет ближайшего владельца.

## Расширение внешних потребителей

Вложенный юнит поднимается к ближайшей общей области, если нескольким внешним владельцам нужен его прямой API.

```text
До:
catalog-screen/ui/product-card/

После:
domains/products/ui/product-card/
```

Подъём выполняется вместе с контрактом, зависимостями и относящейся к ответственности реализацией. Нельзя оставлять двух владельцев одного смысла.

Например, Header из MainLayout поднимается в `compositions/widgets/header`, когда его прямой API требуется ещё и CabinetLayout. Его вложенные Navigation и Search перемещаются вместе с ним и остаются детьми Header, пока им самим не нужны внешние прямые потребители. Группа `widgets` определяется профилем проекта. Повторное отображение Header одним владельцем не является основанием для подъёма.

## Причина изменения

Практический вопрос колокации:

> Ради чьей ответственности этот код должен измениться?

Ответ определяет ближайшего владельца.

```text
Изменяется ради общей раскладки → MainLayout
Изменяется ради верхней области → Header
Изменяется ради навигации → Navigation
Изменяется ради предметного Product → Products
Изменяется ради HTTP transport → HTTP client
```

## Что не поднимается

Код не поднимается только потому, что:

- его можно теоретически переиспользовать;
- он выглядит универсальным;
- файл стал большим;
- появился второй файл рядом;
- выбранный framework рекомендует отдельный hook;
- команда хочет выровнять деревья каталогов.

## Завершённая миграция

Изменение границы завершено, когда:

- определён один владелец;
- весь связанный код перемещён к нему;
- потребители используют фасет;
- старые глубокие пути удалены;
- граф остаётся ацикличным;
- прежняя область больше не определяет ту же ответственность.
