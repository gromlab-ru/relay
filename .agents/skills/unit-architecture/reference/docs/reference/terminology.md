# Терминология

Этот документ задаёт нормативный смысл основных терминов Unit Architecture.

## Frontend root

Граница одного frontend-приложения, внутри которой действуют слои, юниты, фасеты и правила зависимостей.

## Архитектурный профиль проекта

Действующий в определённом frontend root набор командных решений о маркерах фасетов, внутренней структуре юнитов, сегментах и группах композиций. Профиль конкретизирует свободные решения проекта, но не переопределяет нормативный смысл архитектурных сущностей.

## Ответственность

Связный результат или возможность приложения, изменяющиеся по одной причине. Ответственность не выводится из имени папки, framework-механизма, количества файлов или числа потребителей.

## Владелец

Юнит, который определяет контракт, зависимости и внутреннюю реализацию ответственности. Каждый файл внутри frontend root принадлежит ближайшему юниту, кроме специальных точек входа `app` и допустимых небольших ресурсов `shared`.

Место инициализации или подключения возможности не становится её владельцем. Например, Provider и его контекст принадлежат юниту, хранящему их реализацию, даже если готовый Provider подключается в framework entry слоя `app`.

## Юнит

Рекурсивная папка-владелец одной ответственности, имеющая хотя бы один непустой публичный фасет и самостоятельную границу зависимостей. Физически папка объявляется юнитом наличием одного или нескольких маркеров фасетов. Если требования к владельцу не выполнены, это объявленный, но архитектурно некорректный юнит.

## Вложенный юнит

Юнит, физически находящийся внутри другого юнита. Его фасеты доступны непосредственному родителю, но не внешним потребителям напрямую. Родитель владеет общим результатом, ребёнок — выделенной частью этого результата.

## Файл реализации

Минимальная физическая реализация ближайшего юнита. Component, hook, Provider, Guard, service, adapter, type и utility являются видами файлов или определяемых проектом файловых единиц, а не сущностями Unit Architecture.

## Сегмент

Необязательное направление внутренней реализации одного юнита. Сегмент не имеет собственной ответственности, фасетов или границы зависимостей. Набор, имена и физическую структуру сегментов определяет проект.

## Группа

Необязательный навигационный классификатор юнитов и других групп. Группа не содержит собственной реализации, не имеет фасетов и не участвует в графе зависимостей.

## Публичный API

Единый логический контракт юнита для разрешённых потребителей. Публичный API скрывает внутреннюю реализацию и физически представлен фасетами.

## Фасет

Объявленная точка входа в часть публичного API юнита. Фасет может ограничивать API определённой средой выполнения. Только юнит имеет фасеты; сегменты, группы и внутренние папки фасетов не имеют.

## Маркер фасета

Зарезервированный проектом файл или путь, наличие которого объявляет содержащую его папку юнитом, а сам путь — фасетом этого юнита. Пустой маркер объявляет некорректный юнит с пустым фасетом, а не внутреннюю папку.

## Соглашение фасетов

Однозначное проектное сопоставление маркеров фасетов с публичными точками входа, зафиксированное в архитектурном профиле. Unit Architecture не задаёт имена маркеров. Зарезервированный маркер действует во всём frontend root и не используется для локальных реэкспортов.

## Универсальный фасет

Фасет, исполняемый граф которого безопасен во всех поддерживаемых средах приложения. В примерах таким фасетом обычно является `index`.

## Глубокий импорт

Импорт внутреннего пути чужого юнита, который не объявлен его фасетом.

## Зависимость

Направленная статическая связь между двумя юнитами. Обычный импорт, `import type` и реэкспорт одинаково создают архитектурную зависимость. Импорты файлов одного юнита сворачиваются во внутреннюю реализацию.

## Слой

Архитектурная роль юнита, определяющая смысл его ответственности и допустимые целевые слои зависимостей.

## Колокация

Размещение кода в самой узкой области ближайшего владельца, ради ответственности которого этот код существует.

## Подъём

Перемещение кода или юнита к ближайшей общей области при расширении круга потребителей. Подъём не выполняется заранее ради предполагаемого переиспользования.
