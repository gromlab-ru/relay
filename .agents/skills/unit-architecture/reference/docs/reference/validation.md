# Проверка архитектурного решения

Проверка выполняется по владельцам и свёрнутому графу юнитов, а не по внешней симметрии дерева файлов.

## 1. Профиль проекта

- Для изменяемого пути найден применимый архитектурный профиль.
- Профиль однозначно определяет frontend root и сопоставление путей со слоями.
- Зафиксированы все маркеры фасетов, их назначение и ограничения среды.
- Определены соглашения структуры юнитов и словарь сегментов либо явно сохранена свободная форма.
- Определены группы `compositions` и их назначение либо явно зафиксировано отсутствие групп.
- Проектное соглашение не подменяет определения владельца, юнита, фасета, группы или сегмента.

## 2. Ответственность

- Ответственность юнита формулируется одним связным результатом.
- Формулировка не сводится к framework-механизму или типу файла.
- Для одного смысла существует один владелец.
- Юнит не служит пустым контейнером независимых детей.

## 3. Граница

- Проект однозначно определяет маркеры фасетов для всего frontend root.
- Все используемые маркеры явно задокументированы в архитектурном профиле.
- Каждая папка с маркером классифицирована как юнит и отдельный узел графа.
- У юнита есть хотя бы один непустой фасет.
- Все фасеты представляют один логический API.
- Зарезервированные маркеры не используются для локальных реэкспортов.
- Сегменты и группы не имеют фасетов.
- Пустой маркер диагностируется как некорректный юнит с пустым фасетом.

## 4. Колокация

- Код находится у ближайшего владельца, ради которого изменяется.
- Код не поднят заранее ради предполагаемого переиспользования.
- Общий код поднят только до ближайшей общей области.
- После миграции не осталось двух владельцев одной ответственности.

## 5. Слой

- Слой выбран по смыслу результата, а не по типу файлов.
- `app` содержит только framework-интеграцию, инициализацию и подключение готовых публичных API.
- Framework-файлы маршрутов делегируют отображение композициям; продуктовый интерфейс собирается в `compositions`.
- Код Providers, контекстов, состояния и их поведения находится у владельцев ответственностей, а не в `app`.
- Точка подключения Provider задаёт область действия в пределах контракта владельца; доступ к контексту выполняется через API владельца с соблюдением правил зависимостей.
- `compositions` не присваивает предметные правила или техническую интеграцию.
- Композиция владеет вёрсткой и взаимодействиями своей проекции, связывает визуал с доменными данными и операциями, а не только размещает готовые компоненты.
- Самостоятельные области композиции предпочтительно выделены во вложенные юниты; технические DOM-блоки не получили границ механически.
- При подъёме общей области её реализация и вложенные юниты перемещены вместе, без преждевременного раскрытия детей.
- `domains` адаптирует источники к предметному контракту.
- `infra` не вводит продуктовый смысл.
- `ui` не зависит от предметной модели.
- `shared` остаётся детерминированным фундаментом.

## 6. Зависимости

- Каждый межюнитный импорт проходит через фасет.
- Направления соответствуют матрице слоёв.
- `import type` и реэкспорты учтены в графе.
- Same-layer зависимости направлены.
- Свёрнутый граф не содержит циклов.

## 7. Вложенность

- Родитель импортирует непосредственных детей через фасеты.
- Ребёнок не импортирует родителя или предков.
- Соседние дети не импортируют друг друга напрямую.
- Внешний код не выполняет глубокий импорт вложенного юнита.
- При появлении внешних прямых потребителей рассмотрен подъём юнита.

## 8. Среда выполнения

- Каждый исполняемый экспорт находится в минимально подходящем фасете.
- Универсальный фасет не достигает несовместимого runtime-кода.
- Пустые специализированные фасеты отсутствуют.
- Имена средовых фасетов определены проектом.
- Совместимость проверена по транзитивному графу.

## 9. Внутренняя структура

- Сегменты выбраны по реальным потребностям проекта.
- Архитектурное решение не требует симметрии юнитов.
- Component, Provider, Guard, hook и service не получили маркер фасета без отдельной ответственности.
- Доменный UI, использующий типы, операции или реализацию своего домена, остаётся внутренними компонентами без маркеров; одинаковая декомпозиция с композициями не требуется.
- Стайлгайд и framework-конвенции не подменяют правила владения.

## Минимальное обоснование юнита

Для нового юнита достаточно письменно ответить:

```text
Ответственность:
Родитель:
Слой:
Потребители:
Публичный API:
Фасеты:
Исходящие зависимости:
Причина отдельной границы:
```

Если невозможно определить публичный API или причину отдельной границы, код должен остаться реализацией ближайшего владельца.
