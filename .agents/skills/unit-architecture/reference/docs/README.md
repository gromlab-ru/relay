Unit Architecture — рабочее название frontend-архитектуры, которая организует код через слои, рекурсивные юниты, колокацию и явные направленные зависимости.

Модель отвечает на четыре вопроса:

1. Какой юнит владеет конкретной ответственностью?
2. Где должен находиться код, который обслуживает эту ответственность?
3. Что юнит открывает потребителям через публичные фасеты?
4. Какие зависимости между слоями и юнитами допустимы?

Unit Architecture не претендует на универсальное или идеальное решение. Её правила помогают делать границы явными, но могут приводить к неудобной декомпозиции и дополнительным контрактам. Известные ограничения и вопросы, на которые модель пока не даёт достаточно хорошего ответа, описаны в разделе [«Ограничения и компромиссы»](./architecture/trade-offs.md).

## Основная идея

Код появляется рядом с местом использования. Пока он обслуживает существующую ответственность, он остаётся у ближайшего владельца. Когда появляется самостоятельная ответственность с собственным контрактом, она объявляется вложенным юнитом через маркер фасета. Если API нового юнита требуется за пределами родителя, родитель явно включает нужную возможность в свой публичный API.

```text
локальное использование
→ колокация
→ самостоятельная ответственность
→ новый юнит
→ подъём к общей области при расширении потребителей
```

## Структурная модель

```text
Frontend root
└── Layer
    └── [Group*]
        └── Unit
            ├── Facet+
            ├── Files*
            ├── Segment*
            │   ├── Files*
            │   ├── [Group*]
            │   └── Unit*
            └── Unit*
```

Юнит — единственная рекурсивная граница владения. Его внутренняя структура свободна: команда сама выбирает сегменты, framework-паттерны, имена папок и степень колокации файлов.

Маркеры фасетов определяет архитектурный профиль проекта. Один маркер нельзя одновременно использовать как фасет юнита и локальный реэкспорт.

Выбранные командой маркеры фасетов, соглашения внутренней структуры и группы композиций фиксируются в [архитектурном профиле проекта](./architecture/project-profile.md). Профиль конкретизирует свободные решения проекта, но не добавляет их в общий канон.

## Область первой версии

Первая версия описывает архитектурный канон и небольшие изолированные примеры. Она намеренно не задаёт:

- обязательные сегменты;
- структуру framework-компонентов, hooks, Providers или Guards;
- конкретный frontend-фреймворк;
- способ управления состоянием;
- инструмент автоматической проверки;
- правила монорепозитория;
- runnable demo-приложение.

`Unit Architecture` используется как рабочее название и не относится к существующей enterprise-модели Unit-Oriented Architecture.
