# Пример архитектурного профиля React SPA

Этот документ показывает один заполненный [архитектурный профиль проекта](../architecture/project-profile.md). Он не является рекомендуемым шаблоном Unit Architecture: маркеры `index.ts` и `lazy.ts`, словарь сегментов, группы проекций и правила React Router выбраны конкретной командой и могут отсутствовать в другом приложении.

Профиль действует в пределах корня клиентского React SPA. Он определяет маркеры публичных фасетов, внутреннюю форму юнита и классификацию продуктовых проекций в слое `compositions`.

## Публичные фасеты

В проекте используются два маркера фасета:

| Фасет | Назначение |
|---|---|
| `index.ts` | Обычный публичный API для статических импортов |
| `lazy.ts` | Минимальная точка входа для динамического импорта |

Наличие `index.ts` или `lazy.ts` объявляет содержащую их папку юнитом. Объявленный юнит обязан иметь отдельную ответственность, непустой публичный контракт и допустимые зависимости. Оба фасета представляют один логический API юнита и не содержат реализацию.

`index.ts` экспортирует только возможности, нужные обычным межюнитным потребителям. Импорт выполняется через путь юнита:

```ts
import { AccountPage } from '@/compositions/pages/account'
```

`lazy.ts` создаётся только при подтверждённом разделении кода. Он экспортирует минимальный контракт загрузчика и импортируется только через `import()`:

```ts
const loadAccountPage = () => import('@/compositions/pages/account/lazy')
```

Для `lazy`-маршрута React Router фасет публикует компонент страницы под ожидаемым библиотекой именем:

```ts
export { AccountPage as Component } from './account-page'
```

При необходимости этот же фасет может экспортировать `ErrorBoundary`. Предметные `loader` и `action` в нём не размещаются: серверные данные и изменения принадлежат доменным API.

Юнит может иметь один или оба фасета. Если API используется только динамическим потребителем, одного `lazy.ts` достаточно. Второй фасет не создаётся без отдельного способа потребления.

Имена `index.ts` и `lazy.ts` зарезервированы во всём корне приложения. Они не используются для внутренних повторных экспортов. Внутренняя папка с таким файлом становится вложенным юнитом и проходит все проверки архитектурной границы. Любой межюнитный импорт, включая `import type` и динамический импорт, проходит через соответствующий фасет.

## Структура юнита

Юнит содержит фасеты, основные файлы реализации и только необходимые сегменты:

```text
unit-name/
├── index.ts          # если нужен обычный публичный API
├── lazy.ts           # если нужна динамическая загрузка
├── unit-name.tsx     # если ответственность реализуется React-компонентом
├── config/
├── helpers/
├── hooks/
├── providers/
├── stores/
├── styles/
├── types/
└── ui/
```

Это перечень допустимых частей, а не обязательный шаблон. Пустые файлы и папки ради одинакового дерева не создаются. Небольшая реализация может оставаться в корне юнита. Когда файлы образуют одну из закреплённых ниже категорий, используется соответствующий сегмент.

### Общие сегменты

| Сегмент | Что находится внутри |
|---|---|
| `config/` | Декларативная конфигурация владельца |
| `helpers/` | Небольшие внутренние операции и вычисления владельца |
| `hooks/` | React-хуки состояния и жизненного цикла владельца |
| `providers/` | Контексты и Provider-компоненты владельца |
| `stores/` | Клиентское состояние владельца |
| `styles/` | CSS Modules, оформляющие DOM владельца |
| `types/` | Внутренние и публикуемые типы владельца |
| `ui/` | Внутренние React-компоненты и вложенные компоненты-юниты владельца |

Одинаково названный сегмент имеет этот смысл во всех слоях. Папка сегмента не имеет фасета, не является владельцем и не импортируется как самостоятельный API. Папка внутри `ui/` становится вложенным юнитом только при появлении `index.ts` или `lazy.ts`; без маркера она остаётся внутренней реализацией ближайшего владельца.

Словарь не разрешает размещать продуктовый UI или реализацию Providers в `app`. Если техническая сборка дерева Providers находится в `app`, она только подключает готовые публичные API; код Providers и контекстов хранится у владельцев вне `app`.

### Профильные сегменты

Профильные сегменты уточняют устройство отдельных слоёв и применяются только там, где нужна соответствующая роль:

| Сегмент | Применение | Что находится внутри |
|---|---|---|
| `adapters/` | `domains` | Преобразование технического API в предметную операцию |
| `mappers/` | `domains` | Преобразование DTO и других внешних значений в предметные типы и обратно |
| `errors/` | `domains` | Ожидаемые предметные ошибки и их проверки |
| `source-errors/` | `domains` | Проверки технических ошибок конкретного источника |
| `operations/` | `domains`, `infra` | Отдельные операции владельца |
| `generated/` | `infra` | Код, полностью принадлежащий генератору |

Дополнительное соглашение слоя или библиотеки может уточнить порядок применения профильного сегмента, но не переопределяет его смысл. Новый сегмент добавляется в профиль только после появления устойчивой категории файлов, которой не подходит существующее определение.

## Структура compositions

Здесь реализуются вёрстка и сборка продукта, а не только размещение готовых компонентов. Композиции связывают предметные данные и операции с визуалом, владеют локальным состоянием интерфейса и отображением результатов взаимодействия.

Слой `compositions` использует четыре группы продуктовых UI-проекций:

```text
compositions/
├── layouts/
├── pages/
├── screens/
└── widgets/
```

Группа содержит юниты и не имеет собственного фасета или реализации. Она только классифицирует проекционные ответственности и помогает находить их в слое. Группа не задаёт уровень, приоритет или отдельное направление зависимостей. Пустая группа не создаётся.

Для самостоятельных областей вёрстки предпочтительны вложенные юниты: layout колоцирует Header и Footer, Header — Navigation и Search. Родитель координирует детей через их контракты. При появлении прямого потребителя вне родителя область поднимается вместе с детьми, например общий Header двух layouts — в widgets. Технические DOM-блоки без отдельной ответственности остаются внутренней реализацией.

Это не шаблон для доменного UI: компонент, использующий типы, операции или состояние своего домена, остаётся внутри домена без `index.ts` и `lazy.ts`. Его публикует фасет доменного владельца. Вложенный доменный UI-юнит нужен только при самостоятельном контракте без обратных импортов домена.

### layouts

`layouts/` содержит устойчивые каркасы приложения или веток маршрутов. Layout определяет размещение общих областей, например навигации, основного содержимого и footer, но не владеет предметными правилами отображаемых сценариев.

Layout может собирать готовые возможности других композиций, доменов, инфраструктуры и UI, а также принимать изменяемое содержимое через свойства или механизм вложенных маршрутов.

### pages

`pages/` содержит проекции, которые непосредственно подключаются к маршрутам. Page собирает готовые возможности композиций, доменов, инфраструктуры и UI для отображения конкретного URL, но не владеет самим деревом URL.

Page может читать параметры и состояние маршрута через React Router. Для динамического подключения page публикует `lazy.ts` с экспортом `Component`. Обычный `index.ts` добавляется только при наличии статического потребителя.

### screens

`screens/` содержит завершённые экранные проекции, не зависящие от конкретного URL. Screen представляет связный пользовательский сценарий и собирает необходимые ему возможности композиций, доменов, инфраструктуры и UI.

Если проекция читает параметры или состояние маршрута либо существует только для одного URL, исходным владельцем является page, а не screen.

### widgets

`widgets/` содержит крупные самостоятельные области интерфейса. Widget может собирать необходимые ему возможности композиций, доменов, инфраструктуры и UI, но не представляет целую страницу и не знает о дереве маршрутов.

Локальная часть page, screen или layout не поднимается в widgets ради предполагаемого переиспользования.

### Зависимости

Группы `layouts`, `pages`, `screens` и `widgets` не образуют дополнительную иерархию. Любой композиционный юнит может собирать публичные API других композиций, доменов, инфраструктуры, UI и общего кода в пределах матрицы зависимостей Unit Architecture. Конкретная связь определяется ответственностью и потребителями юнитов, а полный граф остаётся ацикличным.

Новая группа появляется только для устойчивой роли нескольких юнитов, которую нельзя однозначно отнести к четырём существующим группам. До создания группы её ответственность, потребители и отличие от существующих групп описываются в этом профиле.

## Граница app и compositions

`app` содержит только техническую интеграцию готовых публичных API с React runtime. В маршрутизации он владеет конфигурацией React Router, деревом URL, подключением redirects, глобальных route error boundaries и динамической загрузкой фасетов. Продуктовые условия переходов и отображаемый UI ошибок остаются у соответствующих владельцев вне `app`.

Отображаемая route-level проекция принадлежит `compositions/pages`. Конфигурация маршрута импортирует её `lazy.ts`, но не реализует страницу внутри `app`:

```text
app/router → compositions/pages/*/lazy.ts
```

Тонкий framework-файл внутри `app` допустим, если React Router требует отдельную форму, которой нельзя предоставить напрямую через фасет page. Такой файл только адаптирует публичный контракт и не присваивает себе отображение или предметное поведение.

`app` может инициализировать и подключать глобальные Providers через фасеты их владельцев. Реализации Providers, контекстов и состояния не создаются внутри `app`. Если область Provider ограничена страницей или другой проекцией, его подключает соответствующая композиция; владелец реализации не меняется.

## Проверка

- Каждый `index.ts` и `lazy.ts` принадлежит юниту с отдельной ответственностью и непустым контрактом.
- Статические потребители используют `index.ts`, а динамические — `lazy.ts` через `import()`.
- Внутренние папки не используют зарезервированные маркеры для повторных экспортов.
- Сегменты соответствуют словарю, не имеют фасетов и создаются только при наличии кода.
- Вложенный юнит не импортирует родителя, предков или соседних детей.
- Каждый юнит `compositions` однозначно отнесён к принятой группе.
- `app` владеет конфигурацией маршрута, а `compositions/pages` — отображаемой страницей.
- `app` только инициализирует и подключает готовые Providers; их код и контексты находятся у владельцев ответственностей.
- Зависимости соответствуют матрице Unit Architecture и не образуют циклов.
