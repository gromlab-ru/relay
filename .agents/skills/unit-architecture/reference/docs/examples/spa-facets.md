# SPA-фасет

## Задача

SPA выполняет весь API Products в одной browser-среде и не имеет несовместимого server runtime.

## Решение

Профиль этого проекта объявляет `index.ts` маркером фасета и резервирует его во всём frontend root.

```text
domains/products/
├── index.ts
└── ...
```

Одного фасета достаточно:

```ts
export type { Product } from './types/product.type'
export { getProducts } from './libs/get-products'
export { ProductCard } from './ui/product-card'
```

Фасет непустой и представляет весь логический API Products для разрешённых потребителей.

## Почему нет browser

Имя среды не добавляется без реального разделения публичного API. Дополнительный `browser.ts` в обычной SPA только создаёт вторую точку входа без отдельного ограничения.

## Почему нет пустых фасетов

```text
products/
├── index.ts
├── client.ts
├── browser.ts
└── server.ts
```

Если проект объявил `index.ts`, `client.ts`, `browser.ts` и `server.ts` маркерами фасетов, все четыре файла являются фасетами одного юнита Products. Каждый фасет должен открывать непустую и обоснованную часть публичного API: `index.ts` — универсальную, `client.ts` — клиентскую framework-границу, `browser.ts` — browser-only возможности, `server.ts` — server-only возможности. Исполняемый экспорт размещается в минимально подходящем фасете и не дублируется между фасетами без необходимости. Пустой специализированный фасет или фасет, механически повторяющий `index.ts`, делает объявленный юнит некорректным.

`index.ts` не импортирует и не реэкспортирует специализированные фасеты прямо или транзитивно.

## Антипример

Не следует экспортировать внутренние helpers через `index` только ради теста. Тест, колоцированный внутри Products, может импортировать внутреннюю реализацию как часть того же юнита.
