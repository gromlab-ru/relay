# Demo App

Рабочее демонстрационное приложение для skill [`react-reference`](../SKILL.md). Оно показывает, как правила документации
соединяются в запускаемой React SPA, и развивается небольшими законченными сценариями.

Обнаруженные пробелы и нестыковки документации записываются в [`DOCUMENTATION-GAPS.md`](../DOCUMENTATION-GAPS.md).

Сейчас приложение содержит каркас и законченный сценарий JWT-авторизации:

- React, TypeScript и Vite;
- алиасы архитектурных слоёв;
- Mantine, проектный `ThemeProvider` и переключение светлой и тёмной тем в `MainLayout`;
- PostCSS, общие стили и CSS Module;
- типизированный React API проектных SVG-иконок и отдельный спрайт, создаваемый `@gromlab/svg-sprites`;
- React Router с `MainLayout`, синхронными основными маршрутами и динамически подключаемыми вторичными сценариями;
- общую OpenAPI-схему серверного API и воспроизводимую генерацию REST-клиента;
- полный API-клиент с общим `HttpClient`, который добавляет access JWT только к защищённым операциям;
- доменный Zustand-store авторизации со статусом `unknown | authenticated | unauthenticated`;
- реактивный жизненный цикл terminal Bearer `401` с проверкой отклонённого credential и очисткой приватного SWR-кеша;
- домен `authentication` для сессии и домен `user` для профиля кабинета;
- SWR-кеш сессии и приватную область профиля, разделённую по `userId`;
- маршрутную границу авторизации для `/account`, форму `/sign-in` и возврат к исходному адресу;
- MSW-обработчики всех реализованных операций серверного API.

Демо-пользователь: `demo@example.com`. Пароль: `demo-password`. Значения уже заполнены в форме входа.

## Команды

Команды выполняются из корня `demo-app`.

Установи зависимости из lock-файла:

```bash
npm ci
```

Запусти приложение для разработки:

```bash
npm run dev
```

Создай новый компонент после определения владельца по
[`инструкции генерации TSX`](../reference/application/components/tsx-generation.md) и
[`описанию шаблонов`](.templates/README.md):

```bash
npm run create -- ui-component status-label src/compositions/screens/account/ui
```

Это пример для нового внутреннего компонента, а не обязательное дополнение экрана. Для самостоятельного
компонента-юнита используй `ui-unit`. Команда `create` запускает закреплённый CLI через `npx`; не создавай новые
компоненты копированием соседних файлов.

Порядок создания целой страницы находится в [`Создании страниц`](../reference/application/pages/README.md),
каркаса в [`Структуре приложения`](../reference/application/structure/README.md). Примеры используют готовые юниты демо
как проверяемый результат, а команды создания предназначены для приложения, где соответствующего юнита ещё нет.

Повторно создай REST-клиент после изменения OpenAPI:

```bash
npm run generate:backend-api
```

Повторно создай SVG-спрайт после изменения исходной иконки или его конфигурации:

```bash
npm run sprites
```

Проверь типы и производственную сборку:

```bash
npm run check
```

Проверь собранное приложение локально:

```bash
npm run preview
```

## Структура

```text
src/
├── app/                          запуск и дерево маршрутов
├── compositions/
│   ├── layouts/main/             постоянный каркас с Outlet
│   ├── route-boundaries/         отдельное поведение маршрутных веток
│   └── screens/                  завершённые экранные сценарии
├── domains/
│   ├── authentication/           auth store, Provider, сессия, AuthGuard, вход, выход и очистка SWR
│   └── user/                     профиль и приватный SWR key
├── infra/app-icons/              созданный генератором React API SVG-спрайта
├── infra/demo-api-mock/          автономная реализация OpenAPI через MSW
├── infra/backend-api/            полный клиент серверного API и добавление JWT
├── shared/assets/svg/            исходные SVG проекта
├── shared/errors/                общий контракт неожиданного сбоя
└── ui/themes/                    визуальная тема, общие стили и Provider Mantine
```

Папка с `index.ts` или `lazy.ts` является публичным юнитом. Синхронный потребитель использует `index.ts`, а динамический
импорт — `lazy.ts`. Межюнитные импорты проходят через соответствующий фасет, а файлы внутри одного владельца используют
относительные пути.

Группа `widgets` предусмотрена архитектурой, но пока не нужна демо. Полная карта и назначения групп находятся в
[`Структуре приложения`](../reference/application/structure/README.md#группы-композиций). Пустые группы не создаются.

`app/router` владеет деревом URL и подключает `MainLayout`. Основной каркас размещает постоянные элементы приложения и
выводит вложенный маршрут через `Outlet`.

Домен `authentication` владеет vanilla store статуса авторизации и публичным selector hook для React.
`AuthenticationProvider` проверяет сессию при запуске и связывает доменный статус с SWR. При terminal Bearer `401`
вызывающий domain adapter выполняет публичный `logout`, после чего Provider очищает сессию и все приватные ключи.

`shared/assets/svg` хранит исходные SVG без React и настройки генератора. `infra/app-icons` явно перечисляет входящие в
спрайт файлы, предоставляет `AppIcon` через `index.ts` и скрывает созданный каталог `.svg-sprite`. Команды `dev`,
`typecheck` и `build` создают спрайт до первого импорта созданного API. Размер и доступное описание иконки задаёт
непосредственный потребитель.

Доменный `AuthGuard` читает статус своего домена и выбирает между ожиданием, доменной ошибкой, отсутствием авторизации и
защищённым содержимым. Он не зависит от React Router и получает варианты отображения через свойства.
`RequireAuthenticationBoundary` применяет эту границу к ветке, требующей аутентификации: сохраняет исходный адрес,
перенаправляет гостя на `/sign-in` и выводит разрешённую ветку через `Outlet`. JWT, API-клиент и технические ошибки
маршрутной границе недоступны. У неё нет входных свойств, но есть стили собственных состояний проверки сессии.

`AccountScreen` получает профиль через публичный хук `domains/user` и выполняет выход через публичное действие
`domains/authentication`. Хук профиля ждёт стабильный `userId` сессии и использует ключ `['private', userId, ...]`. При
выходе домен сначала закрывает auth state, маршрутная граница закрывает кабинет, а hook и Provider очищают сессию и
приватные записи.

`SignInScreen` владеет формой и полным пользовательским действием входа. Экран проверяет ввод, вызывает публичное
действие домена авторизации, отображает предусмотренные ошибки и выполняет маршрутный возврат после успеха. Адаптация
запроса, ошибки источника и синхронизация сессии остаются внутри домена.

Юниты `screens` владеют разметкой и полными пользовательскими сценариями. `app/router` подключает их напрямую, без
компонента-посредника на каждую страницу. Начальный `home` и небольшой `not-found` подключаются статически через
`index.ts`. Экраны входа и кабинета публикуют только `lazy.ts`, потому что эти сценарии не нужны при каждом запуске.
Динамическая граница авторизации в `route-boundaries` ограничивает ветку кабинета, а не повторяет экран.

Различие обычной динамической загрузки и условного выбора экрана, а также ограничения загрузки кода до проверки доступа
описаны в [`Маршрутизации`](../reference/application/routing/README.md#условный-выбор-экрана).
