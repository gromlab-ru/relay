# Code style

Применяй этот раздел ко всем файлам. Если профильное правило точнее, используй его.

## Режим применения

Сначала определи режим задачи.

### Стиль проекта

Это режим по умолчанию для готового проекта.

- Соблюдай существующий стиль затронутых файлов и соседнего кода, даже если он противоречит этому style guide.
- Не создавай внутри проекта новый локальный стиль на основе skill.
- Используй правила skill только там, где проект не задаёт собственного решения.
- Не форматируй и не переписывай существующий код ради соответствия skill.

### Строгий style guide

Используй этот режим, только если:

- пользователь прямо попросил следовать style guide в текущей задаче;
- обязательные правила проекта явно закрепляют этот style guide.

В строгом режиме применяй все релевантные правила skill к новому и затронутому коду. Не расширяй правку на
незатронутые файлы без отдельного запроса.

Если правило skill несовместимо с обязательным formatter, linter или компиляцией проекта, не отключай проверку и не
меняй конфигурацию без разрешения. Зафиксируй конфликт и запроси решение пользователя, если его нельзя обойти в
рамках задачи.

## Приоритеты

В режиме стиля проекта:

1. Обязательные инструкции и автоматические проверки проекта.
2. Устоявшийся стиль затронутого файла и соседнего кода.
3. Этот style guide для неурегулированных решений.

В строгом режиме:

1. Прямое требование пользователя или проекта следовать style guide.
2. Этот style guide.
3. Локальный стиль проекта для неурегулированных решений.

Обязательные автоматические проверки должны продолжать проходить в обоих режимах. Конфликт между ними и строгим
style guide нельзя разрешать молча.

## Форматирование

- Не меняй конфигурацию инструментов в обычной задаче на правку кода.
- Форматируй только затронутый код. Не создавай шумовой diff по всему файлу или проекту.
- Не переименовывай публичные сущности и файлы без явной задачи.
- Используй 2 пробела и ориентир в 120 символов, если проект не задаёт иное.
- Переноси выражение ради читаемости, а не механического соблюдения лимита.

Правила написания общих стилей и CSS Modules находятся в [`css.md`](css.md).

### JavaScript и TypeScript

Для `.js`, `.jsx`, `.ts` и `.tsx`, если инструменты или локальный стиль проекта не задают другое:

- используй одинарные кавычки;
- используй template literal для интерполяции или многострочного текста;
- не ставь semicolon и trailing comma;
- короткие objects, arrays, tuples и вызовы оставляй в одну строку;
- в многострочной форме размещай properties, элементы, параметры и arguments по одному на строке;
- не меняй форматирование всего файла при локальной правке.

## Файлы и папки

- Папки и файлы называй в `kebab-case`.
- Имя должно описывать основную сущность или роль файла либо назначение папки.
- Не добавляй в имя технический термин, который не помогает отличить ответственность сущности.
- Не переименовывай существующую структуру только ради выравнивания соглашений.

## Ролевые файлы

Формат имени: `name.<role>.<ext>`. Суффикс должен в единственном числе описывать роль файла. Следуй локальному
варианту, если проект уже использует другое соглашение.

Типовые суффиксы: `.hook`, `.store`, `.service`, `.type`, `.interface`, `.enum`, `.dto`, `.schema`, `.constant`,
`.config`, `.util`, `.lib`, `.test`, `.mock`.

Для TypeScript примерами являются `user.type.ts` и `use-user.hook.ts`; для JavaScript - `user.service.js` и
`user.test.js`. Файл hook называй `use-name.hook.<ext>`.

## Helpers

Helper является внутренней именованной операцией владельца. Он выделяет самостоятельный шаг реализации, но не имеет
собственного публичного контракта и отдельной архитектурной ответственности.

- Выноси логику в helper, когда имя операции делает основной сценарий понятнее, отделяет этап алгоритма, скрывает
  детали реализации, уменьшает вложенность или упрощает изолированную проверку.
- Единственное использование и небольшое количество строк не запрещают создание helper.
- Не создавай бессмысленную pass-through функцию, которая не добавляет понятного имени или границы реализации.
- Определяй владельца вопросом: ради чьей ответственности изменяется эта операция.
- Размещай helper только в папке `helpers/` ближайшего владельца.
- Называй файл по действию в `kebab-case` без суффикса `.helper`.
- Размещай тест helper рядом с ним и используй суффикс `.test`.

```text
user-card/
├── user-card.tsx
└── helpers/
    ├── format-user-name.ts
    └── format-user-name.test.ts
```

Новый helper создавай в самой узкой области фактического использования. Не поднимай его заранее из-за
предполагаемого переиспользования.

Если helper нужен нескольким внутренним частям одного владельца, перемести его в `helpers/` их ближайшей общей
области внутри этого владельца. Перемещай одну реализацию целиком и удаляй прежние локальные копии.

Внутренний helper не импортируется напрямую другим самостоятельным архитектурным владельцем. Если одна возможность
нужна нескольким юнитам, она перестаёт быть внутренним helper: определи для неё ближайшего допустимого владельца,
публичный контракт и фасет. Не размещай общую реализацию в группе или filesystem ancestor, который не владеет
ответственностью.

## Module boundaries

- Записывай все импорты одним непрерывным блоком без пустых строк между библиотеками, слоями, локальными файлами и
  `import type`.
- Сохраняй порядок: внешние пакеты, алиасы слоёв, относительные импорты; внутри каждой части следуй порядку проекта.
- Между юнитами используй алиас слоя и публичный фасет владельца по
  [`архитектурному профилю`](../application/architecture/project-profile.md#пути-импортов).
- Внутри одного юнита используй относительные импорты.
- Для собственного кода предпочитай named exports.
- Default export используй только по требованию framework, tooling или устойчивого локального стандарта.
- Namespace import применяй только когда этого требует API библиотеки или локальный стандарт.
- Импортируй сущность через публичную точку входа её владельца.
- Не обходи public API глубоким импортом.
- Не создавай barrel без архитектурной границы и реальных consumers.
- Не создавай циклические зависимости ради удобного re-export.
- Не меняй порядок и пути imports только ради вкусового форматирования.

Рабочий формат показывает [`sign-in.screen.tsx`](../../demo-app/src/compositions/screens/sign-in/sign-in.screen.tsx).

## Комментарии

- Объясняй назначение, ограничение, внешний контракт или неочевидную причину. Не пересказывай код.
- Ставь пробел после маркера комментария и точку в конце законченной фразы.
- Удаляй или обновляй комментарий вместе с изменением поведения.
- Не используй комментарий вместо понятного имени или декомпозиции.
- Логические части многострочного комментария разделяй одной пустой строкой.

## Проверка

- Режим применения определён по запросу пользователя и инструкциям проекта.
- В режиме стиля проекта сохранены существующие соглашения, включая противоречащие skill.
- В строгом режиме применены все релевантные правила style guide.
- Обязательные автоматические проверки пройдены.
- Локальный стиль соблюдён в режиме стиля проекта; в строгом режиме расхождения ограничены затронутым кодом.
- Незатронутый код не переформатирован.
- Имена файлов и папок соответствуют их роли.
- Ролевые файлы названы по единой схеме проекта.
- Helpers находятся в `helpers/` ближайшего владельца и названы по действию без суффикса `.helper`.
- Helpers не подняты заранее и не импортируются напрямую между самостоятельными архитектурными владельцами.
- Общая межюнитная возможность имеет собственного публичного владельца и фасет.
- Imports и exports не обходят public API и не создают случайные barrels или циклические зависимости.
- Imports записаны одним блоком без пустых строк.
- Комментарии добавляют контекст, которого нет в коде.
