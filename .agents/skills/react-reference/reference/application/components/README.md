# Создание компонентов

Этот раздел описывает создание любого React-компонента: части страницы, экрана, каркаса, виджета, маршрутной границы,
провайдера или универсального элемента. Назначение определяет владельца, а не способ получения файлов:
каждый новый `.tsx` создаётся запуском генератора по [`обязательной инструкции`](tsx-generation.md).

Генератор создаёт папку, реализацию, тип свойств и CSS Module; для самостоятельного юнита также создаётся фасет.
Не создавай этот комплект вручную, копированием соседнего компонента или копированием шаблона. Локальный шаблон является
входными данными CLI, а не альтернативным способом создания. Единственный пример рабочего набора находится в
[`demo-app/.templates/`](../../../demo-app/.templates/README.md).

## Порядок работы

1. Сформулируй назначение компонента и найди ближайшего владельца по
   [`архитектурным правилам`](../architecture/units/README.md).
2. Для визуальной задачи проверь готовые решения по [`UI`](../ui/README.md). Компонент страницы может собирать Mantine;
   наличие библиотеки не запрещает собственную композицию, но не оправдывает повторную реализацию её примитивов.
3. Определи входные данные, действия и состояние. Выбери внутренний компонент или компонент-юнит по его ответственности,
   а не по размеру JSX. Передавай минимальные свойства, не весь ответ запроса или store без необходимости.
4. Выбери `ui-component` для внутренней реализации либо `ui-unit` для самостоятельного юнита. Запусти генератор по
   [`инструкции`](tsx-generation.md), проверив отсутствие целевой папки.
5. Адаптируй созданные файлы: назначение в JSDoc, тип свойств, корневой элемент, стили и нужные экспорты. Не оставляй
   демонстрационное содержимое и не подменяй запуск CLI ручной заготовкой.
6. Реализуй поведение по правилам JSX, состояния, форм и стилей. При дальнейшей декомпозиции каждый новый компонент
   также создавай через CLI у ближайшего владельца.
7. Подключи компонент к реальному потребителю: внутренний через относительный путь, юнит через публичный фасет.
8. Проверь свойства, события, состояния, доступность и внешний вид, затем выполни применимые
   [`проверки проекта`](../quality/README.md#проверки).

Например, новый внутренний компонент кабинета создаётся из корня приложения:

```bash
npm run create -- ui-component status-label src/compositions/screens/account/ui
```

Это пример для ещё не существующей сущности, а не команда обновления готового компонента. Генератор сам создаёт
`status-label/`; файлы выбранного шаблона нужно прочитать до запуска. Подробный пример страницы находится в
[`Создании страниц`](../pages/README.md).

## Базовая структура

Фасеты и допустимые сегменты определяет [`архитектурный профиль`](../architecture/project-profile.md). Файловая форма
едина для новых React-компонентов, включая провайдеры, гарды и маршрутные границы без собственного DOM. Компонент имеет
собственную папку; для основной реализации компонента-юнита ею служит корень этого юнита. Генератор создаёт начальную
структуру, а после адаптации в ней остаются только нужные файлы.

Начальный комплект компонента-юнита, который полностью создаёт генератор:

```text
component-name/
├── index.ts
├── component-name.tsx
├── styles/
│   └── component-name.module.css
└── types/
    └── component-name-props.type.ts
```

| Элемент | Ответственность |
| --- | --- |
| `index.ts` | Публичный фасет и маркер объявленного юнита |
| `component-name.tsx` | Основная реализация React-компонента |
| `styles/` | CSS Modules владельца |
| `types/` | Свойства компонента и связанные типы |

Визуальный компонент адаптирует этот комплект к своему DOM: свойства описывают реальный контракт, CSS Module оформляет
его элементы. Не начинай экран, каркас или виджет с вручную созданного одиночного TSX. Правила адаптации для компонента
без собственных стилей, свойств или DOM находятся ниже.

Обычный внутренний компонент не имеет фасета. Если ему нужны отдельные свойства и стили, используй ту же файловую форму,
но не добавляй `index.ts`:

```text
component-name/
├── component-name.tsx
├── styles/
│   └── component-name.module.css
└── types/
    └── component-name-props.type.ts
```

Тип свойств любого компонента со свойствами размещай в `types/{name}-props.type.ts`. Импортируй внутренний компонент
относительным путём только внутри владельца. Если отдельные стили и тип свойств не нужны, внутри собственной папки
остаётся один `.tsx`; это не разрешает создавать его вручную или размещать прямо в общем сегменте `ui/` либо
`providers/`. Добавляй фасет только при отдельной ответственности и публичном контракте компонента-юнита. Каждый
компонент документируй обязательным JSDoc по
[`styleguide/jsx-tsx.md`](../../styleguide/jsx-tsx.md#верхнеуровневый-комментарий-компонента).

Рабочую форму вложенного компонента-юнита показывает
[`theme-color-scheme-toggle`](../../../demo-app/src/compositions/layouts/main/ui/header/ui/theme-color-scheme-toggle/):
его родитель использует фасет, а реализация, стили и тип свойств закрыты внутри юнита.

Форму внутреннего компонента без DOM показывает
[`AuthenticationProvider`](../../../demo-app/src/domains/authentication/providers/authentication-provider/):
у него собственная папка и тип свойств, но нет CSS Module и фасета. Компонент остаётся частью домена авторизации.

## Адаптация без лишних файлов

Обязательность генерации не означает обязательный DOM у любого компонента. Провайдер или маршрутная граница могут
только связывать готовые возможности. После запуска CLI удали ненужную обёртку и `RootAttrs`, CSS Module без собственных
стилей и тип свойств, если свойств нет. Не добавляй фиктивные параметры или пустые файлы ради одинакового дерева.

Если граница выводит собственное состояние ожидания или ошибки, его стили остаются у неё. Это показывает
[`RequireAuthenticationBoundary`](../../../demo-app/src/compositions/route-boundaries/require-authentication/):
у компонента нет входных свойств, но есть CSS Module для состояния проверки сессии.

## Сегменты компонента

Для компонента обычно применяются сегменты `ui/`, `styles/`, `types/`, `hooks/` и `helpers/` со значениями из
архитектурного профиля. Создавай только те сегменты, для которых появился код.

Сегмент `ui/` рекурсивен: вложенный компонент может иметь собственный `ui/`. Сам сегмент не имеет фасета и не является
архитектурным владельцем. `index.ts` или `lazy.ts` внутри дочерней папки объявляет её вложенным юнитом.

Папка `ui/` внутри `compositions`, `domains` или другого слоя не относится к верхнеуровневому слою `ui`. Слой
определяется владельцем, внутри которого находится сегмент.

## Компонент и компонент-юнит

React-компонент является механизмом реализации. Компонент-юнит является самостоятельным владельцем ответственности с
публичным фасетом. Наличие отдельного файла, свойств, состояния или CSS Module само по себе не создаёт юнит. Критерии
границы, отношения родителя и ребёнка и правила фасета находятся в
[`architecture/units/README.md`](../architecture/units/README.md#компонент-и-компонент-юнит).

## Выбор роли

Выбирай архитектурную роль компонента по результату для потребителя:

| Результат | Исходное размещение | Правила |
| --- | --- |
| Продуктовая блочная проекция | `compositions` | [`units/compositions.md`](../architecture/units/compositions.md) |
| Самостоятельный предметный визуальный контракт | Внутри доменного юнита | [`units/domains/README.md`](../architecture/units/domains/README.md) |
| Универсальная визуальная возможность | Верхнеуровневый слой `ui` | [`units/ui.md`](../architecture/units/ui.md) |
| Локальная разметка без отдельного контракта | Внутри ближайшего владельца без фасета | [`units/README.md`](../architecture/units/README.md) |

Наличие JSX не определяет роль. Композиционный, доменный, инфраструктурный и UI-юнит могут содержать
React-компоненты, если они реализуют ответственность владельца.

## Проверка

- Готовое визуальное решение выбрано по правилам UI без повторной реализации примитивов библиотеки.
- Для собственного компонента определены ответственность и ближайший владелец.
- Новый `.tsx` создан по инструкции генерации; компонент имеет собственную папку независимо от наличия DOM.
- Созданы только необходимые файлы и сегменты.
- Тип свойств находится в `types/{name}-props.type.ts`, компонент имеет обязательный JSDoc.
- `ui/` используется как внутренний сегмент, а не ошибочно определяется как верхнеуровневый слой.
- Папка с `index.ts` или `lazy.ts` соблюдает ограничения юнита и не зависит от реализации родителей.
- Вложенный компонент-юнит не импортирует реализацию родителя; нужные ему данные родителя передаются через свойства.
- Доменный UI выделен по самостоятельному предметному визуальному контракту, а не по одному факту вызова доменного API.
- Реализация соответствует правилам JSX, состояния и стилей.
