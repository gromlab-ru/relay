# Маршрутизация в React SPA

Используй React Router Data Router через `createBrowserRouter` и `RouterProvider`. Владельцев и фасеты определяет
[`архитектурный профиль`](../architecture/project-profile.md#граница-app-и-compositions). Для новой страницы сначала
выполни [`инструкцию создания страницы`](../pages/README.md); устройство приложения и каркаса описано в
[`Структуре приложения`](../structure/README.md).

## Владельцы

| Владелец | Ответственность |
| --- | --- |
| `app/router` | Дерево URL, вложенность, статические перенаправления, подключение компонентов, общие ошибки и ожидание начальной загрузки |
| `compositions/layouts` | Постоянная компоновка и место для вложенного маршрута через `Outlet` |
| `compositions/screens` | Вёрстка страницы, состояния интерфейса и композиция публичных возможностей |
| `compositions/route-boundaries` | Отдельное поведение ветки: доступ, параметры URL, провайдер или условный выбор экрана |

Подключай каркас и экран напрямую. Не создавай компонент, который только возвращает один готовый экран. Маршрутная
граница нужна не каждому URL, а только отдельному поведению. Каркас не импортирует перечень страниц: состав его
`Outlet` задаётся деревом URL.

## Подключение экранов и каркасов

[`Конфигурация демо`](../../../demo-app/src/app/router/app-router.tsx) сочетает прямые статические импорты и динамическую
загрузку:

```tsx
import { createBrowserRouter } from 'react-router-dom'
import { MainLayout } from 'compositions/layouts/main'
import { HomeScreen } from 'compositions/screens/home'
import { NotFoundScreen } from 'compositions/screens/not-found'
import { RouteErrorBoundary } from './route-error-boundary/route-error-boundary'
import { RoutePending } from './route-pending/route-pending'

export const appRouter = createBrowserRouter([
  {
    path: '/',
    element: <MainLayout />,
    errorElement: <RouteErrorBoundary />,
    hydrateFallbackElement: <RoutePending />,
    children: [
      {
        index: true,
        Component: HomeScreen
      },
      {
        path: 'sign-in',
        lazy: () => import('compositions/screens/sign-in/lazy')
      },
      {
        lazy: () => import('compositions/route-boundaries/require-authentication/lazy'),
        children: [
          {
            path: 'account',
            lazy: () => import('compositions/screens/account/lazy')
          }
        ]
      },
      {
        path: '*',
        Component: NotFoundScreen
      }
    ]
  }
])
```

Граница без `path` применяется к дочерним маршрутам без добавления сегмента URL. На разрешённой ветке она выводит
`Outlet`. Каркас также выводит `Outlet`, но решает задачу постоянной компоновки, а не проверки доступа.

Общие `RoutePending` и `RouteErrorBoundary` принадлежат `app/router` и создаются генератором как внутренние компоненты.
Сама конфигурация роутера может подпадать под
[`системное исключение`](../components/tsx-generation.md#системные-исключения), пока только связывает готовые API.

## Динамическая загрузка

Подключай небольшой начальный или служебный экран статически через `index.ts`. Используй `lazy.ts`, когда отдельный
сценарий и его зависимости не нужны при каждом запуске. Подтверди решение сравнением размера и времени выполнения
начального JavaScript до и после разделения либо данными о редком открытии страницы. Само наличие URL не требует
отдельного чанка.

Фасет динамического экрана находится у самого экрана:

```ts
export { AccountScreen as Component } from './account.screen'
```

Роутер подключает `compositions/screens/account/lazy` напрямую. Для исключительно динамического потребителя одного
`lazy.ts` достаточно; не сохраняй рядом неиспользуемый `index.ts`. Такой же контракт применяется к динамическим
каркасам и границам. Фасет содержит только экспорты, не JSX и не вычисления.

Корневой маршрут задаёт `hydrateFallbackElement` с общим `RoutePending` для начальной загрузки динамической ветки.
Ошибку импорта обрабатывает подходящий `errorElement`. Эти состояния не заменяют загрузку и ошибки предметных данных
внутри экрана.

## Маршрутные границы

Создавай новый компонент границы через `ui-unit` по
[`инструкции генерации`](../components/tsx-generation.md), с каталогом вывода `src/compositions/route-boundaries`.
Адаптируй имя к `<Name>Boundary` и файл к `<name>.boundary.tsx`. Выбор фасета зависит от способа подключения, а не от
названия группы. Отсутствие собственного DOM не отменяет запуск CLI и не требует сохранять ненужный CSS Module.

Граница может:

- Применить публичный контракт авторизации, сохранить исходный адрес и перенаправить гостя.
- Прочитать и проверить параметры URL, затем передать подготовленные значения экрану через свойства.
- Подключить публичный провайдер вокруг `Outlet` на время отображения ветки.
- Получить результат предметной проверки и выбрать соответствующий экран, в том числе динамически.

Реализация сессии остаётся в домене, а реализация провайдера у его владельца. Граница не читает токены и не вызывает
HTTP-клиент. Состояния ожидания и ошибки самой проверки показывай явно, не выдавая неизвестный статус за гостя.

Рабочий пример:
[`RequireAuthenticationBoundary`](../../../demo-app/src/compositions/route-boundaries/require-authentication/require-authentication.boundary.tsx)
применяет публичный `AuthGuard`, показывает состояния проверки, перенаправляет гостя и выводит `Outlet` при разрешении.
Граница не имеет входных свойств, но сохраняет стили собственных состояний. Обычные экраны не получают аналогичной
границы автоматически.

## Условный выбор экрана

Отложенная загрузка известного экрана и выбор между экранами по изменяемому условию являются разными задачами.
`route.lazy` загружает реализацию совпавшего маршрута; React Router не использует его как реактивный переключатель при
смене роли или состояния пользователя.

Если выбор относится к маршруту, реализуй его в `route-boundaries`:

1. Получи условие из публичного API домена. Пока оно не определено, показывай ожидание; ошибку проверки обрабатывай отдельно.
2. Объяви ленивые компоненты на уровне модуля, не внутри функции компонента. Каждый импорт проходит через `lazy.ts`
   соответствующего экрана.
3. После определения условия отрисуй только выбранный экран внутри `Suspense` с осмысленным состоянием ожидания.
   Используй обычные ветви до `return` по правилам JSX, не тернарное выражение внутри разметки.
4. Передай параметры через свойства. При изменении условия повторно выбери экран; не сохраняй выбор один раз при создании
   конфигурации роутера. Ошибку загрузки кода передай ближайшей границе ошибок, а не оставляй вечный индикатор.

`React.lazy` ожидает `default`, поэтому адаптируй публичный именованный экспорт у потребителя:

```ts
import { lazy } from 'react'

const LazyAccountScreen = lazy(() => import('compositions/screens/account/lazy').then(({ Component }) => ({
  default: Component
})))
```

Объявление само не запускает загрузку; она начинается при первом отображении ленивого компонента. Не импортируй другой
фасет того же экрана статически в эту начальную ветку и не вызывай все загрузчики заранее, если требуется загрузить
только выбранный вариант. Если условие переключает лишь локальную часть страницы, оно остаётся у экрана, а не становится
маршрутной границей.

React Router может загрузить код совпавших дочерних маршрутов до отображения родительского гарда. Проверка доступа
ограничивает отображение, а не гарантирует отсутствие загрузки JavaScript. Если загрузка должна начаться только после
проверки, выбирай ленивый экран внутри границы. Сервер независимо проверяет права на операции и данные.

## Граница данных

- Не используй `loader` и `action` для предметных REST-данных.
- GET-состояние сервера получает публичный доменный SWR-хук, изменение выполняет доменная операция с обновлением кеша.
- Экран и граница импортируют домены, композиции и UI только через публичные фасеты.
- `domains` и `infra` не импортируют React Router и не выполняют навигацию.

## Проверка

- Дерево URL находится в `app`, каркасы и экраны подключены напрямую без пустых посредников.
- Каждая маршрутная граница имеет отдельное поведение и нужную область действия.
- Статические импорты используют `index.ts`, динамические `lazy.ts`; глубоких импортов нет.
- Начальная загрузка и ошибки кода имеют явное отображение; загрузка данных не смешана с загрузкой JavaScript.
- Условный выбор реагирует на изменения, не загружает заранее все варианты и не переносит предметные правила в границу.
- Провайдеры живут в нужной области и очищают ресурсы через API своих владельцев.
- Проверены прямой URL, вложенные переходы, обновление страницы, доступ гостя и возврат после входа.
- Новые TSX созданы CLI; сборка подтверждает предполагаемое разделение кода.
