# Автономная имитация API

Используй MSW, когда демонстрационное React-приложение должно полностью работать без внешнего сервера. MSW перехватывает
настоящие HTTP-запросы браузера, поэтому приложение продолжает проходить через настроенный `HttpClient`, созданные из
OpenAPI операции, доменные адаптеры и SWR. Не заменяй эти части тестовыми клиентами.

Это решение предназначено для автономного демо. Оно намеренно работает и при `vite preview`, чтобы собранное приложение
можно было проверить без сервера. Не используй такой worker как способ реализации рабочего API и не включай его в
производственную поставку пользовательского приложения.

## Единый HTTP-контракт

Храни локальную OpenAPI-схему отдельно от исходного кода:

```text
openapi/
└── backend-api.openapi.json
```

Создавай REST-клиент из этого файла воспроизводимой командой `package.json`. Обработчики MSW реализуют те же пути,
методы, тела запросов, ответы и статусы, которые описаны в схеме. Схема определяет контракт клиента, но не создаёт
обработчики MSW автоматически: после изменения операции обнови схему, повторно создай клиент и вручную приведи обработчик
в соответствие.

Пример локальной схемы и команды находится в
[`demo-app`](../../../demo-app/openapi/backend-api.openapi.json) и его
[`package.json`](../../../demo-app/package.json).

Эталонное демо реализует вход, чтение текущей сессии, выход и чтение текущего пользователя. Сверяй обработчики
[`authentication.handlers.ts`](../../../demo-app/src/infra/demo-api-mock/authentication.handlers.ts) и
[`users.handlers.ts`](../../../demo-app/src/infra/demo-api-mock/users.handlers.ts) с соответствующими четырьмя операциями
локальной схемы.

## Размещение

Оформи имитацию отдельным инфраструктурным юнитом:

```text
public/
└── mockServiceWorker.js
src/infra/demo-api-mock/
├── authentication.handlers.ts
├── users.handlers.ts
├── demo-identity.config.ts
├── start-demo-api-mock.ts
└── lazy.ts
```

- Разделяй обработчики по техническим группам OpenAPI, а не по React-компонентам.
- Храни демонстрационные данные и учётные значения внутри этого юнита.
- Проверяй тело запроса и заголовки до формирования ответа.
- Возвращай через `HttpResponse` тот же JSON и HTTP-статус, который обещает схема.
- Не импортируй MSW, обработчики и демонстрационные данные в домены.
- Публикуй запуск через отдельный `lazy.ts`, чтобы код worker загружался отдельным чанком.

Установи MSW как зависимость автономного демо, потому что его код входит и в сборку для preview:

```bash
npm install msw
```

Используй команду менеджера пакетов проекта. Затем создай файл service worker официальной командой MSW и сохраняй его
как статический файл приложения:

```bash
npx msw init public --save
```

Не редактируй `public/mockServiceWorker.js` вручную. Повторно создай его командой установленной версии MSW, когда этого
требует обновление библиотеки.

## Запуск

Собери worker из всех обработчиков и передай путь с учётом `BASE_URL` Vite:

```ts
import { setupWorker } from 'msw/browser'
import { authenticationHandlers } from './authentication.handlers'
import { usersHandlers } from './users.handlers'

const worker = setupWorker(...authenticationHandlers, ...usersHandlers)

export const startDemoApiMock = async (): Promise<void> => {
  await worker.start({
    onUnhandledRequest: 'bypass',
    serviceWorker: {
      url: `${import.meta.env.BASE_URL}mockServiceWorker.js`
    }
  })
}
```

Запусти worker до отображения React и дождись завершения `start()`. Иначе первый запрос может уйти в сеть раньше, чем
MSW получит управление:

```tsx
const startApp = async (): Promise<void> => {
  const { startDemoApiMock } = await import('infra/demo-api-mock/lazy')

  await startDemoApiMock()

  createRoot(rootElement).render(<App />)
}
```

Для автономного демо не ограничивай этот импорт условием `import.meta.env.DEV`: worker нужен и команде `preview`.
`onUnhandledRequest: 'bypass'` оставляет доступными прочие ресурсы и запросы, но каждый запрос локального API обязан иметь
явный обработчик. Отсутствующий обработчик считай рассогласованием демо со схемой, а не обращением к рабочему серверу.

Полная реализация запуска находится в
[`demo-app/src/infra/demo-api-mock`](../../../demo-app/src/infra/demo-api-mock/) и
[`app/main.tsx`](../../../demo-app/src/app/main.tsx).

## Граница с рабочим приложением

MSW в автономном демо является локальной реализацией внешнего HTTP-контракта, а не производственным сервером:

- данные живут в браузере и не являются общими для пользователей;
- worker не предоставляет серверную авторизацию, хранение, аудит и согласованность;
- обработчики не заменяют проверку приложения с настоящим API;
- производственная сборка реального приложения не должна запускать `startDemoApiMock`;
- если один проект собирает и демо, и рабочее приложение, раздели их явными точками входа или режимами сборки.

## Проверка

1. Выполни команду создания REST-клиента из локальной OpenAPI-схемы.
2. Запусти `npm run dev` и пройди все операции демо без внешнего сервера.
3. Выполни производственную сборку демо и запусти `npm run preview`.
4. Убедись, что `mockServiceWorker.js` загружается с учётом базового пути приложения.
5. Проверь успешные и предусмотренные неуспешные ответы каждого обработчика.
6. Сопоставь пути, методы, тела и статусы обработчиков с OpenAPI.
