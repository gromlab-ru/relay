# Формы в React SPA

Для любой новой формы используй `useForm` из `@mantine/form`. Поля, кнопки и сообщения формы собирай из компонентов
Mantine по правилам раздела [`UI`](../ui/README.md). Не добавляй другое средство управления формами или
параллельное состояние тех же значений.

Проверяемая реализация полного цикла находится в
[`SignInScreen`](../../../demo-app/src/compositions/screens/sign-in/sign-in.screen.tsx): экран владеет формой, проверяет
поля, выполняет публичное действие домена, показывает предусмотренные ошибки и обрабатывает успешный результат.

## Порядок работы

1. Определи пользовательский сценарий и ближайшего владельца формы.
2. Опиши отдельный тип значений, которые вводит пользователь.
3. Создай `useForm` в владельце формы и задай исходные значения каждого поля.
4. Подключи компоненты Mantine через `form.key` и `form.getInputProps`.
5. Добавь только устойчивые клиентские проверки ввода.
6. Преобразуй значения формы в публичный входной контракт вызываемой операции.
7. Передай асинхронный обработчик в `form.onSubmit` и отобрази предусмотренные ошибки операции.
8. После успеха выполни действие сценария: переход, закрытие, сброс или сохранение новых исходных значений.
9. Проверь ввод, ошибки, повторную отправку и поведение после успеха.

## Владелец и размещение

Форма принадлежит ближайшему владельцу интерфейса пользовательского действия. Страница, экран или виджет хранит `useForm`,
если сам владеет вводом, отправкой и результатом действия. Внутренний компонент поля не становится отдельным юнитом
только из-за разметки или проверки одного значения.

Вызов публичной доменной операции не переносит форму в домен. Помещай форму в домен только как часть самостоятельного
предметного визуального контракта, который не зависит от конкретного экрана. Одноразовая форма и её пользовательские
сообщения остаются у владельца сценария. Пример: [`SignInScreen`](../../../demo-app/src/compositions/screens/sign-in/sign-in.screen.tsx)
владеет формой входа и вызывает публичную операцию домена авторизации.

Не выноси единственный вызов `useForm` в `useSomethingForm`. Такой хук скрывает владельца без повторного использования
или отдельного жизненного цикла. Если форма разделена на несколько внутренних компонентов, сначала передавай им точные
свойства поля или нужную часть API формы. Не добавляй `createFormContext` только ради сокращения передачи свойств.

## Разделение ответственности

| Ответственность | Владелец |
| --- | --- |
| Значения, ошибки ввода, `touched`, `dirty` и `submitting` | Владелец формы через `useForm` |
| Разметка поля и доступная связь ошибки с полем | Компонент Mantine у владельца формы |
| Тип значений формы | Владелец формы |
| Публичный входной контракт и предусмотренные исходы операции | Доменный юнит |
| Преобразование значений формы во входной контракт операции | Владелец формы |
| Преобразование предметного входа в DTO | Доменный адаптер |
| Отображение предусмотренной ошибки операции | Владелец формы или ближайший владелец действия |
| Передача неожиданного сбоя общему механизму | Владелец действия |

Значения формы описывают ввод пользователя и могут содержать пустые строки, временно неполные значения и служебные
флаги интерфейса. Не используй DTO как тип формы. Не расширяй предметную модель полями, которые нужны только для ввода.

## Настройка useForm

По умолчанию используй `mode: 'uncontrolled'`. Mantine рекомендует этот режим для форм, поскольку изменение поля не
перерисовывает всего владельца.

```tsx
/**
 * Значения формы профиля.
 */
interface ProfileFormValues {
  /**
   * Отображаемое имя пользователя.
   */
  displayName: string
  /**
   * Признак согласия получать уведомления.
   */
  receiveUpdates: boolean
}

const form = useForm<ProfileFormValues>({
  mode: 'uncontrolled',
  initialValues: {
    displayName: '',
    receiveUpdates: false
  }
})
```

В режиме `uncontrolled` `form.values` не содержит гарантированно актуальные значения. Получай их следующими способами:

- используй аргумент обработчика `form.onSubmit` во время отправки;
- вызывай `form.getValues()` для императивного чтения;
- вызывай `form.useWatchValue(path)`, если значение определяет отображение React.

Не добавляй состояние React, Zustand или SWR для копии значений формы. Если черновик должен переживать размонтирование,
перезагрузку или смену маршрута, сначала определи отдельный контракт хранения, срок жизни и правила разрешения
конфликтов.

## Подключение полей

Каждый компонент поля в режиме `uncontrolled` получает `key` и свойства поля из одного пути:

```tsx
<TextInput
  key={form.key('displayName')}
  label="Отображаемое имя"
  required
  {...form.getInputProps('displayName')}
/>
```

Для `Checkbox`, `Switch` и другого логического поля укажи тип `checkbox`, чтобы Mantine управлял `checked`, а не
`value`:

```tsx
<Checkbox
  key={form.key('receiveUpdates')}
  label="Получать уведомления"
  {...form.getInputProps('receiveUpdates', { type: 'checkbox' })}
/>
```

Не передавай полю отдельные `value`, `defaultValue`, `checked`, `error` или обработчик изменения поверх результата
`getInputProps`. Если собственный компонент должен работать в форме, он обязан поддерживать `defaultValue` или
`defaultChecked`, изменение, фокус, потерю фокуса и свойство `error`.

Для условной части формы подпишись только на управляющее поле:

```tsx
const hasDeliveryAddress = form.useWatchValue('hasDeliveryAddress')
```

Не читай `form.getValues()` во время отображения условного блока: это чтение не подписывает компонент на изменения.

## Проверка ввода

Проверяй на клиенте только устойчивые требования к корректному вводу: обязательность, формат, длину и согласованность
нескольких полей. Используй валидаторы `@mantine/form` или короткие чистые функции в `validate`.

По умолчанию включай `validateInputOnBlur: true`. Ошибка появляется после завершения ввода в поле и повторно
проверяется при отправке. Не включай проверку каждого поля на каждое изменение без требования сценария.

```tsx
const form = useForm<ProfileFormValues>({
  mode: 'uncontrolled',
  validateInputOnBlur: true,
  initialValues: {
    displayName: ''
  },
  validate: {
    displayName: (value) => (
      value.trim().length === 0
        ? 'Введите отображаемое имя'
        : null
    )
  }
})
```

Не выполняй сетевой запрос из `validate`. Доступность имени, права пользователя, состояние записи и другие изменяемые
бизнес-правила проверяет операция владельца. Клиентская проверка не заменяет серверную.

Передай в `form.onSubmit` второй обработчик и переведи фокус на первое некорректное поле:

```tsx
const handleValidationError = (errors: typeof form.errors): void => {
  const firstErrorPath = Object.keys(errors)[0]

  if (firstErrorPath !== undefined) {
    form.getInputNode(firstErrorPath)?.focus()
  }
}
```

## Отправка

Форма использует семантический `<form>`. Передавай асинхронную функцию непосредственно в `form.onSubmit`: тогда
Mantine устанавливает `form.submitting` до завершения возвращённого `Promise`.

```tsx
<form
  noValidate
  onSubmit={form.onSubmit(handleSubmit, handleValidationError)}
>
  {/* Поля и действие. */}
</form>
```

На время отправки заблокируй поля через `fieldset` и покажи состояние загрузки на кнопке:

```tsx
<fieldset disabled={form.submitting}>
  {/* Поля. */}
  <Button loading={form.submitting} type="submit">
    Сохранить
  </Button>
</fieldset>
```

Не создавай отдельный `isSubmitting`. Не вызывай API-клиент напрямую из обработчика предметной формы. Вызови публичную
доменную операцию или хук действия, который дополнительно управляет кешем сценария. Если форма является внутренним
компонентом отображения, получи точный обработчик операции через свойства от владельца сценария.

## Ошибки операции

Разделяй результаты отправки:

| Результат | Действие формы |
| --- | --- |
| Ошибка относится к конкретному полю | `form.setFieldError(path, message)` |
| Предусмотренная ошибка относится ко всему действию | Сообщение Mantine рядом с кнопкой отправки |
| Неожиданный сбой | Передача принятому общему механизму и безопасное сообщение пользователю |

Общая ошибка действия не является значением поля. Храни её как локальное состояние владельца формы и очищай при новом
вводе или перед следующей отправкой. Не показывай DTO, ответ источника или техническое сообщение исключения.

Не очищай введённые значения после неуспешной отправки. Граница ошибок React не перехватывает ошибки обработчиков
событий, поэтому неожиданный сбой должен быть обработан явно.

## Исходные данные

Для формы создания передай полные пустые значения в `initialValues`. Для формы редактирования сначала получи предметные
данные и смонтируй форму с готовыми исходными значениями. Это предотвращает замену уже начатого пользовательского ввода
поздним ответом.

Используй `form.initialize(values)` только когда владелец обязан смонтировать форму до получения данных. До инициализации
заблокируй ввод. `initialize` применяется один раз; для перехода между разными сущностями размонтируй прежнего владельца
по устойчивому ключу сущности.

Не копируй новые серверные данные в изменённую форму автоматически. Сначала выбери правило конфликта: сохранить ввод,
предложить обновление или заменить значения после подтверждения пользователя.

## Динамические поля

Для массивов используй `insertListItem`, `removeListItem`, `replaceListItem` и `reorderListItem`. Каждый элемент получает
устойчивый ключ, который не зависит от позиции. `form.key(path)` остаётся ключом самого поля, а устойчивый ключ элемента
размещается на внешнем контейнере строки.

Не изменяй массив напрямую через результат `form.getValues()`. Не используй индекс как ключ React для списка, в котором
элементы добавляются, удаляются или меняются местами.

## После успеха

Не вызывай `form.reset()` автоматически для любой успешной операции:

- если владелец закрывается или выполняется переход, дополнительный сброс не требуется;
- если форма создания остаётся открытой для следующей записи, сброси её явно;
- если форма редактирования остаётся открытой, установи подтверждённые сервером значения как текущие и исходные, затем
  сбрось состояние `dirty`.

Конкретное поведение определяется пользовательским сценарием, а не библиотекой.

## Проверка

- Форма использует `useForm` из `@mantine/form` в режиме `uncontrolled`.
- Каждое поле получает согласованные `form.key` и `form.getInputProps`.
- Логические поля используют `{ type: 'checkbox' }`.
- Условное отображение подписано через `form.useWatchValue`.
- Проверка ввода не выполняет сетевые запросы и не копирует изменяемые бизнес-правила.
- Отправка проходит через `form.onSubmit`, а повторное действие заблокировано через `form.submitting`.
- Полевая, общая ожидаемая и неожиданная ошибки проходят по разным каналам.
- После ошибки введённые значения сохранены.
- После успеха выполнено действие, предусмотренное сценарием.
- Проверены ввод с клавиатуры, фокус первого некорректного поля и доступная связь ошибки с полем.
