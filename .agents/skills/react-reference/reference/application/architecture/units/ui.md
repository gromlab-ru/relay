# UI-юниты

UI-юнит предоставляет универсальную визуальную возможность без предметного смысла. Он владеет устойчивым компонентным
контрактом, DOM, поведением и оформлением, которые нужны нескольким самостоятельным владельцам приложения.

Общее различие внутреннего React-компонента и компонента-юнита описано в [`обзоре ролей`](README.md#компонент-и-компонент-юнит).
Физические фасеты и сегменты определяет [`архитектурный профиль`](../project-profile.md).

## Назначение

К слою `ui` относятся проектные визуальные возможности, которые не знают о предметных моделях и конкретных сценариях:

- элемент управления;
- диалог;
- универсальная область размещения;
- элемент типографики;
- составное визуальное поведение с общим контрактом.

Универсальность не означает максимальную настраиваемость. Компонент должен выражать устойчивую визуальную возможность,
а не принимать свойства для воспроизведения любого возможного интерфейса.

## Критерий отдельного юнита

Помещай компонент в верхнеуровневый слой `ui`, когда одновременно выполняются условия:

- у него есть самостоятельное визуальное назначение;
- он предоставляет собственный публичный контракт;
- он не зависит от предметной модели или сценария;
- он нужен нескольким самостоятельным владельцам;
- изменения DOM, поведения и оформления должны выполняться в одном месте.

Повторение разметки само по себе не подтверждает общий UI-юнит. Сначала проверь, совпадают ли назначение, контракт и
причины изменения. Не поднимай компонент в `ui` ради предполагаемого использования в будущем.

## Граница с другими ролями

- Продуктовая блочная проекция принадлежит [`compositions`](compositions.md), даже если реализована React-компонентом.
- Самостоятельный предметный визуальный контракт принадлежит домену; один только вызов публичного доменного API не
  меняет владельца композиционного интерфейса.
- Provider внешней технической возможности принадлежит инфраструктурному юниту; Provider визуальной темы — `ui/themes`.
- Чистая функция без визуального результата не становится UI-юнитом.

Общая тема библиотеки компонентов, её визуальная конфигурация, `ThemeProvider` и контракт цветовой схемы принадлежат
`ui/themes`. `app` подключает публичный Provider, но не владеет его реализацией.

Папка `ui/` внутри композиционного, доменного или инфраструктурного юнита является сегментом этого владельца, а не
верхнеуровневым слоем `ui`.

## Библиотека компонентов

Mantine является основной библиотекой компонентов проекта. Готовый компонент Mantine не получает проектную обёртку и
не помещается в `ui` только ради повторного экспорта, переименования или значений свойств по умолчанию.

Проектный UI-юнит поверх Mantine оправдан, когда добавляет собственный устойчивый визуальный контракт и имеет несколько
реальных потребителей. Практический порядок выбора и реализации описан в
[`UI`](../../ui/README.md).

## Публичный фасет

`index.ts` публикует только необходимый компонентный контракт:

```ts
export { EmptyState } from './empty-state'
export type { EmptyStateProps } from './types/empty-state-props.type'
```

- Экспортируй компоненты через именованные экспорты, а типы через `export type`.
- Не публикуй внутренние компоненты, вспомогательные функции, CSS Modules и промежуточные типы.
- Межюнитные потребители импортируют UI только через фасет.
- Не добавляй обёртку или псевдоним, который только повторяет внутренний экспорт.

Правила TSX и свойств компонентов находятся в [`styleguide/jsx-tsx.md`](../../../styleguide/jsx-tsx.md), правила CSS
Modules — в [`styleguide/css.md`](../../../styleguide/css.md).

## Проверка

- У компонента есть самостоятельная универсальная визуальная ответственность.
- Подтверждены несколько самостоятельных потребителей.
- Публичный контракт не содержит предметных моделей или конкретного сценария.
- Продуктовая проекция не помещена в `ui` только из-за наличия JSX.
- Компонент Mantine не обёрнут только ради повторного экспорта или значений по умолчанию.
- Публичный фасет минимален и не раскрывает внутреннюю реализацию.
- Свойства и стили принадлежат тому же владельцу, что DOM и визуальное поведение.
