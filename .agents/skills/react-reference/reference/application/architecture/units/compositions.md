# Композиционные юниты

Композиционный юнит владеет связной блочной проекцией продуктового интерфейса. Он собирает готовые публичные API в
завершённую видимую область, которой родитель управляет через один контракт, не зная её внутреннего устройства.

Названия и назначения групп `layouts`, `route-boundaries`, `screens` и `widgets` определяет
[`архитектурный профиль`](../project-profile.md#структура-compositions). Этот документ определяет общую границу любого
композиционного юнита независимо от группы.

## Блочная проекция

Блочная проекция — самостоятельная область интерфейса с собственным назначением, входными данными, действиями и
внутренней компоновкой. Родитель подключает её как завершённый компонент и отвечает только за её место среди других
областей.

Термин не относится к CSS `display: block`, прямоугольной форме или обязательному DOM-контейнеру. Проекция может
возвращать несколько элементов, использовать React portal или передавать часть отображения вложенному маршруту. Важна
архитектурная граница: потребитель работает с результатом целиком и не собирает внутренние части самостоятельно.

Примеры блочных проекций:

- страница маршрута;
- завершённый экран сценария;
- каркас приложения;
- шапка или навигационная область;
- панель поиска;
- крупный продуктовый виджет.

## Чем владеет композиция

Композиционный юнит владеет:

- размещением и порядком частей своей области;
- визуальной координацией готовых возможностей;
- передачей данных и действий между подключёнными контрактами;
- состоянием отображения, которое существует только ради этой проекции;
- вложенными проекционными ответственностями;
- публичным компонентным контрактом блока.

Композиция может напрямую использовать публичные API других композиций, доменов, инфраструктуры, UI и общего кода в
пределах матрицы Unit Architecture. Она не обязана проходить через промежуточную группу или слой.

## Граница ответственности

Композиция не присваивает себе:

- предметные модели, операции и ожидаемые исходы домена;
- настройку HTTP, хранилища, телеметрии или другого технического ресурса;
- универсальный визуальный компонент без продуктового смысла;
- дерево URL и запуск React.

Например, экран может вызвать публичный доменный хук и выбрать состояния отображения. Один только вызов модели, операции
или хука не делает интерфейс доменным. Самостоятельный роутер-независимый визуальный контракт предметной возможности
остаётся в домене; одноразовые разметка, сообщения и результат экранного сценария принадлежат композиции. Композиция
может подключить технический Provider через его фасет, но не переносит к себе настройку внешней библиотеки.

Эту границу показывают [`SignInScreen`](../../../../demo-app/src/compositions/screens/sign-in/sign-in.screen.tsx) и
[`AuthGuard`](../../../../demo-app/src/domains/authentication/ui/auth-guard/auth-guard.tsx): экран владеет формой и
маршрутным результатом входа, а домен предоставляет повторно применимую проверку авторизации без зависимости от роутера.

## Критерий отдельного юнита

Выделяй композиционный юнит, когда одновременно выполняются условия:

- область имеет отдельно формулируемое назначение;
- родитель размещает её как единый блок;
- область предоставляет собственный компонентный контракт;
- внутреннюю компоновку можно изменить без изменения контракта родителя;
- зависимости области можно скрыть за её фасетом.

Вынесенный фрагмент JSX, обёртка, разделитель, локальный хук или контейнер ради CSS остаётся реализацией ближайшего
владельца. Повторение разметки само по себе не требует нового юнита.

## Вложенные проекции

Композиционный юнит может содержать вложенные компоненты-юниты в сегменте `ui/`. Родитель определяет их размещение и
передаёт данные через публичные контракты. Дочерний юнит не импортирует реализацию родителя или соседних детей.

```text
compositions/layouts/main/
├── index.ts
├── main.layout.tsx
└── ui/
    ├── header/
    │   ├── index.ts
    │   └── header.tsx
    └── footer/
        ├── index.ts
        └── footer.tsx
```

В этом примере `MainLayout`, `Header` и `Footer` владеют отдельными блочными проекциями. Папка `ui/` является сегментом,
а не верхнеуровневым слоем `ui`.

## Группы

Группы `layouts`, `route-boundaries`, `screens` и `widgets` только классифицируют композиционные юниты. Они не являются
владельцами, не имеют фасетов и не образуют дополнительную иерархию зависимостей. Любой юнит группы остаётся обычным
узлом слоя `compositions`.

Экран подключается к роутеру напрямую. Граница в `compositions/route-boundaries` нужна только для отдельного поведения
ветки, а не для повторного экспорта экрана. Используй `lazy.ts` только при подтверждённом разделении сборки;
статический потребитель использует `index.ts`.

## Проверка

- Юнит владеет завершённой блочной проекцией, а не произвольно вынесенным JSX.
- Родитель подключает проекцию через контракт и не собирает её внутренние части.
- Предметные правила остались в доменах, а техническая интеграция — в инфраструктуре.
- Группа только классифицирует юнит и не ограничивает его допустимые зависимости.
- Вложенные проекции соблюдают границы родителя и детей.
- URL принадлежит `app`, отдельное поведение ветки относится к `route-boundaries`, экранный сценарий к `screens`.
