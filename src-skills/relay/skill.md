# Relay — рабочая память и управление проектом для агентов

Relay сохраняет **зачем существует проект, чего мы добиваемся, что выполняется, что проверено и где продолжать работу**. Через него оркестратор организует создание продукта, доработки, исправления и выпуски; работники получают ограниченные поручения и возвращают проверяемые результаты. Человек видит те же данные в веб-приложении и может отвечать на вопросы, редактировать планы и принимать работу.

Используй Relay как общую память между участниками и сессиями. Существенный результат, блокер или следующий шаг должны оставаться в проекте после окончания чата. Задача — единица исполнения; её место в продукте задают паспорт, требования и план.

## 1. Как устроен проект

```text
Проект → паспорт и знания
       → план изменения → этапы → задачи → исполнения → проверки → приёмка
       → релиз → установка в окружение → наблюдение и исправления
       → summary и точки продолжения для следующей сессии
```

| Что сохранить                                                | Где это находится                                                  |
| ------------------------------------------------------------ | ------------------------------------------------------------------ |
| Назначение, пользователи, ограничения, стадия продукта       | `passport`; один документ с ID `passport`                          |
| Цель создания или доработки, объём, текущий фокус            | `plan`; `passport.focusPlanId` выбирает план в фокусе              |
| Результат части плана, критерии и зависимости этапов         | `stage`, связанный с планом через `planId`                         |
| Конкретная работа, назначение, статус, описание и summary    | Карточка задачи с числовым ID, например `12`                       |
| Этап задачи, требования, границы поручения, сведения о баге  | Документ `kind: "task"` с ID `task_12`; это контекст карточки `12` |
| Ожидаемое поведение продукта                                 | `requirement`; связывается с задачей через `requirementIds`        |
| Архитектура, инструкция, решение и его причина               | `knowledge`; задача выбирает нужные записи через `knowledgeIds`    |
| Попытка работника: сессия, состояние, ветка, результат       | `run`; у одной задачи может быть несколько попыток                 |
| Сценарий проверки, состояние кода, результат и подтверждение | `check`; приёмка оркестратора — отдельный `review`                 |
| Вопрос, адресат и сохранённый ответ                          | `question`                                                         |
| Состав версии и ограничения; факт установки и проверки       | `release` и связанный `deployment`                                 |
| Снимок состояния, незавершённая работа и место продолжения   | Неизменяемый `checkpoint`                                          |

Паспорт, планы и остальные документы принадлежат **одному проекту**. Workspace — реестр независимых проектов и способ выбирать их. В каждом вызове сохраняй правильный проект: номер `12` в двух проектах означает разные задачи.

Relay хранит сведения в `.relay/tasks` и `.relay/project`. CLI, MCP, API и Web обращаются к одной модели с проверкой связей и ревизий. Запуск работников, изменение кода, Git, тесты, установку и откат выполняй инструментами своей среды; в Relay фиксируй поручения, наблюдения и фактические результаты этих действий.

## 2. Определи роль и подключение

### Независимая модель продукта

При работе с новым разделом «Продукт» начинай с `product_overview` / `product overview`.
Для выбора цели используй `product_entities` / `product entities`: краткие страницы без Markdown. `product_get` / `product get` читает одну фичу, сценарий, приложение или реализацию по ключу либо ID.
Ключи: FEATURE-12, SCENARIO-37, WEB, WEB-FI-12, WEB-SI-37. Все постоянные связи используют ID; при неоднозначном ключе выбери ID из кандидатов, не угадывай цель.
Используй `product_list` для чтения записей порциями и `product_context` для связанного контекста фичи, сценария или приложения. Записывай через `product_save` / `product save`.
CLI также имеет команды `product passport|feature|scenario|application|document create|update`,
`product scope replace` и `product contract update`. Проверяй их наличие в установленной версии.
Перед наполнением прочитай [стандарт содержания](references/PRODUCT-CONTENT.md).
Заголовок — одна строка, краткое описание — многострочный обычный текст, полное описание
и инструкция — структурированный Markdown. Большой слитный абзац не заменяет требования:
раздели цель, правила, поток, ошибки и критерии по смыслу. Не выдумывай сведения ради шаблона.
Markdown передавай **напрямую многострочным текстом** (`--description`, `--body` или строкой
в JSON), не создавай промежуточных MD-файлов. Хранилище само представляет Markdown массивом
строк в JSON. После записи перечитай содержание и связи, затем проверь `product lint`.
Для MCP предпочитай `product_passport_save`, `product_feature_save`, `product_scenario_save`,
`product_application_save`, `product_document_save`, `product_scope_replace`, `product_contract_update`.
Перед серией записей объясни её назначение, после сообщи названия и ID сохранённых объектов.
Общие статусы фич и сценариев вычисляются из контрактов приложений; вручную меняется только
состояние реализации. `done` подтверждает актуальные требования. После изменения требований
прежняя готовность требует переподтверждения. Перед записью читай ревизию, для состава также
версию графа; после потери ответа повторяй тот же запрос с тем же `requestId`.
Документы продукта — ТЗ, описания, правила и решения с типизированными связями, не логи.
Новые канбан-задачи, планы и этапы связаны с продуктом через productLinks; старый паспорт жизненного цикла не объединён с новым продуктом. Реализации хранятся отдельно под applications/<applicationId>/{features,scenarios}/<implementationId>.json. Меняй их через `product_implementation_update` / `product implementation update` с собственной ревизией, requestId и автором. Для исправления ключа используй key, сохраняя ID; перечитай результат и прежние связи. Старые файлы и миграционные журналы вручную не редактируй.

При создании приложения укажи обязательный `slug` (`--slug` в CLI): неизменяемый уникальный в проекте адрес приложения и его доски. Допустимы строчные латинские буквы, цифры и дефисы, 1–64 символа; `product`, `infrastructure`, `new` зарезервированы.
Создание приложения создаёт `boards/<slug>/board.json` и `tasks/`. При init создаются продуктовая и инфраструктурная доски. Укажи `prefix` (`--prefix WEB`) для ключей задач; по умолчанию он получается из slug. Системные префиксы — `PRODUCT` и `INFRA`.
[Контракт досок](references/BOARDS.md).

**Новые задачи досок:** `boards_list`, `board_tasks_list`, `board_task_*`; CLI `boards` и `task list|get|create|update|move|link|links`. Прежние `task_*` и корневые CLI-команды относятся к числовой модели. Проверь наличие новых инструментов в установленной версии.
Постоянный ID — 8 символов, ключ — например `WEB-24`. При переносе ключ меняется, ID и связи сохраняются. Пустые поля допустимы, но агент передаёт известное поручение сразу одним запросом. Изменение требует автора, `ifRevision` и `requestId`; повторяй тот же запрос после неясного ответа.
Оркестратор читает `readiness=ready` для работы без блокеров, `readiness=blocked` и `board_task_links` для графа. Только `done` выполняет зависимость; родительство не задаёт порядок. Читай страницы по nextOffset/version и полный Markdown адресно. [Контракт канбана](references/KANBAN.md).
Продуктовые цели — `productLinks` с kind `feature`, `scenario` или `implementation` и постоянным ID. Запись заменяет набор: сначала прочитай задачу, сохрани нужные прежние цели, после записи перечитай результат.
Требования читай через `product_context`; `productTarget` находит обратные задачи. Подзадача создаётся атомарно с `parentId`; типа эпика нет. Завершённая задача не подтверждает готовность продукта.
Для списка незавершённых задач используй `completion=unfinished`; `searchIn=title` ограничивает q ключами/ID/названием. Фильтрация выполняется до пагинации; существующие связи не удаляются.

- **Оркестратор:** тебе поручена цель проекта или организация изменения. Ты ведёшь планы, назначаешь работу, интегрируешь результаты, принимаешь их и сохраняешь контекст.
- **Работник:** тебе выданы конкретная задача, автор и рабочий каталог. Ты выполняешь её границы, проверяешь результат и передаёшь отчёт. План, назначения, приоритеты и приёмку меняешь только по явному поручению оркестратора.
- Уточняй недостающие проект, ID или полномочия по поручению. Роль определяет инструкцию работы; поле `actor` является подписью записи.

**Если MCP уже подключён:** проверь доступные инструменты, вызови `projects_list`, найди нужный проект. В workspace передавай `project` в каждом проектном вызове. В local его можно опускать. Здесь используются имена инструментов Relay; клиент может добавлять к ним свой префикс.

**Если используешь CLI:** `relay-cli` ниже означает установленную команду или `npx @gromlab/relay-cli`. Работай с `--format json`, проверяй код процесса и `ok`. Из каталога без конфига можно обращаться так:

```bash
relay-cli --server-url http://127.0.0.1:4700 --project app project context --format json
```

`app` здесь — пример ключа из реестра; подставь выданный ключ или ID. В local CLI находит `.relay/config.json` и работает напрямую либо через `server.url`. В workspace рабочие команды идут через сервер; проект выбирается префиксом (`relay-cli app ...`) или `--project`. `--config` выбирает конкретный конфиг. Из worktree используй выданное подключение к общей базе.

**Если проект действительно новый:** оркестратор инициализирует его в нужном каталоге. Серверы — отдельные долгоживущие процессы:

```bash
npx @gromlab/relay-cli init
npx @gromlab/relay-server --open
# В другом процессе, если требуется MCP:
npx @gromlab/relay-mcp --server-url http://127.0.0.1:4700
```

Web/API обычно доступны на `http://127.0.0.1:4700`, MCP — на `http://127.0.0.1:4710/mcp`. Перед запуском проверь уже работающие процессы. В существующем проекте сначала найди его конфиг или сервер; работник получает подключение от оркестратора. Подробная настройка — [STARTUP](references/STARTUP.md).

Для полного цикла нужны `project_context`, `project_record_save`, `task_briefing` или соответствующие команды `project` в CLI. Если их нет, проверь версию и подключение: скилл описывает актуальный контракт исходников, а установленный пакет может быть старее. Не подменяй отсутствующие операции выдуманными командами.

## 3. Прочитай ровно тот контекст, который нужен роли

| Вопрос                                                 | MCP                                   | CLI                           |
| ------------------------------------------------------ | ------------------------------------- | ----------------------------- |
| Какой это проект и что сейчас важно?                   | `project_context`                     | `project context`             |
| Какие статусы настроены?                               | `project_config`                      | `config get`                  |
| Какие задачи готовы, на проверке или блокируют работу? | `project_overview`                    | `overview`                    |
| Что поручено конкретному работнику?                    | `task_briefing({ id: T })`            | `project briefing T`          |
| Каковы актуальные поля и ревизия задачи?               | `task_get({ id: T })`                 | `get T`                       |
| Какие документы существуют?                            | `project_records({ kind: "plan" })`   | `project records --kind plan` |
| Как прочитать документ полностью?                      | `project_record_get({ recordId: R })` | `project get R`               |
| Что изменилось после передачи?                         | `checkpoint_changes({ recordId: C })` | `project changes C`           |

`T` — числовой ID задачи, `R` и `C` — строковые ID документов из ответов. В workspace к MCP-параметрам добавляется `project`; к CLI — выбранный проект.

Оркестратор начинает с `project_context` и `project_overview`. Контекст сокращает длинные тексты, показывает до трёх активных этапов и пяти сигналов; сравни `activeStageCount` и `attentionCount` с возвращёнными списками и дочитай необходимые документы. Если есть checkpoint, прочитай его и изменения после него.

Работник начинает с `task_briefing` и `task_get`, затем читает нужные связи, вопросы и замечания. Проверь назначение и `blockedBy`. `ready: false` у назначенной задачи нормально: это доступность для свободного захвата, а не признак запрета выполнять поручение.

## 4. Цикл оркестратора

1. **Восстанови состояние.** Установи цель, текущий план, проверенные результаты, блокеры и следующий шаг. Сверь важные утверждения с кодом, проверками и окружением.
2. **Определи результат изменения.** Создай или уточни паспорт, требования и план. У этапов должны быть наблюдаемый результат и критерии приёмки. Используй существующие подходящие записи.
3. **Декомпозируй.** Создай задачи; через документы `kind: "task"` привяжи их к этапам, требованиям и знаниям. Добавь реальные зависимости между задачами.
4. **Выдай поручения.** Назначь исполнителя и подходящий статус. Передай проект, ID, `actor`, подключение, рабочую копию, briefing и ожидаемые подтверждения. Запусти работника доступными средствами своей среды.
5. **Следи за фактами.** Читай попытки, отчёты, проверки и вопросы. При отмене или неясном состоянии сверь runtime. Сохраняй принятые решения и ответы.
6. **Прими работу.** Изучи результат, интегрируй изменения и проверь общий сценарий. Запиши `review`; отдельно измени статус карточки. Верни конкретные замечания при доработке.
7. **Заверши этап и план.** Принимай этап по результату и критериям, сохраняя `acceptance`. Завершай план после приёмки этапов; объясняй исключённую или отменённую работу.
8. **Доведи до использования.** Составь `release`, выполни согласованные операции выпуска и запиши реальные установки как `deployment`. После установки проверь целевой сценарий.
9. **Сохрани продолжение.** Обнови summary и `nextStep` плана/паспорта, перед паузой или передачей создай checkpoint.

Для небольшого исправления достаточно небольшой декомпозиции. Поддержка проходит тот же цикл: воспроизведение бага → исправление → регрессионная проверка → приёмка → версия с исправлением. Продукт в эксплуатации сохраняет свою стадию, пока отдельный план проходит разработку.

## 5. Цикл работника

1. Прочитай выданное поручение и актуальную карточку. Если нет исходных данных, назначение другое или требования противоречат поручению — сохрани вопрос и сообщи оркестратору.
2. Получи существующий `runId` или зарегистрируй новую попытку `run` для этой задачи. Сохрани известные сессию, рабочую копию и исходное состояние кода. Собственные сообщения отмечай `source: "agent"`.
3. Выполни работу в заданных границах. Существенный прогресс и диагностику записывай через `log_add`; продуктовый вопрос — через `question`.
4. Выполни проверки и создай `check` с командой/сценарием, результатом, состоянием кода и подтверждением. Непроведённая проверка остаётся `pending`.
5. Обнови свою попытку: `succeeded`, `failed` или `cancelled`, результат, ограничения и причина. Новая попытка получает новый `run`; завершённую нельзя перезапускать сменой статуса.
6. Обнови summary задачи и добавь итоговый отчёт. Верни оркестратору ID попытки и проверок, место результата, оставшиеся вопросы и точный следующий шаг. Приёмку и статус задачи ведёт оркестратор.

Завершение `run` означает завершение попытки. `review` фиксирует приёмку. Статус задачи, готовность этапа и выпуск — отдельные состояния. Флаг `integrated` выставляется после фактического включения результата в общую версию.

## 6. Как записывать данные

**Карточки задач:** `task_create` создаёт работу, `task_update.patch` меняет выбранные поля. CLI-аналоги — `create` и `update`. Например, оркестратор назначает выданную задачу:

```text
task_update({ project: P, id: T, actor: "orchestrator", ifRevision: TASK_REV,
  patch: { assignee: "api-worker", status: "in_progress" } })
```

`P`, `T` и `TASK_REV` берутся из подключения и свежего `task_get`. `in_progress` — стандартный пример; используй статус из конфигурации конкретного проекта.

**Проектные документы:** `project_record_save` создаёт запись по `fields.kind`. Минимальный пример плана через CLI:

```bash
relay-cli project save --actor orchestrator --format json --json \
  '{"requestId":"auth-plan-1","fields":{"kind":"plan","title":"Восстановление доступа","goal":"Пользователь возвращает доступ самостоятельно","status":"active"}}'
```

В ответе сохрани `data.id` и `data.revision`. Строковые ID документов выдаёт Relay; паспорт имеет ID `passport`, контекст задачи `12` — `task_12`. Создавай объекты в порядке ссылок: план перед этапом, карточку перед её контекстом, исполнение перед связанной проверкой.

**Обновление документа заменяет `fields` целиком.** Сначала `project_record_get`, затем копия всех его полей с нужным изменением:

```text
project_record_save({ project: P, actor: A, id: current.id,
  ifRevision: current.revision, fields: { ...current.fields, summary: "Что готово и что дальше" } })
```

Здесь `current` — документ из `data` ответа чтения. Это схема MCP-вызова, не готовый shell-код. Для CLI передавай такой JSON в `project save --json` или `--file -`. Пропуск поля при обновлении сбрасывает его в default. Ревизия карточки `12` и ревизия документа `task_12` независимы.

**Обсуждение и отчёты:** `comment_add` — разговор, `log_add` — история работы. `log.kind: "execution"` является текстовым отчётом; структурированная попытка создаётся как `run`. Сохраняй итог также в Relay:

```text
log_add({ project: P, id: T, actor: A, requestId: "session-42-final",
  kind: "summary", text: "Результат: …\nПроверки: …\nОграничения: …\nСледующий шаг: …" })
```

## 7. Правила достоверности и совместной работы

- **Записывай через инструменты.** CLI/MCP/API проверяют связи и ревизии под блокировкой. Все участники используют одну выбранную базу.
- **Разделяй связи.** `parentId` — декомпозиция, `dependsOn` — зависимость карточек, `stageId` в контексте — место в плане. Подзадача наследует этап до собственного контекста; явный `stageId: null` снимает связь.
- **Проверяй семантику статуса.** `terminal` означает конечность, `satisfiesDependencies` — успех. Отмена не удовлетворяет зависимость. Прогресс плана считает листовые задачи.
- **Подписывай каждую запись.** MCP-операции записи задач и документов требуют `actor`; CLI использует `--actor` или `RELAY_ACTOR`. Назначение `assignee` существует отдельно.
- **Фиксируй факты.** Указывай реально выполненные команды, результаты и коммиты. Для незакоммиченной рабочей копии оставь `check.commit` пустым и опиши проверенное состояние в `details`/`evidence`. Git-операции выполняются в рамках поручения.
- **Указывай источник.** `run.source: runtime` — сведения от среды; `agent` — сообщение агента; `manual` — ручная запись. `check.source: ci` требует действительного результата CI. Отсутствие наблюдений более двух минут вызывает сигнал сверки, а не доказательство остановки.
- **Разрешай конфликты чтением.** При `REVISION_CONFLICT` перечитай объект и согласуй изменение; не подставляй новую ревизию к старому набору полей. Лог и комментарий тоже меняют ревизию карточки.
- **Повторяй осознанно.** Для логов/комментариев сохраняй тот же `requestId` и содержание. Обычное создание проектного документа поддерживает такой ключ. После потерянного ответа обновления, создания карточки, паспорта или `task_T` сначала проверь сохранённое состояние.
- **Читай продолжение.** Проверяй `ok`, `meta.hasMore` и `nextCursor`; сохраняй проект и фильтры. `project_records` MCP поддерживает страницы; CLI `project records` страниц не имеет. При большом ответе выбирай нужный документ/поля либо увеличивай `maxBytes` / `--max-bytes`.
- **Сохраняй точку продолжения.** Checkpoint содержит объяснение состояния, подтверждения, незавершённую работу, ветку/коммит/окружение и следующий шаг. Снимок ревизий создаёт Relay; после возобновления прочитай `checkpoint_changes`.
